# S37 — the bench made honest: what it flashes, what it generates, and the one bitstream S38 puts on the part

Desk session. **The unit was not touched: no ssh session was opened at all**,
no flash, no app stop, no GPIO write, no staged-pair read or write.

**The first sentence belongs to gate 2, because the dispatch said it should.**
`dsp_codegen.py --force` on the unmodified `dsp.csv` rewrites 117 tracked node
ASM files, and **32 of them differ in code, not in comments** — so the
regenerated files were **not committed** and the tree was not made to
reproduce. The drift is exactly two instructions in each of
`C1_FILT_01..32`, it is dead code, and §2 says why that is still a stop.

Everything else landed. `loadlogic.sh` now names only artifacts that rebuild
from a commit; both proved branches are merged; the step-0 bitstream is built,
reproduced twice, staged, and dry-run through the interlock.

## 1. Gate 1 — `loadlogic.sh` names only what can be rebuilt

Finding **S37-1**.

S36 named two defects and deliberately did not make the change. Both are made
here, and both were **proved by rebuilding, not by reading the manifest**.

Each artifact was rebuilt with `git archive <commit> shared/dsp4-logic` into a
fresh scratch tree and built with the repo's own `build.sh`, so nothing
depends on the state of the working tree:

| what | commit | macro | label produced | LEs | pins |
|---|---|---|---|---:|---:|
| `driveall` | `a096c585` | `DRIVE_ALL=1` | `dsp4_logic_driveall.907492a607bd` | 401 | 71 |
| `pisel` | `3152e2b1` | `PI_SELFTEST=1` | `dsp4_logic_pisel.2c1355bbc69b` | 303 | 71 |

Both reproduce the committed label exactly, and **both reproduce the committed
`.pof` byte for byte**.

### 1.1 The svf is not byte-reproducible, and that matters because the svf is what gets flashed

The `.pof` files are bit-exact across rebuilds. The `.svf` files are **not** —
and `loadlogic.sh` and `logic_flash.sh` both play the **svf**, so this had to
be run down rather than waved at.

It is one line, and it is a comment:

```
18c18
< !Device #1: 5M1270Z - output_files/dsp4_logic.pof Fri Sep 11 15:49:12 2026
---
> !Device #1: 5M1270Z - output_files/dsp4_logic.pof Thu Sep 10 06:08:59 2026
```

`!` is the SVF comment character, `quartus_cpf` stamps the wall clock into it,
and with comment lines removed the two files hash identically. So the bytes
openocd actually plays are reproducible; the file the bench md5s is not.

**Consequence, and it is now written into `loadlogic.sh`'s header: byte-identity
is asserted on the POF.** An svf md5 is still the right integrity check for a
*copy* — `logic_flash.sh` compares desk against bench, and that is a copy check,
which is exactly what it should be — but it is not a *rebuild* check and must
never be used as one.

### 1.2 The md5 pairs, old → new

| role | retired | pof md5 | replacement | pof md5 | design ID |
|---|---|---|---|---|---|
| `driveall` | `e13b5dec84e0` | `ab6781b2edee4cfec312b56cd0dee9f4` | `907492a607bd` | `8d52c5d3a3e09267da8a9ffa5913ce0a` | `32'h92a607bd` |
| `pisel` | `bd9c100db7c2` | `9f0d2bcbf1fa2e31ef6529335fb461ae` | `2c1355bbc69b` | `621599e288c7cc6f9ba200a4bb0f506b` | `32'h55bbc69b` |

The retired `bd9c100db7c2` has **no design ID at all** — it predates the stamp
at `3152e2b1` — which is the whole reason it is retired. `e13b5dec84e0` has one
(`32'h5dec84e0`) and it is worse than useless: the part will answer with a
number that identifies a bitstream nobody can rebuild.

### 1.3 Nothing was deleted, and the retired files are not in `attic/`

They are in **`shared/dsp4-logic/bitstream/retired/`**, with a README giving
what each was, what replaced it, and both md5s.

**This is a deliberate deviation from the dispatch**, which said `attic/`.
CLAUDE.md defines `attic/` as the retired D24 ADAU1466/SigmaStudio material and
says "never build from it **or extend it**". Adding live-until-today CPLD
bitstreams to it would extend it. The new directory does the same job — kept,
not flashed, not built from — and sits next to the artifacts it retires, where
someone chasing an md5 in a bench log will actually find it.

### 1.4 The header now carries the rule

`loadlogic.sh` opens with **"every artifact named in this script must be
rebuildable from a commit"**, the two failures that produced the rule, and the
procedure for adding a name (rebuild from the manifest's commit in a clean
tree; check the label; **hash the pof**).

It also now says what it is *not* for: something **new** goes on the part
through `tools/pi/logic_flash.sh`, which holds the AN_EN interlock and stages a
verified rollback. `loadlogic.sh` retries three times and has no interlock,
because it only ever moves between known-good bitstreams.

## 2. Gate 2 — the codegen drift is semantic, so nothing was regenerated

Finding **S37-2**. **Severity: MEDIUM (latent). Status: measured, not fixed —
deliberately.**

`dsp_codegen.py` was run on the committed `MW/D32/DSP/SHARC/dsp.csv` into a
scratch copy of the tracked `src` tree. 117 files differ. Every one was
classified by stripping `/* */` and `//` comments and collapsing whitespace,
then comparing the instruction stream:

| class | files |
|---|---:|
| comment-only (code identical) | **85** |
| ordering-only (same lines, reordered) | **0** |
| **semantic (code lines differ)** | **32** |

### 2.1 The 85 are S26's comment rewrite, never re-run

Benign. Commit `608a1aa3` ("fix rounds ties-to-even, and returns all-ones on
positive overflow") rewrote a comment block in the generator and the tree was
never regenerated over it. The old text says the part *wraps*; the new text says
S26 measured three positive overflow points and got `0xFFFFFFFF` from all
three, so it is **not** a two's-complement wrap. The generator is right and the
tree is out of date, in prose only.

### 2.2 The 32 are two dead instructions in every `C1_FILT_*`

One change, repeated 32 times. In `C1_FILT_01.asm` … `C1_FILT_32.asm`, the
tracked text carries

```
i6 = BLK_CHAIN_B_P1;    /* or BLK_CHAIN_B, alternating by parity */
l6 = 0;
```

inside **`_C1_FILT_nn_process_sample`** — the per-sample entry point — and the
current generator does not emit it. The block entry point
`_C1_FILT_nn_process` keeps its copy in both versions. **There is no other code
difference in any of the 117 files.**

### 2.3 It is dead code, and that was checked rather than assumed

`i6` appears exactly twice in `chip1/shared_kernels.asm`, at lines 606 and 618,
both under `.fkb_*` labels — and `_shk_filt_blk` runs from line 550 to line
624, where `_shk_filt_smp` begins. So **both uses are inside the BLOCK kernel**.
The sample kernel `_shk_filt_smp`, its callee `_shk_filt_start_xfade` and
`_bq_fx_cascade_N` never read `i6` at all.

So the tracked text sets up a pointer the sample path never dereferences. The
generator's version is two instructions cheaper on a per-sample path, ×32
nodes, and it also stops clobbering `i6`/`l6` across a call — which is the safe
direction of travel, not the risky one.

### 2.4 Where it came from: the generator was refined mid-commit and not re-run

The drift is **older than the last regeneration**, which is why it was not
noticed.

* At `4807d23d~1`, `C1_FILT_01.asm` had no `i6` lines at all.
* `4807d23d` ("S26 gate 1: the fix sweep, and gate 2's generator work")
  introduced them — **both copies** — into the committed node ASM.
* The same commit introduced `pool_in_blk` / `pool_in_smp` into
  `dsp_codegen.py`, the flags that gate the sample-path emission.

So the node tree was generated by an **intermediate** state of that commit's
generator, the generator was then refined to drop the sample-path copy, and it
was never re-run before commit. Both halves went in together and have disagreed
ever since.

### 2.5 Why this is still a STOP

The dispatch's rule is "if semantic: STOP, do not commit regenerated files",
and that is the right call even though the effect is nil:

1. **117 files of firmware text would change in a session that cannot test on
   the part.** The unit is out of bounds and the AN_EN ruling is outstanding.
2. **The tracked text is what every image on record was built from.** Changing
   it silently re-bases every staged pair `s20`…`s32` against a tree none of
   them came from.
3. **"Dead" was established by reading the kernels.** That is good evidence and
   it is not a measurement. Two instructions leaving a per-sample path is a
   cycle-count change, and cycle counts are the thing this programme measures.

**What S38 or a later session should do**, in this order: regenerate the 32
FILT nodes and the 85 comment-only files in ONE commit that changes nothing
else; rebuild the s26 and s32 pairs; prove the images differ only by the
expected removal; re-run one capacity row to confirm the direction of the
change. It is a small, clean, testable job — but it is a job with a bench in
it, and this session had no bench.

## 3. Gate 3 — both branches reviewed, proved, and merged

Finding **S37-3**.

### 3.1 The diffs are exactly what S35 and S36 said they were

`s34-converter-clock` touches three files: the qsf (five pin assignments —
142/141 become `conv_bck`/`conv_fs`, 87/85/81 drop to the global unused-pin
reservation), the RTL (the port list, and `assign conv_bck = bck8; assign
conv_fs = fs8;`), and the testbench. Nothing else.

`s36-xlogic-park` touches the same three files in different places: the qsf
(three `WEAK_PULL_UP_RESISTOR` assignments), the RTL (`snake_out`/`dac_main`
become `strap_d32 ? … : 1'bz`), and the testbench. Nothing else. They merged
without conflict.

### 3.2 The fit numbers reproduce S35's and S36's, on clean builds today

| ref | LEs | pins | Fmax | sim |
|---|---:|---:|---|---|
| `main` | 404 | 71 | 70.21 MHz | PASS |
| `s34-converter-clock` | 404 | **68** | 66.18 MHz | PASS |
| `s36-xlogic-park` | **403** | 71 | 71.26 MHz | PASS |
| **merged `main` (`7eabfa5f`)** | **403** | **68** | 66.18 MHz | PASS |

The two fixes compose exactly as predicted and do not interact: the park costs
−1 LE, the converter pair costs −3 pins, and merged main is 403/68. Fmax
spread is fitter seed noise on ~17 MHz of margin, as S35-2 established — main
itself read 68.54 MHz in S36 and 70.21 MHz today from identical source.

### 3.3 Both sim gates were proved to BITE, by mutation

Passing is not evidence; a gate that cannot fail is not a gate.

| branch | mutation | result |
|---|---|---|
| `s34-converter-clock` | `assign conv_fs = fs16;` | **FAIL** — "conv_bck/conv_fs are not the TDM8 pair (bcki[0]/fsi[0])" at t=52143000 |
| `s36-xlogic-park` | restore `assign dac_main = o_dspb[3];` | **FAIL** — "dac_main must drive B_O3 on D32 and be high-Z on D24" at t=3000 |

Both reproduce S35-6 and S36-4.4 exactly, including the timestamps.

### 3.4 The bench instruments were rebuilt from merged main, and every one changed

| instrument | old | LEs/pins | new (merged main) | LEs/pins | design ID |
|---|---|---|---|---|---|
| `maincap` | `d903ae1ac4a9` | 404 / 71 | **`33b6eb00a4e8`** | 403 / 68 | `32'heb00a4e8` |
| `pisel` | `2c1355bbc69b` | 303 / 71 | **`983656926e3e`** | 302 / 68 | `32'h56926e3e` |
| `driveall` | `907492a607bd` | 401 / 71 | **`14df62d98a4d`** | 400 / 68 | `32'h62d98a4d` |
| shipping cfg | — | — | **`4f702a181b61`** | 403 / 68 | `32'h2a181b61` |

The pin change is in every configuration, so every artifact's bytes moved, as
gate 3 predicted.

**The bars do not transfer, and `loadlogic.sh` now says so in its header.** The
82-sample latency bar (S29) and every driven capacity row (S28) were taken on
the old base. They must be **re-taken once** on `maincap`/`pisel`/`driveall`
above, in the first session with the unit — that is the regression that closes
S36-2.

Because of that, the old base is kept and reachable by name:
`maincap-s36`, `pisel-s36`, `driveall-s36`. This is a departure from the
dispatch, which said the old artifacts go to `attic/`. Retiring
`d903ae1ac4a9` would break S36 §3's step 1, whose entire purpose is to
re-establish a platform that has already been flashed, on which 82 ± 1 is a
*reproduction* and not a fresh number. Only the two artifacts gate 1 condemned
— the one with no source and the one with no identity — were retired.

## 4. Gate 4 — the step-0 artifact, and the two things in the dispatch that cannot both be true

```

```

| | |
|---|---|
| built from | `61e38ce3`, branch `s37-step0-shipping-base` |

| logic elements | **156 / 1,270 (12 %)** |

| rollback | `dsp4_logic.a1f6672af6c3.svf`, `dd1e09185804cb2e451d5089cdd56be3` |

**Built twice from a clean `git archive` into fresh scratch trees. The two pof
files are byte-identical**; the two svf files differ only in the wall-clock
comment of §1.1.

156 LEs and 68 pins are **exactly the dispatch's acceptance numbers**, which is
what settles §4.2 below.

### 4.2 "From merged main" and "156 LEs, pins 68" are different bitstreams

The dispatch asked for the step-0 artifact "built from main after the merges
but in the SHIPPING configuration (`a4ee3d1f`'s configuration = the 157-LE
shape, now 156 with the park)", and gave `LEs expected 156 (157 − 1), pins 68`.

Those cannot both be met, because the build switches do not change the RTL:

* **Merged main in the shipping configuration is 403 LEs**, 68 pins —
  `dsp4_logic.4f702a181b61`, built and staged here.
* **156 LEs / 68 pins is the shipping *design*** — `a4ee3d1f`'s 157-LE RTL —
  with the park's −1 LE and the converter pair's −3 pins.

The numbers name the artifact unambiguously, and they agree with S36 §3, which
the dispatch's own READ FIRST list names: step 0 is *not main's RTL at all*.
The engineering reason is S35-3's: flashing merged main as step 0 would put
**247 logic elements that have never run in a shipping configuration** onto the
part in the same operation as a two-pin change, and if anything moved, nothing
in the method could say which change moved it.

**So both were built.** `c62c024714f2` (156 LEs) is step 0 and is what S38
flashes. `4f702a181b61` (403 LEs) is staged beside it as step 2 / S39's
artifact, which is where main's RTL first meets the part in a shipping
configuration.

The branch `s37-step0-shipping-base` is pushed and **must never be merged to
main** — merging it would revert main's 247 LEs. Its sidecar says so.

### 4.3 The step-0 artifact cannot have a readable design ID, and that is structural

The dispatch required "its design-ID readable". **It cannot be.**

The design-ID/knock readback block arrived at `3152e2b1` and costs **+124 LEs**
(S36 §1.1). Adding it would take step 0 from 156 to ~280 logic elements and put
never-benched RTL into the one flash the entire staged plan exists to keep
clean. `a4ee3d1f`'s `build.sh` predates `DESIGN_ID` entirely — there is no
macro to pass and no RTL to consume it.

This is not a regression. Step 0 identifies itself exactly as the bitstream it
replaces does, and exactly as its own rollback does:

| | design ID |
|---|---|
| `a1f6672af6c3` — on the part today, and the rollback | none |
| `s37_shipping_step0.c62c024714f2` — step 0 | none |
| `4f702a181b61` — step 2 / S39 | `32'h2a181b61` |

Identification for S38 is therefore the **md5**, which `logic_flash.sh` records
on the desk and re-verifies on the bench **before the first byte is written**,
plus the flash log. The design ID becomes readable at step 2, which is the
first step carrying main's RTL. Said plainly so that nobody later reads
"no design ID" as an oversight.

## 5. What S38 needs

1. **PW's ruling on the AN_EN interlock** (S35-1). Still the only blocker.
   `logic_flash.sh --dry-run` answers "is it satisfiable right now?" against
   the live unit without writing anything.
2. **The flash is one command**, and it is in the sidecar:
   `tools/pi/logic_flash.sh [--stop-app | --an-en-waived "<reason>"]
   s37_shipping_step0.c62c024714f2.svf`. The rollback default is already
   correct.
3. **The proof is the probe**: J18 P37 = 12.288 MHz, P38 = 48 kHz — dead today.
   Or U3 pins 142/141 at the source. Then `blk_*` 30 s, zero overruns both
   chips. **Not** the latency bar: this base ties `pcm_din` to `1'b0` and has
   no capture path, so the arm cannot run.
4. **Then, in the first session that has the unit**: re-take the 82-sample
   latency bar and the driven capacity rows **once** on the new
   `maincap`/`pisel`/`driveall`, closing S36-2.
5. **The codegen drift (§2) is still open** and wants a session with a bench.
