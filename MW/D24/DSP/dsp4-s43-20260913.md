# S43 — the committed SHARC tree reconciled with its generator, and the drift gate made real

**The unit was never touched.** No ssh to 192.168.1.219, no flash, no boot,
nothing on the part. MW-D24-2 stayed powered down with the analog board
mid-rework. S40 is untouched and still paused. Everything below is desk work:
four builds of the D32 pair on this machine, a git archaeology pass, a new
gate, and the morning sheet.

**The headline is the reassuring one:** the drift was **stale generated
output**, not a hand-edit; the code it concerns has **never been compiled into
a shipping image**; and the reconciled tree builds the shipping pair **byte for
byte identical** to S42's. Nothing that was measured on the part was measured
on the wrong bytes.

---

## 1. What was actually different (S43-1)

S42-5 reported that `dsp_codegen.py --force` rewrites **117 files**, "64 lines
of them CODE in the `_process_sample` path of every `C1_FILT_*` and `C1_EQ_*`
node". The 117 is exact. The attribution needs one correction:

**The 64 code lines are in the 32 `C1_FILT_*` files only.** The 32 `C1_EQ_*`
files differ in comment prose and nothing else. Sorting the whole diff by
content:

| class | files | lines | shipping bytes |
|---|--:|--:|---|
| **code** — `i6 = BLK_CHAIN_B(_P1);` + `l6 = 0;` in `_<nid>_process_sample` | 32 (`C1_FILT_01..32`) | **64** (16 × `_P1`, 16 × plain, 32 × `l6`) | **none** — see §3 |
| **comment** — `WRAPPING.` → `OVERFLOW.` in the alpha-quantisation note | 117 (the 32 FILT again, 32 EQ, `chip1/shared_kernels.asm`, 51 chip-2 nodes, `lib/num_selftest.asm`) | 2,988 diff lines | none by construction |

Every one of the 64 lines is a **deletion**: the committed tree carries them,
the generator does not emit them.

### 1.1 The 64 lines are dead, and the generator removed them on purpose

The per-sample stub set up `i6`/`l6` and jumped to `_shk_filt_smp`.
`_shk_filt_smp` (`chip1/shared_kernels.asm:624`–`807`) **never reads `i6` or
`l6`**, and neither does anything it reaches: `_shk_filt_start_xfade`
(`808`–`1034`), `_bq_fx_cascade_N` (`lib/biquad_fx.asm:114`–`236`) and
`_bq_fx_convert_N` / `_bq_hr_ask` do not mention either register. The **block**
half does — `.fkb_ss_shkfilt` does `i2 = i6;` — and the generator still emits
`i6`/`l6` in the `_process` stub, which is untouched.

That is exactly what the generator says it is doing, in a comment it carries
today (`tools/dsp/dsp_codegen.py:14535`):

> DOES EACH HALF ACTUALLY READ THE POOL REGISTER? The per-sample entry is on
> the hot path — 32 strips × 48 kHz — so a stub that loads a register that
> half never reads is not tidy-looking waste, it is ~3 M instructions a
> second. FILT reads it in the block half only.

**So the generator is right and the tree was stale.** There was no hand-edit to
absorb: nothing had to go back into the generator, because the generator
already contained the intent.

## 2. Provenance — two commits, six minutes apart, both regenerating less than
they changed (S43-2)

`git log -L` on the lines, and `git log -S` on the generator hunk, land on the
same commit for the code and a second for the prose.

### 2.1 The 64 code lines — `4807d23d`, "S26 gate 1: the fix sweep, and gate 2's generator work" (2026-09-10 22:07)

That single commit did three things:

* **created** `chip1/shared_kernels.asm` (954 lines, a new file) — the S18
  shared-kernel split arriving for chip 1;
* **added** the `pool_in_blk` / `pool_in_smp` split to `dsp_codegen.py`
  (`git show 4807d23d^:tools/dsp/dsp_codegen.py | grep -c pool_in_smp` → **0**;
  at `4807d23d` → **5**);
* **committed** `C1_FILT_01..32` stubs that still carry the `i6`/`l6` lines the
  split exists to remove.

The commit was **internally inconsistent at the moment it was made**: its own
generator would not produce its own node files. The node stubs were generated
before the optimisation hunk was written, and the generator was never re-run
afterwards.

### 2.2 The comment — `608a1aa3`, "S26 gate 1 witnessed on the part" (2026-09-10 22:13)

Six minutes later, the bench measured `fix` at three positive overflow points
(2^31, 2^31+256, 2^32 — all returning `0xFFFFFFFF`), which ruled out both
"saturate" and "wrap". The commit corrected the wording in
`tools/dsp/dsp_codegen.py` and `tools/dsp/fixed_ref.py` — **and touched no
generated file**: its stat is three files, the S26 write-up and those two
tools. The 117 node files kept the superseded "WRAPPING." paragraph.

### 2.3 The class, named

Neither is the mandate breach the dispatch braced for. **Both are the same
weaker fault: a generator change committed without a full regeneration.** It is
easy to commit and invisible afterwards, which is precisely why it sat for
three days — and why §4 exists.

## 3. The reconciliation, and the four builds that price it (S43-3)

The reconciliation is one command, because the generator was already the truth:

```bash
python3 tools/dsp/dsp_codegen.py MW/D32/DSP/SHARC/dsp.csv MW/D32/DSP/SHARC/src --force
```

117 files change, **and nothing else in the tree does**. A second run changes
nothing further — the generator is idempotent and the tree is now at its fixed
point.

### 3.1 The shipping pair is byte-identical, and here is why

`DSP4_SHARED_KERNELS` is **not named in `shipping.config`** and `build.sh`
defaults it to **0**. The 64 lines live inside `#if (DSP4_SHARED_KERNELS & 8)`.
**They have never been compiled into a shipping image.** Not in S20, not in
S26, not in S33, not in S39, not in S42.

Built on this machine, `./build.sh clean && ./build.sh all`, twice — once
before the regeneration and once after:

| arm | chip 1 `.ldr` | chip 2 `.ldr` |
|---|---|---|
| S42, as recorded | `825f9b7dac5978c973550c8e40819ba9` | `7b1311e8e56f008fa98046cab59293c6` |
| **committed tree, before the regeneration** | **the same two** | **the same two** |
| **reconciled tree, after it** | **the same two** | **the same two** |

**Gate 2's condition is met exactly: the reconciled tree reproduces S42's pair,
byte for byte.** There is no different pair, nothing to ship silently, and no
line to argue about.

### 3.2 The one arm where the 64 lines do exist, priced

Because "never compiled" is a claim and not a measurement, the shared-kernel
arm was built on both trees as the control:

```bash
DSP4_SHARED_KERNELS=15 ./build.sh all
```

| tree | chip 1 `.ldr` | bytes | chip 2 `.ldr` |
|---|---|--:|---|
| committed (pre-reconciliation) | `e2c532794eb64a3bb81a89832d2a8f29` | 356,152 | `5699b311635fe360b803baecfbb2d7d5` |
| **reconciled** | `b3b3ee4a461faed9129c22e1792f232b` | **355,896** | `5699b311635fe360b803baecfbb2d7d5` |

**−256 bytes, which is 64 lines × 4 bytes of loader stream, exactly.** Chip 2
is byte-identical in both arms, which is what a chip-1-only change must read.
The build's own `shared_kernel_check.py` record-layout gate passed on the
reconciled tree, so the node record offsets are intact.

So the whole measurable consequence of three days of drift is **256 bytes of
dead program memory in a configuration that does not ship**. Worth recording
against S26's chip-1 code-pool table, which was taken on the unreconciled tree
and therefore carries 8 bytes per FILT instance it need not have.

### 3.3 Which bytes the on-part measurements used

The question the dispatch asked — *which version did S19–S39 measure on?* —
has a cleaner answer than "rebuild both from the anchors": **neither**. Every
on-part anchor is a `DSP4_SHARED_KERNELS=0` image, in which the 64 lines are
preprocessed out before the assembler sees them. The comment hunk cannot
affect bytes at all. **No recorded measurement on this project was taken on the
wrong side of this divergence**, and the baseline build above proves it
directly by reproducing S42's pair from the pre-reconciliation tree.

## 4. The drift gate made real (S43-4)

### 4.1 Why nothing caught it

`check-contract-drift.sh` ran `sync-defs.sh`, `validate-matrix-contract.py` and
`MW/D32/DSP/gen_dsp.py --force`, and called that "re-runs the whole
generation". **It never ran `tools/dsp/dsp_codegen.py`.** The 726 files that
script emits — every node `.asm`, both `shared_kernels.asm`, `dsp_block.h`,
`bus_accumulators.asm`, `process_chain.asm`, `block_io.asm` — were in **no gate
at all**. `regenerate-dsp-contract.sh` had the same hole, which is worse: "run
the regenerate script" left 726 generated files untouched.

The strict mode would not have helped either. It checks `git status` on a list
of thirteen paths, none of which is a node file — and `git status` cannot see
drift that is already committed, which is the shape this one had.

### 4.2 `check-sharc-codegen-drift.sh`

New script. It generates into an **empty** scratch directory — never a copy of
the tree, which would let the tree's own content leak into the thing it is
checked against — and requires every emitted file to be byte-identical to its
committed counterpart:

```
SHARC codegen drift check
  generated into a scratch tree: 726 files
  differ from the committed tree: 0
  emitted but absent from the tree: 0
  hand-written (not emitted): 50
SHARC codegen drift check passed (tree == generator output)
```

The **50** is checked too, by name. A generator that quietly stops emitting a
file would otherwise drop that file out of the gate unnoticed; instead it falls
from the generated set into the hand-written set and the list stops matching.
(`chip1/dsp_params.asm` and `chip2/dsp_params.asm` are in that list because
they are generated by `MW/D32/DSP/gen_dsp.py`, not by this generator, and are
gated by `check-contract-drift.sh`'s own `CONTRACT_FILES`.)

### 4.3 Three arms, all run

| arm | result |
|---|---|
| the reconciled tree | **pass** — 726 emitted, 0 differ |
| the tree as committed before this session | **fails, 117 files** — it catches the exact fault it was written for |
| `--negative-control`: one line of `chip1/nodes/C1_FILT_01.asm` hand-edited in a throwaway copy (`i7` loaded with strip 2's record base — it assembles, it is wrong, nothing else says so) | **fails, 1 file**, and the control reports itself as passed |

### 4.4 Wired in

* `check-contract-drift.sh` runs it **first**, before `sync-defs.sh`. The order
  matters: the script's later steps currently fail for a pre-existing reason
  (§5.1), and an appended check would be masked by that failure forever. The
  SHARC gate depends only on `dsp.csv` and the generator, so it stands alone.
* `regenerate-dsp-contract.sh` gains it as **step 0**, so the regenerate flow
  actually regenerates the SHARC sources. Same reasoning for the position.
* `smoke-checklist.md` gains the negative control as step 3 and two checklist
  lines. The absence of output is not a result.

## 5. Two things found on the way

### 5.1 `check-contract-drift.sh` still fails, for the reason S38-8 and S42-12 named — and it damages the tree on its way out (S43-5)

The gate cannot pass today, and not because of anything in this session.
`gen_dsp.py --force` exits on the no-fallback policy: the graph proposes cells
that the landed `defs/products/<p>/dsp.csv` lacks, and `dsp-unmapped.csv`
carries exactly those — **237 on d24**. That is the policy working (the graph
has advanced past the pinned `defs-v2026.09.08.4`) and it is a **hub item**:
the fix is to propose a new `dsp.csv` to the hub gate, never to hand-edit the
landed file. Untouched here.

**New, and worth a line of its own:** when it fails there, it leaves
`MW/D32/MX/_matrix.csv` **damaged**. `sync-defs.sh` re-expands the matrix from
`defs/` without the DSP columns, and `gen_dsp.py` — which backfills
`DspI2c`/`DspSpi`/`DspPage`/`DspAdd`/`DspAddHex` — aborts before writing them.
The file is left with those five columns blank on all 7,000 rows. It looks like
a 7,000-line diff and it is not drift; it is a half-finished regeneration.
Restored with `git checkout --` here. **A failing gate should not leave the
tree worse than it found it**, and that is a defect in the script, not in the
contract. Recorded, not fixed — fixing it means either a temp-file-and-rename
in `sync-defs.sh` or a restore-on-failure trap, and that is a change to the
contract intake path, which is not this session's to make at 22:00 with no
hub round-trip.

### 5.2 S42-5's attribution, corrected

"the `_process_sample` path of every `C1_FILT_*` **and `C1_EQ_*`** node drops
`i6 = BLK_CHAIN_B_P1; l6 = 0;`" — the EQ nodes never had those lines. EQ's
shared class has no `pool_reg` at all (`SHARED_KERNEL_CLASSES` declares one for
`FILT` only), so there was nothing for the split to remove. The EQ files are in
the 117 for the comment and nothing else. The count of 64 code lines was right;
the file attribution was not.
