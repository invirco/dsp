# S34 — what the hub's D24 netlist and TDM map put to the DSP side

Desk session, 2026-09-11. No unit touched: nothing booted, nothing
flashed, no `.pof` produced. Four questions, answered against the ADSP-2156x
HRM, the rev C netlist (mx26 `docs/d24-netlist-global.md`,
`docs/d24-cpld-fanout.csv`, `docs/d24-sharc-dai-fanout.csv`,
`docs/d24-analog-paths.md`) and real Quartus runs on this machine.

**Read gate 4.1 first if the analog board is going on the bench.** The
LOGIC bitstream does not drive the converter clock pair, and no converter
can work until it does.

## 1. TDM16 on one net lane — feasible, and the SHARC is not what stops it

### 1.1 The premise the question carried is wrong twice

The TDM map's CSV header says "a SHARC SPORT's A/B halves share one clock+
format", and from that the question asked which half would *pair* with I3,
guessing I5. Neither part holds.

**Halves do not share a clock.** HRM §21 Signal Descriptions: *"Individual
SPORT halves do not share any of its signals across the pair that comprises
the SPORT top module; however, it is possible to connect the clock and frame
sync signals between the SPORT half pair, as explained in the Multiplexer
Logic section."* That sharing is opt-in — `SPORT_CTL2_A.CKMUXSEL` /
`FSMUXSEL`, combinations 13–16 of HRM Tables 21-7/21-8 — and this design
uses none of it (combinations 1 and 9, "Native operation"). Every half has
its own SRU clock and frame-sync destination: `SPT3_ACLK_I` is `DAI_CLK5.IN0`
and `SPT3_BCLK_I` is `DAI_CLK5.IN1`; `SPT3_AFS_I` is `DAI_FS4.IN0` and
`SPT3_BFS_I` is `DAI_FS4.IN1`. Multichannel format is per half as well —
`SPORT_MCTL_A.WSIZE` and the four `SPORT_CSn_A` registers have `_B` twins.

The D24 card already relies on this: on DSPA every SPORT runs half A at TDM8
(BCK0/FS0) and half B at TDM16 (BCK1/FS1), which would be impossible if the
halves shared a format.

**And I5 is not I3's partner.** I3 is SPORT3 half A on DAI0. Its partner is
SPORT3 **half B** = DSPA O3 = the `MIX_49_64` fabric lane — already TDM16 by
role, and not even enabled in firmware today (`dsp4-plumbing.md` lane tables:
chip 1 TX enables s0–s2 only). I5 is SPORT5 half A, on the other DAI
entirely.

### 1.2 The configuration, if it is wanted

Exactly two SRU lines move. In `MW/D32/DSP/SHARC/src/sru_config.c`, the CG0
block currently gives SPORT3 half A the TDM8 pair; for a TDM16 lane on I3 it
takes DAI0's *other* pair instead — the one already on the pins:

```c
    /* I3 at TDM16: take the DAI0-out pair (pin 19 = BCK1, pin 20 = FS1),
     * which LOGIC already drives at 24.576 MHz / 48 kHz for the mix
     * fabric. SPORT3 half B is on the same pair; that is legal and, on
     * D24, half B is not enabled at all. */
    SRU(DAI0_PB19_O, SPT3_ACLK_I);   /* was DAI0_PB10_O (BCK0) */
    SRU(DAI0_PB20_O, SPT3_AFS_I);    /* was DAI0_PB09_O (FS0)  */
```

`DAI0_PB19_O` and `DAI0_PB20_O` are selection codes 0x12/0x13 in both the
Group A (clock) and Group C (frame sync) source tables, so the route is a
plain SRU write, not a trick. No pin buffer changes direction; `PADS0_DAI0_IE`
already enables all twenty.

If the lane goes on **I5** instead (the retired D32 snake lane, free on D24):

```c
    SRU2(DAI1_PB20_O, SPT5_ACLK_I);  /* DAI1 pin 20 = BCK3 (TDM16) */
    SRU2(DAI1_PB19_O, SPT5_AFS_I);   /* DAI1 pin 19 = FS3  -- note the
                                      * DAI0/DAI1 19/20 swap */
```

Equally legal: SPORT5 half B is `MIX_81_96`, reserved and not enabled.

**Firmware work beyond the two lines.** `sport_config.c::cfg_region()` takes
`wsize` and `mcpde` **per region**, not per lane, and every chip-1 RX lane is
in one region at `wsize=7`. A mixed-format RX region needs those two fields
moved into the per-lane tuple that `dsp_codegen.py::gen_block_io` emits
(`{sport, cs_mask, words_per_sample, region_off}` gains `wsize`, `mcpde`).
Then: `CS0_A` becomes a 16-bit mask, the packed DMA buffer for that lane
doubles, and `tdm-lines.csv` carries `TDM16`/`slot_count=16` for the line so
the whole chain agrees. None of that is deep — it is the region assumption,
in one function.

### 1.3 What LOGIC must change: nothing on the DSP side, everything on the slot side

On the DSP side the CPLD is already done: `bcki[1]`/`fsi[1]` are `bck16`/
`fs16` today, and `i_dspa[3] = ni[3]` is a plain wire, so the CPLD does not
care what rate crosses it.

The slot side is the problem, and it is copper.

**The option-slot clock is one shared copy of the converter clock, not a
per-slot clock.** From the netlist fan-out of U3:

| U3 pin | net | 33R taps | ends at |
|---|---|---|---|
| 142 | `C1` | R111 | ADC/DAC FPC (converter BCK) |
| | | R65 / R66 / R67 | `BCK_1` (slot 2), `BCK_2` (slot 1), `BCK_3` (slot 3) |
| | | R61 | `BCK_4` (D32 header J33) |
| 141 | `L0` | R112 | ADC/DAC FPC (converter FS) |
| | | R62 / R63 / R64 | `FS_1` (slot 2), `FS_2` (slot 1), `FS_3` (slot 3) |
| | | R60 | `FS_4` (J33) |

One pin, five resistor taps, no inversion anywhere (a 33R tap cannot
invert), and note the tap numbering does not follow the slot numbering.
**So an option slot cannot be moved to TDM16 without taking the ADCs and
DACs with it** — which is exactly what the TDM map rules out, because TDM16
on the converter lanes means analog-board work.

The way out is a second clock pair, and the part has the pads for it: U3
pins 85 (`C2`), 81 (`L1`) and 87 (`C0`) are single-pin nets — named on the
schematic, routed to nothing — and the netlist's own words are that they are
"the only genuinely free user I/O on the part". A **rev D** change routes
`BCK_1..3`/`FS_1..3` from `C2`/`L1` instead of `C1`/`L0`, LOGIC generates
24.576 MHz/48 kHz on that pair, and the converters keep theirs. On **rev C**
the same thing is a wire mod: lift R65/R66/R67 and R62/R63/R64 and feed their
slot sides from U3.85/U3.81 — six lifts and two wires across J18, which is
bench work, not a product.

**Verdict: feasible on the SHARC, free in the CPLD, blocked on rev C copper.
It is a rev-D pin change, and it is two pads that already exist.**

## 2. Runtime `net_sel` — what it takes, and what it costs to switch

Designed and costed, not proposed for merge. RTL is on branch
`s34-cpld-cost` (`DSP4_S34_NETSEL`), measured at **+48 LEs**.

### 2.1 The path is not private, and that shapes the design

The provisioned pins are U3 60/61/62. The netlist says what they actually
are:

- **60 = `SPI0`** — the *shared* SPI clock: Pi `SPI_SCK`, both DSPs'
  `SPI2_CLK` through R73/R76, and S-MCU U7 pin 21. This is the DSP **boot
  bus**.
- **61 = `SPI1`** — the shared MOSI: Pi `GPIO10`, both DSPs' `SPI2_MOSI`,
  U7 pin 23, **and** the analog board's mic-gain shift-register chain.
- **62 = `CS_L`** — two pins on the whole net: U3.62 and U7.55. The only
  private wire of the three.

There is **no MISO to the S-MCU**. So the CPLD must be a listener that never
drives 60/61 (they already have two masters with opposite idle polarity — see
`hardware-map.md` §3), and nothing can be read back.

### 2.2 RTL

A 16-bit shift register framed by `CS_L`, two-flop synchronised, sampling
MOSI on the SCK rising edge; frame `{8'hA5, sel[3:0], ~sel[3:0]}`. The
inverted copy is the integrity check that the missing MISO would otherwise
have provided: a frame without a valid complement is dropped, not applied.

Two details that are not decoration:

- **The register holds a delta, not a value.** U3 has no reset and MAX V
  registers power up cleared, so a raw `net_sel` register would come up
  `4'b0000` = every lane on the ADCs — and D24 has no ADC on AD3, so the NET
  inputs would be dead until the S-MCU spoke. `net_sel = net_sel_q ^
  net_sel_default` makes "cleared" mean "the shipping personality".
- **The select is applied at a frame boundary.** A select that moves
  mid-frame splits one TDM word across two sources. Held on the `CS_L`
  rising edge, released at the end of the TDM8 frame.

### 2.3 S-MCU firmware

One command on the matrix endpoint (`S0..S3`/`BUSY` + `SRX`/`MRX`, which U7
already owns) → assert `CS_L` → shift 16 bits on the housekeeping SPI →
release. U7 is already an SPI master on that bus for `CS_C` and `CS_M`, so
this is one more chip select, not a new peripheral.

**The constraint the firmware must respect:** the bus is shared with DSP
boot, and there is no arbitration. `hardware-map.md` §3 measures the
existing collision — U7's housekeeping burst runs every ~254 ms and is why a
chip-1 boot stream cannot fit. A `net_sel` write during a boot stream
corrupts the boot. Rule: **`net_sel` writes only outside a DSP boot window**,
which on rev C means at power-up before boot or on explicit request while
the DSPs are running. The rev-D SPI remap (D8) removes the constraint.

### 2.4 What a switch does to the audio

Nothing tears: the lane changes source between frames, so the DSP gets one
complete frame of the old source and the next complete frame of the new one.
What the listener hears is the **discontinuity between two unrelated
signals** — a click, not a glitch — so the DSP should mute the affected
lane's inputs across the switch. At `DSP4_BLOCK_SIZE=32` a block is 0.67 ms;
mute, write, wait two blocks, unmute is inaudible and needs no new mechanism
(the input nodes already have gain ramps).

## 3. LE cost against the 5M1270Z's 1,270

Measured, Quartus 21.1.1, 2026-09-11; branch `s34-cpld-cost`, projects in
`shared/dsp4-logic/quartus/s34/`. **No bitstream was produced and nothing
was flashed.**

| build | adds | LEs | Δ | pins | Fmax |
|---|---|---|---|---|---|
| shipping, rebuilt today | — | 404 (32 %) | — | 71 | 64.52 MHz |
| `s34a_slot3` | option slot 3 as a second net card | 402 | −2 | 79 | 69.78 MHz |
| `s34b_slot2` | option slot 2 as a second net card | 402 | −2 | 79 | 63.70 MHz |
| `s34c_pack` | codec + MEMS + Pi on one TDM8 lane each way | 419 | **+15** | 71 | 61.62 MHz |
| `s34d_netsel` | runtime `net_sel` over the S-MCU SPI | 452 | **+48** | 74 | 61.90 MHz |
| `s34e_all` | all four | 463 (36 %) | **+59** | 90 | 66.51 MHz |

**The LE ceiling is not what decides any of this.** Everything together is
36 % of the part, with 4.1 ns of setup slack in the worst variant against a
20.35 ns sysclk period. What is tight is **pins**: two option slots take the
part from 62 % to 79 % of its I/O.

Read the two negative deltas as noise — a 2-LE reduction from adding two
multiplexers is the fitter packing 400-odd LEs differently, and Fmax moves
several MHz run to run for the same reason (the committed manifests record
68–70 MHz where today's rebuild of the same source reads 64.5). The lane mux
is one LE per lane by construction: **a second option card costs pins, not
logic.**

The pack's 15 LEs buy two DSPA input lanes and one DSPB output lane, and the
design is worth stating because it is what keeps it at 15: every source
keeps its **own** slot index (codec 0–3, MEMS 5 — the ADAU7302's strapped
slot — Pi 6–7, replayed there by the re-framer, which already holds the
words). A source whose destination slot came *earlier* than its own would
need a full frame of delay: 32 flops per lane, not 15 LEs for the lot. The
one subtlety is the mux select, registered on the BCK8 **falling** edge —
the raw slot index changes at `frame_pos` multiples of 128, which is exactly
the rising edge the DSP samples on.

## 4. The slot map against the copper

### 4.1 THE BITSTREAM DOES NOT DRIVE THE CONVERTER CLOCK — 🔴 blocking

Found while pin-checking the slot map. `quartus/dsp4_logic.qsf` assigns:

```
set_location_assignment PIN_142 -to ic_strap[1]
set_location_assignment PIN_141 -to il_strap[0]
```

and `dsp4_logic_top.v` declares both as `input wire`. Confirmed in the
fitter's own pin report for a build made today:

```
il_strap[0]  : 141 : input : 3.3-V LVTTL
ic_strap[1]  : 142 : input : 3.3-V LVTTL
```

Pins 142 and 141 are board nets `C1` and `L0` — the bit clock and frame
sync of §1.3, feeding the ADC/DAC FPC **and** all three option slots
through their 33R taps. **U3.142 and U3.141 are the only active device pins
on those nets.** As inputs, nothing on the board generates a converter clock
at all, so no ADC and no DAC can produce or accept a sample, and no option
slot has a clock either. The fitter also reports the five strap pins under
"input pin(s) that do not drive logic", which is the same fact from the
synthesis side.

The wire-through lanes are the independent confirmation: `i_dspa[0] = ad[0]`
is a plain wire in the RTL, so the converter frame has to **be** the DSP
frame — which is only possible if one generator makes both.

How it happened: the rev C LOGIC sheet prints `IC0-IC2` / `IL0-IL1` beside
pins 87/142/85/141/81, and the 2026-07-31 pin extraction read all five as
format-config straps (that reading is also in `MW/D24/HW/hardware-map.md`
§"Clock formats"). Three of the five really are spare — 87 (`C0`), 85
(`C2`), 81 (`L1`) are single-pin nets that reach nothing. Two are not.

**The fix is prepared on branch `s34-converter-clock`**, not merged and not
flashed: `conv_bck`/`conv_fs` become outputs carrying `bck8`/`fs8` — the same
pair as `bcki[0]`/`fsi[0]` — the three dead pads leave the port list, and the
sim gate gains a continuous check that the pair is driven and equals the
TDM8 clock pair. Cost: **0 LEs** (404 before and after), 68 pins instead of
71, Fmax 73.67 MHz.

Nothing about this is provable at a desk, and it needs a flash. What it
predicts at the bench is specific: **with today's bitstream, `C1` (J18 P37)
and `L0` (J18 P38) are dead — not 12.288 MHz and 48 kHz — and a scope on
either pin settles it in one probe, with no firmware involved.**

### 4.2 The NET lane indices are the CPLD's, and the mirroring is the card's

Confirmed exactly as the dispatch stated. `NET_OUT_01..08` sits on `B_O4` →
`o_dspb[4]` → `no[0]` → U3.2 → J18 P31 → digital `NI3` → **slot 1 pin A9**,
and the NET input arrives on `ni[3]` → U3.3 → J18 P30 → digital `NO0` →
**slot 1 pin A10**. The index order reverses across J18 in both directions.

Recorded where it belongs: a table and the ruling — *the indices in the slot
map and the RTL are the CPLD's, and the mirroring is the card's to undo* —
are now in `shared/dsp4-logic/README.md`, with pointer notes on the affected
`slot-map.csv` rows. The README also carries the warning that slots 2 and 3
are crossed in a **different shape** (a pairwise `_0/_1 ↔ _2/_3` swap, not a
reversal), so nobody generalises from slot 1 when those lanes are adopted.

### 4.3 The X-logic parking sits on slot-2 lanes

`snake_in`, `snake_out` and `dac_main` are parked on pins 109/110/111,
marked PROVISIONAL. Those three pins are `LOGIC_PLL5_0/1/2` = digital
`NO6`/`NO7`/`NO4` = **option slot 2 lanes A12/A13/A10**. `dac_main` and
`snake_out` are *outputs*. Harmless while no slot-2 card exists; a driver
fight the moment one is fitted. The `s34b_slot2` project re-parks all three
onto the PLL1 group (pins 89/91/93), which reaches only the D32
compatibility header J33 and no device on any D24 board — that is where they
should go whether or not slot 2 is ever adopted.

### 4.4 Output order — `DAC_01` does not come out of OUT_1

Branch `s34-output-order`, prepared, **not merged, not built into any staged
pair.** The trace (mx26 `docs/d24-analog-paths.md` §1) proves AK4458 U81
channel *n* reaches rear XLR `OUT_(9−n)`: `DAC_01`, in slot 0 of `B_O0`,
leaves on J52 = `OUT_8`.

The change is eight rows of `slot-map.csv` — `B_O0` slot *s* carries
`DAC_(8−s)` — and `gen_dsp_csv.py` carries it into `dsp.csv` as eight
`slot_start` values. **No SPI address moves**, so it is a lane-placement
change and not a contract-surface change.

Two things a merge still owes: the node-ASM regeneration (see 4.6), and a
CPLD rebuild, because `slot-map.csv` is hashed into the artifact label even
though this edit adds no constant to the `.vh`.

**The `OUT_9-16` half is deliberately untouched.** U92's eight channels go to
J10 tip/ring, J57, J56, *nothing* (channel 5 is a one-pin net), J55, J53 and
J54 — not a reversed run of XLRs. `B_O1` needs its own mapping decision and
guessing a reversal there would be wrong.

### 4.5 Talkback polarity

Branch `s34-talkback-polarity`, prepared, **not merged.** The talkback XLR's
hot pin (analog J1 pin 2) reaches the codec's `IN4N` through C4 and its cold
pin reaches `IN4P` through C11, so `CODEC_RET_1` arrives 180° out against
every other input. It is inaudible alone and matters when talkback is summed
with the MEMS mic, which is not inverted: they partially cancel.

The undo is `invert=1` on the `INPUT_TDM` node that reads the slot. In the
block kernel the negate lands in the loop's existing `nop` — the loop-end
filler — so it costs **zero cycles**, and a node without the param emits
byte-for-byte what it emitted before (verified by generating the whole tree
twice and diffing: 0 files differ). With the param set, exactly one
generated file changes, by one instruction.

### 4.6 Aside: the tracked node ASM is stale against its generator

Running `dsp_codegen.py --force` on the **unmodified** `dsp.csv` rewrites
**117 files** (+1,180/−536 lines). The differences seen are comment text
carried in from later sessions, but the property that matters is the one
the repo's own rules assert: generated files are regenerated, not edited,
and today a regeneration is not a no-op. Until it is, no generated-file diff
can be read at a glance, and this session deliberately kept the two option
branches clear of it. Worth its own pass: regenerate once, review the diff
for anything that is not a comment, and land it on its own.

## 5. What this session did not do

- Nothing was flashed, deployed, or staged; the unit was not touched.
- The TDM16 lane was **not** built — it is blocked on a rev-D pin change
  (§1.3), so RTL for it would be speculative.
- The slot-2/3 lane RTL is a cost measurement, not a candidate: it uses
  the strap as its select and does not renumber the slot map.
- `B_O1`'s output map (§4.4) and whether the converters need a separate
  MCLK beyond `C1`/`L0` are open, and both are analog-side questions.
