# S35 — the converter clock fix, proved at the desk and stopped at the bench

**THE PROBE, FOR PW, FIRST: with the bitstream now on the unit, J18 P37
(`C1`) and J18 P38 (`L0`) are dead. With the fix flashed they are
12.288 MHz and 48 kHz. U3 pins 142 and 141 are the same two signals at the
source.** No firmware, no app and no DSP boot is involved either way, and
the Pi cannot take the reading — every path from the converter clock to the
CM4 ends at a header (§4). One probe settles S34-1.

**NOTHING WAS FLASHED, AND THE REASON IS THE SESSION'S FIRST FINDING.** The
dispatch's gate 0 is "`pinctrl get 26` (AN_EN) — if AN_EN is HIGH stop and
report (PW may have raised it by hand)". It is high. PW did not raise it:
**the app raises it itself, at every boot, unconditionally** (§1). So gate 3
did not run, gates 1, 2 and 4 did, and the branch is not merged.

**WHAT THE DESK WORK FOUND IS WORTH MORE THAN THE FLASH WOULD HAVE BEEN.**
The fix reviews clean and costs nothing (§2). But **the part is not carrying
main's logic** — the shipping bitstream is a 157-LE design from 2026-08-21
and main is 404 LEs — so "flash the branch" would have put 247 LEs of
never-benched RTL onto the unit in the same operation as the two-pin change,
and gate 3's regression could not have told them apart (§3). The fix was
therefore isolated and built against the design that is actually on the part:
**157 → 157 logic elements, the same five pins, nothing else** — which is
the bitstream that makes gate 3 mean what it says, staged and recommended for
S36.

**AND THE COPPER CONFIRMS THE FIX INDEPENDENTLY OF THE RTL ARGUMENT**: the
far side of the 33R taps is a pair of single-gate buffers whose inputs face
the digital board (§5). The analog board does not make the converter clock.
It is built to receive it from U3, and it has never been sent one.

## 1. Gate 0 — AN_EN is the app's, not PW's, and the interlock cannot be met

Finding **S35-1**.

The app's own log, from the 14:24:37 BST start:

```
14:24:44.678911: GpioShutdownMonitor: Started monitoring GPIO4
14:24:44.680384: Boot.Init() - AN_EN asserted (GPIO 26 high — analog power requested)
14:24:44.680762: Boot.Init() - firmware/mcuList.txt contents: H1S1,H1S3,H1S4
```

AN_EN goes high in `Boot.Init()`, **before** the MCU list is read and two
seconds before any MCU announces. It is not gated on anything.

`w` showed one session on the box — this one. The service history shows PW's
hands: six stop/start cycles between 14:21:32 and 14:24:37 BST, forty minutes
before the dispatch was written and consistent with "PW is away from the
bench" by the time it was.

So the interlock is met never, not rarely, while `matrix-app` runs. This
matters beyond today because **S32 and S33 both recorded "AN_EN never
asserted" as bench-as-found with the app active**. That phrasing meant *the
session did not assert it*; it reads as *the pin was low*. It was not.

This session will not resolve that. It is PW's ruling, and S35-1 sets out the
three shapes it could take.

**What follows is everything the desk could prove without the flash.**

## 2. Gate 1 — the branch is exactly what it claims

Finding **S35-2**. `git diff main..s34-converter-clock` touches four files:
the qsf pin block, the top-level port list plus two `assign`s, the testbench,
and the removal of S34's own dispatch block from `tasks.md`. No logic outside
the port list moves.

Clean builds of both refs were made from `git archive` into scratch trees —
same tool (`/opt/intelFPGA_lite/21.1`), same machine, same slot map — and the
fitter's pin reports differ by **exactly five lines**:

|-----|-----|--------|----------------------|
| 142 | `C1` | `ic_strap[1]` input | **`conv_bck` output** |
| 141 | `L0` | `il_strap[0]` input | **`conv_fs` output** |
| 87 | `C0` | `ic_strap[0]` input | reserved, weak pull-up |
| 85 | `C2` | `ic_strap[2]` input | reserved, weak pull-up |
| 81 | `L1` | `il_strap[1]` input | reserved, weak pull-up |

Every other pin is identical in name, direction, I/O standard and bank.

| | `main` | branch |
|---|---|---|
| logic elements | 404 / 1,270 (32 %) | **404 / 1,270 (32 %)** |
| pins | 71 / 114 (62 %) | 68 / 114 (60 %) |
| Fmax | 68.54 MHz | 70.06 MHz |

**Zero LE cost, confirmed on a rebuild of both sides.** S34 quoted the same
pair of Fmax figures as 73.67/64.52; ours are 70.06/68.54. Both are fitter

number carries meaning past "timing is met with room".

**The X-logic parking is untouched.** Pins 109/110/111 are
`snake_in`/`snake_out`/`dac_main` on both sides, still on option slot 2's
lanes exactly as S34-4 found them. That is S36's, as the dispatch directed.

### 2.1 The sim gate bites

Finding **S35-6**. A passing gate proves nothing until it can fail. Driving
`conv_fs` from `fs16` instead of `fs8` — the other frame sync in the same
module, a wrong answer that still leaves the pin driven — fails it:

```
== tb_logic_top: FAIL
   FAIL: conv_bck/conv_fs are not the TDM8 pair (bcki[0]/fsi[0]) (t=52143000)
```

## 3. Gate 2 — built twice, and then built a third time for a reason

### 3.1 Reproducible

Two independent clean builds of the branch, in separate trees:

```
dsp4_logic.07fba263b1ee.pof   d94633925cf5560353244107d0dbb9be
dsp4_logic.07fba263b1ee.svf   4857818fab5cff1c63413b91aa9cdda4
```

**Byte-identical**, both builds, both artifacts. Sim gate PASS, shipping
configuration (`cfg_bits 16'h0010`), Fmax 70.06 MHz.

### 3.2 The part is not carrying main's logic

Finding **S35-3**, and it is the reason gate 3 needed rethinking rather than
rescheduling.

The shipping bitstream rebuilds **byte-for-byte** from its own commit
`a4ee3d1f` (2026-08-21): pof `f08f3b525ff0fe2f7957a96d958842e6`, matching the
committed artifact and the unit's staged copy (svf
`dd1e09185804cb2e451d5089cdd56be3`). So what is on the part is known exactly
— which is worth stating plainly, because **that bitstream predates the
design-ID stamp and cannot identify itself**. Its manifest has no
`design_id` line, so the readback check `build.sh` documents does not exist
for it. Its identity rests on the flash records, not on the part. This is the
precise failure `build.sh`'s own comment block was written about.

That design is **157 logic elements**. Today's `main` is **404**.

Flashing the branch would put 247 LEs — the PCM reframe and capture paths,
the design-ID and cfg-bits registers, five weeks of RTL that has never been
on this unit — onto the part **in the same operation** as the two-pin
direction change. Gate 3's regression (`blk_*`, the S17 capture, the latency
bar at 82 ±1) would then be measuring all of it at once, and if the bar had
moved, nothing in the method could say which change moved it.

The slot map moved too: shipping carries `sha256:efd8d5…`, today's tree
`sha256:2c53de…` — S34 added pointer notes to `slot-map.csv`, which is inside
the artifact hash whether or not it changes behaviour.

### 3.3 So the fix was isolated

`dsp4_logic.138dba7274d6` is commit `a4ee3d1f` — the exact design on the part
— plus nothing but the pin-direction change, ported by hand to the Aug-21
RTL and testbench, and committed as branch `s35-converter-clock-on-shipping`
(`7ac01126`) so the bitstream has a source to rebuild from:

| | shipping `a1f6672af6c3` | + the fix `138dba7274d6` |
|---|---|---|
| logic elements | 157 / 1,270 (12 %) | **157 / 1,270 (12 %)** |
| pins | 71 / 114 (62 %) | 68 / 114 (60 %) |
| Fmax | 70.21 MHz | 69.92 MHz |
| pin report delta | — | the same five pins, no others |

**The fix is free against the shipping design too, not only against main.**

This is the bitstream that makes gate 3 mean what gate 3 says: flashed
against `a1f6672af6c3`, any movement in the latency bar is the converter
clock pair and can be nothing else. Advancing main's 404 LEs onto the part is
a separate decision that deserves its own regression; merging the two into
one flash spends the evidence for both.

**It is an analysis artifact and a recommendation for S36, not a sanctioned
deliverable.** The dispatch named the branch, and this is not the branch. The
branch is marked not-for-merge in its own commit message: it exists to be
flashed and measured against the part's current contents.

An incidental confirmation of the hash discipline fell out of building it.
Tidying a *comment* in the qsf renamed the artifact — `2ca87cb81796` became
`138dba7274d6`, because the qsf is inside `SRC_HASH` — while the pof bytes
stayed identical at `163c62a8d5a6121a5a855047a103ebad`. The label tracks the
source, not the behaviour, which is the conservative direction: a bitstream
can be renamed by a change that does nothing, but it can never keep its name
through a change that does something.

## 4. Gate 4 — nothing reaches the Pi, so the probe is PW's

Finding **S35-5**. Settled from complete net membership, not inferred from
absence of evidence. Both nets are closed and there is no CM4 pin on either:

* `G2449` `C1` — `dsp:J1.37; J2.37; U3.142; digital:J18.37; R111.1; R61.1;
  R65.1; R66.1; R67.1`
* `G2620` `L0` — `dsp:J1.38; J2.38; U3.141; digital:J18.38; R112.1; R60.1;
  R62.1; R63.1; R64.1`

The TEST pins the RTL already exports do not help, for the same reason. The
dispatch had `test[1] = bck8`, `test[2] = fs16`; the RTL is `test[0] = fs8`,
`test[1] = bck8`, `test[2] = fs16`, `test[3] = frame_pos[9]` — so TEST1 and
TEST2 are the converter pair itself. They reach `U3.13`/`U3.12`, then
`J1/J2.17-18`, `J15.4/6` (DNP per the qsf) and `J18.17-18`:

* `G2685` `LOGIC_TEST1` — `dsp:J1.17; J2.17; U3.13; digital:J15.4; J18.17`
* `G2686` `LOGIC_TEST2` — `dsp:J1.18; J2.18; U3.12; digital:J15.6; J18.18`
* `G2687` `LOGIC_TEST3` — `dsp:J1.19; J2.19; U3.8; digital:J15.8; J18.19`
* `G2688` `LOGIC_TEST4` — `dsp:J1.20; J2.20; U3.7; digital:J15.10; J18.20`

No CM4 GPIO is on any of the four. No edge count was attempted, because none
is possible. Every path from the converter clock to the Pi ends at a header.

**A rev-D wish, cheap and worth it:** one of the four TEST nets to a CM4
GPIO would make this question — and every future clock question — answerable
without hands.

## 5. What the copper says about the fix

Finding **S35-4**. S34 proved U3 is the only possible *driver* of `C1`/`L0`.
The remaining risk in turning an input into an output is the opposite one:
something on the far side of the 33R taps driving *back*, which 33R would not
stop.

It does not. `R111`/`R112` end on `#00716`/`#00717`, which cross the FPC to
the analog board and land on **`U97.2`** and **`U98.2`**. Both parts have pin
1 N/C, pin 3 GND, pin 5 on `MIC_5-8_17-20_+3V3`, pin 2 facing the digital
board and pin 4 on the analog-board distribution — single-gate SOT-23-5
buffers, **input from U3, output to the analog side**.

The analog board does not generate the converter clock. It is built to
receive it from U3 and fan it out, and it has never been sent one. The fix
drives the pin the board already expects to be driven.

The option slots are open and the D32 header unpopulated, so nothing else can
contend today. An option card that drove `BCK_n`/`FS_n` would fight U3
through 33R — which is what the 33R is for, but it is a card-design rule to
write down rather than a defect here.

**A trap for the next reader of the netlist: `C1` and `L0` are each two
different nets.** `G2449`/`G2620` are the digital-board clock pair;
`G2448`/`G2619` are unrelated analog-board nets sharing the name, seven
passives each. The global join separates them by ID; a grep on the name does
not.

## 6. What S36 needs

1. **PW's ruling on the AN_EN interlock** (S35-1). Nothing flashes on this
   unit until it exists. This is the blocker.
2. **Flash the isolated fix `138dba7274d6` first, not the branch.** Against
   `a1f6672af6c3` it is a five-pin delta and zero LEs, so gate 3's bar
   measures the fix and only the fix. Then take the probe reading at
   J18 P37/P38 and S34-1 is closed.
3. **Advancing main's 404 LEs onto the part is a separate flash** with its
   own regression, and it is the larger of the two changes.
4. **The X-logic parking on pins 109–111** (S34-4) is still open.
5. `s34-converter-clock` is **not merged**, per the dispatch: merge only
   after gate 3 passes.

## 7. Method

Every build in this session came from `git archive <ref> shared/dsp4-logic`
into a fresh scratch tree, built with the repo's own `build.sh` — sim gate
included, no `SKIP_SIM` — so no result depends on the state of the working
tree. Five builds: `main`, the branch twice, commit `a4ee3d1f`, and
`a4ee3d1f` plus the ported fix. The `a4ee3d1f` build reproducing the
committed shipping pof byte-for-byte is what licenses every "157 LE" claim
about the part.

Netlist facts are from the hub's generated tables at `~/mx26/docs`
(`d24-netlist-global.csv`, `d24-netlist-global-pins.csv`,
