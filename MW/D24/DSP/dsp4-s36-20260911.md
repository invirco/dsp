# S36 — main's LOGIC RTL against the part: the 247 LEs named, and what the candidates were really measured on

**THE HEADLINE CORRECTS THE DISPATCH THAT ORDERED THIS SESSION, AND IT
CORRECTS A NOTE ADDED TO `window-candidate.md` YESTERDAY.** The 247 logic
elements are not "RTL that has never been on the unit". **They have been on
the unit, repeatedly, and two of the candidates' headline bars were measured
on them** — the 82-sample latency figure and every driven capacity row. What
has never been on the part is a *shipping-configuration* build containing
them. That distinction is the whole of S36-2, and it changes what the staged
bring-up has to prove (§3).

**THE 247 LEs ARE THREE COMMITS, NOT TWENTY-ONE.** Sixteen clean Quartus
builds, one per commit boundary that can move the fit, give 157 → 404 in
three steps and twelve flat ones (§1). The largest is not scaffolding: it
is the CM4 stereo return, a product feature PW allocated.

**AND THE INSTRUMENT HAS TWO SPECIFIC DEFECTS, BOTH FOUND BY THE SAME
METHOD.** Six of the twenty-six committed bitstreams rebuild from **no
committed state of the tree at any point in history** — they were built from
a dirty working tree — and one of the six is the `driveall` artifact
`loadlogic.sh` flashes by name for every driven capacity row taken since S28
(§1.4). Separately, the `pisel` artifact `loadlogic.sh` names predates the
design-ID stamp and cannot identify itself on the part.

Gate 4 (the X-logic parking fix) and gate 5 (the AN_EN-gated flash script)
are both done and are §4 and §5. **The unit was not touched: no flash, no app
stop, no GPIO write, no ssh session at all.** Everything here is desk work
against the repo, the hub's netlist tables and Quartus.

## 0. Method, and why it can be checked without rebuilding anything

Every LE number below comes from a clean `git archive <ref> shared/dsp4-logic`
into a fresh scratch tree, built with the repo's own `build.sh`, so no result
depends on the state of the working tree. Sixteen builds for the census, four
more for the non-shipping configurations that were actually flashed, one per
base for gate 4's fix and one more to test the parking alternative — twenty-
three in all.

The census ran with `SKIP_SIM=1`. That is a deliberate and safe choice for
this purpose: it is a **resource census, not a qualification**, and `SKIP_SIM`
is not inside `SRC_HASH`, so the artifact labels stay directly comparable to
the committed bitstreams. Gate 4's builds ran the sim gate in full.

**The bitstream-to-commit map needed no builds at all, and that is what makes
it exhaustive.** `build.sh`'s `SRC_HASH` is
`sha256(slot-map hash | cfg line | rtl/*.v | qsf | sdc)`, truncated to 12 hex
— a pure function of committed text. So it can be *recomputed* for every
(commit × macro combination) across all 34 commits that have ever touched the
logic tree, and matched against the label in each committed artifact's
filename. 4,352 candidate labels, checked against 26 artifacts.

A refinement the first pass needed. The `cfg:` line shape is a property of
that commit's `build.sh`, which changes on its own schedule, so a tree hash
alone can match a commit whose `build.sh` would never have emitted that
shape. The map below keeps only **self-consistent** matches — the tree
produces the hash AND that commit's own `build.sh` emits that shape — which
is why several artifacts resolve to a short *range* of commits rather than
one. Within each range the RTL, qsf, sdc and slot map are identical; only
docs and `build.sh` differ, so the range is an exact answer, not a vague one.

The method is not assumed to work; it is **validated against eleven
independent Quartus builds**. For each of the eleven census commits, the
label the fitter actually produced equals the label predicted for that
commit at the `cfg:` line shape that commit's own `build.sh` used — and the
shape changes three times over the range (no cfg line → `loopback=` only →
four fields → five fields), in the right chronological order, without being
told to. Eleven for eleven.

**And the three artifacts the argument actually rests on were re-derived the
hard way**, by building them with their macros set and checking the filename
the fitter produced:

```
3152e2b1  PI_MAINCAP=1   -> dsp4_logic_maincap.d903ae1ac4a9    404 LEs
3152e2b1  PI_SELFTEST=1  -> dsp4_logic_pisel.2c1355bbc69b      303 LEs
a096c585  DRIVE_ALL=1    -> dsp4_logic_driveall.907492a607bd   401 LEs
```

Each reproduces the committed artifact's name exactly. `d903ae1ac4a9` is the
`maincap` bitstream S20, S29 and S31 flashed, and it is **a 404-logic-element
design**.

### 1.2 What the three actually are

**`1f66f975`, +155 LEs — the CM4 stereo return, and it is a product feature.**
This is the single largest item in the 247 and it is not bring-up
scaffolding. Until this commit the Pi capture path lived inside
`` `ifdef DSP4_LOOPBACK `` and the shipping build kept `pcm_din` tied to
`1'b0`. The commit deletes the `ifdef` and says why: the CM4 needs a send
**and** a return, the send already existed (Pi I2S → TDM8 A_I6 slots 0/1),
and the return costs no pin and no PCB change because B_O3 is already routed
to LOGIC and `pcm_din` is already a net to Pi GPIO20. The 155 LEs are two
32-bit capture shift registers, two 32-bit holding registers and the
read-out mux. **This is the one item in the 247 that a reviewer should look
at as a product decision rather than as a cost**, because removing it removes
the CM4's return path.

**`2bb0b491`, −32 LEs — the TDM8 rework made the shipping build cheaper.**
The eight-channel work replaced the two per-slot shift/hold pairs (four
32-bit registers) with one shared shift register plus a flat 256-bit
`cap_flat` register file. In the shipping configuration `PI_TDM8` is 0 and
only slots 2 and 3 are ever read, so six slots prune away and what is left —
32 bits of shift plus 64 bits of held word — is **32 LEs cheaper than what it
replaced**. The commit's own comment explains the flattening: a doubly
indexed array makes the MAX V flow try to infer memory the device does not
have, and `quartus_map` segfaults.

**`3152e2b1`, +124 LEs — the design-ID block, built in every configuration on
purpose.** `DESIGN_ID` and `CFG_BITS` registers, the 64-bit knock comparator
(`0xD5D51D1D` / its exact inverse), the 128-frame reply counter, and the
`cap_hold`/`cap_snap` re-timing that fixed the two-frame splice. It is
unconditional by design, and the design note says why: MAX V has no
configuration readback over SVF, the DSPs have no link into this CPLD, and
the TEST pins land on a DNP header, so the CM4's PCM capture is the only path
off the part that needs no hands. **That 124 LEs buys the ability of any
future flash to answer "what are you?"** — and §1.4 is what happens without
it.

## 2. Gate 2 — what the candidates assume, and what the 82 samples mean

Finding **S36-2**.

### 2.1 The note added to `window-candidate.md` yesterday is wrong in a way that matters

It says:

> All of it — both candidates, every bar, the 82-sample latency figure — was
> measured with the LOGIC CPLD carrying `dsp4_logic.a1f6672af6c3`.

**Two of those bars were not.** The part carried `a1f6672af6c3` *before and
after* those sessions, not *during* them:

* **the 82-sample latency figure (S29, n=3)** was measured on
  `dsp4_logic_maincap.d903ae1ac4a9` against the `dsp4_logic_pisel` reference.
  `maincap` is built from **`3152e2b1`** — all 404 LEs.
* **every driven capacity row** (`window-candidate.md` §2.1, the
  `100.82 %` D32 worst-use figure, the S28/S31 product rows) was measured on
  `dsp4_logic_driveall.e13b5dec84e0` — the DRIVE_ALL configuration, and the
  one artifact of the three that has no committed source (§1.4).

Everything else in the document — `famverify`, `busgold`, `goldnode`, the
numeric arms, the gate-4 flip, the silent capacity rows — genuinely was taken
with `a1f6672af6c3` on the part, and none of it moves.

### 2.2 What that means for the 82 samples, proved from the RTL

The question is whether the loop the 82 samples was measured through differs
from the loop the shipping part would present. **The DSP-facing side does
not differ at all, and that is provable rather than assertable.**

**`dsp4_clkgen.v` is byte-identical between `a4ee3d1f` and `main`** — the
diff is empty. So `frame_pos`, BCK8, FS8 and every TDM8 framing strobe the
DSP sees are the same logic.

**The Pi → DSPA transmit path is cycle-for-cycle identical in the shipping
configuration.** Side by side, with `PI_TDM8 = 0`:

| | `a4ee3d1f` | `3152e2b1` |
|---|---|---|
| period index | `out_period = frame_pos[9:2] + 8'd1` | identical |
| slot / bit | `out_period[7:5]` / `out_period[4:0]` | identical |
| launch edge | `bck8_launch` | identical |
| slot 0 source | `left_q[31-bit_ix]` | `pw_flat[{0, 31-bit_ix}]` |
| slot 1 source | `right_q[31-bit_ix]` | `pw_flat[{1, 31-bit_ix}]` |
| slots 2-7 | `1'b0` | `1'b0` (`slot < 3'd2` else zero) |
| word capture | `frame_pos[9:4] == PCM_DATA_DELAY+32 / +0` | `pi_word_pos ==` the same, and `pi_word_pos = frame_pos[9:4]` when `PI_TDM8=0` |

`pw_sel_l` and `pw_sel_r` are hard 0 and 1 when `PI_TDM8` is 0, so `pw_flat`
slots 0 and 1 hold exactly what `left_q` and `right_q` held, written on the
same `frame_pos` values and read on the same edge. **The register file is a
different shape holding the same bits at the same times.** The DSP cannot
tell the two apart.

**The differential is clean, and both arms were the same commit.** S29's
method subtracts a `pisel` CPLD-loop reference from the `maincap` through-DSP
figure. Both bitstreams come from the same RTL, and in `3152e2b1`
`CAP_EXTRA_DELAY` is **0**, so `cap_extra = PI_SELFTEST ? 0 : 0` is zero in
both arms — the Pi-side arithmetic is identical and cancels exactly. What
remains in the 82 is the TDM8 out hop, the DSP, the TDM8 in hop and the
`cap_flat` write.

### 2.3 So: the figure stands, but not for the reason the note gives

**The 82 samples is a sound measurement of the DSP's contribution.** It was
taken on RTL whose DSP-facing half is identical to the shipping part's, with
a differential that cancels the Pi-side framing, on a clock generator that
has not changed a byte.

**It is not, and cannot be, a measurement taken on the shipping bitstream.**
On `a1f6672af6c3` `pcm_din` is tied to `1'b0` and there is no capture path at
all, so the Pi records nothing and the measurement is not merely different —
it is impossible. `loadlogic.sh` exists precisely because of this: on the
shipping bitstream `arecord` returns "Input/output error" and zero frames.

The honest statement for `window-candidate.md` is therefore **not** "measured
with `a1f6672af6c3` on the part", but: *the latency arm requires a bitstream
the shipping part does not carry; it was measured on `maincap`/`pisel` from
`3152e2b1`; the DSP-facing framing is proved identical to the shipping
design's, so the figure transfers.* The correction is made in that document
in this commit.

**No candidate depends on anything else main's RTL provides.** Neither
`shipping.config.s26` nor `.s32` reads the slot-map hash, the design-ID
register or any scope-class gate from LOGIC; the S4 `strap_d32` personality
is unchanged across the whole range; and the slot map's own contents changed
only in pointer comments (`efd8d5…` → `2c53de…`), which are inside the
artifact hash but change no behaviour.

**Flash `dsp4_logic.138dba7274d6`** — `a4ee3d1f` plus the pin-direction
change and nothing else, 157 → 157 LEs, five pins (S35-3). Not the branch.

* **Proof**: the probe at J18 P37 = 12.288 MHz, P38 = 48 kHz (dead today).

**Flash `dsp4_logic_maincap.d903ae1ac4a9`** — already committed, already

### Step 2 — S39: the shipping configuration of main, for the first time

**Build and flash the shipping build of `c0407483` + the step-0 pin change.**

* **Proof**: `blk_*` 30 s zero overruns both chips; the S17 capture; the

**Rebuild `driveall` from `a096c585` (= `907492a607bd`) and repoint

## 4. Gate 4 — the X-logic parking fix

Finding **S36-4**. Branch **`s36-xlogic-park`**, commit `07818879`, **not
merged**.

### 4.1 The defect is on copper that already exists

Pins 110 and 111 are not spare pads. From the hub's fan-out table, each is a
three-board net:

```
U3.110  LOGIC_PLL5_1  G2667   dsp J1/J2.74 | digital J18.74, J2.A13 [NO7]
                              | opt2 SLOT.A13 [open]
U3.111  LOGIC_PLL5_2  G2668   dsp J1/J2.71 | digital J18.71, J2.A10 [NO4]
                              | opt2 SLOT.A10 [open]
U3.109  LOGIC_PLL5_0  G2666   dsp J1/J2.73 | digital J18.73, J2.A12 [NO6]
                              | opt2 SLOT.A12 [open]
```

On a D24 both outputs had a **constant** driver — `snake_out` a hard `1'b0`,
`dac_main` the live B_O3 TDM8 lane. The day a card is fitted to option slot 2
and drives its own A-row, two CMOS outputs meet **with no series resistance
between them**. Unlike the converter-clock pair there is no 33R here to
absorb it, and nothing has to be added to the board for it to happen — only a
card fitted.

### 4.2 The dispatch offered two answers; the netlist settles which

The dispatch asked whether to park on pins 81/85/87 — described there as "the
reserved clock pads" — or to tri-state on D24. **Both halves of that
description are wrong, and the answer is still tri-state.**

**They are not clock pads.** Test-built with `snake_in`/`snake_out`/`dac_main`
moved to pins 87/85/81: `quartus_fit` succeeded with **0 errors**, and the
All Package Pins table types all three as plain **`Row I/O`** — no dedicated
clock, no DIFFIO, no relocation. 404 LEs, 71 pins.

**They really are dead.** The fan-out table gives pin 81 (`L1`, `G2621`),
pin 85 (`C2`, `G2450`) and pin 87 (`C0`, `G2447`) all three as
`(nothing - single-pin net)`, on the `dsp` board alone. They reach nobody.
(Note the trap: the converter pair `C1`/`L0` on pins 142/141 are *not* like
this — they fan out to the 33R taps and the analog board, which is S35-4.)

**So parking would work, and it would still be the wrong fix.** ONE bitstream
serves D24 and D32, because `strap_d32` is a runtime strap and not a build
switch (`dsp4-architecture-decisions.md`). Moving `snake_out` and `dac_main`
to dead pads would forfeit the D32 role these pins exist for. Tri-stating
keeps both products correct in one image:

```verilog
assign snake_out = strap_d32 ? o_dspb[2] : 1'bz;
assign dac_main  = strap_d32 ? o_dspb[3] : 1'bz;
```

High-Z costs the D24 nothing: the Pi capture path reads `o_dspb[3]`
**internally** as `tdm_in` and never through the pin.

**The weak pull-ups are the other half of the fix.** With slot 2 empty all
three pins float on a D24 — `snake_in` always, the other two now that they
are tri-stated — and a floating CMOS input sits near the switching threshold.
The global `RESERVE_ALL_UNUSED_PINS` does **not** cover them, because they
are assigned pins, so each gets `WEAK_PULL_UP_RESISTOR` explicitly.

### 4.3 Measured, on both bases

| base | LEs | pins | Fmax | TRI on 110/111 | weak PU on 109/110/111 |
|---|---:|---:|---|---|---|
| `a4ee3d1f` | 157 | 71 | 70.21 MHz | no | Off |
| `a4ee3d1f` + fix | **156** | 71 | 65.64 MHz | **yes** | **On** |
| `main` (`c0407483`) | 404 | 71 | 68.54 MHz | no | Off |
| `main` + fix | **403** | 71 | 71.26 MHz | **yes** | **On** |

**One LE cheaper on both bases** — the constant-zero driver goes away — and
the pin map is identical either side on both: nothing moved. Fmax spread is
fitter seed noise on ~20 MHz of margin, as S35-2 established.

The fitter confirms the mechanism rather than the intent: `strap_d32` appears
in the fit report as an **`Output enable`** source with fan-out 4, and both
pins carry `TRI Primitive: yes` and `Weak Pull Up: On`, against `no` and
`Off` on main.

### 4.4 The sim gate was extended, and proved to bite

The existing testbench encoded the old behaviour and **failed the fix**,
which is the gate working. It now asserts the new contract, and the check
uses `===` so it distinguishes `1'bz` from `1'b0` — **a driven D24 pin is the
wrong answer whatever value it carries**, which is the whole point.

Proved by mutation: restoring `assign dac_main = o_dspb[3];` fails it at
t=3000 with `dac_main must drive B_O3 on D32 and be high-Z on D24`. Restored,

## 5. Gate 5 — `tools/pi/logic_flash.sh`

Finding **S36-5**. **Not run against the unit.** Proved against stubs.

### 5.1 What it does

Runs on the desk, drives the bench over ssh, same shape as `loadlogic.sh`.
The remote half is a quoted heredoc, and `--self-test` runs **those same
bytes** locally against stub `pinctrl`/`openocd`/`systemctl`, so what is
tested is what is shipped.

* **Refuses unless `pinctrl get 26` reads LOW**, and **fails closed**: an
  unparseable reading, or no `pinctrl` at all, is treated as *not met*. The
  level is taken from the field after the `|` and nowhere else, so a comment
  or pin alias containing `hi`/`lo` cannot decide an interlock.
* **The rollback is verified present and md5-recorded BEFORE the first
  write.** A rollback discovered to be missing after a failed flash is not a
  rollback.
* **FLASH-OK on attempt 1, or the rollback goes straight back.** No retries —
  `loadlogic.sh` retries because it moves between known-good bitstreams; this
  script exists for putting something *new* on the part.
* **Success is S27-5's check, not the IDCODE**: openocd's chain reached its
  `shutdown` with no `tdo check error`. The IDCODE is still read before and
  after, because it separates "the flash failed" from "the tap was never
  there".
* md5 verified on the bench against the desk's; manifest printed; everything
  appended to `/home/app/logic-flash.log`; JTAG pins handed back in the S8-3
  canonical sequence whatever happened.

### 5.2 It implements PW's three rulings as flags, not as workarounds

S35-1 left three shapes. Each has a flag; none has a default:

* `--stop-app` — stops `matrix-app`, waits, and **re-reads GPIO26**. It does
  not assume the pin follows the app down; S35 could not say whether it does,
  because S35 did not stop the app. If the pin stays high, that is a finding
  and the flash still does not happen.
* `--an-en-waived "<written reason>"` — the shape-3 ruling. The reason is
  **mandatory** and is recorded in the log; a bare flag is rejected.
* Gating on something that tracks the rails needs hardware and is not in this
  tool.

### 5.3 Proved, ten cases, against a fake

| # | case | expected | got |
|---|---|---|---|
| 1 | AN_EN HIGH | refuse | **exit 5**, names S35-1 and PW's options |
| 2 | AN_EN unreadable | refuse | **exit 5**, "treated as NOT MET" |
| 3 | AN_EN LOW, `--dry-run` | pass gates, no write | **exit 0** |
| 4 | AN_EN LOW, flash succeeds | flash | **exit 0**, FLASH-OK on attempt 1 |
| 5 | flash fails on attempt 1 | rollback | **exit 7**, ROLLBACK OK |
| 6 | flash and rollback both fail | loud unknown state | **exit 8** |
| 7 | AN_EN HIGH + written waiver | proceed, recorded | **exit 0** |
| 8 | `--an-en-waived "  "` | reject | **exit 2** |
| 9 | staged copy corrupted | refuse before write | **exit 3**, md5 mismatch |
| 10 | rollback absent | refuse before write | **exit 3** |

Cases 9 and 10 refuse **before any write is attempted**, which is the
property that matters.
