# S39 — the instrument was wrong, the converters are running, and the capture is one bit late

**2026-09-12, MW-D24-2 (192.168.1.219), D24 Analog rev B attached and live,
AN_EN HIGH throughout, step-0 bitstream on the part.**

Three of S38's findings were readings of a host symbol map that does not
belong to the image on the part. Corrected, the picture inverts: the
per-strip node state was never zero, the block-cost instrument was never
missing, and the input lanes were never dead. **Every one of the twelve
chip-1 converter lanes is live and carrying a per-lane-distinct noise
floor** — which settles the converter-clock question by construction and
closes the standing probe request.

Audio still does not reach the XLR, and there is now a named, systemic
reason: **the SPORT RX capture is one bit late on every lane**, so every
negative sample arrives as a near-full-scale positive one.

And the S38-3 mechanism is named without needing the bitstream pair at
all: **the block boundary is exactly on time and the work does not
finish.**

## 1. Gate 1, first half — the instrument (S39-1)

Every "it reads zero" result on this bench came through one path:
`peek(sym[name])` — the diag peek window, addressed from the host's
symbol map. Three S38 findings rest on it, and none of them follows from
the source:

* **S38-5**, "`C1_GAIN_01`'s entire node state block is zero, i.e. never
  written". The node ASM declares `.var _gain_coeff_<nid> = 1.0`,
  `_gain_target_<nid> = 1.0`, `_gain_q_<nid> = 0x10000000`. A part that
  booted and took no write must read its *initialisers* there, not zero.
* **S38-3**, "`_proc_cyc`/`_proc_passes` read 0 on both chips, so it is an
  uninstrumented build". `main.asm` writes all three words at the end of
  every block pass on both chips with **no `#if` around them**. There is
  no uninstrumented build in this tree.
* **S38-6**, "all twelve `_rx_slot_C1_IN_nn` are static zero". Those
  variables are dead by construction under block kernels — §4.

### The discriminator

The same variable was asked for by two routes that share nothing:

* **A** — `peek(sym['_gain_coeff_C1_GAIN_01'])`, host map + peek window;
* **B** — the **SPI parameter read** at address `0x0000`, which
  `spi_handler.asm` resolves through `_spi_dispatch_c1` **inside the
  image**, and whose `.spi_read` path reads the very DM word the write
  path targets. There is no shadow store anywhere in that file.

On `blk_*`, with the bench's own map:

    _gain_coeff_C1_GAIN_01   peek 0x00000000  |  spi 0x0000 read 0x3F800000
    _fdr_level_C1_FDR_01     peek 0x00000000  |  spi 0x0050 read 0x3F800000

`0x3F800000` is `1.0f` — the built initialiser, exactly as the source
says. **The kernel is right and the map is wrong.**

### Proof that the map is the variable, not the part

The fresh pair was built from the tracked tree and its symbol map
generated from *its own* `chip1.map.xml`. Booted, the same three
registers were peeked through both maps:

| symbol | new image + **its own** map | new image + the **bench** map |
|---|---|---|
| `_diag_ticks` | 17,355 | 0 |
| `_spi_rx_count` | 179 | 0 |
| `_frame_count` | 63,132 | 0 |

Same part, same instant, same peek window. The map is the only thing that
changed.

### What the bench map actually belongs to

`/home/app/dspboot/chip1.sym.json` is 216,077 bytes — byte-for-byte the
size of the map regenerated from the `build/chip1.map.xml` that was left
in the tree on Sep 11 (S37's arm A, `chip1.ldr` `6396187c`). The image
booted was `blk_*` `ac65ad38`. Two different builds.

The part says so itself: **`blk_*` reads `DIAG_BUILD_CFG2 = 0x00000000`
on both chips.** That register exists in every current build and the
shipping value is `0xC2010244`; the fresh pair reads exactly that. An
image that answers 0 there predates the register.

**Consequence, stated plainly: no peek-addressed reading taken on `blk_*`
is anchored, and that is a whole class of results, not three.** The SPI
parameter reads, the DIAG registers and the meters are unaffected — they
resolve inside the image.

## 2. Gate 1, second half — what writes per-strip node state (S39-2)

**An SPI parameter write. There is no other apply path, and there is no
separate commit, scene or apply step to find.**

`chip1/dsp_params.asm` is generated by `gen_dsp.py` and is a flat table
from SPI address to the **DM address of the node's own variable**:

    _gain_coeff_C1_GAIN_01,    /* 0x0000: C1_GAIN_01 gain coeff */
    _polarity_C1_GAIN_01,      /* 0x0001: C1_GAIN_01 polarity   */
    _fdr_level_C1_FDR_01,      /* 0x0050: C1_FDR_01 level       */

`spi_handler.asm` indexes it and either writes the word directly
(`.spi_instant_plain`, stride 0) or hands it to `_ramp_set_target`, which
sets level **and** target and clears frames. The read path indexes the
same table to the same word. The change-detect the strip nodes gate their
control-rate prep on is `_ctl_epoch[strip]`, bumped on every accepted
write at `.spi_write_answer`.

So the kernel side is complete. **The gap is entirely host-side:**

* `dsp4_config.py --product d24` writes the product SCOPE only — 51
  words on chip 1, 5 on chip 2;
* `matrix-app` has no DSP address for any strip cell (`MW/D24/MX/
  _matrix.csv`, 0 `DspAdd` rows of 4985);

so **a D24 boots with every strip at its build-time initialiser and
nothing ever moves it.** That is the single-SOT item, and it is a missing
*writer*, not a missing mechanism.

`tools/pi/dsp4_apply_strip.py <strip> [aux]` is that writer: it takes
every strip off both buses and mutes it two ways, opens the destination
chains, then writes the named strip's whole chain by cell name out of
`landed-d24.json`. Not one `peek` in it — every read-back is an SPI
parameter read.

    read back: 13 ok / 0 mismatch / 0 unreadable

(The 24 "not in the contract" cells it names are `Chan025`–`Chan032`: a
D24 has 24 strips. Expected, not a defect.)

## 3. Gate 4 — the mechanism, named, without the bitstream pair (S39-3)

The instrument S38 called absent is unconditional in `main.asm`. Read
through a map that matches the image, on the fresh pair:

| | chip 1 | chip 2 |
|---|---|---|
| `_proc_cyc` (last pass) | 376,593 | 337,969 |
| `_proc_cyc_max` | 378,202 | 338,703 |
| per-block budget at 983.04 MHz | 327,680 | 327,680 |
| **cost as a share of budget** | **114.9 %** | **103.1 %** |
| `_proc_passes` in 30.0 s | 78,458 = 2612.5/s | 87,326 = 2910.2/s |
| **shortfall against 3000/s** | **12.92 %** | **2.99 %** |
| shortfall predicted by 1 − 1/cost | 12.97 % | 3.01 % |

Repeated 20 s later: chip 1 114.3 % predicts 12.51 %, measured **12.49 %**;
chip 2 104.0 % predicts 3.85 %, measured **3.59 %**.

The budget denominator is anchored, not assumed: the diag tick rate
measures **1000.03 Hz on chip 1 and 1000.00 Hz on chip 2**, ratio
1.00003, so the core clock is at its 983.04 MHz target.

### The discriminator S38-3 asked for

**`DIAG_FRAME_COUNT` advances at 3000.0/s on chip 1** — 45,010 in 15.00 s
— **while `_proc_passes` advances at 2612/s on the same chip in the same
window.** The block boundary is exactly on time to five figures; the
processing simply does not finish inside it.

**The answer is "more work", not "the boundary moved".** The missed-block
rate is the arithmetic consequence of the over-budget ratio, to within
0.1 percentage point, on both chips and on repeat.

**This did not need the bitstream pair.** Two counters on one boot
separate the two hypotheses, because they measure the boundary and the
work independently. The old-bitstream arm would have said how many
cycles the converter clock *adds*; it could not have said which
hypothesis was right.

**The bitstream arm was in any case not available this session, and
correctly so:** AN_EN is HIGH (the hub raised it), `logic_flash.sh`
refuses at exit 5 with AN_EN high before any write, and GPIO26 must never
be written by this session. The interlock did exactly its job. Recorded
as not-run rather than skipped.

### The figure that matters more than the mechanism

Both chips are **over** the per-block budget on the shipping
configuration — chip 1 by 15 %, chip 2 by 3–4 %. S38-4 already said both
chips sit close to the budget and small changes tip them either way.
This says they are not close to it; they are past it.

## 4. Gate 2 — the chain walk, and the variable that is not on the path (S39-6)

Under `DSP4_BLOCK_KERNELS` a strip does **not** run through
`_buf_C1_IN_01`. `C1_IN_01.asm` says so in its own comment — *"under
block kernels this kernel reads the DMA buffer directly, so the slot var
is unreferenced — kept as a scalar purely so `block_io.asm`'s tables
still resolve"* — and `_C1_IN_01_process` reads the SPORT DMA buffer
straight into `BLK_CHAIN_A`. Every node after it reads and writes
BLOCK-word slots of the shared pool (`blk_pool.h`); the per-node scalars
survive as linkage and carry only the last sample of the block.

On the part, with a map that matches:

    _rx_slot_C1_IN_01            0x00000000      <- dead by construction
    _buf_C1_IN_01                0x00000000      <- dead by construction
    _buf_C1_GAIN_01              0x0FFF0540      <- +0.99976 in Q4.28
    _tap_post_trim_C1_GAIN_01    0x0FFF3640
    _gain_coeff_C1_GAIN_01       0x3F800000      <- 1.0f, correct
    _gain_q_C1_GAIN_01           0x10000000      <- Q4.28 unity, correct
    _mute_C1_GAIN_01             0x00000000

**S38-5 injected a step into `_buf_C1_IN_01` and read `_buf_C1_GAIN_01`.**
The first is not an input to anything and the second is one sample of a
block. "The step reaches `_buf_C1_IN_01` at exactly +0.25 and dies at
`_buf_C1_GAIN_01`" is what writing to a variable nothing reads looks
like.

### An instrument limit that applies to every pool reading below

A peek is a two-transaction handshake serviced once per block, so
sixteen consecutive pool addresses come from **sixteen different
blocks**. A pool read is a mosaic. "Is this point ever non-zero over N
blocks" is a question a mosaic can answer; a waveform is not, and no
frequency is claimed anywhere in this write-up.

## 5. Gate 3 — the converters are running, and the capture is one bit late (S39-4)

The lane the kernel actually reads is
`_rx_active_buf + _c1_rx_off[e] + i*_c1_rx_stride[e]`. Read there, every
lane is live and moving. Raw words, chip 1 lane 1:

    0x7FF60480 0x00065000 0x0001E280 0x0002A980 0x0002A980 0x7FF8B280

Those are not audio as Q1.31, and the shape of the error is the finding.
Across **all twelve chip-1 lanes, 288 words**:

| quarter of the range | words |
|---|---|
| `0x00000000`–`0x3FFFFFFF` (small +) | 140 |
| `0x40000000`–`0x7FFFFFFF` | 148 |
| `0x80000000`–`0xBFFFFFFF` | **0** |
| `0xC0000000`–`0xFFFFFFFF` (small −) | **0** |

**Bit 31 is never set on any word of any lane, and the low 7 bits are
never set either.** Real signed audio cannot do that. A capture one bit
late can, and does exactly this: the sample's sign bit lands in bit 30, a
zero is shifted in above it, so a small negative sample `0xFFF9F000`
arrives as `0x7FFCF800` and a small positive one is unchanged.

Score the same words both ways:

| reading | peak | rms |
|---|---|---|
| as received, Q1.31 | −0.00 dBFS | ≈ −3 dBFS |
| shifted left one bit | ≈ −60 dBFS | −65 to −85 dBFS |

and under the corrected reading the level **varies per lane** — rms
0.000054 to 0.000593 across the twelve — which a dead lane, a stuck lane
or a constant cannot do.

### What this settles

* **The converters are clocked and converting.** Twelve independent
  lanes, each with its own noise floor, landing in their own TDM slots,
  on a part whose block loop is locked to the same SPORT at exactly
  3000 blocks/s (i.e. 48 kHz at BLOCK=16). Nothing that is not being
  clocked produces that. **This closes S34-1 by construction, and the
  standing PROBE PLEASE for J18 P37/P38 is no longer needed to establish
  it.** It would still be the way to confirm the exact 12.288 MHz figure
  if that is ever wanted for its own sake.
* **S38-6 is refuted.** The lanes are not static zero; the twelve
  variables it scanned are.
* **This is the defect standing between this unit and first audio.**
  Every negative sample becomes a near-full-scale positive one, which is
  a violent full-scale artefact on every input. It is what pins the
  meters at −0.00 dBFS peak / −3 dBFS rms in *every* arm including a
  muted one, what saturates the aux bus accumulator at Q4.28 8.0
  (+18.06 dBFS on `Aux001Mtr001`), and what drives the AUX 1 DAC lane
  above full scale.

It is one bit, it is on every lane, and it is therefore a SPORT/TDM
configuration item — frame-sync-to-data delay — not a per-channel fault.
**Fixing it is the next session's first job**, and until it is fixed no
level, no gain law and no meter reading on this unit means anything.

|---|---|---|---|
| 0 | 1.538322 | 1.531704 | **0.000000** |
| 1–7 | 0.000000 | 0.000000 | 0.000000 |

Strip 1 is live at every point in between: chip-1 tap post-trim, tap EQ
and tap pre-fader, then `_buf_C2_MIX_AUX_01`, `_buf_C2_AUX_AFB_01`,
`_buf_C2_MIX_MAIN_L` and `_buf_C2_MAIN_FDR` on chip 2, all non-zero on

**MIC 1's lane does not respond to any of it.** Corrected-reading rms,
five arms on one boot, the mic pre live and unchanged throughout:

| arm | what drives AUX 1 | mic 1 lane rms |
|---|---|---|
| A | aux master MUTED, send off | 0.000339 |
| B | aux open, ch1 send OFF | 0.000351 |
| C | aux open, ch1 send −40 dB | 0.000397 |
| D | aux open, ch1 send **0 dB** | 0.000380 |
| E | aux master MUTED again | 0.000373 |

Under 1 dB of spread and **no ordering** — D is not the loudest and A is

**So the DSP side is proven good from the strip to the TX DMA buffer, and

reaching the TX buffer at all. That is separate from S39-4, separate from
the analog break, and not yet root-caused.

## 7. Control authority — one arm holds, one does not (S39-7)

Driving each control to several values and measuring downstream, rather
than reading it back:

**The channel fader has authority.** `Chan001Level001` 1.0 → 0.1, against
−20 dB expected:

| point | measured |
|---|---|
| `_buf_C2_MIX_MAIN_L` | −18.03 dB |
| `_buf_C2_MIX_AUX_01` | −20.55 dB |
| `_buf_C2_MAIN_FDR` | −21.92 dB |
| chip-1 tap **pre**-fader | +0.78 dB — correctly unmoved |

and at `Level = 0.0` all three go to exact silence. The pre-fader tap not
moving while the three post-fader points move together is the internal
check that makes this a measurement rather than a coincidence.

**The channel gain arm did NOT resolve, and is recorded as unresolved.**
`Chan001Gain001` 1.0 → 0.1 gave −5.63 / −4.89 / −7.23 dB against −20
expected, and the chip-1 pre-fader tap — which is *downstream* of GAIN —
did not move at all. Two reasons not to call that a defect yet:

* the stimulus is the S39-4 artefact, whose amplitude distribution is not
  linear in the true input, so a linear gain need not scale it linearly;
* the estimator's own scatter is about ±2.5 dB — the same point read
  0.1167, 0.1347 and 0.1543 under identical conditions in three sections
  of the same run.

**It needs a controlled stimulus, and a controlled stimulus needs S39-4
fixed first.** Named as the retake rather than guessed at.

**The aux-master arm probed the wrong point and shows nothing (S39-8).**
`_buf_C2_MIX_AUX_01` is *upstream* of `C2_AUX_FDR_01`, so its
non-response to `Aux001Level001` is correct behaviour and is not evidence
either way. A retake needs a point downstream of the aux fader.

## 8. On the generator, and why there is no tone in this write-up

Gate 3 asked for a 1 kHz tone and named the fallbacks. For the record,
what the image actually offers:

* **`C1_NOISE` is a dead node.** Its header says "Pink/white noise + tone
  generator"; the body is an LFSR and a pinking filter with **no
  oscillator**, and its output goes nowhere — `_buf_C1_NOISE` has no
  consumer in `process_chain.asm`, and the dispatch entry for its route
  bitmask (`0x128B`) is `0`, i.e. unmapped. It cannot be routed to a bus
  from the host.
* **`scope.asm` offers impulse and step only** — `_scope_mode` 1 and 2 —
  so the DSP-side stimulus is a single impulse or DC. DC will not survive
  an AC-coupled output stage, so it cannot test the analog loop.
* **A host-toggled square is possible** — flipping `_scope_amp` between
  ±A in step mode — but the link is serviced once per block, so the
  fundamental is limited to a few hundred Hz and is host-timed, i.e.
  jittered. Named as available, not used.

None of it was needed: the loop question was answered by the
`Aux001Mute001` control on the TX lane and the five-arm control on the RX
lane, which is a stronger test than a tone because it has a negative arm.
