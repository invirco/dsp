# S41 — MHRX must fall when the Pi halts

**Result in one line:** the LOGIC CPLD's weak pull-up on pin 74 was the only
thing holding MHRX high, it is off now, the net falls, and a control arm on the
part proves the attribution. The power MCU's own acknowledge was **not**
witnessed, because reading its firmware showed that the test the dispatch chose
— `sudo poweroff` with the rocker ON — cannot reach the acknowledge path.

## 1. The pin, on paper (gate 1)

`M MCU_P17` / G2691 carries the CM4's UART0 TX (GPIO14, J24.55) to three
sinks: M MCU U8.32, LOGIC U3.74, and power MCU U34.6, which watches it as the
"Pi alive" sense. No resistor appears on the net in the signals index, so the
only terminations are inside the three parts.

Pin 74 is **not assigned** in the shipping design and has no RTL port. It is
covered by the global

```
set_global_assignment -name RESERVE_ALL_UNUSED_PINS "AS INPUT TRI-STATED WITH WEAK PULL-UP"
```

and the step-0 fit report says exactly that:

```
; 74  ; 112 ; 3 ; RESERVED_INPUT_WITH_WEAK_PULLUP ; ; ; ; Row I/O ;   ; no ; On  ;
; Reserve all unused pins   ; As input tri-stated with weak pull-up ;
```

That global stays. It is the 2026-08-19 trap's fix and it is what keeps the MH
and panel UARTs from being ground-driven. Pin 74 comes out of it by name and
nothing else does.

**Pre-registered target:** after the change, pin 74 = input, tri-stated, no
weak pull-up. That is what was built.

**U8 pin 32.** No M MCU firmware source exists in mx26 (`src/fw/` has the power
MCU only), so the question was settled by measurement instead of by reading —
see §4. It is not a second pull-up source.

## 2. The bitstream (gate 2)

Branch `s41-mhrx-pullup-off` = `s37-step0-shipping-base` (61e38ce3) + one
commit, `a9e8e05d`, three lines in `quartus/dsp4_logic.qsf`:

```
set_location_assignment PIN_74 -to mhrx
set_instance_assignment -name RESERVE_PIN "AS INPUT TRI-STATED" -to mhrx
set_instance_assignment -name WEAK_PULL_UP_RESISTOR OFF -to mhrx
```

Like its parent, **this branch must never be merged to `main`** — it is the
shipping design that is on the part plus the minimum change, deliberately
without main's later logic elements.

Reserving the pin as an input is not a bus fight: the only driver on the net is
the CM4, push-pull, and this end is an input either way.

**The step-0 baseline was rebuilt first**, from a clean `git archive` of
61e38ce3, and reproduced its recorded pof md5 `79284dad6e9c27995f91806056c9fba5`
exactly — so the fit-report diff below is between two builds of this toolchain
and not against a report from somewhere else.

**The pin-table diff is one row.** "All Package Pins" is 150 lines in both
builds:

```
- ; 74 ; 112 ; 3 ; RESERVED_INPUT_WITH_WEAK_PULLUP ;       ;             ; ; Row I/O ;   ; no ; On  ;
+ ; 74 ; 112 ; 3 ; mhrx                            ; input ; 3.3-V LVTTL ; ; Row I/O ; Y ; no ; Off ;
```

Every other pin's location, direction, I/O standard, bus hold and weak pull-up
are byte-identical, and the logic element count is identical: 156 (28
registers). Total pins 68 -> 69, which is the reserved pin counting as a user
pin.

**And the fitter re-placed the design.** Adding a pin constraint re-seeds
placement: LABs 24 -> 26, peak interconnect 7.6 % -> 10.6 %, every control
signal in a different cell (`u_clkgen|Equal1~0` LC_X10_Y7_N3 -> LC_X6_Y6_N3),
Fmax 66.1 -> 70.05 MHz. The netlist is unchanged — same RTL, same 156 LEs, same
sim gate — but the bitstream bytes are not "step 0 with one bit different", and
the manifest says so, so that nothing is later attributed to a change this
artifact does not contain.

Built twice from clean trees: pof byte-identical, `72a28864d54334215d192070d5742252`.
svf `fc6ce23ed14cda464f277a56cf21ab92` (bodies identical with `!` comments
stripped, as for every artifact here — S37-1).

`logic_flash.sh --dry-run` against it with `--rollback s37_shipping_step0…`:
every gate passed, AN_EN low, IDCODE `0x020a30dd`, **exit 0, nothing written**.

## 4. The proof on the part (gate 4)

### The net — proved, with a control

The instrument is the CM4 itself, which costs one ssh command and no scope:
release GPIO14 from the PL011 and read the net, then put TXD0 back.

| on the part | `pinctrl set 14 ip pn` | `pinctrl set 14 ip pd` | `… ip pu` |
|---|---|---|---|
| step 0 (as found) | **hi** | **hi** | — |
| **s41 fix** | **lo** | **lo** | hi |
| step 0 (control) | **hi** | **hi** | — |
| **s41 fix** (re-flash) | **lo** | **lo** | — |

Before: the net held high even against the CM4's own ~50 k internal pull-down —
an external pull-up stronger than 50 k, which is the MAX V weak pull-up
(~25 k typ). After: low, and still low against nothing at all. `ip pu` reads
high in the fix arm, so the net is not shorted low and the reading is live.

**The control arm is what makes this an attribution.** Nothing about U8 or the
board changed between the arms, and the net followed the bitstream every time —
so **M MCU U8 pin 32 is not a second pull-up source** and neither is the board.
The DSP-side CPLD was the whole of it. The net still reads low after several
rail cycles, so the change is in the configuration flash.

The power MCU has its own pull-down on PA0 (`board.h`), so with the CPLD's
pull-up gone the sense line is actively held low rather than floating.

### The acknowledge — NOT witnessed, and the firmware says why

The gate asked for `sudo poweroff` with the rocker ON, expecting the shutdown
sequence to complete in seconds. It cannot. In mx26 `src/fw/pwr-mcu/main.c`
(ba9b2bc; 0215bc4 adds only the reset log), `ST_ON` has exactly two exits:

```c
case ST_ON:
    if (!rocker_on)  { enter_shutdown(TRIG_SWITCH); break; }
    if (!v12_ok)     { enter_shutdown(TRIG_FAIL);   break; }
```

**MHRX going low in ST_ON does nothing.** The Pi-off acknowledge is inside
`ST_SHUTDOWN`, and `ST_SHUTDOWN` is entered by the rocker or by 12 V failing —
never by the Pi halting on its own. The path this fix serves is therefore the
other one, which is also the original complaint:

> rocker OFF while the Pi is still running -> `enter_shutdown(TRIG_SWITCH)`
> with `pi_alive_at_entry = 1` -> PI_SD -> the app saves and halts -> **MHRX
> must fall** -> ack at `CFG_MHRX_ACK_LOW_MS` = 100 ms, else
> `CFG_SHUTDOWN_TIMEOUT_MS` = 60 s.

That needs a hand on the rocker, and the dispatch's own terms put PW's hands
out of scope and the rocker ON throughout. **It is one minute of PW's time and
it is the only thing left:**

```
# with the unit ON and the Pi up, watch the LED and a clock:
#   flick the rocker OFF.
#   expect: 5 Hz shutdown blink, and the rails drop a second or two after the
#           Pi finishes halting — NOT 60 s later.
#   the old behaviour was the 60 s failsafe every time.
```

### What the `poweroff` run did measure

It was run before the firmware was read, so it is recorded for what it is.
Halt to the next kernel start was **154 s** (network down at +8 s, kernel start
at +162 s, ssh at +180 s). A plain `reboot` — the identical OS shutdown path
with no rail cycle — is **10 s** from network-down to kernel start. So ~144 s
of it happened off the Pi.

With the rocker ON and 12 V present, no firmware path can cycle the rails, so
something reset the MCU. Two further uncommanded cycles followed within four
minutes; the unit then ran 308 s clean and was handed back that way.

**Not attributed to this bitstream** — the CPLD has no rail control, and the
unit ran six minutes clean between the flash and the `poweroff`, including two
DSP boots and four 30 s bars. But it is not explained either, and it is the
same shape as the reset-pulsed-rails loop `ba9b2bc` was written to kill.
`0215bc4` put a reset-cause log in no-init SRAM, readable over SWD; **that is
the next reading**, and it was not taken here because this session was not to
touch the power MCU.
