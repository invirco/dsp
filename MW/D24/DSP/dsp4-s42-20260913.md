# S42 — the one bit named at the source, and AUX 1 was leaving on the wrong XLR

**THE UNIT WAS NEVER TOUCHED.** MW-D24-2 stayed powered down on PW's bench with
the analog board mid-rework. No ssh to 192.168.1.219, no boot, no flash, no
`pinctrl`, nothing on the part. Every figure below comes from the schematic,
the netlist, the HRM, the tracked source, or an artifact built at the desk.
S40's block is untouched.

---

## 0. The four things this session found

1. **The one-bit-late RX has a named cause and a register.** The AK5558 ADCs
   and AK4458 DACs are strapped **TDM128 in the I2S variant** — one bit clock
   between the frame edge and the MSB — and LOGIC already asserts FS one BCK8
   before slot 0. A converter half therefore needs `SPORT_MCTL.MFD = 2`; every
   half had 1. Fixed in the tracked source, **per lane**, so it lands on the
   bitstream that is already on the part.
2. **The transmit side has the exact mirror**, from the same strap, and it was
   never going to be found by the CPLD loopback: a symmetric MFD error cancels
   in a loopback by construction.
3. **AUX 1 was leaving the unit on the Aux Out A8 XLR.** The OUT_1-8 analog
   block is reversed and the DSP slot map did not compensate. That alone
   explains S39-6 — DSP good to the DAC, MIC 1 silent — with no analog fault.
   MAIN Out 1 was on a DAC channel that is not connected to anything.
4. **S39-5b's "seven of eight chip-2 TX lanes always zero" is an instrument
   artefact**, of the same class as S39-1's symbol map: the tool read the first
   eight entries of the 24-entry TX **node** table and called them lanes.

## 1. Gate 1 — the one-bit-late capture, at the source (S42-1)

### 1.1 What the measurement actually says

S39-4 read, across all twelve chip-1 lanes and 288 words: bit 31 never set,
bits 6:0 never set, every word either just under `0x80000000` or just over
`0x00000000`. That is not "roughly a shift"; it is exactly

```
received = (sample >>> 1)
```

with a zero in bit 31 — `0xFFF9F000` arriving as `0x7FFCF800`. A receiver whose
window opens one serial clock **early** produces precisely this: the shift
register takes one extra bit before the MSB, so it ends holding
`{previous bit, sample[31:1]}` and `sample[0]` is lost past the word latch.

And the extra bit is always zero for a reason that closes the loop: the
converters send **24 bits left-justified in a 32-bit slot**, so the bit
immediately before slot *n*'s MSB is slot *n−1*'s LSB, which is pad. Same fact
explains bits 6:0 never being set — those are `sample[7:1]`, also pad.

Three signatures, one mechanism, no free parameters.

### 1.2 The mechanism, with the register and the bit

`SPORT_MCTL_A.MFD` [7:4], "Multichannel Frame Delay — the delay in serial bit
clocks between the frame sync pulse and the first data bit in the frame"
(ADSP-21560/61/64/68 HRM rev 0.3, §21-35). The same chapter, §21-34: *"The
first bit of the transmit data word is driven and the first bit of the receive
data word is sampled in the same serial clock cycle as the frame sync, provided
there is no programmed frame delay (`MFD = 0`)."*

Three things have to agree, and two of them cannot move:

| | what it does | can it move? |
|---|---|---|
| `dsp4_clkgen.v` | `fs8` asserted through BCK8 period 255, i.e. one period before slot 0 | it could, but it would not help — see below |
| AK5558 / AK4458 | TDM128 **I2S** format: MSB one BCK after the frame edge | **no** — pin-strapped |
| `sport_config.c` | `MFD` | **yes, and it is the only one that helps** |

The reason the CPLD's FS phase is not a lever is worth stating once: the DSP
and the converters are slaved to the *same* FS, so moving it moves both. The
only thing that changes their relative alignment is the converter's internal
frame-to-data delay (strapped) against the SPORT's MFD (programmed).

So: FS sampled high at period 255; the converter's MSB at period 1 (one BCK for
the I2S format, on top of the one period LOGIC already leaves); MFD must be
**2**, and was **1**.

### 1.3 The strap, read off the board

D24 Analog rev B, sheet **13/64 "ADC8"**, the AK5558's own notes block,
rendered at 400 dpi and read:

```
TEST    = 0     = internal 100k pull-down.
MCLK    = 12.288MHz.
CKS0-3  = 0100  = 48kHz, 12.288MHz, 256fs.
SLOW/SD = 01    = HPF short delay, sharp roll-off.
DIF0-1  = 10    = I2S 24-bit mode.
TDM0-1  = 01    = TDM128 mode.
DP      = 0     = PCM mode.
HPFE    = 1     = High pass filter enable.
LDOE    = 1     = Enable LDO voltages.
ODP     = 1     = Normal TDM128 outputs.
```

and the pin block beside it confirms the strap wiring: `+3V3 → DIF0`,
`GND → DIF1`, `GND → TDM0`, `+3V3 → TDM1`. **`DIF0-1 = 10` is I2S**, which is
the one-BCK-delayed format. mx26's read of the DAC8 sheet records the same two
straps on the AK4458 (`TDM0-1 = 01`, `DIF0-1 = 10`, `d24-analog-paths.md` §1),
so both directions are framed the same way.

### 1.4 The TX-side mirror, from the same analysis

Yes, and it is a transmit **one bit early**. The same `cfg_region()` wrote
`MFD = 1` on the chip-2 TX halves, so the DSP launched slot 0's MSB one BCK
before the AK4458's window opened. The DAC latched

```
DAC word = {DSP word[30:0], first bit of the next slot}
```

i.e. the value doubled with the sign bit thrown away — a positive word below
half scale survived as 2×, and anything at or above half scale came out with
its sign inverted. The 24-in-32 padding does **not** save this direction: the
lost bit is the MSB, which is signal.

**Why nothing caught it.** The `DSP4_LOOPBACK` bitstream — the instrument whose
whole purpose was to close "BCKI/FSI pair order, sample edge / MFD, within-TDM8
slot order" by measurement — feeds every DSPA input lane from the matching DSPB
output lane through a wire. Both ends use the same MFD. **A symmetric MFD error
cancels exactly in that loop**, so the loopback could confirm slot order and
pair order and was structurally blind to this. Said out loud so the loopback's
other results are not doubted and this one is not expected of it.

### 1.5 The fix, and why it is per lane

`SPORT_MCTL.MFD` is a per-half register, and this board has two framing peers
that genuinely differ:

* **converter-framed halves** — the ADC lanes, the DAC lanes, the codec, the
  MEMS bridge, the option-slot NET lanes: everything on LOGIC's
  `conv_bck`/`conv_fs` pair. `MFD = 2`.
* **LOGIC-framed halves** — the Pi PCM lane into DSPA I6, and the DSPB O3 lane
  the CPLD captures for the Pi's return. `dsp4_pcm_reframe.v` builds both for
  `MFD = 1` and says so in its `out_period`/`in_period` comments. `MFD = 1`.
* **the inter-chip mix fabric** — DSPA O → DSPB I, direct copper, both ends
  move together, so any value is self-consistent. Left at `MFD = 1`.

**This is the property that makes tomorrow possible without a flash.** If MFD
were a single constant, moving it to 2 would misframe the Pi's two lanes
against the bitstream on the part, and fixing that means two constants in
`dsp4_pcm_reframe.v` (`out_period + 1 → + 0`, `in_period − 1`) and a CPLD
flash. Per lane, the converter fix lands on `s41_mhrx_pullup_off.15f3ae07dae1`,
which is already on the part, and nothing else moves.

Bringing the Pi lanes to the converter convention later is one step: those two
RTL constants and two entries in the generator's table, together.

Changed:

| file | change |
|---|---|
| `tools/dsp/dsp_codegen.py` | `MFD_CONVERTER=2 / MFD_CPLD=1 / MFD_FABRIC=1`, `CPLD_FRAMED_SIGNALS`, `lane_mfd()`; `lane_layout(..., mfd=)`; emits `<region>_mfd[]` into `lane_config.c` |
| `MW/D32/DSP/SHARC/src/sport_config.c` | `cfg_region()` takes the per-lane table; `MCTL.MFD` comes from it. Nothing is chosen in this file |

The generated result, which is the whole change in one glance:

```
c1_rx_lanes_mfd[8] = { 2, 2, 2, 2, 2, 2, 1, 2 }   /* lane 6 = A_I6 = Pi PCM */
c1_ic_lanes_mfd[3] = { 1, 1, 1 }                  /* mix fabric */
c2_ic_lanes_mfd[3] = { 1, 1, 1 }                  /* mix fabric */
c2_tx_lanes_mfd[5] = { 2, 2, 2, 1, 2 }            /* lane 3 = B_O3 = Pi return */
```

### 1.7 The exact bench check S40 runs first

`tools/pi/dsp4_s42_align.py [symdir] [samples]`. It writes nothing and moves no
control. Run it before anything else; until it passes, no level, gain law or
meter reading on this unit means anything.

**RX — chip 1, all twelve converter lanes, at
`_rx_active_buf + _c1_rx_off[e] + i*_c1_rx_stride[e]`:**

| test | expected after the fix | what failure looks like |
|---|---|---|
| bit 31 | **exercised** across the twelve lanes (a quiet lane crosses zero) | never set on any word of any lane = still S39-4, the MFD did not reach the part |
| bits 6:0 | **never set** (the 24-in-32 pad, now in the right place) | set = the window is off the other way |
| rms per lane, read as Q1.31 | **−65 … −85 dBFS** — the band S39 measured under the corrected reading | outside it = not a converter noise floor |
| the twelve rms values | **distinct** (S39 measured 0.000054 … 0.000593) | twelve equal numbers = one stuck source, whatever the bit tests say |

The distinctness test is the one a stuck lane cannot fake, and it is why the
tool scores it separately.

**TX — chip 2:** the tool resolves `C2_AUX_OUT_01`, `C2_AUX_OUT_02`,
`C2_MAIN_OUT_01`, `C2_MAIN_OUT_02` and `C2_MAIN_ST_OUT` **by name** through
`_c2_tx_ptrs` (not by position — that is the S39-5b mistake) and prints the
offset, stride and peak each carries. Expected: AUX 1 live and **inside ±1.0 in
Q4.28**, not the 1.538 (+3.75 dBFS, above full scale) S39-6 read — that reading
was the RX artefact arriving at the DAC and it must disappear with the RX fix.
MAIN Out 1/2 now live on B_O1 slots 3 and 2.

**The transmit framing itself is proved by the analog loop and by nothing
else at the desk:** with RX right, AUX 1 → MIC 1 must return a clean scaled
copy. A still-early transmit returns a doubled, sign-wrapped one — a violent
artefact, not a quiet wrong level, so it is unmistakable.

## 2. Gate 2 — the DAC lane ↔ XLR table (S42-2)

The table is `docs/d24-dac-lane-xlr-candidate-20260913.md`, filed as a **defs
candidate**: 27 rows, every chip-2 TX node with its lane, slot, converter
channel, output stage and the connector it physically reaches. Summarised here
only where it changes what the firmware does.

### 2.1 Two derangements, not one

**OUT_1-8 (AK4458 U81, lane B_O0) is REVERSED**: channel *n* comes out of rear
XLR `OUT_(9−n)`. Traced independently on the analog board and again on the
phone-jack board, all eight channels (mx26 `d24-analog-paths.csv`, 267
completed paths). mx26 filed the consequence in S-11 as a question for this
repo — *"either the dsp slot map compensates already, or the sixteen `OUT_nn`
rows need their `carries` column changed"*. **It did not compensate.**

**OUT_9-16 (AK4458 U92, lane B_O1) is a different derangement**, readable only
from D24 Analog rev B sheet **12/64 "OUT_9-16"**, which draws the DAC's 16-wire
bus into six named blocks:

| TDM slot | signal | U92 ch | block | connector | rear panel |
|--:|---|---|---|---|---|
| 0 | `DAC_09` | 1 | PHONES_L | J10 tip | headphones L |
| 1 | `DAC_10` | 2 | PHONES_R | J10 ring | headphones R |
| 2 | `DAC_11` | 3 | MAIN_R | **J57 XLR** | **Main Out R** |
| 3 | `DAC_12` | 4 | MAIN_L | **J56 XLR** | **Main Out L** |
| 4 | `DAC_13` | 5 | — | — | **NOT CONNECTED** (U92 pins 32/33 are one-pin nets) |
| 5 | `DAC_14` | 6 | SUB_W | J55 XLR | Centre/LF Out |
| 6 | `DAC_15` | 7 | MON LR | J53 tip | Monitor Out L |
| 7 | `DAC_16` | 8 | MON LR | J54 tip | Monitor Out R |

### 2.2 What that meant for the unit on the bench

* **AUX 1 left the unit on the Aux Out A8 XLR**, and the Aux Out A1 XLR carried
  aux 8, which was silent. PW's patch is AUX OUTPUT 1 → MIC INPUT 1. **That is
  sufficient on its own to explain S39-6** — "the DSP side is proven good from
  the strip to the TX DMA buffer, and MIC 1 hears nothing" — with no analog
  fault anywhere on the path. The DAC was converting the whole time; the signal
  was leaving on a connector nobody had a cable in.
* **Main Out 1 was on `DAC_13`**, which is not connected to anything, and Main
  Out 2 on the Centre/LF XLR. Nothing reached the MAIN XLRs at all.
* Aux 11 and aux 12 were on the two MAIN XLRs.

### 2.3 The change, in the tracked source

`tools/dsp/gen_dsp_csv.py` gains two named tables, `AUX_DAC` and
`MAIN_OUT_DAC`, with the evidence in place above them. Twelve nodes move slot:

| node | was | is |
|---|---|---|
| `C2_AUX_OUT_01..08` | `DAC_01..08` | `DAC_08..01` — aux *n* now reaches the XLR marked **Aux Out A*n*** |
| `C2_MAIN_OUT_01` | `DAC_13` (not connected) | `DAC_12` = **MAIN L**, analog J56 |
| `C2_MAIN_OUT_02` | `DAC_14` (Centre/LF) | `DAC_11` = **MAIN R**, analog J57 |
| `C2_AUX_OUT_11` | `DAC_11` | `DAC_13` |
| `C2_AUX_OUT_12` | `DAC_12` | `DAC_14` |

`dsp.csv` differs in exactly 12 rows. **No SPI address moved**, nothing was
added or removed: the allocator's totals are identical (chip 1 page 1 / addr
4967, chip 2 page 1 / addr 2175), which is the property that keeps the host,
the ghost table and the landed map valid.

Generated consequence: `_c2_tx_off`/`_c2_tx_ptrs` in `chip2/block_io.asm`
reorder, and 12 `C2_*_OUT_*.asm` node files take their new slot. Fifteen
generated files in all, and the delta was taken by generating the old and new
trees side by side and copying only the files that differ — see §5.2.

### 2.4 The row S39-5b corresponds to

`dsp4_s39_outpath.py` walks `_c2_tx_off[lane]` for `lane in range(0, 8)` and
prints "TX lane 0..7". **That array is not indexed by TDM lane.** It is the
24-entry TX **node** table, ordered by (sport, slot), and its first eight
entries were `C2_AUX_OUT_01..08` — all eight on lane B_O0.

So "lane 0 is AUX 1" is entry 0 and is right; "lanes 1–7 always zero" is aux
2–8 carrying nothing, which is **correct behaviour**, nothing having been
routed to them; and **MAIN was never in the window at all** — `C2_MAIN_OUT_01..04`
are entries 12–15 and `C2_MAIN_ST_OUT` is entry 18. The tool stopped at 7.

There is no "seven silent lanes" defect and no "MAIN absent at the TX buffer"
defect. `dsp4_s42_align.py` resolves nodes by name through `_c2_tx_ptrs`, so
the same mistake cannot be made twice.

### 2.5 What is deliberately NOT changed

Six product questions, listed with the evidence in §5 of the candidate:
`C2_MAIN_OUT_03/04` still sit on the Monitor Out jacks; the Centre/LF XLR is
still fed by aux 12 rather than `C2_SUB_OUT` (which goes to a network lane);
`C2_MON_OUT` is still the codec's talkback-speaker pair; the headphone outputs
have no DSP source node at all; aux 9–12 have no D24 rear connector; and
`C2_MAIN_ST_OUT` stays on `B_O3`, which has no D24 sink by design. Each is a
product decision, not a wiring fact, and this session made none of them.

## 3. Gate 3 — capacity, restated and not changed (S42-3)

Full sheet: `MW/D24/DSP/dsp4-capacity-decision-20260913.md`. The finding in
three lines:

**The gap between the fit tables (59.8 % / 84.4 % driven at D24) and the part
(114.9 % / 103.1 %) is not the graph and is not a measurement error. The fit
tables price a configuration the product does not ship**, and the part says so
in its own register: `shipping.config` → `DIAG_BUILD_CFG2 = 0xC2010244`, which
is exactly what S39 read off both chips; `shipping.config.s26`, the anchor
under every fit table since S20 → `0xC2019E6F`. Six switches differ
(`STRIP_FUSED`, `SIMD_DYN`, `C2_BQ_GRAPH`, `GATE_LINTHR`, `DYN_LUT`,
`SHARED_KERNELS`) and all six are capacity levers.

So the answer to "what does the shipping configuration contain that the fit
tables did not price" is **nothing** — it is the other way round. GEQ at 31
bands on twelve aux buses, four groups and the main bus; twelve aux chains; the
24-strip mask; block 16 — all of it is inside the 59.8 % / 84.4 %. What is
absent from the shipping build is the pairing. S19 measured and said this on
2026-09-10 (*"the configuration `shipping.config` names does not fit either
product"*) and `shipping.config.s20` has been the staged proposal ever since.

The three cheapest levers, all already built and already witnessed:
`C2_BQ_GRAPH` (≈17 points of chip 2 at D24; 0 ulp over 36,864 words on
`bqeverify`), `SIMD_DYN`+`STRIP_FUSED` (the chip-1 lever; famverify 1 of 20
verdicts differs, COMPRESSOR numeric at 0.00518 dB), `GATE_LINTHR` (54 % of the
gate body for ≤0.0002 dB). `DYN_LUT` is named fourth and separately because its
bound is 0.0950 dB — two and a half orders larger than the other three — and
because it is what makes the signal free (+42.5 / +29.3 points of driven-minus-
silent on the shipping configuration, +0.05 / −0.29 on s20).

**And the number itself should be re-taken.** The 114.9 % was measured with
every input at full scale by accident: S39-4's artefact pinned the meters at
−0.00 dBFS in every arm, so every gate and compressor on chip 1 was fully
engaged throughout. With the capture fixed the inputs return to −65…−85 dBFS.
Prediction for S40's first ten minutes: chip 1 falls toward ~76 %, chip 2 toward
~90 %. That does not change the decision — a mixer is not specified at idle —
but PW should be deciding against the honest number.

No edit was made to any configuration file or to the generator's cost model.

## 4. Gate 4 — the MHRX pull-up folded into main's LOGIC tree (S42-4)

The three qsf lines from `s41-mhrx-pullup-off`, appended to **main's**
`shared/dsp4-logic/quartus/dsp4_logic.qsf` with the S41 evidence in the
comment. The branch is **not** merged and must not be: its diff against main

### 4.4 What this artifact is, and is not

It is **the shipping candidate carrying the pull-up in main's lineage**, and it
is 403 LEs — main's RTL, which S37 staged as **step 2**. What is on the part is
`s41_mhrx_pullup_off.15f3ae07dae1`, which is the **156-LE step-0 lineage** plus
the same three qsf lines. The two lineages now both carry the fix; only the
step-0 one has ever been on the part.

**Flashing `ed70d3214c29` puts 247 logic elements that have never run in a
shipping configuration onto the part.** That is S37 §4.2's reason for staging
step 2 separately and it has not changed. It is a bench session's job, under
the four-flash discipline, with the rollback staged first — **not tonight, and
not as a side effect of anything else.**

### 4.5 `logic_flash.sh`'s default rollback was stale AGAIN

It read `s37_shipping_step0.c62c024714f2.svf`. That is what S41 **rolled back
to** during its control arm, not what it **left on the part** — S41 finished by

second unannounced flash, which is the exact defect S41 fixed one step earlier

Now `s41_mhrx_pullup_off.15f3ae07dae1.svf`
(md5 `fc6ce23ed14cda464f277a56cf21ab92`, which matches what S41 recorded), with

visible. **The rollback now points at what is on the part.**

its manifest, records the desk md5, names the new rollback, and stops at
**exit 3 — "not staged on the bench"**, before any write. That is the correct
refusal for a desk session and it is the whole of what was run; the unit was
never contacted.

## 5. Records, and two things found on the way

### 5.1 The tree is not what the generator produces (S42-5)

`python3 tools/dsp/dsp_codegen.py MW/D32/DSP/SHARC/dsp.csv MW/D32/DSP/SHARC/src
--force` on the committed tree rewrites **117 files**. Most of it is comment
prose, but **64 lines are code**: the regenerated `_process_sample` path of
every `C1_FILT_*` and `C1_EQ_*` node drops `i6 = BLK_CHAIN_B_P1; l6 = 0;`.

This is pre-existing drift — the generator moved and the node files were
regenerated with a `--node-type` filter that did not cover them — and it
predates this session. **It was reverted, not absorbed**, so that S42's diff is
only S42. It is the same class of fault as S39-1: the artefact and the thing
that describes it have drifted apart, and nothing checks.

The per-sample path is not the hot path under `DSP4_BLOCK_KERNELS` (the block
kernels jump to `_shk_filt_blk`), so this has not been executing. It still
wants a session: either the generator is right and the tree should be
regenerated wholesale, or the tree is right and the generator has a defect.

### 5.2 How the generated delta was taken

Because of §5.1 a blanket regeneration was not safe. Instead: the old and new
generators were each run into a scratch tree, the two trees diffed (**15 files**
— two `lane_config.c`, `chip2/block_io.asm`, and twelve `C2_*_OUT_*.asm`), each
of those 15 verified byte-identical between the old-generator output and the
committed tree, and only those 15 copied in. So the committed delta is provably
the generator change and nothing else.

### 5.3 A legacy array permutes, and nothing reads it

`_c2_tx_ptrs` reordering permutes `_meter_peaks[]`, which `_meter_scan_chip2`
fills in table order. Nothing addresses it positionally: no host tool in
`tools/pi/` and no path in `gen_dsp.py` reads it, and the product meters are the
`METER` nodes with their own SPI addresses (`Aux001Mtr001` and friends), which
are unaffected. Recorded as a consequence, not a defect.

### 5.4 No contract moved, and `gen_dsp.py` refuses for an older reason (S42-12)

`gen_dsp.py --force` exits with the no-fallback error: the graph proposes 356
cells on d32 and 237 on d24 that the landed `defs/products/<p>/dsp.csv` lacks
(`Chan*CompMtr001`, `Chan*LcrOn001`, `Chan*MatrixOn/Send*`), and the landed
`dsp-unmapped.csv` carries exactly those. **Verified pre-existing**: stashing
every S42 change and re-running gives byte-identical error text and the same
counts. That is the policy working — the graph has advanced past the pinned
`defs-v*` tag — and it is a hub item, not this session's.

The consequence for S42 is the useful one: **no contract artifact moved.** The
twelve slot moves changed no SPI address, no cell and no `_matrix.csv` row
(`dsp_validate.py`: 698 nodes, OK, no errors), so there is nothing to bump and
`release-notes-contract-convention.md` is not engaged.
