# S45 — the D24 matrix gets its DSP addresses from the generator

**The unit was never touched.** No ssh to 192.168.1.219, no flash, no boot, no
build of a shipping image, no bench tool run against hardware. Desk only,
start to finish. S40 is untouched and still paused.

`MW/D24/MX/_matrix.csv` carried a DSP address on 0 of its 4,985 rows because
one path in one file was spelled `SCRIPT_DIR/../MX/_matrix.csv`. That is the
whole cause. The matrix is the only artefact the console app loads and the
only place it can get a DSP address from, so a line that read "D32's matrix"
where it meant "this product's matrix" was a D24 that could not write a single
per-strip DSP node state — and four separate gates passed over it, each asking
a question that did not include this one.

Three things came out of the session. The backfill runs for every product, from
that product's own landed map, with the D32 matrix byte-identical to the hash
it has carried since `cea457e0`. The app's contract is stated and checked: the
matrix as produced satisfies mx26's loader **without an app change**, and the
13 cells the bench tool writes by name carry exactly the addresses the tool
computes, 13 of 13. And the class of failure cannot recur silently — a gate
that would have caught it on day one now runs at the end of both the drift
check and the regenerate flow, with eight negative controls behind it.

Nothing was landed. The one generation that can run today reads the S44
candidate, whose rows have not passed the hub gate, so its output was measured
and restored rather than committed. §5 says what that costs and what unblocks
it.

## 1. The backfill, for every product (S45-1)

### 1.1 What was wrong

`MW/D32/DSP/gen_dsp.py` held two module globals:

```python
MATRIX_CSV   = os.path.join(SCRIPT_DIR, '..', 'MX', '_matrix.csv')
MATRIX_STAGE = os.path.join(SCRIPT_DIR, '..', 'MX', '_matrix.expansion.csv')
```

`SCRIPT_DIR` is `MW/D32/DSP`, so both name D32's files. `main()` read one
matrix, backfilled one matrix and wrote one matrix. Every other product's
`_matrix.csv` came out of `sync-defs.sh` as the bare expansion and stayed that
way, because the expansion does not carry DSP address columns — that is what
the backfill is for.

The address map was never the problem. `defs/products/d24/dsp.csv` has mapped
D24's cells since the hub landed it, and `tools/dsp/landed_map.py` has read it
for the bench tools all along. Only the step that copies those addresses into
the published matrix was missing, and only for D24.

### 1.2 The change

The two globals became functions of the product; `_matrix_path()` — which
already resolved "stage if there is one, else the committed file" for the
proposal path — is now the one implementation of that rule and everything
calls it. `backfill_matrix()` takes the map to fill from as an argument
instead of reading the module global. A new `backfill_product()` does one
product end to end: resolve the source, read, fill, assert coverage, hand back
rows ready to write. `main()` loops over `BACKFILL_PRODUCTS` and writes
nothing until every product has passed — the same shape as `sync-defs.sh`'s
install loop and for the same reason, so a failure on D24 cannot leave D32
rewritten.

**Each product is filled from its OWN landed map, not the merged one.** One
shared address map (decision D3) is a statement about addresses, not about
cell sets: D24 defines 4,985 cells and D32 6,999, and a D32-only cell has no
business carrying an address in D24's matrix. Measured, because "it cannot
happen today" is worth knowing precisely: per-product and merged select
exactly the same cells at this pin — 3,737 for D24, 5,409 for D32, under the
candidate 3,974 and 5,765. The stricter rule costs nothing now and closes the
case where it would not.

`sync-defs.sh` carried its own copy of the list:

```sh
# PRODUCTS WHOSE MATRIX IS BACKFILLED AFTERWARDS. Keep in step with
# MW/D32/DSP/gen_dsp.py: MATRIX_CSV there is D32's and only D32's ...
STAGED_PRODUCTS=(d32)
```

A comment asking whoever came next to keep two files in step by hand, sitting
directly over the fact that they were not in step. Both halves now read
`gen_dsp.py --backfill-products`. D24's expansion is staged exactly as D32's
is, so between `sync-defs.sh` and `gen_dsp.py` the committed D24 matrix holds
the last complete generation — which S44 built for D32 and D24 could not use
because nothing staged it.

### 1.3 Both counts

`gen_dsp.py --backfill-report` is new: it reads the landed map and the
matrices and counts, writes nothing, and says which provenance it counted, so
a number taken under `DSP_LANDED_DIR` cannot be mistaken for a number from the
pin. It exists because `check_proposal()` is fatal by design and the graph has
been ahead of the landed contract since S22 — without it there is no way to
ask what the backfill would fill.

| map | D24 | D32 |
|---|---:|---:|
| landed, `defs-v2026.09.08.4` | **3,737** of 4,985 cells | 5,409 of 6,999 |
| the S44 candidate | **3,974** | 5,765 |
| on disk today | 0 | 5,765 |

The last row restates S44-4 in the generator's own voice: the committed D32
matrix already carries the candidate's 5,765, not the landed 5,409.

### 1.4 Coverage is asserted, per product

```
cells with an address + cells named unmapped == cells defined
```

is checked before anything is written — 3,974 + 1,011 = 4,985 and
5,765 + 1,234 = 6,999 under the candidate. The same invariant the proposal
asserts on the way out, checked on the way back in, so a matrix cannot acquire
a hole that the app has no way to see. Not decorative: renaming one D24 matrix
cell to a name in neither file stops the run and names that cell.

### 1.5 The D32 matrix, byte for byte

| run | result |
|---|---|
| candidate generation, scratch tree | D24 3,974 addresses; D32 identical; D12/D16 identical |
| same, run twice more (with and without `--force`) | D24 matrix identical to the byte both times |
| `DSP_LANDED_DIR=proposals ./check-contract-drift.sh`, real tree | exit 0; D24's matrix the only artefact changed |
| `DSP_LANDED_DIR=proposals ./regenerate-dsp-contract.sh`, real tree | exit 0; same; 765 SHARC sources unchanged |
| `./check-contract-drift.sh` (landed pin), real tree | exit 1 on the S22 drift, as before; all nine contract artefacts byte-identical |

`MW/D32/MX/_matrix.csv` reads
`041b19a585a93f6f24f53609da1e0502a893db20ad3dbea99d0e5cd5e3da8b8f` after every
one of them — the hash it has carried since `cea457e0`. `ghost_cells.h`,
`dsp_address_map.md`, both `dsp_params.asm` and `mx_dsp_map.h` are untouched;
so are D12's and D16's matrices, which have no landed map and are therefore
not backfilled and not checked.

D24's matrix gains the five `Ramp*` columns D32 already carried, 32 columns to
37. The app resolves columns by name, so that is additive for every reader.

## 2. The app's contract (S45-2)

### 2.1 What the app reads, and in what format

One artefact, resolved by `Core/AppContext.ResolveMatrixPath()` in mx26:
`{HomePath}/config/_matrix.mxc` if it is there (packed), else
`{HomePath}/config/_matrix.csv`, else — desktop only, store mounted — the
published `{store}/Products/<P>/pd/generated/_matrix.csv` it was cut from.
`Core/Boot.LoadMatrixData()` loads it; nothing else is read.

`Core/ProjectBuilder.Matrix.cs::GetMatrixCsvHeaders()` resolves the columns
**by header name** into integer indexes:

| column | app field | format |
|---|---|---|
| `DspI2c` | `dspI2cHdr` | legacy ADAU path; the DSP4 backfill does not write it |
| `DspSpi` | `dspSpiHdr` | chip, decimal: `1` = DSPA, `2` = DSPB |
| `DspPage` | `dspPageHdr` | SPI page, decimal |
| `DspAdd` | `dspAddHdr` | word address within the page, **decimal** |
| `DspAddHex` | `dspAddHexHdr` | the same value as `0xNNNN` |

All five are strings as far as the loader is concerned. Nothing in the app
computes an address, derives one from a stride, or carries a fallback table;
an absent or empty column reads as `(undefined)`
(`Views/DspViewer.axaml.cs::SafeCsvRead`).

**So the D24 matrix as produced satisfies the loader with no app change.** The
columns already exist in D24's header — they were simply empty — and the
backfill writes exactly the four the app names, in exactly the form it expects.

### 2.2 What the app still does not have

A writer. `DspViewer` is the only consumer of those columns and it displays
them next to the cell. The only SPI code in the app is
`Services/AnalogChainHardware.cs::SpiDevChain`, the 74HC595 analog chain on
`/dev/spidev0.0` — not the DSP link; `Core/AnalogBringUp.cs` says in as many
words that the DSP boot happens outside the process, in `dsp4_boot.py`.

That is an mx26 item, not a dsp one, and it is not made here. §6 names it.

`tools/pi/dsp4_apply_strip.py` (S39) writes a strip's node state by cell name,
out of `landed-d24.json`, which `tools/dsp/landed_map.py` cuts from
`defs/products/d24/dsp.csv`. For the 13 cells it writes and reads back for
strip 1 → MAIN + AUX 1:

|---|---|---|---|

retire on the app's schedule and not before, without a reconciliation step.**

## 3. The intake gate (S45-3)

`check-matrix-addresses.py`, run by `check-contract-drift.sh` after the
regeneration and by `regenerate-dsp-contract.sh` after its own — on what
generation actually produced, not on what it was asked to produce.

### 3.1 Why nothing already there could have caught it

| gate | what it asks | why this passed it |
|---|---|---|
| `sync-defs.sh` | does the EXPANSION match `defs.lock`? | the expansion has no DSP columns by design |
| `validate-matrix-contract.py` | MxAdd continuity, family allowlist | neither involves a DSP address |
| `check-contract-drift.sh --strict` | did git see the file CHANGE? | a file that was never right does not change |
| `gen_dsp.py::validate()` | do the graph and the matrix agree? | asked of the product it backfilled; silent about the one it did not |

Four gates, each individually correct, and between them a published matrix
missing every address it exists to publish. That is the shape worth
remembering: the gap was not in any one check but in the space none of them
covered.

### 3.2 What it checks

Per product `gen_dsp.py --backfill-products` names — asked of the tool rather
than restated, because a gate holding its own copy of the list is how this
stayed invisible:

1. zero addresses in the matrix while the landed map has any — the S44-5
   class, on its own, with its own message;
2. every cell the map covers carries an address, and it is the map's address;
3. no cell carries an address the map does not give it;
4. the four columns are filled together or not at all, and `DspAddHex` agrees
   with `DspAdd`.

D12 and D16 are not on the list and are reported as skipped: no landed
`dsp.csv` in `defs`, nothing backfills them, and asserting a contract that
does not exist is the failure the no-fallback policy is about.

### 3.3 The negative controls

Each against a scratch copy of a tree the gate passes clean (exit 0,
D32 5,765/5,765 and D24 3,974/3,974):

| # | the tree, damaged | verdict |
|---:|---|---|
| 1 | D24's whole address column blanked | exit 1 — "0 of 4,985 rows … cannot write a single DSP node state" |
| 2 | 12 mapped rows blanked | exit 1 — 12 cells named |
| 3 | one address off by one | exit 1 — cell named, both values printed |
| 4 | `DspAddHex` set to `0xDEAD` | exit 1 — hex/decimal disagreement |
| 5 | one row left with `DspAdd` and nothing else | exit 1 — ragged columns |
| 6 | an address written onto an unmapped cell | exit 1 — "an address no landed map names is an address no kernel answers on" |
| 7 | the `DspAdd` column removed | exit 1 — the app cannot read a column that is not there |
| 8 | the D24 matrix deleted | exit 1 — a backfilled product with no matrix |

Eight of eight. Plus the generator's own coverage assertion, exercised
directly: a D24 matrix cell renamed to a name in neither the map nor the
unmapped file stops `backfill_product()` and names it.

## 5. What did not land, and what unblocks it (S45-4)

**No matrix was committed.** `gen_dsp.py` cannot generate from the landed pin
at all: it exits 1 in `check_proposal()` on the S22–S25 drift S44
characterised, so the only generation that runs today is the candidate one,
and the banner on it is accurate — those rows have not passed the hub gate and
`defs.lock` does not describe them. Run in the tree it is clean and complete;
per dispatch its output was measured and restored.

**The consequence to hold.** From now on
`DSP_LANDED_DIR=proposals/defs/products ./check-contract-drift.sh` leaves a
real 4,985-row diff in `MW/D24/MX/_matrix.csv`. It is correct output with
ungated provenance: **do not commit it.** Under the landed pin nothing
changes — the script still exits 1 above the new gate, which is therefore
never reached, and leaves the tree byte-identical.

**Landing the S44 candidate is what unblocks it.** With the pin describing the
tree, `gen_dsp.py --force` runs from `defs/products/` and D24's matrix gains
its 3,737 addresses in an ordinary regeneration, committed with a pin that
describes them. Nothing else is in the way.

## 6. Hub items

1. **Land the S44 candidate** (`proposals/defs/products/<p>/` +
   `proposals/CONTRACT-PROPOSAL-S44.md`) at the next `defs-v*` tag — already
   the hub's recommendation from S44 and now also the one thing standing
   between D24 and a committed matrix with addresses in it.
2. **mx26 — the app needs a DSP writer, not addresses.** With this change the
   matrix carries them and the loader reads them unchanged; what does not
   exist is anything that writes a cell's value to the DSP over SPI. The
   only SPI in `src/sw/app/` is `Services/AnalogChainHardware.cs::SpiDevChain`
   (74HC595 analog chain, `/dev/spidev0.0`). Needed: the per-strip node-state
   contract S38-5 asked for — which cells, who applies store → node state and
   when (boot, scene load, cell change) — and then a DSP SPI service beside
   `SpiDevChain` that resolves a cell through `dspSpiHdr`/`dspPageHdr`/
   `dspAddHdr` and writes it. `tools/pi/dsp4_apply_strip.py` is the reference
   for what a strip's node state consists of; §2.3 shows the two paths reach
   identical addresses. **No mx26 file was edited by this session.**
3. **D12/D16 have no landed `dsp.csv`.** They are skipped by the new gate by
   design. If the hub ever lands the maps `--propose` already writes for them,
   adding them to `CONTRACT_PRODUCTS` is the whole change — the backfill, the
   staging and the gate all follow the one list.
