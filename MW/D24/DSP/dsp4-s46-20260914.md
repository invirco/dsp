# S46 — the morning sheet §1–§5 on the unit

**Hand-back state.** MW-D24-2 was handed back with `matrix-app` **active**, the
SPI pins in the configuration the app was found in (6 and 24 back to inputs;
7/9/10/11/22/23/25 at `a0`; 8/12 inputs), **AN_EN (GPIO26) low and never
written by this session** — it was read at every gate and nothing else — and
GPIO27, the SWD selects, the analog board, the rocker and `logic_flash.sh`
untouched, per R2. The app's own bring-up ran to its normal conclusion
(`MCU boot verified: H1S1, H1S3, H1S4`; `AnalogBringUp: [ok] S MCU (H1S1)
alive`; `*** AnalogBringUp: AN_EN STAYS LOW`), so the analog rails are not
requested and the board is unpowered — the safe state. **The DSPs were left
booted with the S42 pair and streaming.** R3 asks for them stopped unless the
sheet names streaming as the app's expected state, and the sheet does not; they
were left running because stopping them means driving !RST_D (GPIO16) low and
holding it, which is a larger departure from "as found" than leaving them up,
and because the app's bring-up explicitly cannot query DSP state either way
(`[??] DSPs booted and streaming — no boot-state query`). **This is the one
point where the hand-back is a judgement rather than an instruction; the hub
should say which it wants.**

**§1–§4 passed. §5 did not run to a verdict, and the reason is not a defect in
the DSP: the converters are not powered, so the twelve RX lanes have nothing on
them.** What §5 *can* prove without them was proved, at the register: S42's
one-bit MFD fix is on the part, on all nineteen lanes of both chips.

## 0. The unit was down when the session opened, and power-cycled itself

The dispatch's bench state (hub, 15:10 BST) records MW-D24-2 as **ON and to
stay on**. It was not on the network.

| time (UTC) | observation |
|---|---|
| 14:12:36 | first probe — no ICMP reply; ARP entry for 192.168.1.219 `FAILED` on the wired segment |
| 14:12:58 … 14:14:26 | five further probes, 20 s apart, all unanswered |
| 14:14:20 | **the unit's kernel boot** (`uptime -s`, after NTP correction) |
| 14:14:48 | SSH answers; `uptime -p` = *up 0 minutes* |

The unit was already unreachable at the first probe and came back **during**
the probe window, so nothing this session did caused it: the only packets sent
to that address before it answered were unanswered ICMP echoes and a single
TCP SYN to port 22. The whole subnet was swept for the unit's recorded SSH host
key (`known_hosts` line 70, ed25519 `…LK5v4rmAMaf…`) in case it had moved
address — ten hosts answered on port 22, none of them it.

**Corroborating evidence, and it points at the supply:**

* `vcgencmd get_throttled` = **`0x50000`** — bit 16 *under-voltage has
  occurred*, bit 18 *throttling has occurred*. No "now" bits set.
* `dmesg`: **`hwmon hwmon1: Undervoltage detected!`** at **+7.7 s** into this
  boot — with AN_EN low, so with the analog rails *not* requested.
* The clock was restored ~6 m 46 s behind by `fake-hwclock` and stepped by NTP
  at 15:14:56 BST. **Every "15:07:xx" stamp in this boot's app log is that same
  boot before the step** — the app did not start seven minutes before the
  kernel.

**No prior-boot evidence survives.** `journalctl --list-boots` holds one boot
(no persistent journal), `wtmp` and `/var/log/syslog` are absent, and
`/home/app/logs/log` is rewritten each start. The window in which it went down
can only be bounded by the hub's last interaction (rail measurement, 14:55 BST
= 13:55Z) and the first probe here.

**What this cost, concretely: AN_EN dropped.** The hub raised it by hand at
14:52 BST for the rail test; after the cycle GPIO26 reads `op … | lo` and the
app leaves it there by design. PW's rail-test state is gone and the analog
board is unpowered.

R4 makes an off unit a stop condition. It is recorded here as one, and the
session continued only because the unit came back into a fully verifiable
state — MCUs verified, app running, AN_EN low — and because the DSP-board half
of the sheet needs no analog board. **A sentinel was carried through the whole
session**: boot id `f1078486-…` and boot time 15:14:20 were re-read at every
gate and never changed, so **no further power cycle occurred while the work
ran**. This is S41's uncommanded-power-cycle class recurring; it is not
attributed to any bitstream here either.

## 3. The map is this image's — PASS, after the gate itself was fixed

`dsp4_s39_symcheck.py` first reported **agree 2 / disagree 3 / not-in-map 2**
on both chips, against the sheet's required *agree 5 / disagree 0 /
not-in-map 2*.

**The map was never wrong. The instrument was.** The three "disagreements" are
`_diag_ticks`, `_spi_rx_count` and `_frame_count`, and in each the *register*
column read `--` — the DIAG read raised, the peek did not. The sheet's actual
failure signature is those three peeking **zero**; they peeked 8,904 / 145 /
35,976 on chip 1 and 8,962 / 99 / 35,885 on chip 2.

The cause, read straight out of the exception:

```
register 0xE005 never settled: {'0x100a2': 1, '0x100a4': 1, '0x100a7': 1,
 '0x100a9': 1, '0x100ac': 1, '0x100ae': 1, '0x100b1': 1, ... }
```

Twelve asks, **twelve clean answers, every one larger than the last**.
`dsp4_scope.rd()` resolves a register by voting — it returns a non-zero value
only after seeing the *same* value twice in twelve asks — and **a free-running
counter never repeats**. Four of the seven pairs this gate checks are counters
(TICKS, FRAME_COUNT, SEC_COUNT, SPI_RX_COUNT), so `rd()` cannot read any of
them, on a healthy link and a correct map. Deterministic: 5 of 5 attempts on
each of the four; the three static registers (SPI_ERR_COUNT 0, BLK_OVERRUN
18096, RESP_DROP 0) returned every time.

The test that expresses the question is a **bracket** — ask, peek, ask — and
for a moving counter it is far stronger than equality, because a wrong address
cannot track one:

| | chip 1 | chip 2 |
|---|---|---|
| `_diag_ticks` | 578929 ≤ **578932** ≤ 578933 | 578914 ≤ **578917** ≤ 578918 |
| `_spi_rx_count` | 6160 ≤ **6163** ≤ 6165 | 1063 ≤ **1066** ≤ 1068 |
| `_frame_count` | 1745906 ≤ **1745915** ≤ 1745917 | 1745577 ≤ **1745586** ≤ 1745588 |
| `_spi_err_count` | 0 = 0 | 2 = 2 |
| `_diag_resp_drop` | 0 = 0 | 0 = 0 |

`Scope.rd_counter()` was added and `dsp4_s39_symcheck.py` rewritten onto it.
Re-run on the part: **agree 5 / disagree 0 / not-in-map 2 on both chips** — the
sheet's stated pass, now produced by the tool. `rd()` itself is unchanged, so
no other tool's behaviour moves.

**`DIAG_BUILD_CFG2 = 0xC2010244` on both chips**, exactly the word the sheet
requires (`DIAG_BUILD_CFG = 0xCF45FF10`).

## 5. The gate — **NOT TAKEN**, and the reason is the converters, not the DSP

### 5.0 What the gate proves without a converter: the MFD fix is on the part

This is the session's positive result and it answers the dispatch's question
directly. `SPORT_MCTL.MFD` is bits 7:4, written per lane by `sport_cfg_init()`
out of the generated `<region>_mfd[]` tables. Read back from the SPORT MMRs at
`0x31002000 + sport·0x100 (+0x80 for half B) + 0x08`:

| chip | region | MCTL read | MFD read | generated table | |
|---|---|---|---|---|---|
| 1 | rx, half A (converters), sports 0–7 | `0x725` ×7, `0x715` on sport 6 | **2,2,2,2,2,2,1,2** | `c1_rx_lanes_mfd` = 2,2,2,2,2,2,1,2 | **OK** |
| 1 | ic, half B (to chip 2), sports 0–2 | `0x0F15` | **1,1,1** | `c1_ic_lanes_mfd` = 1,1,1 | **OK** |
| 2 | ic, half A (from chip 1), sports 0–2 | `0x0F15` | **1,1,1** | `c2_ic_lanes_mfd` = 1,1,1 | **OK** |
| 2 | tx, half B (to the DACs), sports 0–4 | `0x721` ×4, `0x711` on sport 3 | **2,2,2,1,2** | `c2_tx_lanes_mfd` = 2,2,2,1,2 | **OK** |

**Nineteen lanes, nineteen matches, both chips, register for register.
S42's one-bit fix reached the part**, including the deliberate exceptions —
chip 1's lane 6 and chip 2's TX lane 3 are the CPLD/fabric lanes and are
correctly still MFD 1. This read needs no analog board and is now part of the
gate.

### 5.1 RX, twelve chip-1 converter lanes — **no verdict is available**

The gate as it stood reported:

```
RX: FAIL
  - bits 6:0 set on some word — the 24-in-32 pad is not where it should be,
    so the window is off the other way
  - lane(s) 1..12 outside the -65..-85 dBFS converter noise band
```

**That verdict is wrong, and it is wrong in a way worth naming.** The raw words
say why:

```
lane  1 off    0 stride 8  nonzero  6/16
   FFFFFFFF FFFFFFFF FFFFFFFF FFFFFFFF FFFFFFFF FFFFFFFF 00000000 00000000
   00000000 00000000 00000000 00000000 00000000 00000000 00000000 00000000
lane  3 off    2 stride 8  nonzero  6/16
   FFFFFFFF FFFFFFFF FFFFFFFF FFFFFFFF FFFFFFFF FFFFFFFF 00000000 00000000
   ...
```

Over **48 words per lane across three captures 0.4 s apart, on all twelve
lanes, exactly two values appear: `0x00000000` and `0xFFFFFFFF`** — with rare
one-bit variants (`FFFFEFFB`, `FFFFFFFB`, `FFFFDFFF`, `80280002`) that are a
line sampled mid-transition. That is an **idle, undriven TDM bus**. A powered,
clocking AK5558 produces a *dithered* noise floor — dozens of distinct small
values in 32 words even with its input open — never two.

And `0xFFFFFFFF` sets bit 31 **and** bits 6:0. So both of the gate's bit tests
score on it, and the tool reported *"bits 6:0 set → the window moved the other
way; MFD is 3 or the strap reading is wrong"* — **an MFD verdict on a converter
bank that was not switched on.** This is the same class of error S39-4 cost a
whole measurement set to.

**Why the converters are not powered**, from the attach procedure the hub's own
bench state cites: on the rev B analog board *"every switching supply on the
analog board is isolated from its destination electronics by links that are
NOT fitted yet"*, and the S46 bench state records **every ±15 V isolation link
OPEN**. On top of that, AN_EN went low in the power cycle (§0), so the analog
switchers are not even running.

**Therefore the morning sheet's §0 is wrong on one point, and the dispatch
inherited it.** §0's table says *"§1–§6 in full — the whole DSP side … none of
it needs the analog board"*. That holds for §1–§4 and for §5.3. It does **not**
hold for §5.1: its pass criteria are *the converter noise floor* (−65…−85 dBFS)
and *twelve distinct converter noise floors*, and both are statements about
powered AK5558s. **§5.1 and §5.2 are analog-board-dependent and belong in the
"when the links are in" list.**

### 5.2 Chip 2 — the section did not exist, and now does

The sheet asks for "the same two bit tests on chip 2's receive lanes".
`dsp4_s42_align.py` had **no chip-2 receive section at all** — it scored chip
1's RX and chip 2's TX and nothing between — so the gate could not have
satisfied the dispatch even on a healthy unit. Every symbol it needs is
exported by this image (`_c2_ic_rx_off`, `_c2_ic_rx_stride`, `_c2_ic_rx_ptrs`,
`_ic_rx_active_buf`, and a `_rx_ic_slot_<NAME>` per node), so the section was
written and run, resolving **by name** through the pointer table exactly as the
TX section does:

| lane | idx | off | stride | distinct values |
|---|---:|---:|---:|---:|
| `C2_RECV_MAIN_L` | 0 | 0 | 16 | 2 |
| `C2_RECV_MAIN_R` | 1 | 1 | 16 | 1 |
| `C2_RECV_SUB` | 2 | 2 | 16 | 1 |
| `C2_RECV_GRP_01` | 3 | 3 | 16 | 1 |
| `C2_RECV_AUX_01` | 7 | 7 | 16 | 2 |
| `C2_RECV_AUX_02` | 8 | 8 | 16 | 1 |
| `C2_RECV_FX_01` | 19 | 259 | 16 | 1 |

The name resolution works and the index → offset mapping is coherent. The data
is zeros and `FFFFFFFF`, because these lanes are **downstream of chip 1's
converter inputs** — they carry what chip 1 received, and chip 1 received
nothing. **No chip-2 framing verdict is taken either.** `C2_RECV_MTX_01` does
not resolve in `_c2_ic_rx_ptrs`; that is recorded, not chased.

### 5.3 TX, chip 2, resolved by name — **PASS**

All five nodes resolve **by name** through `_c2_tx_ptrs`, so S42's slot move is
on the part:

| node | off | stride | peak Q4.28 | destination |
|---|---:|---:|---:|---|
| `C2_AUX_OUT_01` | 7 | 8 | 0.00000 | `DAC_08` → rear XLR **Aux Out A1** |
| `C2_AUX_OUT_02` | 6 | 8 | 0.00000 | `DAC_07` → rear XLR Aux Out A2 |
| `C2_MAIN_OUT_01` | 131 | 8 | 0.00000 | `DAC_12` → analog J56 = **MAIN L** |
| `C2_MAIN_OUT_02` | 130 | 8 | 0.00000 | `DAC_11` → analog J57 = **MAIN R** |
| `C2_MAIN_ST_OUT` | 384 | 8 | 0.00000 | B_O3, no D24 sink |

**AUX 1 is no longer above full scale.** S39-6 read **1.538** in Q4.28
(+3.75 dBFS); it now reads 0.00000. That is consistent with the RX artefact
having gone, but it is **not positive proof of level** — with no converter
input there is nothing for the lane to carry, so 0 is also what a dead path
reads. The honest statement is: *the ceiling artefact is absent, and the lane
will only be proved live when the converters are.*

**A scoring gap found while reading this:** the tool failed a TX lane only at
`pk > 8.0`, the Q4.28 accumulator ceiling — but the sheet's §5.3 criterion is
**inside ±1.0**, and S39-6's 1.538 sits between the two. The ceiling test alone
would have *passed* the exact reading the gate exists to catch. The ±1.0
criterion is now applied.

### 5.4 What the gate now does

`dsp4_s42_align.py` refuses the RX verdict when ≥ ¾ of the lanes read as an
idle bus (≤ 4 distinct values and ≥ 90 % of words at a rail) and **exits 2 —
inconclusive, not failed** — naming the converters as the thing to fix and
pointing at the MCTL read as the part that does not need them. Run on the part
after the change:

```
MFD: PASS — every lane's SPORT_MCTL.MFD equals the generated table on both
     chips. S42's one-bit fix is on the part.
RX:  FAIL — idle/undriven TDM bus on 11 of 12 lanes ... NO MFD VERDICT IS TAKEN
TX:  PASS
VERDICT: NOT TAKEN ... Exit 2 = inconclusive, not failed.
```

## 6. When the links are in — what this session could not attempt

Per R5, nothing below was tried. Each needs the analog board's ±15 V isolation
links fitted and AN_EN high, both of which are PW's hands.

1. **§5.1 — the per-lane MFD proof in audio.** Re-run `dsp4_s42_align.py`. It
   now exits 2 until the converters drive the bus. Required: bit 31 exercised,
   bits 6:0 never set, rms per lane −65…−85 dBFS, and **twelve distinct** noise
   floors (S39's corrected reading spanned 0.000054…0.000593). Record all
   twelve in dBFS — that table is S40 gate 1's evidence. **The registers are
   already proven right (§5.0), so a failure here is the converters or the
   strap, not the fix.**
2. **§5.2 — the chip-2 bit tests in audio**, from the section now in the tool.
3. **§5.3 — AUX 1 proved live**, inside ±1.0 in Q4.28 rather than merely not
   pinned.
4. **§6 — the capacity re-take** (`dsp4_s39_cost.py 1|2 /home/app/s42 30`).
   Not attempted: it is outside R1's §1–§5, and its expected figures (≈76 % /
   ≈90 %) are quoted against *driven* converter inputs, so taking it on a dead
   bus would measure the silent-loaded case and be mistaken for the driven one.
   It needs no analog board only in the sense that it will *run*; for the
   number the sheet wants, it needs the same converters.
5. **§7 — the AUX 1 → MIC 1 loop**, cable in **Aux Out A1**, and with it the
   only proof of the transmit framing (`DSP4_LOOPBACK` is structurally blind to
   it; a still-early transmit returns a doubled, sign-wrapped copy).
6. **S40 gates 3–4** — the loop heard, then the dBFS full-scale derivations
   (a) DAC side, (b) ADC side, (c) the loop transfer at step 0.

**And one item that is not audio: the supply.** The under-voltage flag and the
uncommanded cycle in §0 happened with the analog rails *off*. Powering the
analog board adds load to a supply that already browned out. Worth a meter on
the CM4's 5 V before AN_EN goes high again.
