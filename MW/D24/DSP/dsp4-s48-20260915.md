# S48 — first audio on rev C: blocked at the parameter link

**THERE IS NO FIRST AUDIO ON REV C TODAY, AND THE PATH WAS NEVER REACHED.**
The MIC 5 → AUX 1 (OUT_01) path was not opened, no level was taken on either
side, and no dBFS figure or rail reading appears in this document — because
the session stopped at gate 1, at the step before any of that: **with the
analog board powered, neither SHARC answers the parameter link.** The S42
pair boots exactly as it did in S46 — same bytes, same milliseconds — and
then nothing comes back. What does come back on MISO is the analog board's
own 74HC595 mic-gain chain echoing the host's MOSI eight SCLK bits late,
through the dead-U2 1 kΩ bodge, because that chain is powered whenever
AN_EN is high. The unit is handed back exactly as found: AN_EN high and
never written, `matrix-app` active with all three MCUs verified, the DSPs
booted, the chain's safe image latched by the app, the rocker, CS_M, the
SWD selects and GPIO27 untouched.

## 3. What is actually on MISO

Rather than believe the phasing exception, the raw words were read. 400
collect transactions per chip, no phasing assumed:

| chip | distinct word-pairs in 400 | MAGIC hits | modal reply |
|---|---:|---:|---|
| 1 | 4 | **0** | `0x00E0FE00` ×390 |
| 2 | 2 | **0** | `0x00E0FE00` ×391 |

The transmitted word is `0xE0FE0000`. The reply is that word **right-shifted
by exactly one byte**. Four checks identify it:

1. **It is not a sub-word phase slip.** The reply was searched for the MAGIC
   constant `0xD5B40001` at *every bit offset*, six tries per chip. It is
   not there at any offset. A slipped-but-present answer would have been
   found; there is no answer.
2. **It is synchronous logic, not an MCU.** The delay is exactly **8 bits at
   8 MHz and at 10 MHz**, and moves by one further bit in SPI modes 1/2/3 —
   a shift register clocked by SCK.
3. **MISO is driven, not floating.** With GPIO9 forced `a0 pd` and then
   `a0 pu`, the returned bytes were unchanged. A floating net follows its
   pull; this one does not.
4. **The SHARC drives nothing.** The decisive A/B: identical transaction
   pairs with the chip select **asserted** and **deasserted**, six each.
   Byte-identical on both chips. A deasserted SHARC tri-states MISO, so a
   reply that does not change when the part is deselected was never the
   part's.

The source is in this repo's own record, in the S38 bench-state block:

> U2 (MISO buffer) dead and replaced by a 1 kΩ link pin 2→4 — the chain end
> drives SPI0 MISO WEAKLY, so a DSP slave boot over SPI0 is fine (a SHARC
> wins the net)

The mic-gain 74HC595 chain sits on the shared `!SPI0/1/2` nets
(`MW/D24/HW/hardware-map.md` §3) and reaches MISO through that bodge. **It
is powered only when AN_EN is high — which is exactly what changed between
S46 and today.** Note what this does *not* say: a 1 kΩ source cannot
outdrive a SHARC. The chain is not stealing the bus. It is filling a
silence the SHARC is leaving.

## 4. How far the SHARCs got

Both SPI_RDY lines read **high**. GPIO12 carries a 10 K pulldown (R34/R22),
so a high there is driven, not a host pull-up artefact, and per `SpiLink`'s
own contract it means the part is out of reset with FCPL=1 flow control
configured in `dma_config.c`. Under **300 back-to-back transactions with CS
held asserted, RDY never fell** on either chip.

That is weaker evidence than it looks, and it is recorded as such: an
autobuffered RX DMA drains the receive FIFO with no help from the core, so
RDY proves the DMA, **not a running core**. What is certain is that in
roughly 1,400 transactions neither the block-loop poll nor the **1 kHz timer
ISR backstop** — in the image since 2026-08-23, and the specific reason a
starved main loop still answers — produced one response.

## 5. The one variable that moved, and the test that settles it

S46 reached this link cleanly on 2026-09-14 with the same pair, the same
tools and the same procedure. Since then: the CPLD has not been reflashed
(2026-09-13), `config.txt` has not changed (2026-09-11), the images are
md5-identical, and the boot stream behaves identically. **The bench change
is that the analog board is now powered** — which does two things at once:
it puts the 74HC595 chain on MISO (§3), and it starts the converters
clocking, so this image's audio graph runs for real for the first time.

The second matters more. S8-2 measured that graph at `_proc_cyc` **330,389 /
286,757 against a 163,830-cycle budget**, roughly 2× over, with chip 1
missing **75.1 %** of blocks — and that was on a *silent* bus. A block ISR
that overruns every block, at a priority above the 1 kHz timer, starves both
service paths, which is exactly what ~1,400 unanswered transactions look
like. Memory of the same mechanism is already on record for the shipping
image ("stops answering the parameter link after CONFIG_COMMIT … the
over-budget graph starving the main-loop poll, not a fault"); here it would
begin at boot instead, because the SPORTs start clocking immediately.

**This is a hypothesis, and it has one clean test that this session may not
run.** R4 makes AN_EN the hub's pin. The test:

> Drop AN_EN for sixty seconds, re-run `dsp4_boot.py --dir /home/app/s42`
> and `dsp4_checkchip.py`, then raise AN_EN again.

* **Link returns with the rails down** ⇒ the converter clocks are the cause;
  the D24 graph does not fit in real time once the bus is live, and first
  audio needs a reduced-graph image (`DSP4_STRIPS` / `DSP4_NODE_LIMIT`) or
  the block-cost work — a hub decision, not a bench tweak.
* **Link stays dead with the rails down** ⇒ the cores stopped during the
  boot itself: a D73-class event, on both chips at once, which would be new.

Either answer is worth the minute it costs, and neither can be had without
that pin.
