# S48 — first audio on rev C: the DSP reaches the DAC lane on demand, the loop does not come back

**THE DSP SIDE OF FIRST AUDIO IS DONE, ON A PURPOSE-BUILT INSTRUMENT IMAGE.**
With `DSP4_SCOPE_BLK_TAP=1` the host can drive the node chain for the first
time, and `C2_AUX_OUT_01` — DAC_08, analog J45, rear XLR OUT_01 — moves from
its **−88 dBFS floor to exactly 0.50000 Q4.28 (−6.02 dBFS) on demand**, mutes
to a true zero and inverts cleanly with polarity. **THE ANALOG LOOP DOES NOT
RETURN IT.** Driving the step and capturing MIC 5's input block gives captures
that are **identical to within 0.2 dB whether the stimulus is driven or not**,
at mic gains 16, 32 and 63. MIC 5's own side is demonstrably alive — its
captured noise floor tracks the preamp gain code −133.0 → −107.1 → −101.4 →
−96.2 dBFS — so the break is **at or after the DAC**, which is precisely the
boundary no DSP-side measurement can cross. The next instrument is PW's scope
on OUT_01.

**And a correction that matters more than the level: the analog control chain
was not in the state the record said it was.** The first sanctioned
`chain-safe` of the session moved every converter lane by ~45 dB, which a
chain already safe cannot do — so this session's earlier "eight distinct
converter noise floors in the −65…−85 dBFS band" were **eight unknown mic gain
codes**. See §5.

No +5 V rail figure is quoted beside a signal level in this document, because
every level that carries signal is a DSP-side digital level in dBFS, where the
rail does not enter; the rail matters for the analog-side derivation, which is
exactly the half that did not happen.

## 1. The link was dead, and the cause was CS_M

The session opened against a dead parameter link. The S42 pair booted exactly
as in S46 — md5s re-verified on the unit, `825f9b7dac5978c973550c8e40819ba9`
and `7b1311e8e56f008fa98046cab59293c6`, **451,584 B on CS1 in 605.7 ms**,
**308,224 B on CS2 in 413.4 ms**, S46's timings to a tenth of a millisecond —
and then `cannot phase the parameter link: MAGIC never came back`, on both
chips, twice.

Reading the raw words rather than trusting the exception: 400 collects
returned **4 distinct word-pairs, 0 hits on MAGIC**, 390 of them the
transmitted word **right-shifted by exactly one byte**. Four checks:

| question | test | answer |
|---|---|---|
| a slipped answer? | search the reply for MAGIC at **every bit offset** | not there, 6 tries/chip — **no answer at all** |
| an MCU bit-banging? | delay at 8 MHz and 10 MHz | **exactly 8 bits at both** — synchronous logic |
| MISO floating? | force GPIO9 `a0 pd`, then `a0 pu` | **unchanged** — MISO is driven |
| is it the SHARC? | A/B, chip select asserted vs deasserted | **byte-identical** — the SHARC drives nothing |

**The hub named it: GPIO27 was idling as an input with a pull-DOWN, holding
CS_M LOW, which leaves the analog MISO buffer U2 ENABLED and driving SPI2
MISO continuously.** H1S1 stopped holding CS_M high when it was reflashed on
09-14. Setting GPIO27 to input pull-UP (CS_M high, U2 tri-stated) fixed it
outright — the next probe returned `w0 0xE0002000 / w1 0xD5B40001`, echo and
MAGIC, word-aligned, and the same A/B now reads the SHARC with CS asserted
and silence with it deasserted.

**Two things this session got wrong before the hub's answer, recorded as
corrections rather than quietly dropped.** The echo was attributed to the
74HC595 chain's own shift output — wrong device, right bus. And the silence
was hypothesised to be the over-budget graph starving the link once the
converters clocked — **also wrong**: the graph *is* over budget
(`BLK_OVERRUN` 2,245 / 2,230 accumulated at boot) and the link answers
perfectly regardless. AN_EN was read at every gate and written at none
throughout, so neither error cost the bench anything.

## 3. A defect that had to be fixed to run this session at all

`dsp4_apply_strip.py` line 33 is `sys.argv = ['s']` — emptying argv so
`dsp4_scope`'s import-time parser does not consume the arguments — and
`STRIP`/`AUX` were read **after** it. Both were therefore pinned to 1 on every
invocation ever made. Asked for strip 5, the tool printed `strip 5 -> MAIN and
AUX 1` and then wrote and read back `Chan001…` cells, reporting 13 ok. That
is a wrong answer dressed as a right one.

Fixed by taking `sys.argv[1:]` **before** the clear, exactly as
`dsp4_s42_align.py` already does (`_argv = list(sys.argv)`). Nothing in the
prior record is invalidated — S46 §4 ran `1 1` and correctly reported strip 1
— but any "strip N" claim predating this fix is strip 1 wearing another
number.

## 4. Gate 2 — MFD PASS and the bit tests stand; the RX LEVELS below are WITHDRAWN

**Read this section with §5.** The MFD result, the bit tests and the TX
readings are sound. The per-lane dBFS levels are not: they were taken before
the analog control chain was asserted, and §5 shows the chain was holding
unknown mic gain codes at the time. They are left here as measured, struck
through in effect, because the withdrawal is the finding.

both chips — chip 1 rx `[2,2,2,2,2,2,1,2]`, chip 1 ic `[1,1,1]`, chip 2 ic

## 5. THE ANALOG CHAIN WAS NOT SAFE, AND IT INVALIDATES §4's RX SPREAD

The dispatch's bench state records "74HC595 chain proven 200/200, safe image
loaded (every input muted, gain minimum, phantom off)". The first sanctioned
chain write of this session — `app cli chain-safe` — **moved every converter
lane by about 45 dB**:

| | lanes 1–4 (MIC 1–4, dead section) | lanes 5–12 |
|---|---|---|
| before any chain write | −114…−118 dBFS | **−67…−82 dBFS**, "eight distinct floors" |
| after `chain-safe` + ch5 at gain 0 | −114…−117 dBFS | **−111…−115 dBFS** |

A chain that is already in the safe image cannot move 45 dB when the safe
image is written to it. The mechanism is in the app's own banner for that
command — `25x 74HC595, 200 bits, SPI0 shift, CS_M latch, MISO loopback via
U2`. **Every DSP parameter transaction shifts through those shift registers**,
and **CS_M is the latch**. CS_M sat low through the whole period the parameter
link was dead (§1), and went high when the hub changed GPIO27's pull — and
that rising edge latched whatever the preceding DSP traffic had left in the
register.

**Consequences, stated plainly:**

1. §4's "eight distinct noise floors inside the −65…−85 dBFS band" were eight
   **unknown gain codes**, not a converter baseline. That reading is withdrawn.
2. The **bit tests in §4 stand** — `lo7` never set, bit 31 exercised — because
   those are framing facts and hold in both chain states.
3. `dsp4_s42_align.py`'s −65…−85 dBFS band comes from S39, measured the same
   way, and should be **re-derived against a chain that is known**. Not this
   session's to re-specify.
4. Bench procedure from here: **assert the chain, then measure.** Do not trust
   an analog level taken after DSP traffic without a chain write in between.
   Within a measurement the latched outputs are stable, because nothing pulses
   CS_M unless `chain-set`/`chain-safe` runs.

## 7. Gate 3 — the DSP reaches the DAC lane; the loop does not come back

### 7.1 The two things the first attempt got wrong

**The injection point is the RX SLOT, not the node buffer.**
`_scope_inject_blk` compares the address the host named against `_scope_inj`
and each per-strip call site returns immediately unless they match, so
`_scope_inj` must be `_rx_slot_C1_IN_NN`. Naming `_buf_C1_IN_NN` arms a site
that never fires, silently.

**The stimulus is sustained by arming a `src` that matches no node.**
`_scope_tap` advances `_scope_idx` only for the watched node and clears
`_scope_arm` only when the buffer fills, so pointing `_scope_src` at
`_scope_buf` itself keeps the injector driving indefinitely. Armed on a real
node instead, the drive lasts 1024 samples — 21 ms — and then stops, which
reads as a dead path.

### 7.2 What the DSP does on demand

`_scope_inj_blk` = **0x90330** — the strip's call site fired. `C2_AUX_OUT_01`,
against a −88 dBFS floor:

| `_scope_amp` | Q4.28 in | AUX 1 TX out | ratio |
|---|---:|---:|---:|
| `0x01000000` | 0.0625 | **0.50000 (−6.02 dBFS)** | **×8.00** |
| `0x02000000` | 0.1250 | 0.84589 (−1.45 dBFS) | ×6.77 |
| `0x04000000` | 0.2500 | 1.00594 (+0.05 dBFS) | ×4.02 |

Exactly linear at ×8 in the first row and compressing above it — a limiter or
the tube stage, not a scaling error. **0x01000000 is the linear operating
point** and every level here is quoted there. The third row sits at **1.006
Q4.28, just past the ±1.0 criterion**, i.e. already beyond DAC full scale.

**Full scale, stated first (PW's convention).** These TX figures are dBFS
against **1.0 Q4.28**, the value that maps to the DAC's full scale. The
accumulator ceiling is 8.0, three bits above, and `dsp4_s42_align.py` and the
S39/S42/S46 records quote that convention instead — the two differ by exactly
**18.06 dB**, so the same lane reads −6.02 dBFS here and −24.08 dBFS there.

### 7.3 The loop, and the negative arm that saved the result

The drive and the capture must be **different strips** — the loop returns into
MIC 5, so injecting into strip 5 would overwrite the very slot the return
arrives on. Donor strip 6 → AUX 1 → OUT_01 → cable → MIC 5 → strip 5's input,
captured:

| mic gain code | capture, drive OFF | capture, drive ON | difference |
|---:|---:|---:|---:|
| 16 | −107.11 dBFS | −107.14 dBFS | **−0.03 dB** |
| 32 | −101.38 dBFS | −101.47 dBFS | **−0.09 dB** |
| 63 | −96.22 dBFS | −96.44 dBFS | **−0.22 dB** |

**Identical to within 0.2 dB with the stimulus on and off.** The loop returns
nothing. One earlier capture read −70.31 dBFS at gain 16 and did not
reproduce; **without the drive-off control it would have been filed as first
audio.**

What *is* proved by the same numbers: the rising floor −133.0 (gain 0) →
−107.1 → −101.4 → −96.2 dBFS **is MIC 5's own preamp gain law**, so the 595
chain, the preamp, the AK5558 and the RX lane are alive and behaving end to
end. The break is **at or after the DAC** — and `C2_AUX_OUT_01` proves what
the DSP handed the AK4458, never what the AK4458 did with it. `!RST_C` is S
MCU PA11 and the app reports converter reset as `Unknown`, so **the DACs'
running state has never been established on this unit**.

### 7.4 Why the first method could not have worked

`rx_rms()` re-reads the same 16-word active block, so however long it runs it
sees about **0.33 ms** of audio. Against a host-timed ~1 Hz toggle, the chance
of landing on an edge is under one in a thousand — so an AC-coupled path,
which passes only edges, reads as silence however alive it is. That is the
whole explanation for the tenths-of-a-dB movements in §4's loop arms. Any
future loop or latency measurement on this bench belongs in a **capture**.

## 10. The two tool bugs, with their fixes

**(1) `dsp4_apply_strip.py` could never write any strip but 1, and said it
did.** Line 33 was `sys.argv = ['s']` — emptying argv so `dsp4_scope`'s
import-time parser does not consume the arguments — with `STRIP`/`AUX` read
**after** it, so both were pinned to 1 on every invocation ever made. Asked
for strip 5 it printed `strip 5 -> MAIN and AUX 1` and then wrote and read
back `Chan001…` cells, reporting 13 ok: a wrong answer dressed as a right one.
**Fix:** take `sys.argv[1:]` *before* the clear, as `dsp4_s42_align.py`
already does (`_argv = list(sys.argv)`). Nothing in the prior record is
invalidated — S46 §4 ran `1 1` and correctly reported strip 1 — but any
"strip N" claim predating this fix is strip 1 wearing another number.

**(2) `/home/app/dspboot/chip1.sym.json` is not the running image's map, and
peeking through it returns plausible zeros rather than an error.** The staged
map is `f2e0c082…`, the dspboot copy `b694276e…`. A first cut of the loop
instrument hardcoded the dspboot path and every lane read `0.0000000 / -inf`
across all five arms — a clean, symmetrical, entirely fictional "the
converters are silent", because `_rx_active_buf` peeked as **0** and every
window read then landed at absolute address 128. **Fix:** every tool takes the
symbol directory as an argument, defaulting to the staged pair, and
`dsp4_s48_loop.py` / `dsp4_s48_audio.py` **refuse to measure** when
`_rx_active_buf` peeks 0 twice. `dsp4_apply_strip.py` survived the same
hardcoding only because it deliberately uses no `peek()` at all; it has been
given the same argument anyway, since it is one added peek away from the same
failure.
