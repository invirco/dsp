# S44 — the intake path made atomic, and the 237 cells named

**The unit was never touched.** No ssh to 192.168.1.219, no flash, no boot, no
build of a shipping image. Desk only, start to finish.

Two things came out of it. A gate that damaged the artefact it checked no
longer can, proven by killing it eleven ways. And the 237-cell D24
disagreement that has been failing that gate since S22 is characterised down
to the commit and the cell: **every one of the 237 is a cell the landed file
already names as unmapped, no address moves, and no cell name is repurposed.**
The proposal is filed; landing it is the hub's call.

---

## 1. The intake path made atomic (S44-1)

### 1.1 What was wrong

`MW/<P>/MX/_matrix.csv` has two authors and neither knew it:

- `sync-defs.sh` runs `defs/tools/expand_matrix.py` and writes the bare
  expansion — no DSP address columns, because they are not part of the
  expansion;
- `MW/D32/DSP/gen_dsp.py` backfills `DspI2c`/`DspSpi`/`DspPage`/`DspAdd`/
  `DspAddHex` afterwards.

Each half wrote straight over the committed file with `open(path, 'w')`. So
when `check-contract-drift.sh` ran the first, then died inside the second on
the no-fallback dsp.csv check, the tree was left holding a D32 matrix with
those five columns blank on all 6,999 rows (S43-5). It looked like a
7,000-line diff and it was not drift; it was half a regeneration, committed by
the gate that was supposed to protect it.

There was a second fault in the same lines, and it had nothing to do with
`gen_dsp.py`: `sync-defs.sh` wrote the expansion over the committed file and
hashed it against `defs.lock` **afterwards**. A lock mismatch — the one thing
the lock exists to catch — therefore exited 1 with the tree already rewritten
by the definitions it had just refused.

### 1.2 Temp file and rename, and why not a trap

A restore-on-failure trap is a promise the process has to stay alive to keep.
`kill -9`, a segfault, an OOM kill and a power cut all skip it, and the window
in which the file is half-written is exactly the window a trap cannot cover.

`rename(2)` needs nothing to survive. POSIX requires it to be atomic within a
filesystem: at every instant the path names either the whole old file or the
whole new one, whoever dies and whenever. So every write to a landed artefact
now goes to a temp file **in the target's own directory** (a cross-device
rename is a copy, and a copy is not atomic), is `fsync`'d, and is renamed into
place; the containing directory is `fsync`'d after, so the rename itself is
durable.

Measured, not asserted. A 195 MB payload written over a 12-byte file, the
writer `SIGKILL`ed at fifteen points across the write:

| | kills landing mid-write | target left whole-old | left whole-new | **left half-written** |
|---|---:|---:|---:|---:|
| `open(path, 'w')` | 4 | 0 | 0 | **4** |
| temp + fsync + rename | 5 | 5 | 0 | **0** |

Four of four against zero of five. That is the whole argument.

### 1.3 The pair, not just each half

Per-write atomicity is not enough here, because the finished D32 matrix is the
output of TWO processes. `sync-defs.sh` therefore no longer writes D32's
matrix at all. It stages the bare expansion at
`MW/D32/MX/_matrix.expansion.csv` (gitignored) and `gen_dsp.py` — now the only
writer of the finished file — reads the stage, backfills, renames the result
into place, and removes the stage only once every other output is on disk
under its final name. Between the two processes the committed file still holds
the last complete generation.

`validate-matrix-contract.py` runs between them, so it reads the stage when
there is one; otherwise it would validate the previous generation and pass a
new one unseen. Same for `gen_dsp.py`'s own `_matrix_path()`.

The three products with no backfill step (D12, D16, D24) have no stage: their
expansion IS the whole artefact, and it lands by rename — but only after all
four have verified, so a mismatch on D32 no longer rewrites D12's matrix.

### 1.4 Everything else that writes

`gen_dsp.py`: `_matrix.csv`, `ghost_cells.h` ×3, `mx_dsp_map.h`,
`dsp_params.asm` ×2, `dsp_address_map.md` and the proposal CSVs, all through
`_atomic_write()`.

`tools/dsp/dsp_codegen.py`: all 25 generated-source writes through an
`atomic_open()` context manager. **Per file only, and the limit is worth
naming.** The emitter is two-pass — `gen_shared_kernels()` rewrites each node
`.asm` to wrap it in `#if (DSP4_SHARED_KERNELS & 1)` after the first pass has
written it plain — so a kill between the passes leaves a tree of *whole*
files, 61 of them in the first-pass form. No file is ever truncated, but the
tree is not transactional. That is precisely what
`check-sharc-codegen-drift.sh` (S43-4) catches, by content, and a rerun
repairs. Making the codegen transactional would mean generating to a scratch
tree and swapping the directory; it is a real improvement and it is not this
change.

### 1.5 One more thing the gate was hiding (S44-2)

`check-contract-drift.sh` runs `gen_dsp.py --force >/dev/null`. The
`DSP_LANDED_DIR` banner — "these rows have not passed the hub gate and the
defs pin does not describe this build" — went to **stdout**. The one gate that
most needs to hear it was the only place it could not be heard: a whole
contract check could pass against ungated rows in silence. Moved to stderr.

### 1.6 The negative controls

Against the committed tree, with the nine contract artefacts hashed together
before and after each run:

| arm | what was killed | runs | artefacts changed |
|---|---|---:|---:|
| A | `sync-defs.sh`, `SIGKILL` at 0.2 s … 3.4 s | 9 | **0** |
| B | the pair run to completion | 3 | **0** (identical bytes, stage consumed each time) |
| C | the real `check-contract-drift.sh`, run to its no-fallback exit 1 | 1 | **0** |
| — | `gen_dsp.py`, `SIGKILL` at 11 points across its 0.815 s | 11 | **0** |

`MW/D32/MX/_matrix.csv` reads
`041b19a585a93f6f24f53609da1e0502a893db20ad3dbea99d0e5cd5e3da8b8f` before and
after all of it — the same hash it had at `cea457e0`. The 726 SHARC sources
are still byte-identical to their generator.

A `SIGKILL` does leave a temp file behind (nothing else could). They are
gitignored, and because that means they would otherwise accumulate unseen
forever, both writers now sweep temps whose pid is gone — and only those, so a
concurrent run's temp is left alone.

Committed on its own as `aed43455`, ahead of anything to do with the contract.

## 2. The 237 cells, named (S44-3)

### 2.1 They are one class, not four

The dispatch asked which of four classes each cell falls in. The answer is
that 237 of 237 fall in the first and none in the other three:

| class | D24 | D32 |
|---|---:|---:|
| a cell the generator now emits that the landed file predates | **237** | **356** |
| a cell whose address moved | 0 | 0 |
| a mask/scope difference | 0 | 0 |
| the S42 lane fix | 0 | 0 |

Checked directly rather than inferred. All 3,737 D24 / 5,409 D32 rows present
in both files are identical in **every** column, not only the address. Nothing
is removed from either map. And the bookkeeping invariant holds on both sides:

```
D24   landed 3,737 + 1,248 = 4,985      proposed 3,974 + 1,011 = 4,985
D32   landed 5,409 + 1,590 = 6,999      proposed 5,765 + 1,234 = 6,999
```

— which is `rows(dsp.csv) + rows(dsp-unmapped.csv) == cells(_matrix.csv)`, so
the disagreement is entirely a MOVE of cells from the unmapped file into the
mapped one. Every one of the 237 is a cell the landed contract already names.

The dispatch's three guesses are all no: not new GEQ cells (the 31-band GEQ
landed *in* `defs-v2026.09.08.4`), not the 24-strip mask, not the S42 lane
rows — `8f4a9d17` changed the DAC lane ↔ XLR mapping and the proposal's cell
set is identical either side of it.

### 2.2 The commits that created them

| 100 | `9ffdb4ee` S22 | the matrix mixer built | `ChanMatrixOn` ×48, `ChanMatrixSend` ×48, `MatrixLevel` ×2, `MatrixMute` ×2 | `no-graph-node` ×100 |
| 120 | `4fdfe5ed` S23 | the FX returns given a bus at all; the comp GR meter published | `FxAuxOn` ×48, `FxAuxSend` ×48, `ChanCompMtr` ×24 | `no-graph-node` ×96, `unbacked-meter` ×24 |

D32's 356 are the same three plus `24f46ca1` S25's 32 `ChanLcrOn` (the one pan

The `unbacked-meter` 24 are worth a word, because they are the only class
whose *reason* changed rather than whose node appeared. The landed file says

reads "meter word +3: compressor gain reduction, dB, clamped to [-80, 0]

## 3. The proposal (S44-4)

`proposals/defs/products/<p>/{dsp.csv,dsp-unmapped.csv}`, with the cover note
at `proposals/CONTRACT-PROPOSAL-S44.md` carrying the contract fields
`release-notes-contract-convention.md` requires.

**It was already there and already correct.** `gen_dsp.py --propose` against
the pinned `defs-v2026.09.08.4` regenerated all eight files and produced **no
diff** — the candidate in the tree is exactly what the generator emits today.
Nothing was hand-written, hand-edited, or newly authored; the layout mirrors
`defs/products/` so the hub lands it by copying the tree across and tagging.
A second file at `MW/D24/DSP/proposals/` would have been a second copy of a
generated artefact, which is the thing this repo is not allowed to grow.

Both verdicts, run:

- `./check-contract-drift.sh` → **exit 1**, on d32 (356) and d24 (237), as
  before. Leaves `_matrix.csv` byte-identical now.
- `DSP_LANDED_DIR=proposals/defs/products ./check-contract-drift.sh` →
  **exit 0**, banner on stderr, everything regenerated.

### 3.2 What the app side needs — and one thing to be told plainly (S44-4, S44-5)

Running the drift check against the candidate rewrote every generated artifact
and left **no diff**. That is a finding, not a convenience:

**the committed generated tree is ALREADY built from this proposal, and has
been since S22–S25. Only `defs` lags.** `MW/D32/MX/_matrix.csv` carries DSP
addresses on 5,765 of 6,999 rows where the landed map covers 5,409;
`ghost_cells.h` says `GHOST_CELLS_COUNT 5810`, which is the proposed union,
not the landed 5,449. So the gate's failure is not tree drift. It is a
contract bump that was never taken to the hub, and landing the proposal makes
the pin describe the tree again without moving a byte of the tree.

Separately, and not fixed by landing anything: **`MW/D24/MX/_matrix.csv`
carries no DSP addresses at all** — 0 of 4,985 rows. `gen_dsp.py` backfills
D32's matrix and only D32's, so a D24 app has no address column to read and
must go to `defs/products/d24/dsp.csv` directly. That is the single-SOT gap
S38-5 named, still open, and it is a generator item.
