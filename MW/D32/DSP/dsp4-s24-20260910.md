## 1. Gate 1 — the three net answers

Full working in `docs/net-contract-answers.md`. In one line each:

**(a) Through-DSP latency at 96 kHz = 82 samples / 854 µs, BY
CONSTRUCTION.** It is not measured and three separate things stop it being
measured, the first of which is the part: the data sheet caps
`fSPTCLKEXT` at 31.25 MHz when transmitting data or frame sync, and a TDM16
lane — which is every line of the inter-chip mix fabric — needs 49.152 MHz
at 96 kHz. The CPLD cannot generate those clocks either (one 49.152 MHz XO,
a 1024-sysclk frame; at 96 kHz TDM16's BCK becomes the sysclk itself), and
CCLK is already at the part's ceiling so utilisation doubles whatever the
block size: S23's worst driven row, D32 chip 2 at 90.95 %, becomes about
182 %. That is D6's platform split measured rather than asserted.

The construction fits every measured 48 kHz row on record to within one
sample:

    L = (4 + n_tx_early) x BLOCK + 2 samples

— four block periods (DSPA RX half, DSPA process→gather, DSPB RX half,
DSPB process→gather), one more block per chip carrying `DSP4_TX_EARLY`,
and two samples of TDM framing. At BLOCK=16 with `TX_EARLY=2` that is
**82**, which is the contract figure exactly. **In samples the figure does
not move with the sample rate** — every term is a block or a frame — so
96 kHz is 82 samples and 854 µs.

**(b) The block interface needs 8-byte alignment, set by the SHARC CORE.**
Not by its DMA, which is `MSIZE04`/`XMOD 4` and wants 4; not by the
framework, which declares no alignment at all and does not get one — of
5,452 DM symbols in the chip-1 map of the S23 pair, **2,204 sit at ODD word
addresses**. The 8 comes from the SIMD dual-data access the block kernels
open with `PEYEN` and read as `dm(i0, 2)`, two consecutive words in one
access. **40 is a multiple of 8, so `MWN_AUDIO_PAYLOAD_OFF` STAYS AT 40.**

The caveat that matters is not about the offset: 8-byte alignment is a
requirement on the ABSOLUTE address of sample 0, and one 802.1Q tag
inserted by a customer switch moves the MW-Net header by 4 bytes and
**flips** it. The field offsets are untouched — the header is found by
EtherType scan, exactly as the message table intends — but in-place
consumption is not, and moving `PAYLOAD_OFF` to 48 would not fix it because
it changes the offset and not the base.

**(c) In-place = yes for the read — and on the DSP product the question is
answered one boundary out.** The DSP product's MW-Net endpoint is the
RT1180 option card, and what crosses the option slot is **TDM8, not
packets**: `no[3:0]` (`B_O4..B_O7`, 32 channels out) and `ni[3:0]` muxed
onto `A_I0..A_I3` in. No Ethernet frame, no receive buffer and no MW-Net
header ever reaches SHARC memory. The in-place question that *does* exist
is answered on the part and has been running on every block of every
shipping image: `C1_IN_nn_process` points `i0` at the DMA ring and reads
`dm(i0, m0)` at the lane stride straight into the block pool, with **no
staging copy**, and the payload's declared tick-major `[tick][chan]` layout
*is* the TDM32 DMA block layout, so the stride mechanism is the one already
there. The one honest qualification: the wire is S32LE = Q1.31 and this
graph is Q4.28, so the reader pays `ashift by -3` folded into the same
loop. No copy; one transform.

## 2. Gate 2 — the use-proportional cost, and it is not the crosspoints

S23's rows priced every new node RUNNING and said so: they do not include
the two costs proportional to USE. An aux sum whose six coefficients are
all zero takes the block-level bypass; a matrix bus row whose thirty-two
are all zero is skipped by the fabric for one compare per block.

`s23xp` — the arm S23 wrote down and could not run, because it ran
`BUILD=0` against a staging path no image had ever been written to — is
here as a LADDER rather than a single row, because a single all-open row
gives a total and no slope. Every rung is taken **on one boot**, driven,
with the plugin load (`SETUP_MODE=loadfx FXTYPE=3`), on the S23 candidate
image, so the only thing that changes between two rungs is how many
crosspoints are live. Every rung writes the whole family — sources above
the count explicitly off — so a rung is a complete state and not an
increment on the one before it.

`f:m` = FX returns opened into EVERY aux bus : strips opened into EVERY
matrix bus.

Two boots, chip 1 / chip 2 average % of budget:

| rung | what it means | boot 1 | boot 2 | chip 2 overruns |
|---|---|---|---|--:|
| **0:0** | every crosspoint closed — **the control** | 77.07 / **90.93** | 77.06 / **90.78** | 0 |
| 1:0 | one FX return into each of the 12 aux buses | 77.07 / **100.70** | 77.40 / **100.80** | **600** |
| 6:0 | all six into each of the 12 | 77.06 / **100.81** | 77.23 / **100.78** | **600** |
| 0:1 | one strip into each of the 2 matrix buses | 77.39 / 91.05 | 77.64 / 90.78 | 0 |
| 0:32 | all 32 strips into each of the 2 | 78.20 / 90.77 | 78.30 / 91.26 | 0 |
| **6:32** | **worst use** | **78.46 / 100.72** | **78.36 / 100.71** | **601** |

**The control passed and it is what makes the rest readable**: rung 0:0
reads chip 2 at 90.93 / 90.78 % against S23's driven row of 90.95 % on the
same image and the same instrument, so the ladder is measuring the
crosspoints and nothing else.

### What it costs, and the surprise

- **0:0 → 1:0 is +9.77 and +10.02 points of chip 2.** That is twelve aux
  buses leaving the bypass, with ONE live send each.
- **1:0 → 6:0 is +0.11 and −0.02 points.** That is five more live
  crosspoints on each of those twelve buses.

**So a bus that stops being empty costs 0.81–0.84 points of chip 2, and
opening the other five sends on it costs nothing this instrument can
resolve.** The two boots disagree in sign on that second figure and both
are inside the ±0.3-point boot-to-boot spread S20 measured — **boot 1 alone
would have supported "about 0.002 points a crosspoint", and boot 2 says
that number is noise.** What can be said is an upper bound: five more live
crosspoints on a bus cost less than a tenth of a point, against 0.82 for
the bus itself.

The MACs are free; the bypass is the whole price. Read that against S23-5,
which measured the bypass as worth 9.89 points when it was introduced: this
session measures the same ~9.9 points from the other side, by switching it
off one desk operation at a time.

- **The matrix is chip 1's and it is cheap**: 0:0 → 0:32 is **+1.13 and
  +1.24 points of chip 1** for 64 live crosspoints on two buses. Chip 2
  does not move with the matrix — its four readings scatter from −0.16 to
  +0.48 about zero — which is what the graph predicts: the matrix output
  strips are a fader and an output, and they do not care whether the bus
  carries signal.
- **The two are additive**: 90.93 + 9.77 = 100.70 against a measured worst
  use of 100.72 on chip 2, and 77.07 + 1.13 = 78.20 against 78.46 on chip 1.

### And the product statement, which is the point

**D32 chip 2 DOES NOT FIT AT WORST USE: 100.72 % and 100.71 % with 600–601
of 90,049 blocks missed (0.67 %), on both boots.** It does not fit as soon
as an FX return is sent to all twelve aux buses — rung 1:0 already
overruns, on a single send per bus.

At 0.82 points a bus, chip 2's ~9.1 points of margin at rung 0:0 buy about
**eleven** of the twelve aux buses. That figure interpolates between two
measured points (0 buses and 12); §2a is the ladder that tests the
linearity rather than assuming it.

The first ladder said the expensive axis is BUSES and not sources, so the
second ladder varies buses: ONE FX return opened into aux buses 1..N and
nothing else, N = 0, 4, 8, 11, 12, every rung on one boot, driven, plugin
load, on the **S24 candidate** (`2fdd9f95` / `9222c2ee`).

| aux buses carrying a live FX return | chip 1 | chip 2 avg | chip 2 worst | Δ vs 0 | chip 2 overruns |
|---:|--:|--:|--:|--:|--:|
| 0 | 77.04 | **91.50** | — | — | 0 |
| 4 | 77.23 | **94.07** | 94.75 | +2.57 | 0 |
| 8 | 77.03 | **97.60** | 97.90 | +6.10 | 0 |
| **11** | 77.26 | **100.05** | **100.47** | +8.55 | **0** |
| **12** | 77.71 | **100.76** | **101.27** | +9.26 | **649** |

**It is close to linear at 0.77 points a bus** (9.26 over twelve; the

trend the boot spread does not cover). The 12-bus figure reproduces the

give each other.

**And the product answer is a measured integer, not an extrapolation:**

> **Eleven of the twelve aux buses can carry an FX return with ZERO missed
> blocks** — 100.05 % average, 100.47 % worst, 0 of 90,049 blocks missed.
> **The twelfth is where blocks start being missed**: 100.76 % / 101.27 %,
> 649 of 90,049 (0.72 %).

Note that the eleven-bus row is already OVER 100 % of the nominal budget
and still misses nothing: the percentage and the deadline are not the same
test, and the arbiter is and remains `DIAG_BLK_OVERRUN`. The row that
matters is the one where that counter leaves zero, and it is the twelfth
bus.

## 3. Gate 3 — the main output strips get their own Level, Mute and HPFs

PW's rulings landed mid-session (`tasks.md`, HUB ADDENDUM 2026-09-10) and
they bear on this gate and every gate after it. **R6–R11 are HELD for the
team's final block diagram**, so no more matrix or FX-topology cells were
built; nothing in this gate is either.

### 3a. Three HPF bands per strip that were already there (S24-4)

`dsp-unmapped.csv` carried `Main{L,R,Ctr}[1-1]EqHpf[2-4]` as
`no-graph-node`, with the reason "the generator gives a non-Main strip one
HPF (band 1) and the masters give the output strips four". **The generator
already handled it.** The EQ expander has, since it was written:

```
    # Main output zones allow any band as HPF (fun 1-4); others only band 1.
    if cat == 'Main':
        for b in range(1, bands + 1): ...
```

and the four post-crossover output EQs do not carry cat `Main`. They carry
`MainL` / `MainR` / `MainCtr` / `MainSub`, because that is what the output
strips ARE. **So the test named the main BUS strip and missed the main
OUTPUT strips, and a feature that was fully built reported as unbuilt for
as long as the table has existed.**

The fix is one condition. It costs **no arithmetic and no address**: an
`EqHpf` cell aliases its band's own coefficient base exactly as band 1
always did, so the frequency→coefficient design step is the one already
there and the only change is that three more cells can reach it. **D32 +6,
D24 +9.**

The band count is the MASTER's and not the loop's — `MainSub[1-1]
EqHpf[1-1]` gets one off the same four iterations — which is also why this
survives **PW ruling R2** either way it lands. R2 says the mains carry the
aux EQ complement and lists `EqHpf` without a multiplicity; if the hub
lands that as `EqHpf[1-1]` on the mains, bands 2–4 stop being defined and
stop being emitted, with no change here. **R2's multiplicity is worth
confirming rather than reading off a list** — the masters say `[1-4]`
today.

### 3b. Level and Mute, on the output node rather than in a new one

`Main{L,R,Ctr,Sub}[1-1]Level/Mute` was open question Q1: "the
post-crossover output chain has EQ + COMP + LIM and no FADER_PAN or DELAY
node, so the strip's own level, mute and delay reach no word".

**Built on the `OUTPUT_TDM` node itself, not as a new fader.** That node is
already a per-block copy from the limiter's block onto the TX slot array,
so a level is one multiply on a word it already loads and a mute is that
level folded to zero. A FADER_PAN would have added a node, a block buffer,
a pan the master does not define, and a place in the chain for the ordering
repair to move — on the chip whose worst-use row §2 has just shown
overruns.

**The fold and the bypass are S23's, deliberately.** Level (ramped float)
and mute (a flag) become ONE Q4.28 coefficient once per block with the mute
multiplied in, and where that coefficient is exactly 2^28 the node runs its
old copy loop untouched:

```
  mrf = x * 2**28  ->  _mrf_rns28  ->  (x * 2**28 + 2**27) >> 28  =  x
```

so the bypass and the multiply agree word for word. **The shipping default
is unity and unmuted, so the default image takes the copy path on every
block and pays one compare for it**; a desk that pulls a main output down
pays the multiply on that output alone — one more cost proportional to use,
and priced like the others.

The round-and-saturate in the multiply loop is **inlined, not called**:
every block-kernel path in this generator inlines it and `call _mrf_rns28`
inside a hardware loop is the one shape the rest of the tree avoids. The
arithmetic is `_mrf_rns28`'s instruction for instruction. The per-sample
(`DSP4_BLOCK_KERNELS=0`) build gets the same coefficient and the same
bypass, because that build is the scalar control every audio bar scores the
block form against and a feature that existed only in the block form would
make the control a different product.

**Addresses: a SECOND SPI block, allocated after every other chip-2
address** — the same device ROUTING's matrix sends use, and for the same
reason: the node has a single word of its own and growing it would have
moved every chip-2 address above it. Two words per output, Level then Mute.
**D32 +6, D24 +8, and the `dsp.csv` diff is four rows gaining
`mo_page`/`mo_addr` and NOTHING else.**

### 3b-i. Witnessed on the part: the fold is exact, five of five

`s24probe.sh` / `dsp4_s24_probe.py`, D32, on the S24 tap arm
(`17cc5a0e` / `e94dc5a3`). `Main{L}001Level/Mute` written through the
contract, `_out_coeff_C2_MAIN_OUT_01` read back off the part:

| level | mute | `_out_coeff` | want | |
|--:|--:|---|---|---|
| 1.0 | 0 | `0x10000000` | `0x10000000` | **exactly 2^28 — the node takes the copy path** |
| 0.5 | 0 | `0x08000000` | `0x08000000` | OK |
| 0.25 | 0 | `0x04000000` | `0x04000000` | OK |
| 1.0 | **1** | `0x00000000` | `0x00000000` | **mute folds to exactly zero, not small** |
| **0.0** | 0 | `0x00000000` | `0x00000000` | **the independent control** |

with the probe's own control (`_fdr_level_C2_MAIN_FDR` = `0x3F800000`)
proving the graph was running.

**Its first two runs reported the opposite and were wrong, and that is
worth the paragraph (S24-7).** `_out_coeff` read `0x00000000` at every
level — the exact sentence a broken feature produces — and so did every
control word beside it. The cause was the read window: DM symbols are read
with `Scope.peek(Scope.addr(...))` and `Scope.rd()` reads the SPI
diagnostic/cell window, where a DM word address lands outside the dispatch
table and **answers zero**. That is S22-4's shape one level along. The
probe now takes its control FIRST and refuses a verdict when the control
reads zero, the way `dsp4_dsp_latency.py` was taught to refuse a 0.0 %
coherent fraction after S11-6.

**What is NOT witnessed, and no claim is made from it**: the audio. The
probe's capture bars — an exactly-zero output block under mute, a peak
passthrough at unity — returned `capture stalled at 0 of 1024 samples` on
every attempt, because the injection point this probe passes
(`_rx_ic_slot_C2_RECV_MAIN_L`) is not one the chain's scope gate injects
into. One line and one boot.

### 3c. Delay is NOT built, and the reason is memory rather than cells

`Main{L,R,Ctr,Sub}[1-1]Delay[1-1]` stays in `dsp-unmapped.csv` with a
better reason than it had. The master asks for 250 ms, which is 12,000
words = 48,000 bytes of chip-2 L2 per output and **192,000 for all four

It fits. It is still PW's call, because it is half of what remains on a
chip whose worst-use row already overruns, and because the value of an
output delay on this product is a product question and not a generator one.

## 4. Gates 4–5 — what PW's rulings changed, and what is built

The addendum answered all thirteen questions. Here is what each is worth to
this tree, and the honest state of each.

**R3 — the compressor GR meter's floor moves from −40 dB to −80 dB.**
Built: one constant in `gen_comp_gr` (`0xC2200000` → `0xC2A00000`) and the
reason strings that quote the range. **This moves chip 1**, so the
byte-identity in §3d is gate 3's alone and is stated as such.

R3 also asks a question this change does not answer, and it is recorded in
the generator rather than assumed away: raising the meter's floor raises
what the meter can REPORT, not what the compressor can DO. −80 dB is a gain
word of 26,844 counts at 2^28, so the resolution is fine — but whether the
level→gain table's input span reaches that far is a property of
`dyn_lut_design.py` and **has not been measured**. Until it is, a reading
between −40 and −80 is the meter's arithmetic on the gain word and is only
as true as the table behind it. R3's own witness (a signal 80 dB over
threshold reading −80 with the audio agreeing) is the measurement that
settles it and it is not taken here.

**R4 — the aux pick-off is answered and it was never a missing DSP
function.** `Chan*AuxPick*` already implements all four positions in the
router (`0=PreEQ 1=PostEQ 2=PreFdr 3=PostFdr`, default PostFdr), which is
exactly the DSP truth R4 names, and every channel is already independent.
`Aux*PickOff` is an app batch button with no word for a kernel to read, so
it moves from `no-graph-node` to `host-managed` with PW's reason — **12
D32 cells and 8 D24 cells stop being a DSP function the graph has failed to
build**. R4's one open sub-question (does post-fader ignore mute?) is PW's
own and is carried.

**R5 — LCR is fully specified and deliberately NOT built.** One 127 ×
(gL, gC, gR) table in DM, `Sys[1-1]LcrLaw[1-1]` selecting which law is
loaded, every channel's `Pan` an INDEX into it, `Chan*CtrOn` still gating
the centre leg. Two reasons it is not built at the end of this session and
both are in the unmapped reason: the selecting cell has not landed in defs
yet, and **R5 amended puts NON-LCR channels on the same table**, which
changes the pan law of every strip on a chip whose code pool is at 90.7 %.
That needs its own gate and a pan-law witness, not a tail-end addition.

**R1 — the FX ducker's cells are real and its meaning is settled**
(`DuckThr` = the dry level above which the return is pulled down, −60..0;
`DuckSens` = the depth of the pull, 0..−40; attack/release fixed
constants). `Fx*DuckThr` moves out of `s1-2-no-behaviour` into
`no-graph-node` with that meaning, because it is now a DSP function the
graph does not build rather than a definition with no behaviour. Not built:
it is a new sidechain compressor per return on the chip §2 has just shown
overrunning, so it gets priced and gated like any other chip-2 addition.

**R6–R11 — held.** No matrix or FX-topology cells were built. S22's four
matrix rows and S23's FX builds stand exactly as they are, which is what
the addendum asks for. Note for the diagram work: §2 prices S22's matrix at
**+1.13 points of chip 1 when it is actually used**, which is the number
R6's "S22's four extra matrix rows RETIRE once the diagram lands" is
trading away.

**R12, R13 — defs changes the hub lands.** R12 (every level/send family
declares its dB→linear law in the master) closes the `ChanGateRng`/D39
mismatch class at the source and this tree reads it from the contract; R13
(`Chan[1-64]GateMtr[1-1]`) cannot be bound until the cells exist, and when
they do it is the same binding `CompMtr` has.

### Still not built, and not guessed at

`Chan*AntiClip` (32/24 cells), `Rta*On`/`Rta*Src`, `Noise*Dest`,
`Talk*Dest`, `Fx*PingPongStart`, and the four `Main*LimiterRng`. None is
ruled by the addendum and none is built. The RTA in particular is a meter
family and a new node class, and pricing it driven — which the dispatch
asks for — is a build and a boot this session's bench time did not have.
