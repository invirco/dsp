## 1. The configuration, named once

`MW/D32/DSP/SHARC/shipping.config.s20`. It is a **proposal**: a complete
configuration file in the same format as `shipping.config`, with every switch
named at the value that was measured and the session that proved it cited in
place. `build.sh` reads whatever `SHIPPING_CONFIG` points at, so building it is
one command and there is no environment soup behind any number below:

```
SHIPPING_CONFIG=$PWD/shipping.config.s20 ./build.sh all
```

Five switches move against `shipping.config` and nothing else does:

| switch | shipping | s20 | evidence |
|---|--:|--:|---|
| `DSP4_STRIP_FUSED` | 0 | **1** | S11 — famverify verdict for verdict, three arms BIT_EXACT |
| `DSP4_SIMD_DYN` | 0 | **1** | S12-5 — "SIMD_DYN is audio-correct"; 17/20 LIVE, contract 20/20, 3 BIT_EXACT |
| `DSP4_C2_BQ_GRAPH` | 0 | **1** | S13-1 — the defect S12-5 found, mechanism named and FIXED, finding CLOSED |
| `DSP4_GATE_LINTHR` | 0 | **1** | S15-7 — 54 % of the gate body; ≤0.0002 dB threshold shift, PW's to sign off |
| `DSP4_DYN_LUT` | 0 | **1** | S15 + **S16-6** (the LIMITER too, 253 → 92 c/sample-pair); 0.0950 dB bound |

Three more are named rather than left to a default, because each has a reason
that is not a preference:

* **`DSP4_TX_EARLY=2` and `DSP4_GATHER_FIRST=1`** — PW's Option A ruling of
  2026-09-09, unchanged, and GATHER_FIRST is the dependency Option A has
  (with it off the same arm reads 98.2156 % ordered and chip 2 misses 2.7 %
  of blocks).
* **`DSP4_BQ_SIMD_PIPE=0`**, with **2** measured beside it as `s20f_*`. It is
  bit-exact against the unpipelined loop *by construction* — same operations,
  same operands, same order of additions — and worth ~5 points of chip 2. That
  is an argument, and this project's rule is that the part says so; S19 already
  found `s16f` indistinguishable from `s16` within its own boot-to-boot
  spread, so the 5 points are not what decides the window. The safe default
  for a proposal is the control loop, and the pipelined arm is measured.
* **`DSP4_SHARED_KERNELS=0`**, and it is **not a choice**: `build.sh` exits 2
  on `DSP4_SHARED_KERNELS` with `DSP4_SIMD_DYN`. The SIMD pair drivers call
  `_C1_COMP_nn_process_sample` directly, and a shared body reached that way
  would run on whatever record base the last strip left in the register. S18's
  own recommendation agrees from the other side: it is a BYTES lever
  (−38,634 of chip 1's code pool for +0.69 points) and the code pool is no
  longer what stops anything. **§1.2 is where that stops being obviously
  true.**

### 1.1 The part reads back what the file says, to the bit

The tree had no way to ask that question about a configuration other than
`shipping.config`: `check_shipping_config.sh` proves the file and the bench
mirror in `tools/pi/dsp4_buildcfg.py` are one fact, and it is written around
that one file. So two things were added, and they are the only tooling this
session needed:

* **`tools/dsp/cfg_words.py`** — the two `DIAG_BUILD_CFG` words any named
  configuration must read back, computed from the file, from `build.sh`'s
  defaults READ OUT OF `build.sh`, and from the derivations (each stated with
  the source line that owns it: `DSP4_GAIN_FLOAT` follows `DSP4_BQ_FLOAT`,
  `dsp_block.h` forces `DSP4_BQ_GUARD` off in a float build,
  `DSP4_SIMD_STRIPS` follows `DSP4_SIMD_DYN`). It honours an ENVIRONMENT
  override the way `build.sh` does and names it in the provenance, so it
  scores the arm that is actually on the part and not the file. Cross-check:
  on `shipping.config` it reproduces `check_shipping_config.sh`'s
  `0xCF45FF10` / `0xC2010244` independently.
* **`MW/D32/DSP/SHARC/cfgverify.sh`** (+ `cfgverify_run.sh`) — boots the image
  and reads both words off BOTH chips, then checks them against the file.

Measured:

| `s20_*` | `32dc1ea1` / `29d00a5e` | `0xCF45FF10` | `0xC2011E4F` | **matches `shipping.config.s20` to the bit, both chips** |
| `s20f_*` | `20f04ffe` / `7802f1f2` | `0xCF45FF10` | `0xC2015E4F` | **matches to the bit** with the one named override (`DSP4_BQ_SIMD_PIPE=2`, bit 14 — `0x00004000`, and nothing else) |

### 1.2 THE ONE COST THAT IS NOT CYCLES: chip 1's code pool has 380 bytes left

This is the finding of gate 1 and it is not in S19's table, because S19 never
built this configuration.

| arm | chip 1 code (Blocks 3+2) | free | code in Block 1 | DM |
|---|--:|--:|--:|--:|
| default (`shipping.config`) | 235,064 / 262,144 (89.7 %) | **27,080** | none | 251,412 (67.0 %) |
| `s20_*` | 261,764 / 262,144 (99.9 %) | **380** | **1,692** | 298,922 (79.7 %) |
| `s20f_*` | 261,828 / 262,144 (99.9 %) | **316** | **1,692** | 298,922 (79.7 %) |
| `s20_*` + the scope tap (the bar image) | 262,004 / 262,144 (99.9 %) | 140 | 7,708 | 304,942 (81.3 %) |

**The 1,692 bytes in Block 1 are the three design-step objects and nothing
else** — `afb_design_fx` (666), `xover_design_fx` (622), `geq_design_fx` (404).
Every one of them runs once per parameter move, never per block, and every one
of them is on `DSP4_COLD_OBJS`. So S16-1's list did exactly the job it was
built for: the image that does not fit Blocks 3+2 got to CHOOSE what pays the
contended fetch, and what pays is cold code. No per-block kernel is fetched
from Block 1 on either arm. The tap image spills 7,708 bytes and all eleven
objects are on the same list.

**What is left before that stops being true: 380 bytes of free pool, plus
6,666 bytes of cold code still sitting in Blocks 3+2 — call it 7,046 bytes of
growth before a HOT kernel is fetched from the DM/DMA block.** That is the
real margin on chip 1 in this configuration, and it is the sentence PW needs
beside the cycle numbers, because:

* S15-8 already named chip 1's code pool as the binding resource for the
  dynamics integration, and this configuration is the dynamics integration;
* S18's lever that returns 38,634 of those bytes **cannot be combined with
  this configuration** — `build.sh` refuses it — so the obvious answer is
  closed until the SIMD pair drivers learn the shared calling convention;
* the LDF's third tier is not free: it is the block the DM overflow and the
  DMA ping-pong buffers live in.

Nothing here changes an instruction. It is a placement fact about an image
that fits, stated so the next node added to chip 1 is a decision rather than
a surprise.

## 2. The audio question, settled by the record

S19's reason for not recommending this configuration was: *"what stands
against it is S12-5/S12-7, unchanged."* **Neither is unchanged. Both were
closed, by name, in the two sessions after the one that opened them.**

### S12-5 is half a finding, and its own title says which half

The finding is titled **"SIMD_DYN is audio-correct; `DSP4_C2_BQ_GRAPH` is
not"**, and the first clause is a result, not a caveat. With
`DSP4_STRIP_FUSED=1 DSP4_SIMD_DYN=1 DSP4_C2_BQ_GRAPH=0`, S12 measured
verdict-for-verdict identity with the shipping configuration: 17 of 20
families LIVE, contract 20/20 with 0 FAILED, COMPRESSOR / FADER_PAN /
TUBE_SAT **BIT_EXACT**, GATE's numeric arm `NO_STIMULUS` exactly as the
shipping arm reports it. "The paired dynamics, the pair-ordered chain, the odd
pool, chip 1's paired biquads and chip 2's paired *dynamics* are all clean" is
S12's own sentence.

The open half was `DSP4_C2_BQ_GRAPH`: a GEQ band gain and an AFB notch gain
never became coefficients at all, on 18 of the 24 chip-2 pairs.

### S13-1 closed it, with the mechanism and three independent witnesses

**S13-1: "the paired chip-2 biquad graph dropped the write UPSTREAM of the
latch, not at it." Severity high (audio). Status CLOSED.**

The mechanism: the pair driver's steady test never read the pending-DESIGN
flag. The generator's note asserted every coefficient write goes through
`_<pfx>_coeffs_next_` / `_<pfx>_swap_pending_`, which holds only for the
classes the host writes COEFFICIENTS to. A GEQ takes 31 band gains, an AFB six
notches, a crossover a corner frequency: the host writes those and sets
`_<pfx>_dirty_`, and the design step that turns them into coefficients — and
only then raises `swap_pending` — runs at the top of the NODE BODY, which is
the body the latch exists to skip. Latched, the design never ran, `swap_pending`
never rose, the latch never came down, and the pair ran its `.var` bypass
initialisers for ever. 12 GEQ + 6 AFB pairs affected; the 6 EQ/OEQ pairs and
the whole of chip 1's `DSP4_BQ_GRAPH` were always correct, **because chip 1 has
no design-driven class at all** — which is why the S12 candidate read clean and
only the arm that fits D32 did not.

The fix is two DM reads and an OR per pair per block, in
`tools/dsp/dsp_codegen.py::gen_bq_pairs_c2`: the steady test reads
`_<pfx>_dirty_` for any class that has one, guarded on that class's
`DSP4_<CLS>_DESIGN` macro. Witnessed three ways — `geqverify` and `afbverify`
design AND live-bank arms at 1–4 ulp with the switch ON, against 50.9 M / 83.9 M
ulp before; famverify GEQ and ANTI_FB both LIVE paired, moved 64/64;
`bqeverify` PASS, 0 ulp over 36,864 words.

### S12-7 was closed by S15-9

S12-7 was that `DIAG_BUILD_CFG2` did not carry `DSP4_C2_BQ_GRAPH`, so two
images that differ in AUDIO read back the same word. **S15-9 put it in bit 12**
(with `DSP4_GATE_LINTHR` in 11, `DSP4_DYN_LUT` in 10, `DSP4_BQ_SIMD_PIPE` in
14:13), S18-4 taught the bench decoder to read them, and §1.1 above is that
loop closing on the part: `0xC2011E4F` names all five switches, and
`s20f_*`'s `0xC2015E4F` differs in exactly the one bit its override sets.

### So the answer to gate 2's question is: nothing real remains, and the record already said so

Two pieces of bookkeeping follow, and they are why S19 could read the record
and reach the opposite conclusion:

* **S12-5's status line still says `OPEN — the chip-2 aux biquad pair`** while
  S13-1, which closed exactly that, says `CLOSED` and does not reference it.
  Filed as **S20-1** and corrected in `findings.md`: a finding whose defect has
  been fixed and witnessed reads OPEN, and a session that trusts the status
  lines gets the wrong answer.
* **`shipping.config`'s own comment on `DSP4_C2_BQ_GRAPH` is stale.** It says,
  in the file that exists to be the single source of truth about the shipping
  build: *"NAMED HERE AT 0 BECAUSE IT IS NOT AUDIO-CORRECT, measured on the
  part 2026-09-09 (findings S12-5)"*, and *"DIAG_BUILD_CFG2 does NOT carry this
  bit"*. Both sentences were true when written and neither has been true since
  S13 and S15 respectively. Filed as **S20-2**; the value 0 in
  `shipping.config` is left alone (that is PW's ruling to move) and the comment
  is corrected in place, because a wrong reason on a right line is how S19 lost
  a session's recommendation.

That is the record's answer. §3 is the part's.

### `busgold` is NOT bit-exact on this configuration, and that is the correct result

This is the one bar whose verdict is not a PASS, so it is worked through rather
than summarised.

**First, the bar was scoring the wrong arm (S20-4, fixed).** `busgold.sh` pins
`DSP4_SIMD_DYN=${SIMD:-0} DSP4_STRIP_FUSED=${FUSED:-0}` on `build.sh`'s command
line, and `build.sh`'s rule is that the environment wins over the configuration
file. So run against `shipping.config.s20` — a file that names both at 1 — the
bar silently built an arm with both at 0, and its own capture said so
(`paired_build=False bq_paired_build=False`). A bar cannot witness a
configuration whose defining switches it overrides. The two switches still
exist as `SIMD=`/`FUSED=` (they are how the pairing is A/B'd) but they now
default to what the configuration file says.

**Second, this bar's golden CANNOT be bit-exact on a `DSP4_DYN_LUT` arm, and
the reason is in `busgold.sh`'s own header.** The harness configures both
strips with opposite dynamics settings and deliberately does not write
`CompPar`, so the strip's compressor is FULLY WET in the capture — that is
exactly what review finding D59 changed and why the golden was re-baselined on
2026-08-30. The compressor's gain computer is the thing `DSP4_DYN_LUT`
replaces. A bit-exact capture would mean the table was not reaching the audio.

So the question is not whether the words differ but by HOW MUCH, and that is a
dB question the bar could not answer: `dsp4_pairgraph.py --compare` reports
LSBs, and a maxdiff of 303,276 LSBs reads identically for a table interpolating
to 0.04 dB and for a node that has stopped working. `tools/dsp/busdev.py`
(new, the same correction S16-4 made to `node_verify`) reports the level
difference:

```
postD59 vs s20:  235 of 256 words differ
                 0 of them zero in one capture and not the other
                 worst level difference 0.03934 dB at word 21
                 (67108851 vs 66805575, delta -303276 LSB)
                 bound 0.0950 dB: PASS
```

**0.03934 dB worst word, against the table's own 0.0950 dB design bound.** Not
one word is zero in one capture and non-zero in the other, which is the
signature a dead node would leave. For scale, the audio change D59 made to this
same capture was a maxdiff of 45,807,405 LSBs — 151 times larger.

### `goldnode` — still failing, still S18-7, and it is the bar and not the audio

It is a defect in the bar's capture layer, filed with a named mechanism, and it
is not re-litigated here. Nothing in `s20` touches it.

## 7. The proposal for PW

**Adopt `shipping.config.s20` as the shipped configuration for the window, and
deploy `s20_*`.** The case is one sentence per switch and it is all on the
record:

| switch | why it is on | what it costs |
|---|---|---|
| `DSP4_DYN_LUT` | it is the switch that makes the product fit under load. Driven minus silent on the shipping default is +42.5 points of chip 1 and +29.3 of chip 2; with the table it is +1.0 and 0.0 (S19) | a **numeric-spec deviation**: 0.0950 dB worst case over the documented sweep, against PW's 0.1 dB ruling of 2026-09-09. | `DSP4_GATE_LINTHR` | 54 % of the gate body, and the gate is on the same expensive branch | a **numeric-spec deviation**: the gate's effective threshold shifts by ≤0.0002 dB. **PW's sign-off, not a measurement** |
| `DSP4_STRIP_FUSED` | 1.08 % of chip 2 | **nothing.** famverify verdict for verdict; 0 of 256 bus words |
| `DSP4_SIMD_DYN` | 29.6 % of chip 2 — the difference between D32 fitting and not | **nothing measured.** S12-5's own title says audio-correct; this session: 0 of 256 bus words, 0 ULP on the cascade |
| `DSP4_C2_BQ_GRAPH` | ~20 points of chip 2 at D32 (chip 2's pairs own their interleaved arrays and do not gather per block) | **nothing.** The defect S12-5 found was S13-1, fixed and closed; this session's live-tone arms deliver +12.000 dB and −18.000 dB through the paired AUX GEQ and AFB to within 0.003 dB |

**Two of the five are PW's rulings and three are not.** `DSP4_DYN_LUT` and
`DSP4_GATE_LINTHR` are numeric-spec deviations and need sign-off; the other
three are measurements with no deviation to sign off.

### What is left open on chip 2 at D32

Three things, none of which this configuration closes:

* **The FX engines' driven cost is not measured.** S19's load configuration
  deliberately leaves the six FX engines alone — switching them on would not be
  comparable with the silent row it is subtracted from — so every driven figure
  in §4, including `s20_*`'s, is taken with the FX engines idle. On the
  dynamics-bypassed arm S19 measured that switching them off moves chip 2's
  driven figure by 0.00, so they are not on the expensive branch the dynamics
  are; but "idle" is not "engaged", and a desk with six reverbs running is not
  what was measured. **This is the biggest single unknown left in the D32
  budget and it should be the next session's gate 1.**
* **GEQ is the wall on chip 2 (S13-5): 6.03 cycles per band-sample, 11.0 % of
  budget in the aux GEQs alone.** `DSP4_C2_BQ_GRAPH` is the lever that has been
  applied to it; the next one is the six-slot primitive.
* **The six-slot biquad primitive, `DSP4_BQ_SIMD_PIPE=2`, is worth ~5 points of
  chip 2 for no audio cost by construction** and is measured here as `s20f_*`.
  It is named at 0 in the proposal because a proposal should default to the
  control loop, and it is available the moment chip 2 needs 5 points.

### Rollback
