### 1a. The family walk gains a matrix family — and the walk had a blind spot

`dsp4_family_verify.py`'s family list was keyed by the landed contract's
`NodeType` column, and `Chan*MatrixSend/On` are cells of a **ROUTING** while
`Matrix*Level/Mute` are cells of a **FADER_PAN**. Both of those families were
already passing before the matrix existed. **So a NodeType-keyed walk could
not give the matrix a family however hard it looked, and would have gone on
reporting the graph complete with the feature un-witnessed.** That is the
shape of defect this bar exists to catch, one level up.

Fixed by making the default family list the UNION of the landed NodeTypes and
the harness's own table: an entry in `FAMILIES` is a claim that something is
answerable for, and it runs whether or not its name is a NodeType. Four
entries are added, each with an explicit `contract_cells` list so the sweep
writes the four words that are new rather than re-writing sixty routing words
to reach them:

- **MATRIX** (chip 1) — the crosspoint, witnessed at `_buf_C1_BUS_MTX_01`,
  probed on `Chan001MatrixSend001` with `MainOn` taken off so the matrix send
  is the only live crosspoint on the strip.
- **MATRIX_OUT** (chip 2) — the output strip's Level and Mute, witnessed at
  `_buf_C2_MTX_FDR_01`, injected at the matrix bus's own receive slot.
- **FX_RETURN** (chip 2) — gate 2, witnessed at `_buf_C2_MIX_MAIN_L`, which
  is the node whose `inputs` was missing the return.
- **MIX_BUS** (chip 2) — gate 3. MIX_BUS *is* a NodeType and it had no cells
  at all before this session.

### 1b. The bus vector: the matrix buses carry the same sum as a proven one

`mtxgold.sh` / `mtxgold_run.sh`, and it needs **no stored golden**, which is
the point. The dense crosspoint path is ONE path: a strip's post-fader block
is parked once, each bus's row of `_xpc` holds one Q4.28 coefficient per
strip, and one shared pass accumulates every bus in exact 80-bit arithmetic
and reads it out with a single rns+saturate. So a strip sent at UNITY into
aux 1, matrix 1 and matrix 2 is the same source, times a coefficient of
exactly 2^28, into three accumulators that differ only in which row of the
matrix they are — and the three bus sums must be **identical**, not close.

That is a bar with no baseline to go stale, and it can fail three ways a
stored golden could not tell apart: a matrix bus row indexed wrong in `_xpc`,
a send-coefficient stride slipped by one, or one accumulator overlapping
another's triple in `bus_accumulators.asm`. All four captures are taken on
ONE boot, because comparing across boots would put the boot between them.

Arm `chip1.ldr c3e7a030` / `chip2.ldr 911cf656` from
`shipping.config.s21` with `DSP4_STRIPS=2` (busgold's own arm, and its
switches default from the configuration file rather than from 0 — S20-4),
strip 1 driven and strip 2 muted, 256 words per capture, one boot:

| capture | bus | sha256 | non-zero |
|---|---|---|--:|
| `aux1` (first on the boot) | `_buf_C1_BUS_AUX_01` | `963c848437fa7208` | 256/256 |
| `mtx1` | `_buf_C1_BUS_MTX_01` | **`b67e59ca785515bd`** | 256/256 |
| `mtx2` | `_buf_C1_BUS_MTX_02` | **`b67e59ca785515bd`** | 256/256 |
| `aux1b` (the same bus as `aux1`, last) | `_buf_C1_BUS_AUX_01` | **`b67e59ca785515bd`** | 256/256 |
| `mtx1off` (the negative control) | `_buf_C1_BUS_MTX_01` | `5f70bf18a0860070` | **0/256** |

**Three captures of THREE DIFFERENT BUSES are byte for byte identical**, and
the negative control — matrix 1 with `Chan001MatrixOn001` at 0 and the send
level left alone — is **exactly zero, all 256 words**. So the matrix bus rows
are in the fabric on exactly the footing the aux rows are, and the assign bit
reaches the coefficient.

**The odd one out is `aux1`, and taking it twice is what made that
readable.** The first capture of a boot differs from every later one by 1,412
LSB from word 21 (−99.5 dB relative), and `aux1` vs `aux1b` — the SAME bus,
same boot, same graph — reports the identical 235-of-256 / first=21 /
maxdiff=1412 as `aux1` vs `mtx1`. **That is the instrument, not the bus**
(finding S23-1): a 256-sample capture starts wherever the strip's gate and
compressor envelopes happen to be when the arm lands, and the first arm after
`gainfix` starts from a different history than the ones behind it. Without
the repeat the honest reading of `aux1 vs mtx1` would have been "differs by
1,412 LSB and I do not know why"; with it the reading is "every capture after
the first is bit-exact across all three buses".

## 2. Gate 2 — the FX returns reach the MAIN mix, and `Fx<n>On` has a reader

**S22-2: `C2_FX_FDR_nn` has declared `outputs=C2_MIX_MAIN_L;C2_MIX_MAIN_R`
since the graph was written, and neither mix node listed a single FX return
among its `inputs`.** `gen_mix_bus_fixed` MACs over `inputs` and nothing
else, so no `_buf_C2_FX_FDR_*` was read by any mix node on either chip: the
six engines have been inaudible on every image this tree has built, while
costing their full price. `outputs` is documentation; `inputs` is the graph.

**The fix is six identifiers.** `main_l_sources` and `main_r_sources` gain
the six returns, and the main mixes go from 17 sources to 23.

**There is no send cell and none was invented.** The cell master gives the
return `Fx[1-8]Level`, `Fx[1-8]Mute`, `Fx[1-8]Dca` and `Fx[1-8]DcaOn` and
that is the whole of its level control — there is no `Fx*MainOn`, no
`Fx*MainSend` and no `Fx*Pan` — so the crosspoint is a constant 1.0 and this
gate adds no cell and moves no address. The engine is mono end to end (the
reverb's `_R` buffers were deleted 2026-09-08 because nothing read them), so
both mix legs read the same block.

### `Fx<n>On` gets its reader, and it parks the engine

**S21-4 was that `Fx[1-8]On[1-1]` — "FX system on/off" in the cell master —
has no reader.** It had an address, the host could write it, `_fx_on_<nid>`
was declared in the node's own DM, and **not one emitted instruction in this
tree ever loaded it.** The switch did nothing at either value.

It now gates the engine in two places, and the second is an optimisation of
the first rather than a second behaviour:

1. **the per-sample body** tests `_fx_on_<nid>` at entry and, when it is 0,
   stores zero to `_buf_`, `_buf_L_` and `_buf_R_` and returns. (The store
   uses `r1` and not `r0` deliberately: `gen_fx_engine_fixed()` finds the
   node's float-island entry and exit by matching the exact text of the
   input read and the `_buf_` store, and a second `dm(_buf_<nid>) = r0;`
   anywhere in the body would make that match ambiguous and stop the
   generator.)
2. **the block wrapper** tests the same word before staging anything,
   publishes a block of zeros and never enters the loop. Same arithmetic,
   same result, so the two builds stay bit-identical by construction —
   which is the whole licence for putting a shortcut in front of a
   reference body. It is a table (`_C2_PARK_GATE`) rather than a special
   case in one generator, and it refuses to park a node that also publishes
   a wide-meter block, because the park would leave that block stale.

Because the engine publishes zero, the return strip publishes zero and every
destination reads zero — one gate, not one per crosspoint.

**THE ENGINE'S STATE IS FROZEN, NOT CLEARED, and that is what "parked"
means.** The comb, allpass and delay lines keep whatever they last held, so
an engine switched off and on again inside its own decay time releases the
tail it was holding. Clearing them is 24,587 words an engine and it is not
obvious that clearing is what the product wants; it is a question for PW
(§6), not a thing to decide here.

## 3. Gate 3 — the FX returns reach the aux buses

`Fx[1-8]AuxOn[1-12]` and `Fx[1-8]AuxSend[1-12]`: 144 cells on D32, 96 on
D24, the last big product-visible block of the completeness list after the
matrix.

### Where the sum happens, and why it is one node per aux

The twelve aux buses are summed on **chip 1** (bus-major fabric, 32 channels
a bus) and arrive on chip 2 already mixed, one word per sample, at
`C2_RECV_AUX_nn`. The six FX returns live on **chip 2**. So the FX
contribution cannot join the chip-1 accumulate at all — it has to be added
on chip 2, downstream of the receive and upstream of the aux fader, which is
exactly one more summing node per aux bus:

```
  C2_RECV_AUX_nn -> C2_MIX_AUX_nn -> C2_AUX_FDR_nn -> EQ -> GEQ -> AFB -> ...
                    ^ + C2_FX_FDR_01..06
```

and MIX_BUS is already that node. Its chip-2 form is an exact MRF sum of
`inputs` against Q4.28 coefficients converted at block rate — the same
arithmetic as the main mix and the same reference (`fixed_ref.mix_sum`). It
gains an optional **switched-send** half: `fx_sends=N` says the last N
sources are crosspoints, each with an on/off flag and a ramped send level
whose Q4.28 coefficient is the two folded together at block rate. That is
the 08-25 crosspoint mandate applied on chip 2 — an off or zero send is a
coefficient of exactly zero and there is nothing left for the per-sample
path to test. A `dsp.csv` without `fx_sends` emits none of it, so the main
mixes' own diff stays readable.

**S22 SKETCHED A DIFFERENT SHAPE and this is a deliberate departure from
it.** S22 proposed the crosspoints on the return strip's own node, "category
`Fx`, one instance per return, 24 SPI words", so that
`Fx001AuxSend001..012` would be contiguous. Per-AUX placement costs the same
144 words, needs no new node class and no cross-node coefficient reads, and
contiguity buys nothing here — the host addresses one cell at a time, and
only `add_dispatch_block` (coefficient SETS) needs a run. Said out loud
because the sketch is in the S22 write-up and the tree now disagrees with it.

### The ramp state is a runtime contract, and the generator is what states it

The four send arrays are emitted as `value`, `_target_`, `_step_`,
`_frames_` in consecutive `.var` declarations of equal width, because
`_ramp_set_target` writes the companions at +s/+2s/+3s from the value
address and `gen_dsp.py::build_ramp_stride_map()` reads THAT ADJACENCY out
of the emitted ASM to tell the SPI handler what `s` is. Nothing was typed:
chip 2's stride table came back with **72 entries at stride 6** — twelve aux
nodes times six returns — beside the 94 scalars, which is the generator
recognising the new quads on its own.

### The pickoff is post-fader and it is not selectable

The cell master defines `Chan*AuxPick` and `Chan*FxPick` and **no
`Fx*AuxPick`**, so there is no cell to dispatch a choice to. Post-fader
matches the channel sends' own default and is what the graph can take for
free (`_blk_C2_FX_FDR_nn` is the return strip's published block).
**Pre-fader is equally available at zero cost** (`_blk_C2_FX_ENG_nn`), so
which one the product means is a question for PW (§6) and not a thing to
decide here.

### The cost, and the bypass it forced (S23-5)

The twelve sums were priced driven before anything else was said about them,
and the number was bad: **D24 chip 2 at 87.67 % against S21's 74.08 % on the
same instrument, the same clock and the same plugin load — +13.59 points,
with every `Fx*AuxOn` at its shipping default of 0.** On D32, where S21's
chip 2 was already 87.08 %, the same addition would not have fitted.

The cause is the generic wrapper, not the arithmetic: it stages every source
through its scalar `_buf_` word on EVERY sample, six instructions per source,
whatever the coefficients are. Seven sources is about 63 instructions a
sample a node before a single MAC, paid identically whether an FX return is
sent to that aux or not.

**Thirteen points for a crosspoint nobody has switched on is the wrong
trade**, and the fix needs no kernel restructuring. The switched coefficients
are folded at block rate with the on/off bit multiplied in, so one OR over
the fold answers "is any crosspoint live this block?" for free. When the
answer is no, and the node has exactly ONE plain source at a coefficient of
exactly 2^28, the whole sum IS that source unchanged:

```
  mrf = x * 2**28   (exact)  ->  _mrf_rns28  ->  (x * 2**28 + 2**27) >> 28  =  x
```

so the bypass is a block copy and it is **identical, not close**. The
block-rate send prep moves out of the per-sample body under block kernels to
make that decision possible before the sum runs; in the per-sample build it
stays in the body behind the `_sample_idx == 0` guard, which fires once per
block there too — same arithmetic, same rate, same result.

It is emitted ONLY where the argument holds — `n_plain == 1`, checked at
generate time, and the plain gain read back as exactly `1.0f` at run time —
so the main mixes (seventeen plain sources, no switched ones) get neither the
bypass nor the prep and their emitted text is byte-identical to the pre-S23
generator. **And the exactness had already been measured before the bypass
existed**, which is what makes it a fix rather than a hope: with the sends
off, `_buf_C2_MIX_AUX_01` reproduced `_buf_C2_RECV_AUX_01` in 32 of 32
words.

Cost of the bypass: one compare per switched send plus a block copy, about 38
instructions a block against 1,008. **An aux bus nobody sends an FX return
to is very nearly free; one that is used pays the full sum on that bus
alone.**

### The chain had to be re-ordered, and the pair families are what said so

`C2_MIX_AUX_nn` reads `_blk_C2_FX_FDR_ff`, so every return must publish
before the first aux sum. `repair_process_order()` would fix that on its
own — and that is exactly the trap: it fixes it by moving each producer to
just before its earliest consumer, which drops `C2_MIX_AUX_02..12` INTO the
middle of the aux chain. The chip-2 pair families require each family's
nodes to be a contiguous run of the chain, and `c2_pair_groups()` said so in
as many words:

```
  chip 2 pair family AUX: its 84 nodes are not a contiguous run of the
  chain (60..154), so the pair order cannot be built by reordering that run
```

Left to the repair, the twelve aux limiters and the paired EQ/GEQ/AFB
cascades would have had to un-pair. Fixed by SPLICING the FX chain and all
twelve sums in front of the aux chain in the row order — rows are reordered,
addresses are not, since an address is allocated at the `add()` call — after
which the AUX family's 84 nodes are untouched and no repair move is needed
at all. `dsp_validate` is back to its four pre-existing process-order notes
(USB and BT into the main mix) and the emitted chain runs
`RECV_AUX → FX_ENG → FX_FDR → MIX_AUX → AUX_FDR → C2BQP_AUX_*`.

### On the part

Same arm and the same boot as gate 2, **and re-run after the bypass landed**
— which matters here more than anywhere else, because the bypass is the path
these captures now take when the sends are off:

```
  send ON  return peak 0x0D3A1800   aux 1 sum peak 0x0D3A1800
  AuxOn=0  aux 1 sum peak 0x00000000   <- negative control 1
  Send=0   aux 1 sum peak 0x00000000   <- negative control 2
  PASS: the return reaches aux 1, and only when sent
  passthrough with every send off: 0 of 32 words differ from _buf_C2_RECV_AUX_01
  PASS: gate 3 — the aux sum is BIT-EXACT passthrough with the sends off
```

The return reaches aux 1 at unity, and **both** negative controls read
exactly zero: the assign bit at 0 with the send level standing, and the send
level at 0.0 with the assign bit standing. Two words, independently tested,
because a probe that only tests the flag cannot tell a working send from a
coefficient stuck at unity.

**The passthrough is the result that matters most**, because this gate
inserted a node into the aux chain. With every send off, the receive
coefficient is exactly 1.0, so `(x * 2**28 + 2**27) >> 28 == x` and the sum
is bit-exact by construction — which makes "0 of 32 words differ" a real bar
and not a tolerance.

## 4. Gate 4 — the compressor gain-reduction meter

`Chan[1-64]CompMtr[1-1]` was listed `unbacked-meter` for two reasons and
only one of them was real.

**The real one**: the meter's SPI block is four words and **base+3 was
dispatched to nothing**, so the cell had no address. S22's note said base+3
was "the meter's own state array"; that is true of **DM** offset +3 and not
of the SPI block, and the difference is the whole of this gate. `_mtr_fold`
takes the address of `_mtr_peak_<nid>` and reaches `_mtr_rms_`, `_mtr_gr_`
and `_mtr_st_[4]` by OFFSET, so a word inserted at DM offset +3 would push
`_mtr_st_` up by one and every meter on both chips would fold into the wrong
four words. The new word is declared AFTER `_mtr_acc_`, and it takes SPI
offset +3, which no dispatch entry claimed.

**The one that was not addressed at all**: there was no declared SOURCE.
Pointing a meter at "the compressor" by string surgery on its own node id is
the second address map this repo keeps deleting, so the link is a param on
the row — `comp_gr_src=C1_COMP_nn` — resolved by the generator, and a
`comp_gr` tap without one is a hard error rather than a guess. It goes after
`taps=` on purpose: `_parse_taps` reads to the end of the params or to the
next `key=` token.

**What it publishes.** `_comp_gain_<comp>` is the compressor's own Q4.28
gain, unity when it is not reducing, and the kernel already stores it on
every sample as a display word — so there is no new per-sample work
anywhere. The meter converts it ONCE PER BLOCK:

```
  gr_dB = 20*log10(g) = (20/log2(10)) * log2(g)
```

through `_log2q_fx` (Q4.28 → log2 Q6.25), which both the table and the
polynomial arm of `dyn_fx.asm` export under the same name and the same
register contract (r0–r5, i0, l0, MRF — a strict subset of what the fold
below it sets up for itself). **Clamped to [−40, 0] dB**, which is the range
the dispatch names; a gain word of exactly zero comes out of `_log2q_fx` at
about −175 dB and lands on the floor rather than on an infinity. The clamp
is the one thing here that is a decision rather than a derivation, and it is
PW's to change.

It is emitted in BOTH arms — the block body and the per-sample body — so the
two builds publish the same word once per block.

### On the part, and the first run measured the recovery instead

Chip 1, same boot, strip 1 driven through the chain witness, compressor on,
CompPar 100 %, ratio 4.0, attack 0.5 ms, release 30 s:

```
  chain witness: _buf_C1_GATE_01        peak 0x07FFE779
  chain witness: _buf_C1_COMP_01        peak 0x02BD1D96
  thr    0.0 dB (no reduction): audio  +0.00 dB, _comp_gain 0x10000000 = 1.000000
                               ->  meter   +0.000 dB, 20log10(gain)   +0.000 dB, err 0.0000 dB  ok
  thr  -40.0 dB (reducing):    audio -28.76 dB, _comp_gain 0x009570D3 = 0.036485
                               ->  meter  -28.758 dB, 20log10(gain)  -28.758 dB, err 0.0000 dB  ok
```

**Three independent measurements of one quantity agree.** The AUDIO drops
28.76 dB between `_buf_C1_GATE_01` and `_buf_C1_COMP_01`; the compressor's
own gain word is 0.036485, whose 20·log10 is −28.758 dB; and the meter
publishes −28.758 dB. The meter against the gain word is exact to 0.0000 dB
and against the audio to 0.002 dB. At threshold 0 dB the compressor does not
reduce and the meter reads +0.000 dB, which is the negative control.

**The first run of this probe read `_comp_gain_` at unity in both arms and
concluded the meter had not moved.** It had set attack and release to 0.5 ms
for the family walk's reason — so the envelope settles inside the capture —
and then read the gain word AFTERWARDS. The scope's step injection stops
when the tap disarms, and at a 0.5 ms release the gain is back at
`0x10000000` long before a paced peek can reach it. The audio said the
compressor was working the whole time (`_buf_C1_COMP_01` at `0x02BD1D96`
against `_buf_C1_GATE_01` at `0x07FFE779`, −9.5 dB), so what was measured
was the RECOVERY. **Attack stays fast; release is 30 seconds**, so the
reduced gain is still standing when the two words are read, and the check is
the arithmetic BETWEEN them — the meter must be 20·log10 of the gain word —
rather than either value against a number typed here.

**`Chan*GateMtr` is still not written.** It is bound to `_mtr_gr_` at meter
word +2 and nothing stores to it; that is recorded defect 4 and it stays
open. The same three instructions would close it off `_gate_gain_<nid>`, and
whether the product wants a gate GR meter at the same range is a question
for PW (§6) rather than a thing to add to a dispatched gate.

## 6. The definition questions, carried and not answered

S22 carried three matrix questions to PW (`d32.csv` says `mtx,12` against a
master that caps `Matrix[1-4]`; `Chan[1-64]MatrixSend[1-2]` does not track
the `mtx` count so D32's buses 3 and 4 have masters and no source; the
topology master names `bus.main→bus.mtx` and `bus.grp→bus.mtx` for which no
cell exists). All three are still open and nothing here assumed an answer.

Seven more come out of this session. `dsp-definitions-needed.md` is not in
this tree — it is on PW's desktop — so they are recorded here and in the
dispatch block.

1. **Is the FX return meant to be assignable to the main mix at all?** It
   reaches it at unity because the cell master defines no `Fx*MainOn` and no
   `Fx*MainSend`, only `Level`/`Mute`. Every other source of the main mix
   has an assign bit; this one cannot have one.
2. **Is the FX return mono by design?** The engine publishes one word, so
   both main legs read the same block. `Fx*StereoWidth` and
   `Fx*PingPongStart` are defined cells; there is no `Fx*Pan`. A genuinely
   stereo return is a design change with a cycle cost, and it needs a cell
   before it can have a pan.
3. **Should `Fx*On` = 0 CLEAR the engine's state or hold it?** Parked, the
   comb, allpass and delay lines freeze, so an engine switched off and on
   inside its decay time releases the tail it was holding. Clearing is
   24,587 words an engine, affordable in chunks; freezing is free.
4. **Is the FX→aux send pre-fader or post-fader?** There is no `Fx*AuxPick`
   to dispatch a choice to. Built post-fader; pre-fader is available at zero
   cost.
5. **`Fx[1-8]AuxOn/AuxSend[1-12]` is declared for eight returns.** The graph
   builds the intersection with each product's `fx` count (six on D32, four
   on D24). Confirm `[1-8]` is the family cap and not a product count.
6. **`Fx*AuxSend` carries a `dB:` table and the DSP word is a LINEAR gain**,
   with no conversion declared in `wire-units.csv` — the same mismatch class
   as `ChanGateRng` (D39) and `Chan*AuxSend`. Should the send families
   declare the dB→linear conversion, or is the host applying it?
7. **`Chan*CompMtr`'s range and sign**: built as dB of gain reduction
   clamped to [−40, 0], negative meaning reduction. And **is a
   `Chan*GateMtr` wanted** — its word exists and nothing writes it.
