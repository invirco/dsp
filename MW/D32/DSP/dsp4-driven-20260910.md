# S19 — the DRIVEN capacity instrument, and every staged pair re-priced under load

Session S19, 2026-09-10. Bench: rev C unit. Contract `defs-v2026.09.08.4`,
unchanged. `shipping.config` unchanged. Predecessor
`dsp4-s18-20260910.md` (dsp `4ea4825`).

**The DSP firmware does not move at all.** No source file under
`MW/D32/DSP/SHARC/src/` changed this session; the default build is
`302d6142` / `3b3a6f8e`, byte for byte the pair S17 and S18 left, rebuilt
and checked before the first row was taken. What changed is the
INSTRUMENT: a LOGIC bitstream, a stimulus on the CM4, a parameter setup
and three rows per boot instead of one.

---

## 0. What S18 left, and the one sentence that turned out to be wrong

S18 established that the capacity record is a silence record: chip 2's
dynamics have a cheap branch below threshold, so the same image and the
same product read 92.7 % of budget silent and 112.3 % engaged. It also
said this, and it is the sentence this session had to test first:

> Chip 1's cost is signal-INDEPENDENT, and that is measured, not assumed.
> … Chip 1's 113 % in the driven arm is therefore the INSTRUMENT — the
> square-wave synthesis `DSP4_PROFILE_SIGNAL` puts in its 46 input
> kernels — and is not a product figure.

**It is not the instrument. It is the product figure.** Driven from
OUTSIDE the part, with a stimulus the DSP executes not one instruction
for, chip 1 reads **113.23 % of budget at D24 on the shipping default,
with 11.6 % of its blocks missed** — within 0.2 points of the number S18
attributed to its own square synthesis.

The evidence S18 reasoned from was real and the inference from it was
not. On its hot boot a near-full-scale signal reached chip 2's main bus
while chip 1 read 71.69 %, and the conclusion drawn was that chip 1 does
not care about signal. But the path that signal took was
`XIN_PI → XS_XFER_PI → C2_XR_PI → C2_PI_IN → C2_MIX_MAIN` — the CM4's
playback transfer, which crosses chip 1 as an INPUT_TDM node and an
INTERCHIP_SEND node and touches **no strip, no GATE and no COMPRESSOR**.
Chip 1 was silent on that boot in the only sense that costs it anything.

## 1. The instrument: a stimulus the part does not pay for

### The three things that were wrong with the old one

`DSP4_PROFILE_SIGNAL=1` synthesises a −6 dBFS square inside each of the
46 input kernels. As an instrument it has three problems, and only the
first was on record:

* the part pays for it, so its cost has to be netted off;
* it is a BUILD switch, so the driven arm and the silent arm are
  different images, taken on different boots, and the difference between
  them carries every difference between the two;
* it drives the INPUT KERNELS, which is not where a desk's signal comes
  from. Nothing on chip 2's aux, group or sub buses is driven by it
  except through whatever routing happens to be open — and at boot the
  routing is MAIN and nothing else.

### What replaced it

**A LOGIC bitstream that broadcasts the CM4's playback onto every DSPA
input lane.** `shared/dsp4-logic`, `DRIVE_ALL=1`, artifact
**`dsp4_logic_driveall.e13b5dec84e0`** (design_id `5dec84e0`, cfg_bits
`0x0020`, fmax 68.13 MHz, sim gate PASS). It is nine lines of RTL: the
re-framer already de-frames the Pi's stereo into a 256-bit slot array,
and a second launch register reads that array with the slot index forced
to `slot[0]`, so all eight TDM8 slots carry audio, L on even slots and R
on odd. The top level assigns `i_dspa = {8{pcm_drive}}` under the macro.

Three properties follow, and they are why this is worth a bitstream:

* **The DSP pays nothing.** The stimulus arrives on the wire. There is no
  instruction to net off, on either chip.
* **It is runtime-switched.** Silent and driven are the same image, the
  same boot, the same measured clock and the same parameter state; the
  only difference is whether `aplay` is running. Nothing else in the
  capacity record has ever had that.
* **Every input kernel is driven at once** — 46 of them on chip 1,
  including the codec, MEMS and snake lanes — so all 32 strips carry
  full scale and the mix fabric can be opened up to reach chip 2.

**Two artifacts, and why.** The comment block inside the `DRIVE_ALL`
`ifdef` originally repeated S18's conclusion that chip 1 is
signal-independent. This session disproved it (§0), so the comment was
corrected — and the artifact hash covers `rtl/*.v` byte for byte, so
correcting a comment renames the bitstream. Both are committed:
**`e13b5dec84e0`** is the one every row in §3 was taken on, and
**`907492a607bd`** is what the tree now reproduces. They differ in comment
text only; each stamps its own design ID (`5dec84e0` / `92a607bd`), so a
part can still say which one it is carrying.

The stimulus itself is a **400 Hz full-scale square, R = −L**, generated
gaplessly into `hw:0,1` (`drive_audio.sh`). Square rather than sine
because |x| is then constant at full scale: every dynamics node is above
threshold in every sample of every block, so the regime does not
modulate between blocks. R = −L so that a lane or slot quietly reading
its neighbour shows up as a cancellation instead of hiding behind two
identical channels. A looped FILE is not good enough — the restart is
tens of milliseconds of silence, which drops every envelope on the part
in the middle of a dwell — so the stream is generated and piped.

### It reaches the part, and the part says so

With the stimulus playing, read off chip 1 (Q4.28, `0x0FFFFFFF` = 1.0):

| word | value |
|---|---|
| `_buf_C1_XIN_PI_L` / `_R` | `0x0FFFFFFF` |
| `_buf_C1_XIN_MEMS` | `0x0FFFFFFF` |
| `_buf_C1_GAIN_01` (strip 1, post-trim) | `0x0FFFFFFF` |
| `_gate_envelope_C1_GATE_01` | `0x0FFFFFF6` |
| `_comp_envelope_C1_COMP_01` | `0x0FFFFFC4` |

A lane that is not in the shipping product's own signal path — MEMS —
carrying full scale is the proof that the broadcast is doing what it
claims and not just the product's Pi tap working.

### THE INSTRUMENT'S OWN COST: 0.28 points on chip 1, 0.53 on chip 2

Gate 1 asks for this to be measured rather than argued, and the way to
measure it is to take the driven-minus-silent delta on a graph with no
dynamics left in it. Same image, same boot, every COMPRESSOR, GATE and
LIMITER switched off over the parameter link, then the six FX engines
too:

| arm | chip 1 silent | chip 1 driven | Δ | chip 2 silent | chip 2 driven | Δ |
|---|--:|--:|--:|--:|--:|--:|
| dynamics bypassed | 33.55 % | 33.53 % | **−0.02** | 73.99 % | 74.70 % | **+0.71** |
| dynamics + FX bypassed | 33.27 % | 33.55 % | **+0.28** | 74.17 % | 74.70 % | **+0.53** |

**The instrument costs the DSP zero cycles by construction** — it is a
CPLD mux and a CM4 playback, and no DSP instruction executes on its
behalf. What the table measures is the residue: what the graph still
costs more of when signal is present after every branchy audio class has
been switched off. It is **+0.28 points on chip 1 and +0.53 on chip 2**,
against the ~40 points the dynamics turn out to be worth, and the likely
mechanism is the meters' peak-update branch (the FX rows say it is not
the FX engines: switching them off moves chip 2's driven figure by 0.00).

Compare with what the old instrument needed netting off: S18 counted
0.18 points for `DSP4_PROFILE_SIGNAL` on chip 2 and, on chip 1, wrote off
41 points as instrument. **The 41 points were not the instrument.**

### And the silence figures in the record were not silence either

On the shipping bitstream the ADC lanes are connected, and an open
converter input is not zero. With the drive bitstream and no playback,
chip 2's regime reads **0 of 10 compressor envelopes, 0 of 4 gate, 0 of
18 limiter** — genuinely nothing. The record's "silent" boots read 5 of
18 limiters live at `0x0000000C`, which is the converters' noise floor
clearing the −0.5 dB limiter threshold's cheap-branch test.

| | chip 1 D24 | chip 2 D24 |
|---|--:|--:|
| the record's "silence" (S17/S18, shipping bitstream) | 71.65–71.84 % | 92.67–92.84 % |
| TRUE silence (drive bitstream, nothing playing) | **70.51 %** | **89.76 %** |

So the silence figures were about 1.2 points high on chip 1 and 3 points
high on chip 2, for the same reason everything else in this session is
about: nobody was reading what the graph was carrying.

## 2. The ladder: three rows on one boot

A driven row on its own cannot be subtracted from anything, because
getting the signal to chip 2's aux, group and sub chains needs the bus
assigns opened, and opening them costs cycles of its own. So every arm
takes three rows on one boot, one clock, one image
(`capacity_run.sh`, `DRIVEN=1`):

| row | regime | what it is for |
|---|---|---|
| **A** `sil-default` | silent, the config the product boots with | comparable with every figure already in the record |
| **B** `sil-load` | silent, every bus assign and send open, every dynamics node on at −60 dB | **B − A** is what the CONFIGURATION costs |
| **C** `driven` | the same, with the stimulus playing | **C − B** is what the SIGNAL costs. **C is the product number.** |

The load configuration is written over the parameter link from the
landed contract map (`dsp4_driven_setup.py`): `MainOn`, `CtrOn`, `GrpOn`,
`AuxOn`, `AuxSend` = 1.0, `Mute` = 0 on every strip, and `CompOn`,
`GateOn`, `LimiterOn` = 1 with `CompThr`, `GateThr`, `LimiterThr` =
−60 dB on every dynamics node of both chips. The FX engines are left
alone deliberately: they are a separate question and switching them on
would not be comparable with the silent row it is subtracted from.

**The regime is PROVED before row C is taken.** `dsp4_c2regime.py
--require-driven` reads every envelope word on the chip and refuses
unless all of them are live. A driven row whose graph was quietly still
on the cheap branch is precisely the error this instrument exists to
end.

### What the three columns say

**The configuration costs chip 1 and almost nothing on chip 2.** Opening
every bus assign and every send (B − A) is +5.9 points at D24 and +9.6 at
D32 on chip 1, and +0.2 on chip 2 either way — which is what the graph
shape predicts: the crosspoint MACs are chip 1's, and chip 2's cost is its
own output chains whatever is arriving on them.

**The signal costs what the dynamics cost, and nothing else does.**
C − B on the shipping default is **+42.5 points on chip 1 and +29.3 on
chip 2** at D24, +56.9 and +32.7 at D32. On `s16_*` — the same graph with
COMPRESSOR and LIMITER on the LUT and the GATE on a linear threshold — the
same column is **+1.0 on chip 1 and 0.0 on chip 2** at D24, and +0.8 and
+0.1 to +0.4 at D32. That is the LUT's whole claim, measured on the part in the graph:
**the above-threshold path costs the same as the below-threshold one.**

### The silence table pointed at the wrong pair

Ranked on silence, `blk` is the cheapest arm on the board and `s16` looks
like a 5-point regression:

| D24, chip 1 | silent | driven |
|---|--:|--:|
| `blk` | **70.5 %** — best | 118.9 %, 15.8 % of blocks missed |
| `s16` | 75.9 % — worst | **82.4 %, zero** |

The dynamics table is not an optimisation that costs 5 points at idle. It
is the difference between a desk that runs and a desk that drops one block
in six as soon as someone opens a fader.

### And the S16 decision table is not describing the staged pair

S16 records `s16_*` at **46.8 % / 55.2 %** (D24) and **60.3 % / 66.7 %**
(D32). Rebuilt from `shipping.config` plus its two switches — which is what
the staged pair carries — it reads **75.9 % / 94.7 %** and
**99.0 % / 115.3 %** at silence. The gap is not drift: those figures belong
to an arm that also carries `DSP4_STRIP_FUSED` and `DSP4_SIMD_DYN`, which
is `s16sd` in this table (48.1 % / 62.2 % on chip 1, against S16's 46.8 % /
60.3 %), plus `DSP4_C2_BQ_GRAPH=1` for chip 2's remainder — and S16's own
footnote names that last one. `shipping.config` names all three at 0, and
the staged `s16_*` pair is built with them off.

## 4. What ships

**D24: take `s16_*`.** 82.4–82.8 % of chip 1's budget and
94.4–94.6 % of chip 2's, driven, with the regime proved on both chips and
**zero missed blocks over 90,049 blocks per chip on each of two boots**.
`s16f_*` is indistinguishable from it in cycles (within 0.7 points on
chip 1 and 0.2 on chip 2, which is the spread between its own two boots) and buys the six-slot biquad for nothing measurable, so it is
the better of the two if its numeric arm is otherwise acceptable. Chip 2's
margin is 5 points and that is the number to watch, not chip 1's 17.

**D32: nothing that was staged before today fits, and `s16sd` does.**
`s16_*` at D32 is 109.5 % / 115.5 % driven with 8.7 % and 13.3 % of blocks
missed — and it misses them at SILENCE too, so this is not a dynamics
problem: chip 2 is over budget at D32 before any signal arrives.
`DSP4_STRIP_FUSED=1 DSP4_SIMD_DYN=1` on top of `s16_*` reads **71.3 % /
93.9 % driven with zero overruns**, and that is the only configuration
measured on this bench that fits D32 under load.

**But `s16sd` is not a recommendation this session can make.** It carries
`DSP4_SIMD_DYN`, and what stands against it is unchanged and is PW's call,
not a capacity question: S12-5's finding that chip 2's paired biquads do
not reach the audio (which is why `DSP4_C2_BQ_GRAPH` stays 0 here and why
this arm is 20 points more expensive on chip 2 than S16's row), and
S12-7's — that `DIAG_BUILD_CFG2` cannot see `DSP4_C2_BQ_GRAPH`, so the two
images read back the same word and differ in audio. What S19 adds is that
the alternative is no longer "D32 fits without it at 112.7 %": **D32 does
not fit without it under load by 15 points on chip 2 and 10 on chip 1.**

**`s18_*` is orthogonal and stays orthogonal.** It is a BYTES lever
(−38,634 of chip 1's code pool) and it costs 0.7 points, driven exactly as
silent (119.6 % against `blk`'s 118.9 % at D24). It neither helps nor hurts
the fit and can be combined with any row above.

**Recommendation in one line: ship `s16_*` (or `s16f_*`) for D24 now, and
treat D32 as blocked on the `DSP4_SIMD_DYN` audio question rather than on
capacity — because on driven numbers that switch is not an optimisation,
it is the difference between fitting and dropping one block in eight.**

### Every earlier figure in the window note is a silence figure

The window note's capacity paragraph has been rewritten on driven numbers
and every figure carried over from before today is labelled `(silence)`.

both arms of its own A/B, and could not say why. It can be said now,

**Three of the four arms read a capture point the graph does not write,
and the fourth is the one that produced numbers.** That is exactly the
shape S18 reported: `the injection is NOT reaching _buf_C1_DLY_01`, `the
negative control cannot separate`, and one arm (COMP) that got far enough
to disagree on 70 of 96 samples.

**So the bar is wrong and the audio is not.** The signal is demonstrably
present at every stage of the strip — `_buf_C1_GAIN_01`, `_gate_gain`,
`_comp_gain` and `_tap_post_fader` all carry it — and it is the per-node
one-word scalars of the classes whose block kernels keep their
intermediates in the block pool that are never written. Since when: since
`DSP4_BLOCK_KERNELS` landed, which is S12-2's class of defect appearing in
a bar for the third time.

**Not fixed here.** The fix is to move `goldnode`'s capture points onto
words the block-kernel graph writes — the `_tap_*` taps and the pooled
block buffers rather than `_buf_<nid>` — and that is a rewrite of the bar's
capture layer, not an afternoon's edit. It is now a known defect with a
named mechanism instead of an unexplained FAIL on the shipping image.
