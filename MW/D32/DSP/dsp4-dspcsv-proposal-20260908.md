# DSP address file — proposal for `defs/products/{d24,d32}/dsp.csv`

**Session:** 2026-09-08, desk only, no bench.
**Contract pin:** `defs-v2026.09.08` (`b0e4b487`), unchanged by this work.
**Ruling:** PW 2026-09-08 #5 — the DSP address file is PROPOSED by this repo
and LANDED by the hub at the gate.

Deliverables in this repo:

| file | rows | what it is |
|---|---|---|
| `proposals/defs/products/d32/dsp.csv` | 5,358 | every D32 cell that reaches a DSP address |
| `proposals/defs/products/d32/dsp-unmapped.csv` | 1,590 | every D32 cell that does not, with the reason |
| `proposals/defs/products/d24/dsp.csv` | 3,698 | every D24 cell that reaches a DSP address |
| `proposals/defs/products/d24/dsp-unmapped.csv` | 1,248 | every D24 cell that does not, with the reason |

Both pairs are GENERATED by `MW/D32/DSP/gen_dsp.py` from the DSP4 node graph
and are regenerated by `./regenerate-dsp-contract.sh`. Nothing in them is
typed.

## 1. The invariant, which is the point of the deliverable

For each product, before either file is written:

```
rows(dsp.csv) + rows(dsp-unmapped.csv) == cells(<p>-mx-master.csv expansion)
5358 + 1590 == 6948   (D32)
3698 + 1248 == 4946   (D24)
```

There is no third bucket. A cell family that is in neither file **stops the
generator** (`_UNMAPPED_REASONS`, no-fallback), and a graph node that holds an
SPI address and reaches no cell **stops the generator** unless
`_UNREACHED_REASONS` says why. S1 could report 1,011 cells as "no DSP mapping
(MCU-only or unmapped)", which is indistinguishable from "nobody looked"; that
sentence can no longer be written.

The written `dsp.csv` is then **read back** and compared against the address
table it was written from (`verify_proposal_roundtrip`): 5,358 and 3,698 rows
identical. The file is a definition the hub can land and everything downstream
can read, not a report about one.

## 2. ONE address map, two products

Decision D3 (`dsp4-architecture-decisions.md`) binds one stable DSP address map
across D24 and D32. The proposal honours it by construction rather than by
convention: the **superset graph is expanded once** and each product's file is
the intersection of that expansion with its own cell set.

- 3,658 cells appear in both files. **Address disagreements: 0.**
- 1,700 cells are D32-only (channels 25–32, aux 9–12, the snake returns).
- 40 cells are D24-only — the whole of `MainCtr`, which D24's def reaches
  through `main.ctr,1` and D32's does not.

D24's own `MW/D24/DSP/SHARC/dsp.csv` was **not** used to derive D24's
addresses, and that is deliberate. It is the lagging legacy tree — 201 nodes,
32 channels of gain/EQ/comp, one reverb, a stereo master EQ+limiter, no
faders, no routing, no aux, no groups, no meters, no crossover — and deriving
D24's addresses from it would create exactly the second address map D3
forbids and defs S1 spent a session deleting.

## 3. S1-1: the main section

PW confirmed the model mid-session (hub relay, 2026-09-08). The four chains
the graph builds off `C2_MAIN_XOVER` are the four output strips, in DAC order:

| graph chain | output | master strip | D24 | D32 |
|---|---|---|---|---|
| `C2_MAIN_OEQ_01` → `OCOMP_01` → `OLIM_01` → `OUT_01`, meter `C2_MTR_MAIN_01` | DAC_13 | `MainL` | ✓ | ✓ |
| `C2_MAIN_OEQ_02` → `OCOMP_02` → `OLIM_02` → `OUT_02`, meter `C2_MTR_MAIN_02` | DAC_14 | `MainR` | ✓ | ✓ |
| `C2_MAIN_OEQ_03` → `OCOMP_03` → `OLIM_03` → `OUT_03`, meter `C2_MTR_MAIN_03` | DAC_15 | `MainCtr` | ✓ | out of scope |
| `C2_MAIN_OEQ_04` → `OCOMP_04` → `OLIM_04` → `OUT_04`, meter `C2_MTR_MAIN_04` | DAC_16 | `MainSub` | ✓ | ✓ |

`Main[1-1]` is the stereo mix-bus strip: `C2_MAIN_FDR` (Level, Mute),
`C2_MAIN_GEQ` (Geq 1–28), `C2_MAIN_DLY` (Delay), plus CueSel/Name/Dca which
are host-side. `C2_MAIN_XOVER` carries CrossoverFreq/CrossoverSlope for all
four output strips at its one address — many cells to one word, the normal
shape here.

**The ruling is corroborated by defs itself, not only relayed.**
`defs/tools/def_master.py` gates `MainL`/`MainR` on the `main` scope,
`MainCtr` on `main` + `main.ctr`, and `MainSub` on `sub`; its `FUNC_GATES`
put Comp on `main.comp`, Limiter on `main.lim` and Crossover on `sub.xover`
for those strips; and the D24-only cell `Main001Out3Mode001` is gated on
`main.ctr` — an **out 3 mode** cell that exists exactly when the centre
output does. Output 3 is the centre.

## 5. The meter tap vocabulary was wrong about what the DSP writes

Every meter node meters ONE tap point and lays three float words at its base
(`dsp_codegen.py::gen_meter_fixed`, and the node ASM's own comment "the host
reaches the rest by offset"):

```
+0  _mtr_peak_<nid>   linear peak, the host contract
+1  _mtr_rms_<nid>    linear TRUE rms
+2  _mtr_gr_<nid>     gain reduction — declared and never written (defect 4)
+3  _mtr_st_<nid>[4]  the meter's OWN state (pk_lo pk_hi ms_lo ms_hi)
```

So `taps=` names meter WORDS, not tap points. Two things followed from
reading it as tap points:

1. **`taps=L;R` on the four main-output meters claimed a stereo pair.** The
   nodes are `ch_count=1` mono outputs and the masters give each output strip
   one `Mtr[1-1]`. The second cell was the RMS word wearing an `R` label —
   two of the 23 orphan cells S1 reported. Those four nodes now declare
   `taps=peak;rms`, and the other 23 meters — which declared nothing at all —
   declare `taps=peak`. `expand_meter` is now a vocabulary that refuses both
   an undeclared meter and an unknown tap name.

   **The RMS word keeps its dispatch entry and loses only its cell.** The
   first cut of this change dropped both, and that moved `chip2.ldr` — the
   SPI dispatch table is compiled in, so four table slots went null and the
   host lost a real measurement to fix a labelling mistake. The word exists
   and the kernel writes it; `_METER_TAPS` now distinguishes "no word" from
   "a word no cell names", which is the shape `FADER_PAN` already uses for
   the pan word on a non-Chan/Aux strip. With the dispatch kept, both images
   rebuild byte for byte.
2. **`comp_gr` has no word.** `Chan*CompMtr001` was being given base+3 —
   `_mtr_st[0]`, the meter's internal peak-hold state. A cell pointed at
   another variable's scratch is not reaching a DSP address, so CompMtr is
   now listed as `unbacked-meter` with that reason instead. The `gate_gr`
   word at +2 IS declared and still is not written; `GateMtr001` keeps its
   address with that stated in its `Notes`, because the word is real and
   the contract place for it is right.

A second defect was found and fixed while rewriting the expander: the first
version parsed the taps with `parse_params()`, which splits on `;` — the same
character that separates the taps. `taps=post_trim;post_fader;gate_gr;comp_gr`
came back as `{'taps': 'post_trim'}` and three of the four channel-meter
words vanished silently. `_parse_taps()` reads the list to the end of the
params or the next `key=`, whichever comes first.

**No image changed as a result.** `dsp_codegen.py` never reads `taps=` — it
is a `gen_dsp.py` input only. See §8.

## 7. Open questions for PW

**Q1 — the output strips have no fader, mute or delay.** `MainL`, `MainR`,
`MainCtr` and `MainSub` each define `Level`, `Mute` and `Delay`; chain N is
EQ + COMP + LIM only. 12 cells across the four strips reach no word. Adding a
`FADER_PAN` and a `DELAY` per chain is four faders and four delay lines on
chip 2, which is the tighter part at 83.16% — a capacity question, not a
desk one.

**Q2 — `Main001Out3Mode001` (D24).** The centre-output mode cell exists
exactly when `main.ctr` does, and `C2_MAIN_XOVER` feeds all four outputs
unconditionally. Nothing selects output 3's source. What are the modes?

**Q3 — `CtrOn` is the one place the model and the graph cannot both be
right.** Every channel defines `CtrOn[1-1]` (both products, including D32
which has no `MainCtr`), and its DSP word is `_rtg_sub_on_<nid>` — a
per-channel assign to the graph's `BUS_SUB` mix bus, which feeds the
`C2_SUB_*` strip the ruling retires. If there is no centre/sub mix bus, then
`CtrOn` has no destination; if `CtrOn` is real, then that bus is real and
outputs 3 and 4 are not simply crossover taps. **The cell keeps its address in
this proposal** — it is a crosspoint the graph implements and the masters
name — but one of the two has to give.

**Q4 — `Aux*PickOff*`.** The DSP's send pickoff is per crosspoint
(`Chan*AuxPick*`, 12 per channel). Is the aux-master `PickOff` a host fold
onto those, or does it want its own word?

**Q5 — `Chan*CueSel*` / `Main001CueSel001`.** The DSP has one monitor source
word (`Mon001InputSel001`). Is per-strip cue a host fold onto it?

**Q6 — `Chan*LcrOn*` (D32).** The router has `MainOn` and `CtrOn` and no LCR
divergence law.

**Q7 — the S1-2 families.** `Fx*DuckThr*` (6) and `PeqGain` (12 per main
output strip that carries it) became definitions again at
`defs-v2026.09.08`. The FX engine has `DuckOn` and `DuckSens` words and no
threshold; no node carries a parametric gain bank. They are listed as
`s1-2-no-behaviour`, deliberately not pruned — pruning is what caused S1-2.

**Q8 — `Main*EqHpf` funs 2–4.** `expand_eq_biquad` gives a non-`Main`
category one HPF (band 1); the masters give each output strip four. Is the
HPF band a per-strip choice?

**Q9 — `StereoWidth` has no declared default** on any FX engine, and its
kernel word has no initialiser (reads 0 until the host writes it).

# Amendment, 2026-09-08 (session 29): `CrossoverSlope`, and the 31-band GEQ

Two rows came out of the inert-families pass. This section is the
proposal for both; `MW/D32/DSP/gen_dsp.py` is what changes, and the
regenerated `proposals/defs/products/{d24,d32}/dsp.csv` is the artifact
the hub lands.

## A. `CrossoverSlope` — one word, and it is free

**The defect.** `MainCtr`, `MainL`, `MainR` and `MainSub` each carry a
`CrossoverFreq` AND a `CrossoverSlope`, and **all eight resolve to
0x0575**. The contract's own note says "shared crossover word". Measured
on the part 2026-09-08: writing 500 Hz and then a slope left
`0x00000018` — the integer 24 — sitting where a frequency belongs. The
kernel ignores an out-of-domain word rather than clamping it, so the
split stays where the last legal frequency put it and **the slope is not
settable at all**.

**ONE SHARED WORD, NOT ONE PER STRIP, and the crossover design is why.**
There is a single `CROSSOVER` node in this graph — `C2_MAIN_XOVER` —
feeding all four main outputs from one LP/HP split. The four
`CrossoverFreq` cells already alias one word for exactly that reason. A
slope that differed per strip would ask one filter pair to have two
orders at once; the four `CrossoverSlope` cells alias the one slope word
the same way, and the notes column should say so in the same words.

**LANDED 2026-09-09 AS `base + 1`, BUT NOT AT 0x0576** — the 31-band
GEQ re-layout in §B landed in the same proposal and moved
`C2_MAIN_XOVER` from 1397 to 1436, so the frequency is 0x059C and the
slope 0x059D. The reasoning below is unchanged; only the base is.
See `dsp4-geq31-relayout-20260909.md`.

The original analysis, against the 28-band map: the
crossover node's dispatch block is *nominally* twenty-four words but the
node only owns **four**: `C2_MAIN_XOVER` sits at 1397 and
`C2_MAIN_OEQ_01` at 1401, so the expander's `base+4 .. base+23` are
overwritten by the EQ that follows (that overlap is real and is filed as
S4-9). What the crossover actually holds is 0x0575–0x0578, of which
0x0576, 0x0577 and 0x0578 dispatch to nothing today — a write to one
raises an SPI error. The slope takes 0x0576. No address in either
product moves; the row count does not change; both files' round-trip and
the `rows(dsp.csv) + rows(dsp-unmapped.csv) == cells()` invariant hold as
they stand.

```
MainCtr001CrossoverSlope001,C2_MAIN_XOVER,CROSSOVER,2,1,1398,0x0576,rw,
    InstantCtl,Instant,0,0,Linear,Scalar,0=6/3=24/[Lin],shared crossover slope
                                    (and the same for MainL / MainR / MainSub)
```

**LAND IT WITH THE DESIGN, NOT BEFORE IT.** An address that the DSP does
not read is the disease this whole session has been unpicking — three
families whose parameters landed perfectly at symbols nothing consumed.
The DSP side is small and is specified here so the two can land
together:

| slope | what it is | what the node can do |
|---:|---|---|
| 24 | LR4 — two cascaded Butterworth sections, Q = 1/√2 | **shipping today**; both stages of a path identical |
| 12 | LR2 — one 2nd-order section, Q = 0.5 | the SAME five offset formulas with `1/(2Q)` at 1.0 instead of 0.7071, and the second stage of each path written as the compiled identity |
| 6 | 1st-order | expressible, but it is not a Linkwitz-Riley alignment: each path is 3 dB down at the corner, not 6, which is a different acoustic contract from the one the product ships |
| 18 | 3rd-order | not a Linkwitz-Riley alignment at any order; the LP+HP sum is not flat |

So 12 and 24 are honoured and 6 and 18 are **ignored, not clamped** —
the rule the frequency domain already uses, for the same reason. The
whole DSP change is a choice of one constant and whether the second
stage of each path is a copy or the identity; `xover_ref.py` gains the
same switch and `xoververify.sh` scores both slopes at every corner.

## B. The 31-band GEQ — the cells exist, the address space does not

`defs-v2026.09.08.3` lands `Geq[1-31]` for Aux/Main/Grp in the cell
master (D24 4,946 → 4,985 cells, fingerprint `3d41d5850df3`). **It does
not add DSP addresses, and it could not have.**

`defs/products/<p>/dsp.csv` is generated from the DSP4 node graph, and
in that graph **a GEQ node's address block is exactly its band count**:

```
   28  C2_AUX_GEQ_01   GEQ        <- 28 words
   56  C2_AUX_AFB_01   ANTI_FB    <- starts immediately after
   80  C2_AUX_LIM_01   LIMITER
```

There is no slack. Three more bands per GEQ node is **+3 words on
seventeen nodes = +51 words on chip 2**, and because the blocks are
packed end to end, **every chip-2 address above 28 moves.** That is not
a row; it is a re-layout of the chip-2 map, and it invalidates every
cached address in every host that has one.

It is also not free in cycles. Each GEQ node gains three biquad stages
in a cascade that runs unconditionally every block, on seventeen nodes —
and chip 2's margin with the FX reverb running is now measured at
**5.98 %** (`dsp4-fx-afb-20260908.md` §0). The 31-band graph can be
generated today (`gen_dsp_csv.py --geq-bands 31`) and measured by
`sigprofile2.sh` through `DSP_CSV`; **that measurement is the gate on
this change, and it was not taken in this session.**

What this repo can say now:

* the design is already band-count generic and is checked at all 31 ISO
  bands in `geq_ref` (`f_i = 1000·10^((i−17)/10)`, 19.95 Hz – 19,953 Hz);
* `dsp_codegen.py` emits `_geq_band_<N>` for whatever band counts the
  graph instantiates, so the tables follow the graph with no edit;
* nothing else in the DSP needs to change.

**The proposal is therefore a sequence, not a row**: (1) measure the
31-band graph at block 16 against the shipping one on one instrument in
one session; (2) if it fits, regenerate the graph at `--geq-bands 31`
and let `gen_dsp.py` re-lay the chip-2 map; (3) land the resulting
`dsp.csv` at a gate, with the address move called out, because it is the
first time this contract has moved an address rather than added one.

**DONE 2026-09-09, steps (2) and (3) — and step (1) is reported with
them rather than ahead of them, because the address map and the cost are
answers to different questions and only one of them was ever going to
block.** `--geq-bands 31` is now the generator's DEFAULT (the 28-band
map is reproducible with `--geq-bands 28`, which is how the two were
diffed row for row). The counts, what moved, and what every host has to
do about it are in `dsp4-geq31-relayout-20260909.md`; the measured cost
is in this session's status line in `tasks.md`.
