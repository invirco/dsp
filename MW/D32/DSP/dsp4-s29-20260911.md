# S29 — what D32 pays for scope class 0, and the latency bar

Session 29, 2026-09-11. Bench: rev C unit, `app@192.168.1.219`.
Image under test: the window candidate `shipping.config.s26`
(`chip1.ldr 6396187c`, `chip2.ldr 9222c2ee`), rebuilt byte for byte at the
top of this session.

---

## 1. Gate 1 — scope class 0, named

### 1.1 What the class IS

**Scope class 0 is product function, not an instrument.** It is the D32's
digital snake return path, and it is reachable from cells the app writes,
on the gated contract, with a physical lane behind it.

The class is `CFG_PRODUCT_ID` = 0 (`_product_id`), and the graph carries
exactly **34 scoped nodes** of 698 — 32 in class 0 (`scope=D32`) and 2 in
class 1 (`scope=D24`):

| chip | class | type | n | nodes |
|---|---|---|--:|---|
| 1 | D32 | `INPUT_TDM` | 8 | `C1_XIN_SNK_01..08` — SPORT 5, slots 0–7 |
| 1 | D32 | `INTERCHIP_SEND` | 8 | `C1_XS_XFER_SNAKE_01..08` — global mix slots 29–36 |
| 2 | D32 | `INTERCHIP_RECV` | 8 | `C2_XR_SNAKE_01..08` — the same slots |
| 2 | D32 | `AUX_INPUT` | 8 | `C2_SNK_IN_01..08` — summed into `C2_MIX_MAIN_L/R` |
| 2 | D24 | `OUTPUT_TDM` | 2 | `C2_MON_OUT`, `C2_CODEC_AUX_OUT` |

It is 16 nodes a chip, and the D32 half of it is one unbroken signal path
from a connector to the main bus:

```
  CAT6 snake  ->  A_I5 (TDM8, SPORT 5, slots 0-7)   8 x SNAKE_RET_nn
              ->  C1_XIN_SNK_nn        chip 1 input kernels
              ->  C1_XS_XFER_SNAKE_nn  MIX_1 slots 13-15 / MIX_2 slots 0-4
              ->  C2_XR_SNAKE_nn       chip 2, global mix slots 29-36
              ->  C2_SNK_IN_nn         AUX_INPUT, level + on
              ->  C2_MIX_MAIN_L, C2_MIX_MAIN_R
```

### 1.2 The cells the app writes

**Sixteen D32 cells are dispatched to these nodes, and every one of them is
in the GATED contract** — `defs/products/d32/dsp.csv`, not a proposal:

| cell family | n | node | page | addr | mode | ramp |
|---|--:|---|--:|--:|---|---|
| `Snk[1-8]On[1-1]` | 8 | `C2_SNK_IN_01..08` | 1 | 1862, 1864 … 1876 | `rw` | `InstantCtl` |
| `Snk[1-8]Level[1-1]` | 8 | `C2_SNK_IN_01..08` | 1 | 1861, 1863 … 1875 | `rw` | `GainFast`, `0=-20/127=6/[Lin]` |

They exist in `defs/common/cells/mx_master.csv` (lines 252–253) and in
**`defs/gen/matrix/d32-mx-master.csv` ONLY** — `grep -ci snk` returns 0 for
the D24, D16 and D12 masters. They are D32's because the D32 product def
says `io.snake,1` (`defs/products/d32/d32.csv:65`) and no other product def
does.

The hardware agrees. `shared/dsp4-logic/tdm-lines.csv` line 7 gives
`A_I5,I5,,SNAKE,TDM8,8,CG2,,D32,ok,"D32 snake return; unused on D24"`, the
CPLD top level routes `i_dspa[5] = strap_d32 ? snake_in : 1'b0`, and
`B_O2` carries `SNAKE_OUT_01..08` on the way back out. The class is a
connector on the product, a lane in the LOGIC, 16 cells on the contract and
32 nodes in the graph.

**So the answer to gate 1's question is the one that makes the cost real**:
the snake IS MW-Net, D32's two-piece stage-box link (the D32C/D32R CAT6
snake of the product manual, up to 46 m), and D32 is the only product in
the range that has one. If it cost cycles, the product pays for them.

### 1.3 How the class is gated, exactly

`_product_id` is read in exactly two places, and nowhere else in the
firmware:

1. **`_scope_gates_apply`** (`chip2/scope_gates.asm`, generated): an
   8-entry table that force-zeroes `_auxin_on_C2_SNK_IN_01..08` at
   CONFIG_COMMIT when the booted class is not 0. Chip 1's table is
   **empty** — `_scope_gate_count = 0` — because the generator's
   `ENABLE_SYMS` only knows `AUX_INPUT`. On its own this gate would be
   nearly free, and would also be nearly pointless: all eight of those
   nodes carry `on=0` in `dsp.csv` and come up off.
2. **The chain's RUN gates** (`chip{1,2}/process_chain.asm`, under
   `DSP4_BLOCK_KERNELS && DSP4_SCOPE_GATE`, both 1 in
   `shipping.config.s26`). This is the one that costs. The scoped nodes are
   contiguous in call order, so the generator emits **one compare and one
   branch per RUN** rather than a per-node skip table — a per-node table was
   measured on the part on 2026-08-24 and was a net loss (244,795 against
   243,235 cycles/block). Six runs are emitted on chip 1 and twelve on
   chip 2 across the strip-ordered and pair-ordered chains; in any one
   chain it is two runs of 8 a chip for class 0, plus two runs of 1 on
   chip 2 for class 1:

   ```
   #if DSP4_BLOCK_KERNELS && DSP4_SCOPE_GATE
       /* nodes 294..301 are D32-only */
       r2 = dm(_product_id);
       r3 = 0;
       comp(r2, r3);
       if ne jump (pc, .bqgrun0_end);
   #endif
   ```

**Booting a D32 with `CFG_PRODUCT_ID = 1` therefore skips the CALLS to 16
chip-1 nodes and 16 chip-2 nodes, and adds the calls to 2 chip-2 nodes** —
`C2_MON_OUT` and `C2_CODEC_AUX_OUT`, which a D32 skips and a D24 runs. That
is the arm gate 2 measures, and it is one config word.

### 1.4 What the class does NOT gate, and it matters for reading S28-6

The gate is on the CALL, not on the LINK. Every one of the 34 scoped nodes
is assembled, linked and present in both images whatever the class word
says — S28's code-pool finding one level down: *a smaller product buys
cycles, not memory.* Chip 1's code pool is 180,954 of 262,144 bytes and
chip 2's 164,168 on every product of the range, and gating scope class 0
off does not move either by a byte.

It also does not gate anything a matrix cell can reach. The eight
`C2_SNK_IN_nn` come up with `on=0` in `dsp.csv`, and
`dsp4_driven_setup.py`'s `FAM_CLASS` filter deliberately excludes them from
the `On` family it writes (*"an unfiltered `On = 1` would … open eight snake
inputs and the Pi/USB/BT feeds, none of which is the plugin load being
priced"*). **So in every capacity row this programme has taken, on every
product, the snake AUX_INPUT bodies have been on their cheap branch.** What
the D32 pays for is 32 nodes being CALLED, not 8 aux inputs doing work.

## 2. Gate 2 — measured, on the part

### 2.1 The arm, and what makes it one word

**ONE IMAGE, TWO CONFIG WORDS.** Both arms are the window candidate,
`shipping.config.s26`, rebuilt at the top of this session and **byte for
byte** what `window-candidate.md` quotes and what `~/dspboot/s26_*` holds:
`chip1.ldr 6396187c`, `chip2.ldr 9222c2ee`, 425,668 and 407,584 bytes. The
second arm boots the *same staged image* — not a rebuild of it — so nothing
but `CFG_PRODUCT_ID` can differ.

| | control (`s29ctl`) | scope-off (`s29ns`) |
|---|---|---|
| `CFG_PRODUCT_ID` | **0** (D32's own) | **1** (the class every other product boots) |
| `CFG_CHAN_MASK` | `0xFFFFFFFF` | `0xFFFFFFFF` |
| `CFG_AUX_MASK` | `0x00000FFF` | `0x00000FFF` |
| `CFG_OUT_MUX` | 1 | 1 |

**reads `DIAG_PRODUCT_ID` (0xE010) back off BOTH CHIPS and prints it**, so
an arm that claims to have gated the snake off says so in the part's own
words:

```
    chip 1: PRODUCT_ID (scope class) = 0
    chip 2: PRODUCT_ID (scope class) = 0
```

Bench: `driveall` LOGIC (`e13b5dec84e0`), IDCODE `0x020a30dd` before and

**SIX ROWS ON ONE BOOT, WHICH NEEDED AN INSTRUMENT FIX (S29-1).** Until this
session no arm had ever set `FXTYPES` and `USELEVELS` together, and the two
ladders do not compose: the FX ladder's `off` rung leaves the six engines
OFF, and `--mode use` writes crosspoint families only. A boot that ran both
would have taken S24's worst-use rung with the plugin load absent — which is
not the row S24 measured and not the row that overruns. `capacity_run.sh`
now RE-APPLIES the load between the two ladders and re-proves the regime,
and says so in the log. Witnessed on every boot: `chip 1 loadfx: 1632
written, 0 FAILED`, `6 of 6 engines on, Type [3], 6 of 6 comb delay lines
carrying signal`. An arm that sets only one of the two variables is
untouched, so no row already in the record moves.

### 2.3 Why this is a measurement and not a night

Three things make the 3.5 points real:

1. **The control arm reproduces the record to the block.** S27 and S28 read
   D32 chip 2 at 100.81 and 100.82 driven with the load, missing **1,943** of
   270,000; S29's control reads **100.75** and misses **1,943**. Row B's
   1,912 against S28's 1,914. Three different nights, the same image, the
   same count.
2. **The resolution is ±0.27 points**, established by S28 re-measuring both
   anchors on one night over sixteen comparisons. 3.43 is thirteen times it.
   Chip 1's 0.22–0.61 is nearer the floor and is quoted as the smaller,
   softer number it is.
3. **The two arms are the same bytes.** Arm 2 ran `BUILD=0` against arm 1's
   staging directory, so it booted the identical `chip1.ldr` / `chip2.ldr`
   the control had just been measured on. The only difference that reached
   the part is `0xF000`, and both chips were asked what they got.

### 2.4 S28-6 is confirmed, by measurement instead of by a line

S28 inferred this step from four points and a slope, and said so carefully:
the D24→D32 segment is dearer than the two below it, and the suspect is the
scope class. The prediction and the measurement:

| | S28's segment excess | S29, measured |
|---|--:|--:|
| chip 2 | (3.29 − 2.36) pts/aux × 4 aux = **+3.7** | **+3.53** |
| chip 1 | (1.82 − 1.755) pts/strip × 8 strips = **+0.5** | **+0.40** |

**So the "dear last segment" IS scope class 0, and the two-anchor
construction's under-prediction of D12 and D16 has its named cause.** The
construction in `tools/dsp/product_fit.py` interpolates a line through D24
and D32 that carries a step it should treat as a constant; a corrected
construction subtracts 3.53 / 0.40 from the D32 anchor before taking the
slope. That is a change to the CONSTRUCTION and not to any measured row, and
it is not made in the session that measured it — the same discipline S21-6
used on its own tick defect.

### 2.5 What the 3.5 points ARE, and the lead they open

3.53 points of chip 2 is 11,570 cycles a block, 723 a sample at block 16,
across **16 nodes** — eight `INTERCHIP_RECV` and eight `AUX_INPUT` — so
about **45 cycles a sample a node**. Chip 1's 0.40 points is 1,310 cycles a
block over its own 16 (eight `INPUT_TDM`, eight `INTERCHIP_SEND`), about 5 a
sample a node, which is roughly what a slot copy costs.

**The chip-2 half is the expensive half, and every one of those eight aux
inputs is SWITCHED OFF while it costs that.** `C2_SNK_IN_01..08` carry
`on=0` in `dsp.csv`, nothing in any capacity row turns them on
(`dsp4_driven_setup.py`'s `FAM_CLASS` filter excludes them deliberately),
and they still cost what they cost — because the price is being CALLED, not
doing work. That is exactly the shape S23-5 and S24 found one level up, where
an aux bus with all-zero coefficients was paying 0.82 points until it got a
block-level bypass, and it is the obvious next lever: **an AUX_INPUT whose
`on` is 0 should be skipped at the chain, the way a scoped node is.** On this
measurement that is worth up to ~3.5 points of chip 2 on a D32 whose snake is
idle — and D32 chip 2 misses fitting by **0.81 points**.

That is a LEAD, not a result. It is not taken here: it changes the shipping
image inside the release window, and this session's mandate was to price the
class, not to re-cut it.

## 3. Gate 3 — the consequence, stated for PW

### 3.1 Scope class 0 is product function, so the ruling stands

**D32 chip 2 does not fit at worst use, and the window candidate should be
signed with that on the record, unchanged.** The candidate reads **100.81 %
of budget with 1,943 of 270,000 blocks missed (0.72 %)** at twelve auxes fed
— S24's finding, S27's, S28's and now S29's, four measurements on three
nights that agree to the block.

The tempting sentence this session could have written — *"gate the snake off
and D32 fits"* — is **not available**, and gate 1 is why:

* the snake is `io.snake,1` in the D32's own product definition;
* it is **16 cells on the gated contract** (`Snk[1-8]On`, `Snk[1-8]Level`,
  mode `rw`) that the app writes and the desk exposes;
* it is a **connector and a lane**: `A_I5` in the CPLD, `strap_d32` selecting
  it, `B_O2` carrying the return;
* it is the **D32C/D32R stage-box link** — the product ships as two boxes
  joined by one CAT6 up to 46 m, and the snake IS that link.

A D32 with scope class 0 gated off is not a cheaper D32. It is a D32 with no
stage box, which is not a D32.

### 3.2 What it does for the user, in one line

**Eight channels of digital snake return from the D32R stage box, mixed into
the main bus with their own level and on/off per channel** — the return leg
of the two-piece design, and the only product in the range that has one.

### 3.3 What PW is actually being told

1. **The price of the snake is now known and it is 3.5 points of chip 2.**
   It was never in the budget as its own line; S28 found it hiding inside a
   per-aux slope and S29 has weighed it.
2. **It is the whole of D32's deficit and more.** Chip 2 misses by 0.81
   points at worst use; the snake costs 3.43.
3. **The remedy is not to remove the function.** It is to stop paying for
   idle nodes — §2.5's lead — and that is a cycle-budget question for after
   the window, not a product question.
4. **Nothing in this session changes `shipping.config`, `.s21` or `.s26`.**
   The candidate PW has been asked to sign is unchanged, and no cell,
   address, `defs` pin or config word moved.

## 4. Gate 4 — the latency bar, restored

### 4.1 The break was the duplex overlay, and the DSP was innocent

S27-7 read four buffers at the END of the main chain, found a constant
`0xfffffffc` at all four, and concluded the stimulus was not reaching the
DSP's input — *"the break is upstream on the playback side"*. **Reading the
end of a dead chain tells you it is dead, not where it died.** S29 wrote
`tools/pi/dsp4_s29_playpath.py`, which walks every stage of the playback
path on both chips, with the stimulus ON and OFF, and calls a stage live only
if it moves when playing and does not when silent:

```
  pcm_tdm -> i_dspa[6] -> C1_XIN_PI_L/R -> (inter-chip slots 27,28)
          -> C2_XR_PI_L/R -> C2_PI_IN -> C2_MIX_MAIN_L/R
          -> C2_MAIN_FDR -> C2_MAIN_DLY -> C2_MAIN_ST_OUT -> B_O3
```

Run on the `driveall` bitstream and again on **`maincap` — the very
bitstream S27 used** — under the standing `dsp4-pcm-slave` overlay:

**THE WHOLE PLAYBACK CHAIN IS LIVE, EVERY STAGE, BOTH BITSTREAMS.** Each
stage reads `0x0fffffff` / `0xf0000000` (the full-scale square) while
playing and a constant while silent, right through to `C2_MAIN_ST_OUT`, the
lane the capture reads. The two negative controls held: `_buf_C1_IN_01` (an
ADC lane) and `_buf_C2_RECV_MAIN_L` (chip 1's 32-strip bus, which the
pass-through setup silences) are **dead at `0x00000000` in both states**, so
the signal is arriving by the Pi path and not leaking in from the strips.

**So the playback side works and has worked. What S27 changed, and what
broke, was the PCM overlay.** S27 flipped the bench to `dsp4-pcm-duplex` on
S12-10's advice, ran the arm there, and got the null. S17 had already
established the true requirement and recorded it: under the slave overlay the
card exposes capture on device 0 and playback on device 1, and
`dsp4_dsp_latency.py` drives them separately. S12-10's "needs a duplex
overlay" was wrong when it was written; S17 fixed the tool without retiring
the claim, and S27 followed the claim back into a null. **The bench needed no
overlay flip, this session took none, and the tool's own refusal message
still names the duplex overlay as a requirement — it should not.**

### 4.2 The bar, measured on the window candidate

`maincap` flashed (`d903ae1ac4a9`, FLASH OK attempt 1, IDCODE `0x020a30dd`
before and after), the staged window-candidate pair booted from
`/home/app/dspcap/s29ctl`, pass-through setup applied, `latency.sh` with

| LOGIC only, the CPLD loop reference | `pisel` `bd9c100db7c2` | 1 × 20 | **14433** | 15 | **100.0 %** | 4 |
| **window candidate `s26`** | `maincap` | 3 × 20 | **14515 / 14515 / 14514** | 11 / 16 / 13 | **100.0 %** | 1 |

**Coherent fraction 100.0 % on all 80 reps**, against S27's 0.0 % on every
rep of every arm. Through-DSP latency is the difference against the CPLD
loop, because the absolute offset carries the `arecord` pre-roll and the ALSA

| boot | samples | ms at 48 kHz |
|---|--:|--:|
| 1 | **82** | **1.708** |
| 2 | **82** | **1.708** |
| 3 | **81** | 1.688 |

**THE CONTRACT FIGURE OF 82 SAMPLES / 1.708 ms NOW BELONGS TO THE WINDOW

### 4.3 The control, and that it can fail

The LOGIC-only reference is the control and it discriminates: it sits **82
samples below** the DSP arm and its peak width is **4 against 1**, so the two
arms are not the same measurement with a different label. It can fail, and
during this session it **did** — the first attempt returned

```
  aplay -D hw:dsp4pcm,1 failed (rc 1): audio open error: Device or resource busy
  A capture with no stimulus in it is not a latency.
```

because the playback device was still held by the probe's own stimulus. **The
instrument refused rather than scoring a silent capture**, which is S17's fix
doing exactly what S12-10 needed it to do.

## 5. Findings

* **S29-1 — the FX ladder and the USE ladder could not share a boot, and
  nothing said so.** `capacity_run.sh` runs the FX ladder first; its `off`
  rung leaves the six engines off, and `--mode use` writes crosspoint
  families only. Any arm setting both `FXTYPES` and `USELEVELS` would have
  taken S24's worst-use rung with the plugin load absent and called it worst
  use. No arm had ever set both, so the defect was latent rather than
  wrong-in-the-record. FIXED: the load is re-applied and the regime re-proved
  between the two ladders, with a line in the log. Arms that set one variable
  are untouched.
* **S29-2 — scope class 0 costs chip 2 3.43–3.69 points and chip 1
  0.22–0.61, flat across six regimes, and it is the whole of D32's
  deficit.** Measured as one config word on one image, two boots an arm.
  Every overrunning D32 row runs clean without it. It is PRODUCT FUNCTION
  (the D32R stage-box snake, 16 cells on the gated contract), so the product
  cannot decline to pay it, and the worst-use ruling stands.
* **S29-3 — S28-6's mechanism is confirmed.** The "dear last segment" of the
  four-product construction is scope class 0 and not strips or aux buses:
  predicted +3.7 / +0.5 from the segment slopes, measured +3.53 / +0.40.
  `tools/dsp/product_fit.py` should subtract the class from the D32 anchor
  before taking its slope; NOT done in the session that measured it.
* **S29-4 — eight aux inputs that are SWITCHED OFF cost 3.5 points of chip
  2.** The chip-2 half of the class is eight `AUX_INPUT` nodes with `on=0`,
  and the price is being called, not doing work — the S23-5/S24 bypass
  finding one node class down. A `on == 0` skip at the chain is worth up to
  ~3.5 points on an idle D32 snake, against a 0.81-point deficit. A LEAD;
  not taken inside the window.
* **S29-5 — the latency null was the duplex overlay, and S12-10's
  attribution has been wrong since S17 fixed it.** The playback chain is
  live end to end on both `driveall` and `maincap` under the standing SLAVE
  overlay, proved stage by stage with a silent control and two negative
  controls. S27 flipped to duplex on S12-10's advice and inherited a null
  that the tool's own refusal message still recommends. The refusal text
  ("the through-DSP arm needs the `_maincap` bitstream AND a duplex PCM
  overlay") is half right and should lose its second clause.
* **S29-6 — the through-DSP latency contract is MEASURED on the window
  candidate: 82 / 82 / 81 samples over three boots**, 100.0 % coherent on
  all 80 reps, against the `pisel` CPLD-loop reference at median 14433. S20's
  82 samples was carried on an argument; it is now the candidate's own
  number.
* **S29-7 — `s20restore.sh` cannot clear `blk_*`'s counters, so its overrun
  figure is a boot-transient and reads the same every time.** Two passes
  returned chip 2 at **exactly 2,240** of 90,049, and the tool says in the
  same breath that the `_proc_cyc_max` latch did not drop, because `blk_*`
  predates `DIAG_CLEAR`. An identical count on two independent boots is a
  fixed startup accrual, not a measurement of the dwell. See §6.

* **It took three restore passes again, and the reason is now named
  (S29-7).** Passes 1 and 2 both reported chip 2 at **exactly 2,240 overruns
  of 90,049** — the same count S28's pass 1 reported. An identical figure on
  two independent boots is not a dwell measurement: `blk_*` predates
  `DIAG_CLEAR`, the tool says so in the same output (*"THE LATCH DID NOT
  DROP"*), and the count is a fixed boot-transient accrued before the dwell
  starts. Pass 3 read 0 and 0. **The restore ladder is not flaky so much as
  unreadable on this pair**, and `s20restore.sh` quotes a number it cannot
  clear.
* **`matrix-app` is active and it has NOT announced an MCU — this is
  carried, not smoothed.** Five restarts, **0 of 3 H1S announce lines every
  time**, against S28's 3 of 3 on the first restart. The app is running and
  holds `/dev/ttyAMA0`, and its journal carries no MCU text at all. This is
  the MCU/app side and not the DSP: every DSP witness above is clean. It is
  worse than the ~1-in-4 race S27-6 documented and filed against mx26 B13,
  and it wants a session with the MCUs rather than a corner of this one.
* **No staged pair was replaced, and none was added.** All of `s20_*`
  through `s28_*` verified by md5 against S28's list — unchanged, every one,
  including `s26_chip1.ldr` `6396187c…` / `s26_chip2.ldr` `9222c2ee…` and

* **No deploy.** `shipping.config`, `shipping.config.s21` and

* **`fit-table.csv` is NOT regenerated.** D32's measured rows reproduce S28's
