# S16 — the last link and the new wall: the code pool read by symbol, the audio verdict on the table, and the LIMITER on it

Session S16, 2026-09-10. Bench: rev C unit, shipping CPLD
`a1f6672af6c3`, `dsp4-pcm-slave`. Contract `defs-v2026.09.08.4`,
unchanged. `shipping.config` unchanged.

**Every switch in this session is off by default and the default build is
one image throughout: `20588957` / `a1509a2a`, before and after the
LIMITER work.** That is not S15's `6ebd0807` / `a3582da1`, and the whole
difference is the link ORDER §1 changes — every object contributes the
same code bytes, proved object by object, and the audio is proved by the
bars rather than by the md5.

---

## 0. What S15 left, and what this session was asked to close

S15 landed the level→gain table (`DSP4_DYN_LUT`) and the paired linear
gate threshold (`DSP4_GATE_LINTHR`), took chip 1 from 75.4 % to 60.3 % at
D32, and named two things it had not done:

* **the audio-domain verdict was not obtained** — `dsp4_comp_gr.py`
  returned its own refusal, and `famverify`'s witness was recorded as not
  fitting beside the paired kernels at all;
* **the LIMITER was not on the table**, which is why chip 2 sat at 76.6 %.

Both are closed. A third thing, which S15 could not have known, is closed
with them: **the lever was inert on chip 2 altogether** (§7).

## 1. The wall was a PLACEMENT, and nothing had chosen it

S15-8 read chip 1's code pool at 99.9 % with 244 bytes free and concluded
"the LDF's overflow tier is the last one; there is nothing behind it".
The first half is right. The second is not.

### The third tier existed, was in use, and was invisible

The LDF has carried a third code tier since 2026-09-09 — `sec_swco_ovf2`,
into whatever Block 1 has left after the DM overflow and the DMA
ping-pong buffers. On the `DSP4_DYN_LUT` arm it was already holding
**1,598 bytes of code**, and `dsp_memreport.py` counted those bytes
against *"DM data + stack"* because its code pool is Block 3 + Block 2
and nothing else.

So "code 99.9 %, free 228" was not the pool's state. It was two thirds of
it.

### Which bytes went there was decided alphabetically

The linker fills an output section in command-line order, and `build.sh`
built that order with `find | sort`. The objects that spilled into
Block 1 were therefore the ones whose names sort last:

| arm | what was in Block 1 |
|---|---|
| `DYN_LUT` | `meter_fx` — the per-block meter fold and `_gsimd_gain_blk`, the SIMD gain kernel |
| `DYN_LUT` + scope witness | `dyn_simd_fx` — **the SIMD dynamics kernel, the hottest routine in the graph** — plus `biquad_fx`, `dyn_lut_fx`, `dyn_fx` |

Block 1 is where the DM overflow and the DMA buffers live, so that code
fetches against DDE traffic every block. The arithmetic was exact. The
fetch was not free. And the choice was made by `sort`.

### What the pool actually holds

`tools/dsp/dsp_codepool.py` is new — the pool by object, by symbol, and
by node CLASS, across all three tiers, which is the reading that makes
the shape obvious. Chip 1, the `s16_*` arm, 263,448 bytes:

| | bytes | share | | each |
|---|--:|--:|--:|--:|
| node RTG | 40,256 | 15.3 % | ×32 | 1,258 |
| node COMP | 35,264 | 13.4 % | ×32 | 1,102 |
| node GATE | 34,304 | 13.0 % | ×32 | 1,072 |
| node FILT | 30,976 | 11.8 % | ×32 | 968 |
| node EQ | 21,248 | 8.1 % | ×32 | 664 |
| node FDR | 16,768 | 6.4 % | ×32 | 524 |
| node DLY | 16,384 | 6.2 % | ×32 | 512 |
| node TUBE | 12,480 | 4.7 % | ×32 | 390 |
| `dyn_pairs` (the fused pair drivers) | 11,040 | 4.2 % | | |
| node GAIN | 6,336 | 2.4 % | ×32 | 198 |
| `bq_pairs` | 5,670 | 2.2 % | | |
| everything else | ~33,000 | 12.5 % | | |

**Eighty-five per cent of chip 1's code pool is thirty-two copies of nine
kernels.** The instances are identical modulo their state symbols — a
diff of `C1_RTG_01.asm` against `C1_RTG_02.asm` is 546 lines of renamed
symbols and nothing else.

### The recommendation, and what was landed instead

The bytes that could leave without changing audio, in order of size:

1. **The per-node instances collapsed onto one shared routine per class**,
   parameterised by a state-block base in an I-register. The eight big
   classes are **207,680 bytes** between them and a shared routine plus a
   per-node stub would return most of it — RTG alone is ~38,000. This is
   the only lever with real room in it, and it is a generator project of
   its own: it costs indirect addressing and a call per node per block,
   which is exactly what S13 and S14 spent code to buy back. **Not
   attempted here. It is the recommendation.**
2. **Instrument-only code** — already handled: the selftests, shootouts
   and probes are behind switches that are off, and none of them link
   into a shipping arm. Nothing to reclaim.
3. **Dead paths behind off switches** — likewise none. The per-node
   `_process` bodies are NOT dead in the fused arm: `dyn_pairs.asm` calls
   them as the scalar fallback when a pair cannot form (one channel off,
   one sidechain filter on), and their `_process_sample` entry runs
   sample 0 of every block. They are live.

**What was landed is not a deletion at all.** The cold objects are named
in `build.sh` (`DSP4_COLD_OBJS`) and appended last, so the third tier
holds what should be there:

| chip-1 arm | Block 1 code, before | after |
|---|---|---|
| shipping default | 0 | **0** — inert |
| `DYN_LUT` | `meter_fx`, `xover_design_fx` — 1,598 B | the three design steps — 1,692 B |
| `DYN_LUT` + witness | `dyn_simd_fx` and the dynamics path — 7,634 B | boot, config, instrument, design steps — 7,702 B |

The list is `diag`, `spi_handler`, `scope`, `scope_gates`,
`product_config`, `cgu_init`, `sport_config`, `sport_init`, `dma_config`,
`sru_config`, `afb_design_fx`, `geq_design_fx`, `xover_design_fx` —
everything on it runs once per boot or once per parameter move, and
nothing on it runs per block.

### The audio is unchanged, and that is checked rather than argued

The instruction stream cannot have changed: no source moved, only the
order the linker saw the objects in. `dsp_codepool.py --diff` says so
per object — **every object contributes exactly the same number of code
bytes in both link orders, total delta +0** — and the bars say the rest:

| bar | result |
|---|---|
| `golden_harness` | **59/59** |
| `dsp_validate` | OK |
| `dyn_simd_inline_check` | **5 of 5 bodies identical instruction for instruction** |
| `bq_simd_pipe_check` | **BIT-IDENTICAL**, all three schedules |
| `dyn_lut_design.py --selftest` | PASS |
| `famverify`, 20 families, both chips | verdict for verdict against the shipping pair (§2) |

**The image md5 moves and the audio does not.** Default
`6ebd0807`/`a3582da1` → `20588957`/`a1509a2a`.

`dsp_memreport.py` now reports the third tier as a tier, names the
contended fetch, and points at `DSP4_COLD_OBJS`.

## 2. THE LAST LINK: the table's gain reaches the audio

### The witness fits

With §1's placement, the arm
`STRIP_FUSED + SIMD_DYN + GATE_LINTHR + DYN_LUT + SCOPE_BLK_TAP` links
with **8 bytes to spare in Block 2** and 7,702 bytes of cold code in
Block 1, and runs the whole 20-family walk. `famverify.sh`'s header,
which said it does not fit, is corrected in place.

The tap is still an instrument: some of its own code is in the contended
block by design, and no capacity number in this write-up comes from an
image built with it.

### famverify, verdict for verdict

Three walks on the same bench, same tap, same contract: the shipping
default, S15's `DYN_LUT` arm, and S16's arm with the LIMITER table.

| | shipping | S15 arm | S16 arm |
|---|---|---|---|
| COMPRESSOR | LIVE / **BIT_EXACT** | LIVE / **FAILED** | LIVE / **FAILED** |
| every other family (19) | identical | identical | identical |

**One verdict moves out of twenty, and it is the one that has to.**

### How far that FAILED is

`dsp4_node_verify.py` now reports the worst deviation in dB rather than a
count, because a count reads the same for a kernel that is wrong and for
a kernel that is a different ARM of the same arithmetic:

```
step  amp 0x0D3A17B5  model 0 of 96 bit-exact  negative control differs in 96 of 96
      worst deviation 0.00518 dB at sample 18 (part 37538308, model 37515935)
```

All six converted parameters match bit for bit. **0.00518 dB**, against
the table's own 0.0950 dB design bound and PW's 0.1 dB bar.

### dsp4_comp_gr.py, with a signal source

S15 recorded this tool's refusal and attributed it to "a capacity arm has
no signal source". It has one — the scope IS the signal source — and the
refusal had a mechanism, three defects deep (§S16-3). Fixed, on the LUT
arm:

```
BLOCK TAP: inject _rx_slot_C1_IN_01, witness _buf_C1_COMP_01, block 16
PARAMS thr=-30 ratio=8 att=0.5 amp=0x08000000
GAIN REDUCTION at the tail: -20.98 dB (settled 11986899 vs injected 134217728)
```

The static compressor law predicts **20.982 dB** of reduction for a
−6.02 dBFS step at −30 dB, 8:1. Measured **20.982 dB**. And against the
polynomial arm, sample for sample through the same injection:

| | |
|---|--:|
| samples compared | 64 |
| bit-identical | **43** |
| worst difference, in the attack | **0.00175 dB** |
| settled tail, polynomial | 11,986,899 |
| settled tail, table | **11,986,899** — identical |

### The gate's threshold, across the linear-domain compare

`dyn_state_bound.py` gained §6, which measures the shift instead of
asserting it: for each threshold the wire can carry, the smallest
envelope each arm opens on — the log arm by search over `log2_q`, the
linear arm from `gate_thr_lin_q` — using the polynomials the part runs.

Over `GateThr`'s contract range `0=-80/127=0/[Lin]`:

| | |
|---|--:|
| worst effective-threshold shift | **+0.000320 dB** at a threshold of −79.9 dB |
| and that corner is | **one Q4.28 LSB**, not a polynomial disagreement |
| worst at any threshold at or above −60 dB | **+0.000122 dB** |
| points exceeding the documented 0.0002 dB | 19 of 801, all at thresholds ≤ −77.1 dB |

Below about −77 dB the linear threshold word is only a few tens of Q4.28
LSBs, so one LSB is already worth more than the bar — the excursion is
the word size, not the arm. **The documented 0.0002 dB holds across the
useful range.**

On the part, after §S16-4 taught the reference which arm it was reading:
all three converted gate parameters match bit for bit, `2,684,355` on
both sides.

### The verdict

**The LUT's gain reaches the audio unchanged — YES.** The witnesses are
famverify at 20 families verdict for verdict, `node_verify` at 0.00518 dB
against the polynomial model, `comp_gr` at −20.98 dB of real reduction
matching the static law to 0.0003 dB with a bit-identical settled value,
and — for the limiter — 0.00214 dB through the attack (§3).

## 3. The LIMITER on the table, which is where chip 2's cost was

S14-4 measured 162 of `_lim_pair_blk`'s 251 instructions per sample-pair
as log2 + exp2. That 65 % is the highest share of any body in the tree,
and the reason is structural: the limiter has no makeup and no parallel
blend, so **the gain computer IS the limiter**.

It is now on the same machinery, with no new arithmetic — `_lim_cgp_` is
already a `_compgain_fx` parameter block (threshold, slope `0x7FFFFFFF`,
hard knee), so `_dyn_lut_step` designs it unchanged. Three edits: the
node template's three declarations and design-step call, the LUT loop in
`_lim_pair_blk` (`src/lib2`, chip 2 only), and the pair driver's table
pointers.

| measurement | result |
|---|--:|
| `dyn_lut_design.py --sweep`, LIMITER over −30..0 dB (its contract range) | **0.0604 dB** worst — PASS against 0.1 dB |
| `dsp4_dyn_lut_check.py` on `C2_AUX_LIM_01`, off the part | **337 of 337 words identical** to the host model |
| `dyn_shootout` rungs 18 → 19, on the part | 253.3 → **92.1 c/sample-pair** |
| the saving | **161.1 c/sample-pair, 63.6 %** |
| `dyn_state_bound.py` §5, LIMITER corners with the node's own slope word | every table word inside [0, 1] in Q4.28 |
| audio, `dsp4_dyn_lut_audio.py` | **0.00214 dB** worst through the attack, bit-identical settled |

The shootout's 161.1 confirms S14-4's 162 almost exactly, and it is the
largest fractional saving on the whole ladder — against the compressor
body's 56.7 % and the gate's 54.2 %.

**Chip 2 at D32: 76.66 / 76.77 % → 66.72 / 66.55 %.** Ten points.

### Why famverify cannot witness the table, and what can

famverify's audio arm moves a cell and asks whether the samples moved.
For a `DSP4_DYN_LUT` node that is the wrong gesture: the cell it moves is
the THRESHOLD, the threshold IS the curve, and a moved curve **restarts
the design step** — so the capture runs the exact polynomial. The LIMITER
family's audio record is bit-identical on the shipping arm and on the
table arm (peak `0x00818682` both), and that identity is the design
working, not the table being absent.

`tools/pi/dsp4_dyn_lut_audio.py` is the instrument that can see past it:
two captures around the design step, the first with the table stale.
Getting a verdict out of it took three corrections and each is worth
keeping (§S16-10) — it printed a `0.00000 dB PASS` while both captures
ran on the table, then refused runs whose samples genuinely were the
polynomial's because it read the cursor after the SPI readback rather
than at the instant the window filled. With the cursor read in the right
place and `DYN_LUT_CHUNK=1` widening the stale window to 112 ms against
the buffer's 21 ms:

```
cursor: 11 after the write, 239 WHEN THE WINDOW FILLED, 337 after the readback
23 of 64 samples differ; worst 0.00214 dB at sample 5
```

Cursor 239 of 337 at the fill: the whole window is provably the
polynomial's. Once the envelope settles the two arms are bit-identical.

## 4. S16-7: the lever was INERT on chip 2, and it read as a measurement

`_comp_pair_blk` branches on `_dlut_live` once per block. Chip 1's pair
driver writes it. **Chip 2's did not** — the generator emitted no such
block for `_c2_dyn_driver` at all — so the flag sat at its initialiser
and every chip-2 pair took the polynomial loop.

It cost nothing and it looked measured. S15 recorded chip 2 moving
76.07 % → 76.55 % across the switch, which is noise, and wrote it up as
"chip 2 barely moves — its 18 LIMITERs are not on the table yet". True,
and half the story: chip 2's ten compressors were not on the table
either. **Nothing in the tree could have said so** — the flag has no
host-side reader and `DIAG_BUILD_CFG2` reads the switch as ON regardless.

`dsp_codegen.py::_emit_lut_pair` now emits the pair's table bases and its
live flag for both `comp` and `lim`, on the family pairs and the
cross-chain pairs.

**The size of the move is the proof.** Predicted: 9 limiter pairs +
5 compressor pairs, × 15 samples, × ~161 c/sample-pair = 33,839 cycles =
**10.33 %** of a 327,680-cycle block. Measured: **9.83 %**. Ninety-five
per cent, with the shortfall accounted for by the sample-0 scalar path
each pair runs — the same 89 %-of-prediction agreement S15 found on
chip 1, for the same reason.

## 6. Hygiene

### S15-10, resolved by looking

`~/dspboot/chip{1,2}.ldr` read `08d0b9a4` / `6a349c13` on the part — **no
staged pair at all**. They are the shared scratch slot `dsp4_boot.py`
boots by default. The staged pairs are the PREFIXED ones and every one of
them was intact.

So `famverify.sh`'s header was wrong, not the scripts, and it is
corrected. Two corrections to S15-10 while closing it: the count is about
**thirty** scripts, not ten, and what protects the artifacts is the
prefix while what protects concurrent runs from each other is
`bench_lock.sh`. **The thirty-script STAGE sweep was NOT done** — it is
mechanical, it cannot be verified on the bench in one sitting, and
nothing is at risk while it is outstanding.

### `dyn_state_bound` §3, attributed

It had returned FAIL since before S15, with its worst corner at an **HPF
of 8 kHz**. The defs do not allow an HPF of 8 kHz:
`Chan001GateFilterHpf001` is `0=20/64=1000/[Log]` and
`Chan001GateFilterLpf001` is `0=500/127=20000/[Log]` — two different
ranges — and §3 swept both over one grid running to 18 kHz.

The sweep now takes its ranges from the landed CSV. Inside the contract
the worst cascade bound is **125.01 at HPF 521 Hz, LPF 500 Hz, Q 10 →
H = 4**, not 5.

**The bound was wrong by one bit and the finding stands.** H = 4 is still
reachable, an HPF above the LPF is a recallable preset rather than a
dialled setting, and the two sidechain classes are still left at H = 0.
§3 still returns FAIL, deliberately, and the fix is unchanged: convert
those sections when the parameters change rather than on every
invocation.

### The recommendation, in one line

**Take `s16_*`.** It is the first pair that puts both dynamics levers on
both chips, it is measured at zero overruns over 270,082 blocks per chip on
each of two products, its arithmetic is 0.005 dB from the polynomial it
replaces on the compressor and 0.002 dB on the limiter, and it leaves
chip 2 with a third of its budget and 130 kB of code pool free — which is
where the next thing will have to go, because chip 1's has 388 bytes.
