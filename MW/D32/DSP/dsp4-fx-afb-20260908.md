# The FX engine made honest, anti-feedback made real, and the capacity number that was a projection

**Session 29, 2026-09-08.** The last of the four inert families now
processes. The FX engine — which had never run in any capacity
measurement, in four sessions of capacity measurements — has been
measured at the operating point, and it carries a sample for the first
time. Six defects came out of making it do so, and one of them had been
hiding another for months.

## 1. The FX engine had six defects and one of them hid the rest

Every one of these is in `tools/dsp/dsp_codegen.py::gen_fx_engine`, so
every one was in all six engines of every product.

### 1.1 The dry input was destroyed by a loop counter — in every algorithm

```
    f15 = f0;                    /* dry input saved in f15 */
    ...
    r15 = 1;
    r1 = r1 + r15;               /* advance the write pointer */
```

`rN` and `fN` are the same register on SHARC. Every algorithm in the
node advanced its delay-line cursor with a scratch `1` in **r15**, so
the moment any delay line stepped, the saved dry signal became the
integer 1 — which as a float32 is 1.4e-45. The mix epilogue's
`f1 = f15 * f8` then multiplied the dry path by zero, and the reverb's
comb loop, which adds `f15` into all eight combs, fed the input to the
FIRST comb and denormal noise to the other seven.

**This is why Type 0 looked like a working pass-through and Type 3 read
peak zero.** Type 0 fell through to `.fx_passthru_`, the one path in the
node that touches no integer scratch, so the dry survived there and
nowhere else. Every increment is `r1 = r1 + 1` now — one instruction
instead of two, and it does not alias a float.

### 1.2 The write pointer was destroyed by the sample it had just read

Under it, and only visible once the dry input reached the delay lines:

```
    f13 = dm(i0, 0);             /* the delayed tap */
    f1  = dm(_fx_feedback_);     /* <- f1 IS r1, the write pointer */
    ...
    m0 = r1;  modify(i0, m0);
    dm(i0, 0) = f3;              /* written wherever the feedback's bits point */
```

In the ECHO path the pointer became the float bits of the feedback
coefficient. With the landed feedback of 0.0 those bits are
`0x00000000`, so **every sample was written to `buf[0]`, the cursor
advanced to 1 and stuck, and the tap read a part of the line nothing had
ever written.** Measured on the part: Type 0, Mix 1.0, delay 240, peak
**0.000000** over 1024 samples — silence, out of a path that reads as
correct. The same line is in Ping-Pong and Flanger.

**In the REVERB it is worse, because there the clobbering value is
audio.** The comb loop reads its delayed sample into `f1` while `r1`
holds that comb's write pointer, then stores the result back into
`_fx_rv_comb_wptrs` and uses it as an offset on the next block:

```
    r1 = dm(i3, 0);              /* wptr */
    ...
    f1 = dm(i0, 0);              /* delayed sample — r1 is gone */
    r1 = r1 + 1;  comp(r1, r2);  if ge r1 = r1 - r2;
    dm(i3, 1) = r1;              /* a float's bits, stored as a pointer */
```

A float32 sample's bit pattern is about 1e9. **Every comb wrote at
`comb_buf + 1e9` and the SPI link stopped answering.** The allpass chain
has the same line.

**IT HID BEHIND 1.1 FOR AS LONG AS THE ENGINE EXISTED.** While the dry
input was being destroyed, the comb lines only ever held zeros — whose
bit pattern is `0x00000000`, a pointer of zero, in range, every block.
**The reverb could not crash because it could not carry a sample.**
Fixing the dry path made it carry one and it wedged the bench on the
first capture; the reverb now runs with its pointers inside their own
lines, read off the part and printed in the bar.

### 1.3 No L register, alone among every kernel in this tree

`_C2_FX_ENG_NN_process` used `modify(i0, m0)` on four buffers and
post-modify on four table walks and set **no length register at all**.
On SHARC that is a linear pointer add only while `lN` is zero.

It survived because `C_RUNTIME_INIT` zeroes `l0..l15` at boot and
nothing on chip 2 writes one — but the **chip-1 delay nodes do** (they
set `l0` and `l2` to the delay-line length and do not restore them),
review finding **D70** measured the boot kernel leaving `l6` and `l7` at
`0x2FF`, and both ISRs run on the secondary DAG. The kernel was one
graph change away from writing its comb feedback into somebody else's
state. `l0 = l3 = l4 = l5 = l6 = 0` at the top of the body, which is
what `lib/biquad_fx.asm`, `lib/bq_headroom.asm`, the DLY nodes and every
block wrapper already do.

### 1.4 Doubling read a 720-sample delay from an eight-word buffer

The reverb class allocated `_fx_echo_buf[8]`, commented "for phaser
fallback", and the Doubling path read 720 samples back from it with a
wrap constant of 8 — an index **711 words before the array**.

**Sized from the design, and the delay bounded, and here is which and
why.** Doubling wants a fixed 15 ms (720 samples). Echo wants
`Fx001DelayTime001`, whose Table domain is 1..1000 ms = up to 48,000
samples; six engines at 48,000 words is 1.15 MB against 364 kB free in
the delay pool, so the BUFFER is 12,000 words — 250 ms, the same length
every aux delay line in the product already carries — and the KERNEL
CLAMPS the requested delay into it. A host asking for 800 ms gets 250:
a bounded, audible, stated limit rather than a read off the end of an
array.

**It costs nothing net, because the same node was already wasting more
than it needed.** `_fx_comb_buf_R` and `_fx_allpass_buf_R` were
allocated at full size — 12,587 words an engine, 75,522 across the six —
and **not one emitted instruction read or wrote either of them**. The
Freeverb body runs one comb bank and one allpass chain, reads `_L`,
writes `_L`, and publishes one word. Removing them pays for the delay
line with 595 words an engine to spare, and the linker agrees: the delay
pool goes from 1,708,216 bytes to **1,694,112**. Making the engine
genuinely stereo is a design change with its own cycle cost, and it is
not made by leaving two arrays lying about in case it happens.

### 1.5 Two formats in two words of the same node

```
    dm(_buf_L_{nid}) = r0;       /* float32 bits */
    dm(_buf_{nid})   = r0;       /* rewritten by the float island to Q4.28 */
```

`_buf_L` was stored **before** the fixed-point conversion, so it carried
float32 while `_buf_` carried Q4.28. `_buf_R` was written only by
Ping-Pong, and also as a float. Nothing in the tree reads either
(checked across all 724 assembly files), and the engine is mono end to
end, so both now carry exactly what the node publishes.

### 1.6 Types with no algorithm fell through silently

Types 1, 4, 5 and 6 have no case in the reverb class and jumped to the
dry pass-through, which on a capture is indistinguishable from an engine
that ran and had nothing to do. **That is how Type 0 = Echo, the landed
default, went four sessions without anyone noticing it was not an
algorithm.** They now jump to an explicit bypass that parks the Type in
`_fx_bypassed_<nid>`, which the family walk and the bar can read.

**Remaining unimplemented for the reverb class: 1 (Ping-Pong), 4
(Chorus), 5 (Flanger), 6 (Phaser).** Ping-Pong is left out deliberately
rather than half-built: it produces a stereo pair and this node
publishes one word. Chorus, Flanger and Phaser are emitted for the
`modulation` class, which this graph does not instantiate; their
register aliasing is fixed alongside the others so the class is not
adopted with known defects in it.

### 1.7 The generator printed one default and emitted another

The node header has always said `/* Default type: Reverb */` — the
graph declares `type=Reverb` on all six engines — and the `.var` was
hardcoded to 0 whatever it said. That is now a real choice:
`DSP4_FX_TYPE_DECLARED=1` boots at the declared Type. **It is a flag and
not simply the default because of what it costs — §0 — and which Type
the product boots at is a capacity decision, and capacity decisions are
PW's.**

**A 1024-SAMPLE WINDOW CANNOT CONTAIN A FREEVERB RESPONSE, and the
2026-09-08 family walk scored this family over a 32-SAMPLE ONE.** The
comb lengths are 1116–1617 samples and there is no direct path from
input to output — the wet signal IS the comb read — so the first
reverberant sample arrives 1116 samples after the impulse, past the end
of the scope buffer. A window thirty-five times too short cannot see a
reverb even when the reverb is perfect. That is half of why the "peak
zero on both arms" verdict meant nothing; §1.1 is the other half.

So the reverb arm drives a STEP and arms **twice, a handshake apart,
fetching only the second window**. The fetch is the slow part, not the
capture: reading 1024 words back over the diag link takes seconds, and
half a second is 24,000 samples, by which time a comb with 0.6 of
feedback has been round its line fifteen times. Armed properly the tail
is 1,024 non-zero samples of it.

## 3. ANTI_FB — the GEQ's fix applied to a notch bank

Same disease, third node. The eighteen parameter addresses always
dispatched to the right symbols — the family walk read 1000.0 Hz,
−18.0 dB and Q 4.0 back off the part at `_afb_notch_freq/_gain/_q` —
and nothing turned them into coefficients. `_afb_on` took its write and
was read by no emitted line anywhere in the tree.

### What a notch is here, and why it is a peaking section

A textbook RBJ `notch` has no depth parameter — it is infinitely deep at
f0 — and the contract carries `AntiFbNotchGain` with the domain
`0=-18/127=0/[Lin]`. **The depth IS the parameter**, so the section that
honours the contract is RBJ peaking at negative gain, which is the same
design the parametric EQ, the graphic EQ and the crossover all use. At
0 dB it is the exact identity, which is what makes "the notch is off"
mean "the sample comes through word for word".

### What was built

| | |
|---|---|
| `tools/dsp/afb_ref.py` | NORMATIVE. RBJ peaking over the contract's own domains (40–12,000 Hz, −18–0 dB, Q 1–20), checked against `bq_float_ref.rbj_peak`: worst relative **2.2e-16**. |
| `src/lib/afb_design_fx.asm` | the kernel. Two polynomials, two reciprocals, one exponent. |
| `src/afb_tables.asm` | GENERATED from `afb_ref` by `dsp_codegen.py`. |
| `_afb_dirty_<nid>` | GENERATED into `_spi_dispatch_cN_dirty[]`, the GEQ's trigger arrangement for the GEQ's reason. |

### The three things that had to be right

**NOTHING IS A PER-NOTCH CONSTANT, and that is the difference from the
GEQ.** A graphic EQ band has a fixed centre and Q, so `alpha` and
`k2 = 2(1 − cos w0)` are generated constants and only `A` moves. Here
frequency AND Q are both host-settable across the whole audio band, so
`sin w0` and `1 − cos w0` are computed on the part, over
x ∈ [0.00524, π/2].

**`1 − cos x` comes from its own polynomial and never from a
subtraction** — `xover_design_fx.asm`'s argument over a much wider
domain. At 40 Hz `cos x` is 0.9999863 and `1 − cos x` is 1.4e-5; formed
in float32 by subtracting, four significant digits of the quantity the
entire pole placement rests on would be gone. `Pu` is a degree-5 fit of
`(1 − cos x)/(x²/2)` **in x²**, so the even symmetry of the cosine is
exact by construction rather than by fit. Worst relative error
**8.9e-12**; the sine's is **5.9e-11**.

**A is 2^v with |v| up to 1.4949, and this tree's exponent polynomial is
fitted on [−1, 1].** Rather than carry a second fit, the kernel
evaluates 2^(v/2) — inside ±0.7475, comfortably in domain — and
**squares it**, and takes 1/A from 2^(−v/2) squared rather than from a
second reciprocal. Worst relative error **1.1e-9**, eighteen times finer
than a float32 ulp. There is exactly one literal for 2^x in this repo:
`geq_ref.EXP2_POLY`, which `afb_ref` imports rather than copying.

### `_afb_on` is read here and nowhere else; `_afb_ctrl_on` still is not

Off designs the compiled identity into every stage, so an anti-feedback
node the host has not switched on passes its input word for word. It is
not a branch in the audio path — the cascade issues the same instruction
stream either way, which is why turning every notch on costs nothing
measurable at the block rate.

**`AntiFbCtrlOn` is deliberately left unread.** It enables an AUTOMATIC
feedback detector — the thing that finds a ringing frequency and sets a
notch itself — and no detector exists in this firmware. Wiring it to the
design step would make an empty switch look implemented. It is not in
the recompute run, the kernel says so, and so does this.

## 5. The two `defs` asks — one proposed, one blocked on the tag itself

Both are written up in full in
`MW/D32/DSP/dsp4-dspcsv-proposal-20260908.md` (Amendment, session 29).

### `CrossoverSlope` — proposed, and it costs no address

Eight cells resolve to 0x0575 today. The proposal is **0x0576**, a word
the crossover node already owns and nothing dispatches to (the node's
block is nominally 24 words but `C2_MAIN_OEQ_01` starts four words later
and overwrites the rest — S4-9), so **no address in either product
moves**. **ONE shared slope word, not one per strip**: there is a single
`CROSSOVER` node feeding all four main outputs from one LP/HP split,
which is exactly why the four `CrossoverFreq` cells already share one
word; a per-strip slope would ask one filter pair to have two orders at
once.

The DSP side is specified with it, because an address the firmware does
not read is the disease this session has spent its whole length
unpicking: **12 (LR2) and 24 (LR4) are honoured** — the same five offset
expressions, with `1/(2Q)` at 1.0 instead of 0.70711 and the second
stage of each path written as the compiled identity — and **6 and 18 are
ignored, not clamped**, because neither is a Linkwitz-Riley alignment
this node's shape can hold. `xover_ref.py` carries the model for both
and checks it: each path 6.0206 dB down at the corner at either slope.

**It was prototyped and then reverted, deliberately, and the guard is
why.** `gen_dsp.py::check_proposal()` refuses to generate anything once
the graph disagrees with the landed `defs/products/<p>/dsp.csv` — which
is precisely what moving the slope's address does. That is the
propose/land boundary working: the address and the design land together,
at a hub gate, not out of a session.

### The 31-band GEQ — the tag lands the cells and this repo cannot take it

`defs-v2026.09.08.3` is visible and it lands `Geq[1-31]` for
Aux/Main/Grp in the cell master (D24 4,946 → 4,985 cells, fingerprint
`3d41d5850df3`). **The pin was advanced, the tree regenerated, and it
was reverted to `defs-v2026.09.08.2`, for a reason that is a finding
rather than a preference.**

The tag changes `common/cells/mx_master.csv` and the six product masters
and **touches `products/<p>/` not at all**. So the 39 new D24 cells (51
on D32) reach no DSP address — correctly, because a GEQ node's address
block is *exactly* its band count and chip 2 is packed end to end — and
`gen_dsp.py`'s no-fallback check stops:

```
ERROR: cell 'Aux001Geq029' (Aux/Geq) reaches no DSP address and
       _UNMAPPED_REASONS in gen_dsp.py does not say why.
```

That part is this repo's to fix and is fixed here: `GEQ_BANDS` is one
constant that both the expander and the reason read, and the reason is
matched on the BAND NUMBER rather than on the family, so a band inside
1–28 that ever stopped reaching an address would still stop the
generator — which a family-wide `('Aux', 'Geq')` entry would have
hidden.

**What is not this repo's to fix is the next error**, and it is why the
pin went back:

```
ERROR: d24/dsp-unmapped.csv cell set disagrees with the graph —
       39 the graph proposes and the landed file lacks
```

`products/<p>/dsp-unmapped.csv` is a LANDED file. Thirty-nine cells were
added to the master without the thirty-nine rows that account for them,
and this repo cannot write them: `check_proposal()` runs BEFORE
`--propose`, so once the graph and the landed file disagree the
generator will not emit the proposal that would close the gap either.
**`defs-v2026.09.08.3` needs `products/{d24,d32}/dsp-unmapped.csv`
regenerated and landed with it**; until then the pin stays at
`.2` and `Aux001Geq029..031` **cannot be proved on the part, because
they have no address to write.** The measurement that gates the real
31-band change — the 31-band graph at block 16 against the shipping one
on one instrument — is specified in the proposal and was not taken here.
