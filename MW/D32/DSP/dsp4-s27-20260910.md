# S27 — the shared-class cycle ladder, the window candidate, and three instruments

S26 recovered 58,072 bytes of chip 1's code pool by giving GATE and FILT the
shared-kernel treatment, proved the audio byte-identical, and said in as many
words that the CYCLE cost was not measured. This session measured it, on the
part, driven, on both products, with and without the plugin load, two boots
each — and then assembled the window candidate in one document so PW can sign
in a minute rather than reading eight addenda.

---

## 0. What this session settled

1. **Shared GATE costs nothing and shared FILT costs nothing.**
   Twenty-four chip-1 arm-to-control comparisons — three classes × two
   products × four regimes, each the mean of two boots — and not one of them
   is distinguishable from the instrument measuring itself. **Ship both.**
2. **The ladder's own resolution is measured, not asserted** (§1.3). GATE and
   FILT are chip-1 classes and `chip2.ldr` is byte-identical in all four arms,
   so every chip-2 delta in the tables is a null arm: the same binary compared
   with itself. It swings up to 0.39 points on the average and 0.56 on the
   worst block. Every chip-1 delta is inside that.
3. **The window candidate is `shipping.config.s26`** and it is assembled in
   `MW/D32/DSP/window-candidate.md` — the configuration, the md5s, every bar
   run on it this session, the three numeric deviations PW signs, and what the
   app has to rebuild against (nothing).
4. **The part cannot tell `shipping.config.s21` from `shipping.config.s26`**
   (S27-3). `DIAG_BUILD_CFG2` has room for two bits of `DSP4_SHARED_KERNELS`
   and the mask now has four; mask 3 and mask 15 produce the **same two
   words**, so `cfgverify`'s "the part matches to the bit" is true and proves
   less than it sounds. Found by reading this candidate's own cfgverify
   output. Not fixed here, deliberately — widening the word moves
   DIAG_BUILD_CFG2 on every image, including every md5 this session quotes —
   and both the host tool and the bench decoder now say so out loud.
5. **The S23-1 first-capture rule is in the capture tool** (S27-4), and the
   first version of it was inert: it read a free-running counter with a VOTED
   reader, which can never settle. Fixed and witnessed on the part — `boot
   capture #1` now prints beside every busgold capture.
6. **`loadlogic.sh` could not tell a failed CPLD flash from a good one**
   (S27-5): its success check was the IDCODE, and a MAX V answers its IDCODE
   whether or not the configuration took. It now requires openocd's own
   `programmed successfully` line, retries, and keeps every attempt.
7. **Two bars fail on the candidate and both fail identically on the S21 arm
   measured in the same tree**: COMPRESSOR's numeric arm (the model is the
   polynomial path, the part is the LUT — 0.00518 dB, reproduced to the digit
   from S21's `s20` arm) and FADER_PAN's (S25-6, the stale pan model). Neither
   is this change and neither is new; §2.3 gives the evidence.

### 1.3 The null arm, which is what makes "costs nothing" a measurement

`chip2.ldr` is the same 407,584 bytes in every arm. So every chip-2
arm-to-control delta in the tables above is the instrument comparing one
binary with itself, across two boots, on two products, in four regimes —
twenty-four comparisons of a thing that cannot have changed:

```
  largest chip-2 average delta:      0.39 points
  largest chip-2 worst-block delta:  0.56 points
  chip-1 boot-to-boot spread:        32 pairs, max 0.59, mean 0.19 points
```

And the chip-1 deltas, over every product, row and boot:

| class | avg Δ (chip 1) | worst-block Δ (chip 1) |
|---|---|---|
| shared GATE | −0.11 … +0.28 | −0.26 … +0.70 |
| shared FILT | −0.11 … +0.23 | −0.25 … +0.29 |
| both | −0.12 … +0.12 | −0.06 … +0.29 |

**Every chip-1 excursion is the size of the null arm's own.** The largest
single chip-1 figure in the whole ladder is GATE's +0.70 on one D32 worst-block
cell; the null arm's largest is 0.56 on a D32 worst-block cell in the same
arm, in the opposite direction. The both-classes arm — the candidate — is the
quietest of the three, which is what additivity of two zeroes looks like.

**So: shared GATE costs 0.0 points and shared FILT costs 0.0 points, per
product and per chip, bounded by ±0.3 on the average and ±0.7 on the worst
block, against an instrument that cannot resolve better than ±0.4 / ±0.6.**
Neither class is anywhere near the 0.5-point revert threshold, and it is worth
saying plainly that the threshold sits *at* this instrument's resolution: a
class that genuinely cost 0.5 points would have been a marginal call, and
neither of these is marginal.

**Why this was not safe to assume from S21.** S21 measured COMP and TUBE,
whose inline bodies were the two smallest on the chip. GATE and FILT are the
two largest the pattern fits; their stubs are entered per block *and* per
sample; FILT's stub carries a second register load (`i6`, the block pool)
that COMP's does not, and FILT's per-sample entry runs 32 strips × 48 kHz.
The expectation was still that a stub is a handful of instructions. The
expectation was right, and it is now a measurement.

### 2.1 The two bars that fail, and the two arms they fail on

`goldnode` on the candidate returns **NODE VERIFY FAILED: 3 verdicts against
4 measurable stimuli**, and a bar that fails is worth more than a bar that
passes only if the failure is attributed. Both failures are attributed, and
neither is GATE or FILT.

**GATE — the class this session moved — passes.**

```
  cvt gate range floor (D39: dB on the wire)          2684355 / 2684355  ok
  cvt gate threshold -> Q4.28 LINEAR (GATE_LINTHR)    2684355 / 2684355  ok
  cvt gate attack alpha -> Q0.31                    107374184 / 107374184 ok
  phase profile: 0:61 1:61 ... 14:62 15:64
  impulse  amp 0x0D3A17B5  model 64 of 64 bit-exact
           negative control differs in 2 of 64 (predicted 2)
```

The negative control fires on exactly the two vectors the model predicts, so
this is a bar that can fail and did not. TUBE_SAT is 96 of 96 bit-exact on
both stimuli with both its negative controls firing as predicted.

**COMPRESSOR's numeric arm fails, and it failed identically before GATE and
FILT were shared.** The candidate reads:

```
  step  amp 0x0D3A17B5  model 0 of 96 bit-exact
  worst deviation 0.00518 dB at sample 18
        (part 37538308, model 37515935, d +22373); 96 of 96 samples differ
```

S21's `s20` arm — `shipping.config.s20` plus the shared-kernel switch, mask 3,
GATE and FILT still inlined — reads **the same three numbers to the digit**:
`0 of 96`, `worst deviation 0.00518 dB at sample 18`, `part 37538308, model
37515935, d +22373`. The mechanism is `DSP4_DYN_LUT`: the part computes the
compressor's gain from the baked table and `fixed_ref` computes it from the
polynomial, and 0.00518 dB is well inside the table's own 0.0950 dB design
bound. The arms that pass on the SAME run (`0x1A6F2E93` and `0x02741F14`, 96
of 96 bit-exact) are the ones whose level does not land on the LUT's
interpolated region. S21's arms taken on `shipping.config`, where DYN_LUT is
0, read 96 of 96 bit-exact — which is the control that identifies the cause.

**FADER_PAN's numeric arm fails, and that is S25-6, carried and untouched:**

```
  cvt fdr LEFT pan leg (linear law; D42 open)   183217856 / 183341408  <-- MISMATCH
  cvt fdr RIGHT pan leg                          85217608 /  85094040  <-- MISMATCH
```

`fixed_ref`'s pan model predates R5's table and has not been rewritten, for
S25's stated reason: a bar rewritten to agree with the thing it measures, in
the same change, is not a bar. It is carried again here (§5).

**Neither failure moves between the control and the candidate**, which is the
only question gate 1 and gate 2 put to `goldnode`.

## 3. Gate 3 — instrument debt

### 3.1 (a) S23-1 — the first capture of a boot, made a rule the tool enforces

**What S23-1 found.** A bus capture is 256 samples from the arm, and the
strip's gate and compressor are wherever the PREVIOUS capture's step
injection left their envelopes. On the FIRST capture of a boot there is no
previous injection, so it carries a dynamics-history term of up to 1,412 LSB
that no later capture on that boot carries. S23-1 proved it by taking aux 1
first and last on one boot: the two differ in 235 of 256 words, while three
captures of three DIFFERENT buses taken later are byte for byte identical.

**Why that was not enough.** Every stored golden in `goldens/` is a first
capture, and `busgold.sh`, `ctlgate.sh`, `bqgraph.sh` and `gainsimd.sh` are
sound today for one reason: they take one capture per boot, so the term is on
both sides and cancels. That rule lived in a finding and in nothing the tool
could check — and **the run scripts break it by accident.**
`pairgraph_run.sh` retries a failed capture up to four times on the same boot
and compares whichever attempt succeeds against a first-capture golden. The
retry is silent and the comparison looks clean.

**The rule is in `tools/pi/dsp4_pairgraph.py` now.** A capture reads
`DIAG_FRAME_COUNT`, keeps a ledger, knows its own index within the boot,
stamps it into the JSON, and **refuses to be the second capture of a boot**
unless the caller says which comparable regime it wants:

* `--force` — take it anyway. For a bar that compares captures WITHIN one
  boot and carries its own control. `mtxgold.sh` is that bar (its `aux1b`
  arm IS S23-1's measurement) and now passes `--force` explicitly.
* `--settle` — take a throwaway capture first and measure the second, so the
  history term is settled whatever the position in the boot. This is the
  forward path: it makes a first capture comparable instead of documenting
  that it is not. It is not the default and it is STAMPED, because a settled
  capture and an unsettled golden are different measurements.

`compare()` reads the stamps and says so: settled-vs-unsettled is a warning,
a non-first unsettled capture against a first capture is a warning, and an
unstamped file is named as unstamped rather than assumed to be either.

The refusal exits non-zero, which the run scripts already treat as "no
capture" and answer by RE-BOOTING — so a bar that used to silently produce an
incomparable capture now costs one extra boot instead. Nothing was changed in
the run scripts to make that work; it is the behaviour they already had.

**Every way this guard can be wrong makes it permit, never refuse** — the
frame counter wrapping after 8.3 days of continuous running, a tool that
strobes `DIAG_CLEAR`, an unreadable register. An instrument guard must not be
able to fail a bar that is sound.

**S27-4: the first version of this guard was inert, and the bench said so.**
It read `DIAG_FRAME_COUNT` with `Scope.rd`, which is a VOTED reader — it asks
until one value comes back twice. A free-running counter never repeats, so
the first busgold run printed:

```
  WARNING: DIAG_FRAME_COUNT unreadable (register 0xE004 never settled:
    {0x9c13: 1, 0x9c1a: 1, 0x9c21: 1, 0x9c29: 1, ... 0x9c64: 1})
  boot capture #?
```

Twelve distinct, monotonically increasing values — twelve correct readings,
rejected for not being identical. `dsp4_capacity.moving()` already had the
rule for this (single unvoted asks, monotonicity instead of repetition) and
the guard now uses it. The witness is the next busgold run on the same
candidate:

```
  strip 1 driven, 2 muted, xp=main ... sha256 4126c00730a31f5f
  boot capture #1
```

Same capture, same sha, and the stamp is there. It is worth recording that
the inert version failed exactly as designed — it warned, stamped the capture
`None`, and let the bar finish.

### 3.2 (b) The CPLD flash — eleven playbacks, no MASK failure, and a success check that was never a check

**S24 flashed the shipping bitstream three times before it took, with an svf
MASK failure.** The dispatch asked for five flashes with the IDCODE read
before and after, and for retry logic if the failure recurred.

**It did not recur. Eleven SVF playbacks across eight invocations, every one
of them clean:**

| # | bitstream | playbacks | IDCODE before → after | result |
|--:|---|--:|---|---|
| 1 | `driveall` | 1 | `0x020a30dd` → `0x020a30dd` | took (the whole ladder's driven regimes prove it) |
| 2 | `shipping` | 3 | `0x020a30dd` → `0x020a30dd` | took; the CHECK was wrong (below) |
| 3 | `driveall` | 3 | `0x020a30dd` → `0x020a30dd` | took; same |
| 4 | `shipping` | 3 | `0x020a30dd` → `0x020a30dd` | took; same |
| 5 | `driveall` | 1 | `0x020a30dd` → `0x020a30dd` | **FLASH OK on attempt 1** |
| 6 | `shipping` | 1 | `0x020a30dd` → `0x020a30dd` | **FLASH OK on attempt 1** |
| 7 | `maincap` | 1 | `0x020a30dd` → `0x020a30dd` | **FLASH OK on attempt 1** |
| 8 | `shipping` | 1 | `0x020a30dd` → `0x020a30dd` | **FLASH OK on attempt 1** |

**S27-5: the IDCODE was never the check, and the first replacement for it was
wrong in the other direction.** `loadlogic.sh` used to decide a flash had
worked by reading the IDCODE back — and a MAX V answers its IDCODE from the
JTAG tap whether or not the configuration flash took, so the check passes on
a flash that failed halfway. That is exactly the state S24 hit, with nothing
in the script able to say so.

The replacement required openocd's upstream `svf file programmed
successfully for N commands` line. **This openocd does not print it**, and
invocations 2–4 above — nine good flashes — were all reported as failures,
each retried three times, for a total of nine playbacks where three were
wanted. The bench was never in danger (every playback completed and the
final state was the intended one) but the check was inverted, which is worse
than no check.

**So the check was measured against this openocd instead of assumed.** Its
svf driver echoes each SVF command and prints no summary; a run that
completes ends with `shutdown command invoked`, because `-c 'init; svf ...;
shutdown'` is ONE command chain and a failing svf aborts it before the
shutdown; a TDO/MASK mismatch prints `tdo check error at line N` with
READ/WANT/MASK beneath it. The check is now: the chain reached its shutdown,
and no `tdo check error` on the way. `Error: Translation from khz to adapter
speed not implemented` appears on every single run and is benign, so it is
excluded by name. Invocations 5–8 exercise the corrected form and each reads
`FLASH OK on attempt 1 (40790 lines of SVF played, chain reached shutdown)`.
The script retries three times, prints a loud line per failed attempt, keeps
every attempt's full openocd output in `/home/app/logic-flash.log`, reads the
IDCODE before AND after, and exits 7 with "the CPLD is in an UNKNOWN state"
when no attempt succeeds.

**And a better restore proof than the IDCODE, found by accident.**
`dsp4_logic_id.py` reads the LOGIC design-ID register through the CM4 PCM
link. On the `dsp4-pcm-slave` overlay it answers "no reply" for EVERY
bitstream, so it cannot identify anything — which is why the shipping
bitstream's "no reply" has never been worth much. On the **duplex** overlay
(§3.4) it read `design_id: 32'hae1ac4a9  cfg_bits: 16'h0004  pi_maincap`
from the maincap arm and then "no reply" from the shipping arm ten minutes
later, on the same working capture path. **That pair is a positive
identification of the shipping bitstream**: a path proven to answer, saying
nothing, which is what a build predating the ID register does.

### 3.3 (c) The matrix-app restart, reproduced — and mx26's B13 has it backwards

**B13 (filed 2026-08-24 from this bench) says: the first matrix-app restart
after reflashing the SHARCs verifies only H1S3 or none of the three MCUs; the
second restart always verifies all three.** Seven restarts were sampled on
the restored bench, reading the app's own `/home/app/logs/log` after each:

| restart (BST) | MCUs verified |
|---|---|
| 03:21:29 — the FIRST after the DSP reflash and reboot | **3 of 3** (H1S1, H1S3, H1S4) |
| 03:22:26 | **1 of 3** — H1S3 only, 2 warned |
| 03:23:41 | 3 of 3 |
| 03:24:16 | 3 of 3 |
| 03:24:51 | 3 of 3 |
| 03:25:27 | **1 of 3** — H1S3 only, 2 warned |
| 03:26:02 | 3 of 3 |

**Both halves of B13's model are wrong.** The first restart after a reflash
verified all three, and two LATER restarts failed. **It is a race, it lands
on about one restart in four, and "restart it twice" is not a reliable
workaround** — it happens to work because a second attempt is another roll.

**The failure signature is exact and identical both times**, and the app
names the mechanism itself:

```
03:25:27.036330: MCU verified: // H1S3 SW Right
03:25:33.230047: Boot.Loop() - WARNING: MCU not verified after S_RUN: H1S1 (no startup announcement received)
03:25:33.230486: Boot.Loop() - MCU boot verified: H1S3
03:25:33.230566: Boot.Loop() - WARNING: MCU not verified after S_RUN: H1S4 (no startup announcement received)
```

against a good restart, where all three announce within 40 ms of each other:

```
03:26:02.034245: MCU verified: // H1S1 DSP
03:26:02.052807: MCU verified: // H1S4 SW Left
03:26:02.072541: MCU verified: // H1S3 SW Right
03:26:08.276488..276703: Boot.Loop() - MCU boot verified: H1S1 / H1S3 / H1S4
```

**H1S3 announces on every single restart and is never the one that fails.**
H1S1 and H1S4 fail together or not at all. The announcement window is ~9.2 s
after the app starts and the `Boot.Loop()` verdict lands ~6.2 s after that.

**One methodological note that cost an hour the first time**:
`/home/app/logs/log` is REWRITTEN when the app starts, so reading "the lines
added since a mark" returns nothing on every restart after the first. Each
restart's verdict has to be read from the whole file. The first pass of this
repro reported "0 lines added" for restarts 2 and 3 and nearly filed that as
the finding.

Filed to mx26 B13 with this table, the two log extracts and the reproduction.

### 3.4 The latency bar: attempted with the capture path proven, and it still returns S12-10's null

`latency.sh` is in gate 2's bar list and **it did not produce a number.**
What was done, and what it means:

* The bench was flipped from `dsp4-pcm-slave` to **`dsp4-pcm-duplex`** (a
  `config.txt` line and a Pi reboot; `config.txt.s27bak` written first, the
  card came back as `card 2: dsp4pcm` with ONE device that plays and
  captures) and the **`maincap`** bitstream was flashed.
* Both halves of S12-10's named requirement were therefore satisfied **and
  positively identified, not assumed**: `dsp4_logic_id.py` read
  `pi_maincap` / `ae1ac4a9` off the part through that very capture path.
* `latency.sh` was taught to forward `DSP4_PCM_DEV` (the tool has read it
  since S17; no run script could set it, so the duplex overlay could only be
  used by running the tool by hand). Addressed by NAME, so the card index
  moving from 0 to 2 does not matter.
* The result, 20 reps × 2 boots and again at 2 reps: **offset 14779 on every
  rep, spread 0, coherent fraction 0.0 % on every one** — S11-6's and
  S12-10's signature exactly — and `dsp4_dsp_latency.py` REFUSED the verdict,
  which is the S12-10 fix doing its job.

**So S12-10's attribution is incomplete.** It named the slave overlay as the
cause; the null survives the duplex overlay with the maincap bitstream
proven on the part. The new evidence is from the DSP's own side:
`dsp4_passthru_setup.py` reports `chip1: 48 strip cells written` and
`chip2: 12 cells written, all present in the contract`, and then the main
chain reads

```
    _buf_C2_MIX_MAIN_L   0xfffffffc
    _buf_C2_MAIN_FDR     0xfffffffc
    _buf_C2_MAIN_DLY     0xfffffffc
    _buf_C2_MAIN_ST_OUT  0xfffffffc
```

— a constant −4 LSB, identical at every point of the chain. That is not
silence and it is not the stimulus: **nothing is arriving at the DSP's
input**, so the capture has nothing to correlate with and the missing link is
upstream of the DSP, on the playback side of the loop. Chasing it is a bench
bring-up of unknown shape and was not started at 02:40 on the tail of this
session.

**The through-DSP latency contract therefore stands where S20 measured it,
82 samples / 1.708 ms at block 16, and this session did not re-measure it.**
The candidate cannot have moved it — latency is set by the block size and
`DSP4_TX_EARLY`, and `cfgverify` read both off the part this session (`BLOCK
16`, `DSP4_TX_EARLY 2`) identical to the control's — but that is an argument,
not a measurement, and it is recorded as one.
