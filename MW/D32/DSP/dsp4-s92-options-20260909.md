# S9-2 — the first frame of each DMA half, costed for a ruling

**This is a costing, not a proposal to land. PW rules.**

## The defect, restated in one paragraph

With zero blocks missed, the **first frame of each DMA half still goes out
carrying what that half held two blocks earlier**. The gather runs at the
END of a block period the graph has spent 92.7 % of; the DDE clocks frame 0
of the half out at the TOP of that period. Frame 0's deadline is therefore
a whole block period earlier than the block's own deadline, and under load
the core loses that race every block. Measured on the transmit stamp over
192,000 frames (`_maincap d903ae1ac4a9`): graph out of the way **100.0000 %**
exact, load cut to one strip and one aux **100.0000 %**, full D24 graph
**87.4999 %** (one late frame in sixteen), full D24 plus the Pi playback
input **81.2499 %** (two in sixteen). **The count of late frames tracks the
LOAD, not the block size** — which is what says this is a deadline, not an
indexing error.

## What ships today, stated as what it is

`DSP4_GATHER_FIRST=1` moves the gather in front of `_scope_record` and the
parameter-link poll inside the block-kernel loop. It is worth **about one
frame of margin and it is not a fix**: without the Pi input it takes
87.4999 % → 100.0000 %; with the Pi input added, both orders read
81.2499 %, repeatably. It removes the first late frame and not the second,
and it will stop being enough the next time the graph grows. It is kept on
those terms.

## The two structural options

Both buy the same thing — the output for block N−1 is complete and sitting
in memory before period N begins, so frame 0 has a full block period of
slack instead of none — and both cost the same **one block of output
latency: 16 samples, 0.333 ms at 48 kHz**.

### Option A — write block N−1's outputs at the top of period N

The graph gathers into a **staging block** instead of straight into the
DMA half. At the top of the next period, before anything else, that
staging block is moved into the half the DDE is about to clock.

| | |
|---|---|
| **output latency added** | +16 samples, **0.333 ms** |
| **cycles added** | ~640/block on chip 2 if the move is a copy (20 output channels × 16 samples = 320 words at ~2 cycles/word), **0.20 % of the 327,680 budget**. Zero if the staging block and the DMA half are swapped by pointer instead of copied — but then the DMA descriptor has to point at the staging buffer, which is Option B. |
| **DM added** | 320 words on chip 2 for the staging block, plus chip 1's IC TX region. Nothing near the 08-24 DM ceiling. |
| **what changes in the panel MCU / app contract** | **Nothing in the SPI contract** — it carries cells and meters, not sample timing, and no host writes or reads anything whose meaning depends on when a frame leaves. What DOES change is the **published through-DSP latency**, which grows by 16 samples / 0.333 ms; the alignment contract and the window note carry that number and must be reissued with it. Say that rather than "no impact". |
| **risk** | **Low, and it is the kind of risk this firmware has already handled once.** It reorders work inside the period; it does not change the DMA topology. The one thing to reason about carefully is its interaction with `DSP4_BLK_LATCH` (the 2026-09-09 ping/pong phase fix): both touch the TX buffer pointers, and `_blk_latch_bufs` exists precisely because the generated scatter/gather reload the pointer per sample. The move must be latched by the same mechanism, in the same place, once per block. |

### Option B — a third TX buffer

The DDE walks a three-deep TCB chain; the core always writes the buffer two
ahead of the one being clocked out.

| | |
|---|---|
| **output latency added** | +16 samples, **0.333 ms** — the same |
| **cycles added** | **Essentially zero.** The gather is unchanged; only the buffer-select arithmetic changes, from a toggle to a modulo-3 index. A few cycles per block. |
| **DM added** | one more TX half: 320 words on chip 2, and the same again on chip 1's IC TX region |
| **what changes in the panel MCU / app contract** | the same as A: **nothing in the SPI contract**, and the same +0.333 ms on the published through-DSP latency |
| **risk** | **Higher, and it is topology risk.** The block interrupt currently maps one-to-one onto a ping/pong toggle, and `_set_tx_bufs` / `_blk_latch_bufs` are both written against that. A three-deep chain breaks that mapping, so the phase fix has to be re-derived rather than adjusted — and getting the phase wrong here is exactly the 2026-09-09 order defect, which took a purpose-built instrument (`tx_probe.asm`) to see at all. It also **desynchronises RX from TX**: the RX side stays two-deep, so the "one interrupt, one half, both directions" assumption that the diagnostics and the staircase scorer rest on stops being true. |

## Recommendation

**Option A.** It buys the identical 0.333 ms for 0.20 % of budget, and the
0.20 % is what pays for staying inside a DMA topology that has just been
made correct and proven at 100.0000 % ordered on the part. Option B's only
advantage over A is those 640 cycles, which is not a reason to re-derive
the ping/pong phase and unpick the RX/TX lock in the same window that the
phase fix is shipping in.

Two things PW should weigh against "do neither for now":

* The residual is **audible in principle and not in practice yet** — one
  frame in sixteen carrying a two-block-old sample is a 6.25 % duty
  impulse-rate error on every output lane, and the lanes are the converter
  lanes (`_gather_chip2` writes all twenty chip-2 outputs from the same
  half through one pointer). It has not been listened to on this bench
  because no analogue loopback is wired.
* The margin `DSP4_GATHER_FIRST` provides is **consumed by load**, and the
  D32 all-ones configuration is already over budget (S9-3). Any capacity
  work that succeeds will not give this margin back; any graph growth takes
  more of it.

## What would settle it on the bench, if PW wants evidence before ruling

The transmit stamp already measures it to a frame: `_maincap` +
`DSP4_TXPROBE=1` + `dsp4_tx_order.py`, the four load rows above. Option A
prototyped behind a build flag would be one build and one boot to score
against those same four rows, and a 100.0000 % row at full D24 load **with**
the Pi input is the acceptance. That is a half-session, not a session.
