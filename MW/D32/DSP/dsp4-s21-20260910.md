# S21 — the headroom PW asked for, measured driven; and chip 1's 380 bytes made 40,572

Session S21, 2026-09-10. Bench: rev C unit. Contract `defs-v2026.09.08.4`,
unchanged. `shipping.config` **unchanged**, and `shipping.config.s20`
unchanged. Predecessor `dsp4-s20-20260910.md` (dsp `1693c57`).

**W0, taken first, before anything was measured.** The default build reads
`302d6142` / `3b3a6f8e` and `shipping.config.s20` reads `32dc1ea1` /
`29d00a5e` — byte for byte the pairs S17 through S20 left, from the tree as
this session found it *and* from the tree after every generator change below.
The only file under `MW/D32/DSP/SHARC/src/` that changed is
`chip1/shared_kernels.asm`, which is generated, is behind
`#if DSP4_SHARED_KERNELS`, and is therefore absent from both of those images.

## 0. The question, and the answer in four numbers

PW's requirement of 2026-08-28: **32 strips is the MINIMUM, and the fit must
carry headroom for plugins.** S20 delivered a configuration that fits both
products under load — `shipping.config.s20`, D24 53.8 / 59.0 %, D32 71.6 /
72.6 %, zero overruns — with two things unmeasured and one thing wrong:

* the FX engines, which ARE the plugin load, had never been driven in a
  capacity measurement, and the last figure the record had for them was a
  silence estimate of 6–7 % of chip 2 scaled from block 8;
* chip 1's code pool had **380 bytes** free, and S18's 40 kB lever was
  refused by `build.sh` in combination with the configuration;
* `goldnode` had failed identically on every staged pair since S18.

All three are settled below, and a fourth thing turned up in the instrument
itself.

## 1. The FX engines, driven, on the pair that ships

### 1.1 What the product actually implements, before any number

`gen_fx_engine` emits three classes — `reverb`, `echo`, `modulation` — and
**every one of the six engines in `dsp.csv` is the `reverb` class**
(`C2_FX_ENG_01..06`, `type=Reverb`, no `fx_class` parameter, so the
generator's default applies). That class implements exactly three of the
seven Types the host can select:

| Type | name | reverb class | what the part does |
|--:|---|---|---|
| 0 | Echo | **implemented** | 250 ms delay line, clamped, with feedback |
| 1 | PingPong | no | parks the Type in `_fx_bypassed_<nid>`, passes dry |
| 2 | Doubling | **implemented** | fixed 15 ms (720-sample) thickening |
| 3 | Reverb | **implemented** | Freeverb: 8 comb-LPF + 4 series allpass |
| 4 | Chorus | no | parks the Type, passes dry |
| 5 | Flanger | no | parks the Type, passes dry |
| 6 | Phaser | no | parks the Type, passes dry |

So "the other FX types the product offers" is a shorter list than the host's
menu: **Echo, Doubling and Reverb are algorithms; PingPong, Chorus, Flanger
and Phaser reach one shared `.fx_bypass_` label** and are measured once,
below, as one rung. Ping-pong is left out deliberately (it wants a stereo
pair and this node publishes one word); the other three exist only in the
`modulation` class, which no node in the graph declares.

### 1.2 The instrument

`capacity.sh --driven` gained a mode and a ladder:

* **`SETUP_MODE=loadfx`** — everything `--mode load` did (every bus assign
  and send open, every dynamics node on at a −60 dB threshold) **plus** the
  six FX buses: `Chan<nn>FxOn<k> = 1` and `Chan<nn>FxSend<k> = 1.0` on every
  strip, the engines on, all wet, at a named Type, with the engine
  parameters written to the patch `dsp.csv` declares. Until this session
  every driven row in the record left `Chan<nn>FxSend` at 0.0, so
  `BUS_FX_01..06` carried silence however loud the inputs were and the six
  engines ran their algorithm over zeros.
* **`FXTYPES="4 3 0 2"`** — a rung per algorithm **on one boot**: same image,
  same measured clock, same DMA phase, same routes and dynamics, and the only
  thing that moves between two rungs is the six engines' `Type` cell. The FX
  cost is therefore a within-boot difference and not a difference of two
  boots, which matters when the difference is a few points and the
  boot-to-boot spread is ±0.3.
* **`dsp4_c2regime.py --require-fx --fx-type N`** — the regime PROVED before
  every rung: six engines enabled, all six at the Type asked for, none parked
  in the unimplemented-Type bypass when the Type is an implemented one, all
  six comb delay lines carrying signal at eleven probe offsets, all six
  engines publishing a non-zero word.

The baseline rung is **Type 4**, not "engines off", and §1.4 says why.

### 1.4 `Fx<n>On` has no reader (S21-4)

The ladder's first draft used `Fx<n>On = 0` as its baseline and the row came
back **identical to the rung before it**. It is not a measurement error:
`_fx_on_<nid>` is named by exactly one thing in the whole tree — the SPI
dispatch table in `chip2/dsp_params.asm`, which is what lets the host WRITE
it — and by no instruction in any kernel. The FX_ENGINE body has no on/off
branch at all.

So a host that switches an FX engine off gets neither silence nor a saved
cycle: the algorithm runs and its output stays in the mix at whatever `Mix`
holds. The rung is kept in the ladder as the witness for that.

**And it is not the only one.** Of the FX_ENGINE's 34 per-node words, sixteen
are named by no kernel instruction, and eleven of those sixteen are
host-writable SPI cells:

| cell | SPI (engine 1) | word | reaches the audio? |
|---|---|---|---|
| `Type` | 0x0655 | `_fx_type` | **yes** |
| `Mix` | 0x0668 | `_fx_mix` | **yes** |
| `Damp` | 0x065B | `_fx_damp` | **yes** (the comb one-pole) |
| `Feedback` | 0x0659 | `_fx_feedback` | **yes** (comb and allpass) |
| `DelayTime` | 0x0658 | `_fx_delay_ms` | **yes** (Echo, Doubling) |
| `On` | 0x0654 | `_fx_on` | no reader |
| `Decay` | 0x0656 | `_fx_decay` | no reader |
| `PreDelay` | 0x0657 | `_fx_predelay` | no reader |
| `EqLo` / `EqMid` / `EqPresence` | 0x065C–5E | `_fx_eq_*` | no reader |
| `FX HPF[0..4]` | 0x065F–63 | `_fx_hpf_coeffs` | no reader |
| `ModRate` / `ModLevel` | 0x0664–65 | `_fx_mod_*` | no reader |
| `LfoShape` | 0x0666 | `_fx_lfo_shape` | no reader |
| `StereoWidth` | 0x0667 | `_fx_width` | no reader |
| `Balance` / `DuckOn` / `DuckSens` | 0x065A, 69, 6A | — | dispatched to address 0 |

That has a bearing on the gate the dispatch asked for. "The other FX types at
their **worst settings**" assumes the settings move the cost, and on this
engine they cannot: five cells reach the arithmetic, none of them is a
branch, and the Freeverb body executes the same instructions for every value
of every one of them. **The cycle figure for each Type is THE figure, not a
best case** — which is a better answer than a worst-case hunt, and it is the
reason the reverb rung reproduces to 0.05 points across boots.

It also means the reverb is, today, a Freeverb whose room size and decay do
nothing.

## 2. Shared kernels and SIMD_DYN: the refusal did not hold

### 2.1 Why `build.sh` refused, and why the reason was not a finding (S21-2)

From S18 until this session `build.sh` exited 2 on
`DSP4_SHARED_KERNELS` together with `DSP4_SIMD_DYN`, printing:

> The SIMD pair drivers call `_C1_COMP_nn_process_sample` directly; a shared
> body reached that way would run on whatever record base the last strip left
> in the register.

The premise is true and the conclusion does not follow.
`_C1_COMP_nn_process_sample` is not the shared body — it is **that node's own
stub**. `gen_shared_kernels` emits `_process` and `_process_sample` entry
points **per node**, and each one sets `i7` to that node's record base and
`i5` to that node's predecessor buffer before jumping to `_shk_comp_smp`:

```
_C1_COMP_01_process_sample:
    i7 = _comp_on_C1_COMP_01;
    l7 = 0;
    i5 = _buf_C1_GATE_01;
    l5 = 0;
    jump _shk_comp_smp;
```

A pair driver that calls that label gets the right strip for exactly the
reason the chain does. And the pair KERNELS never call a node body at all:
`_comp_pair_blk` and `_gate_pair_blk` take both channels' record bases in
r4–r7 and run their own sample loop, so the pairing and the sharing act on
different code.

The refusal is replaced by a **check**, not by an argument.
`shared_kernel_check.py --entries` runs on every `SHARED_KERNELS` build and
fails it if any `_shk_<cls>_*` entry point is named by anything but one of
that class's per-node stubs, if a stub jumps without loading its own record
base, or if a stub loads more than one base or more than one predecessor
buffer. On the s21 arm it reports **64 stubs per class, each loading its own
record base** (32 nodes × two entry points), for COMP and for TUBE.

**And the check has two negative controls, run this session.** Point one
stub's base load at another strip (`C1_COMP_07`'s `i7 = _comp_on_C1_COMP_01`)
and it fails both of that node's entry points by name. Make one caller reach
the body directly (`dyn_pairs.asm`: `call _shk_comp_smp` in place of
`call _C1_COMP_01_process_sample`) and it fails that too — *"`_shk_comp_smp`
is named at 'call _shk_comp_smp;', which is not one of class comp's per-node
stubs"*. **The second control is literally the defect the refusal was written
about, and the check catches it.**

### 2.2 What actually did not build, and it was not the pairing (S21-3)

Turning the refusal off produced three failures in a row, all of them in the
same place and none of them about SIMD:

1. **`Rn = Rn + <const>` is not an instruction on this core.** With
   `DSP4_DYN_LUT=1` the shared COMP body carries the LUT design step, which
   passes four record ADDRESSES in r0–r3. The rewrite emitted `r0 = i7;
   r0 = r0 + SHK_COMP_OFF_comp_cgp;` and easm21k answered *"Semantic Error in
   type 2 instruction / Operands don't fit instruction template 'REG EQUAL
   REG PLUS_OP REG'"*. Fixed by loading the OFFSET as the immediate and
   adding the base AS A REGISTER, which needs one scratch data register;
   `r11` is free in both bodies, and the generator now CHECKS that rather
   than assuming it — a class whose body mentions its scratch register fails
   codegen. `r11` is already clobbered at those very sites in the inline arm
   (`_dyn_lut_step` and `_compgain_fx` under it clobber r0–r12), so the
   shared arm's write to it changes nothing that was live.
2. **`shared_kernels.asm` did not inherit `#include "lib/dyn_lut.h"`.** The
   include is emitted in a node file's HEADER, not in the body the shared
   pass splits, so the generated file referenced `DYN_LUT_N` and defined it
   nowhere — a LINK error.
3. **`shared_kernel_check.py` could not evaluate `DYN_LUT_N`.** Its
   `defines_from()` matched only `#define NAME <integer>`, and `DYN_LUT_N` is
   `(((DYN_LUT_OCTHI - DYN_LUT_OCTLO + 1) << DYN_LUT_K) + 1)`. An absent name
   resolved to 0, so `.var _comp_lut_<nid>[DYN_LUT_N]` scored as a
   **zero-word field**, every COMP field after the table looked 337 words
   misplaced, and the check reported the LINKER as wrong about a layout that
   was correct. Now the expressions are evaluated, and an unresolvable length
   is a hard error rather than a zero.

**All three are `SHARED_KERNELS` + `DYN_LUT`, not `SHARED_KERNELS` +
`SIMD_DYN`.** S18 never met them because S18's shared-kernel arm was built
from `shipping.config`, where `DSP4_DYN_LUT` is 0 and the entire design step
sits in a preprocessor arm that was never assembled. The switch pair that was
refused for two sessions was not the pair that was broken.

## 3. `goldnode` fixed (S21-5)

S19-7 attributed the failure: three of the bar's four arms read `_buf_`
scalars the block-kernel graph never writes. This session fixed the bar, and
the fix is not a new instrument — it is the one the tree already had.

**The mechanism, stated completely.** Under `DSP4_BLOCK_KERNELS` a strip
node's per-node `_buf_<nid>` is not the signal path: a block kernel reads its
predecessor's block out of a shared pool slot through `i3` and writes its own
through `i4`. Some classes leave the block's last sample in `_buf_<nid>` as a
linkage scalar for scalar nodes downstream (FADER_PAN does, which is why
FDR's OUTPUT arm read live); most never touch it. `_scope_record` then reads
`_scope_src + _sample_idx` — sixteen consecutive words from the named address
— so an arm pointed at a one-word scalar captures one word that may be stale
and fifteen that belong to the next variable in the map. GATE's arm was worse
still: its OUTPUT was `_gate_gain_<nid>`, a word the block kernel writes ONCE
per block, so the gain trajectory the model computed could not be captured at
that address under any stimulus.

**The fix.** `goldnode.sh` builds its arm with `DSP4_SCOPE_BLK_TAP=1` — the
block-aware witness S9-5 built for exactly this and famverify has used since
S10 — under whatever `SHIPPING_CONFIG` names. The tap copies a node's WHOLE
BLOCK out of the pool slot its kernel just wrote, and `_scope_record` stands
down so there is one witness rather than two. COMP, TUBE and FDR need
nothing else: their arms already named `_buf_<nid>` symbols, and read through
the tap they come back **96 of 96 bit-exact with their negative controls
firing as predicted.**

**The GATE arm took two attempts, and the first one is worth recording.**
Pointing it at `_buf_C1_GATE_nn` — the node's block — made the ADDRESS real
and left the QUANTITY unable to separate the twin: the gate's output is
`x * gain`, and the product is zero wherever the stimulus is. After an
impulse the output is zero however the gate behaves; under a step the gate
never closes, so the hold counter never matters. Measured on the part: the
hold-less twin agreed on every amplitude in the search, on both stimuli. The
original comment in this tool said exactly that and was right about the
arithmetic while being wrong about the address.

**The ladder is only visible in the gain**, so the arm reads
`_gate_gain_C1_GATE_nn` through `_scope_tap1` — the one-word-per-block
witness TALKBACK and NOISE_GEN already use — at one REAL word per block, and
`run_node` captures the input at fs over sixteen times as many samples and
subsamples the model to match. `_gate_gain_<nid>` and `_comp_gain_<nid>` are
registered as extra tap witnesses in `dsp_codegen.py`, behind the same
`#if DSP4_SCOPE_BLK_TAP` guard as every other tap, so both shipped images are
byte-identical with and without them — re-verified after the change:
`302d6142` / `3b3a6f8e` and `81f799f9` / `11366344`. The bar reads the block
size off `DIAG_BUILD_CFG` rather than assuming 16, so it cannot compare a
block-8 image against the wrong phase.

**The arm is not the shipping image and the run says so.** `goldnode.sh` now
builds the control FIRST and prints both md5s, so the log carries the staged
pair's bytes beside the witness arm's and the only difference between them is
the tap.

or 62 of 64; **phase 15 alone scores 64 of 64.** The bar scores the predicted
phase and prints the rest, so a wrong prediction would show in the log
instead of being absorbed by a search.

Two arms legitimately cannot separate their twin on one of their two
stimuli, and the run says so rather than counting it: GATE's STEP (the gate
never closes under a step) and COMP's IMPULSE (one non-zero sample, and the
makeup's second rounding needs a sustained level). Each node's other stimulus
separates, which is why the run is a pass.

### On `shipping.config.s20`: three arms bit-exact, and one that cannot be scored (S21-7)

```
control (tap OFF, shipping.config.s20): chip1.ldr 32dc1ea1  chip2.ldr 29d00a5e  <-- the staged pair
witness (tap=1, shipping.config.s20):   chip1.ldr 065693ca  chip2.ldr 4cfa4763

```

**COMP's 0 of 96 is the LUT table doing its job, and the number is the
cross-check.** `s20_*` runs the compressor's gain computer from
`DSP4_DYN_LUT`'s table while `fixed_ref` runs the polynomial, so bit-exact
would prove the table unreachable. The worst deviation is **0.00518 dB** —
the same figure S20's famverify measured independently, to five decimal
places, against the table's 0.0950 dB design bound and PW's 0.1 dB ruling.
Two different bars, two different stimuli, the same number.

**GATE cannot be scored on any `DSP4_SIMD_DYN` image, and that is S21-7 —
a finding of its own, not a property of this bar.** A four-way bisect (each
of the s20 switches off in turn, GATE arm only) puts it on `DSP4_SIMD_DYN`

words freeze at the last driven level — `[221910951, 268435447, 268435456]`,

PARTNER strip of the same pair has a hold counter that decrements on every
sample. §5 carries it to PW; `tools/pi/dsp4_gate_latch.py` is the instrument.

**So gate 3 is closed on the shipping pair and open on the SIMD pair, for a
reason that is now named and measured instead of being the bar's own
defect** — which is the difference between this session and S19-7.

## 4. The worst-block figure was one diag tick too big (S21-6)

This was not on the dispatch and it changes a column in the decision table.

About one capacity row in six in this tree's record carries a worst-block
figure between 350 % and 390 % of budget **with zero missed blocks over
135,000** — which cannot both be true. The caveat printed beside it since
S13-2 was "the raw latch, including the config ladder", and that is not the
explanation either: several of the affected rows are row A, taken before any
parameter is written, and the figure is the POST-clear latch over the dwell.

**The mechanism is in the measurement and it is two instructions wide.**
`main.asm` closes each block pass with

```
    r2 = tcount;                  /* the free-running core timer */
    r0 = dm(_diag_ticks);         /* incremented by the tick ISR   */
    ...  cycles = (ticks - t0) * DIAG_TPERIOD + (c0 - tcount)
```

If the tick ISR fires **between those two reads**, the tick it just counted is
included in `ticks` while the matching timer wrap is not reflected in the
`tcount` already sitting in r2, and the pass is credited with one whole
`DIAG_TPERIOD` it did not spend. TPERIOD is 983,040 cycles at the shipped
CCLK, which is 300 % of a block-16 budget — exactly the size of the anomaly.

**Measured across the whole record.** Every row in the S20 and S21 goldens
whose worst figure exceeds 150 % of budget lands **within half a point of its
own average** once one TPERIOD is subtracted:

| row | chip | raw worst | − TPERIOD | that row's average |
|---|--:|--:|--:|--:|
| `s20` D24 r1 silent-loaded | 1 | 353.59 % | **53.59 %** | 53.78 % |
| `s20` D24 r2 driven | 1 | 353.61 % | **53.61 %** | 53.79 % |
| `s20` D32 r1 silent-loaded | 2 | 386.89 % | **86.90 %** | 87.30 % |
| `s20` D32 r1 fx Type 0 | 1 | 375.09 % | **75.09 %** | 74.60 % |
| `s20` D32 r1 fx Type 0 | 2 | 372.42 % | **72.42 %** | 71.99 % |
| `s20` D32 r1 fx On=0 | 2 | 387.33 % | **87.33 %** | 86.93 % |
| `s20` D32 r2 silent-default | 1 | 361.80 % | **61.80 %** | 62.25 % |
| `s20f` D24 r1 silent-loaded | 2 | 355.13 % | **55.12 %** | 55.12 % |
| `s20f` D24 r2 silent-default | 2 | 354.94 % | **54.94 %** | 55.22 % |

Eleven rows, both chips, both products, three arms, and not one of them lands

## 7. For PW's window

### The recommendation, in one line

**Adopt `shipping.config.s21`: it is `shipping.config.s20` plus one line, it
is bit-exact against it on every audio bar, it costs nothing measurable in
cycles, and it turns chip 1's 380 free bytes into 40,572 with no code left in
the contended DM/DMA block.** Deploy `s21_*`. The two switches that need PW's
signature are the same two as in S20 — `DSP4_DYN_LUT` and
`DSP4_GATE_LINTHR`, both numeric-spec deviations — and `DSP4_SHARED_KERNELS`
adds none: it is the same emitter's instructions, entered per strip through a
checked stub.

### What the headroom actually is

| | chip 1 | chip 2 | headroom on chip 2 | overruns |
|---|--:|--:|--:|---|
| **D24, `s21_*`, six reverbs fed and wet** | **56.49 %** | **74.08 %** | **25.9 %** | zero |
| **D32, `s21_*`, six reverbs fed and wet** | **75.20 %** | **87.08 %** | **12.9 %** | zero |
| D24, `s21_*`, engines parked | 56.49 % | 57.44 % | 42.6 % | zero |
| D32, `s21_*`, engines parked | 75.18 % | 70.58 % | 29.4 % | zero |

**Both products fit with the worst plugin load the product can be asked for,
and the reverb is what that load is: 16.6 points of chip 2 at D32 and 16.7 at
D24.** Echo and Doubling cost 1–2 points; the four unimplemented Types cost
less than the algorithms they stand in for.

Every earlier figure in this note that says "driven" was taken with the FX
buses silent. The rows above are the first ones that are not.

### The one thing that should change PW's reading of S20's proposal

**`DSP4_SIMD_DYN` has an unresolved per-strip gate-state question (S21-7),
and it was found by fixing goldnode rather than by looking for it.** On any
image with that switch on, the ODD strip of every gate pair has four frozen
state words — envelope, gain, target and hold count, unchanging over twelve
seconds with nothing driving — while the partner strip's hold counter
decrements on every sample. At the source level `_DYNCOMP_nn_mm_process` ends
with an explicit epilogue that copies the pair's gain display back into each
node's own word, and `_DYNGATE_nn_mm_process` has no write-back at all.

**Whether the audio differs is NOT established and must not be assumed either
way.** Every sample-level bar the tree has passes on this configuration:
famverify GATE LIVE on both arms and 0 of 20 families between `s21_*` and
`s20_*`, `busgold` bit-exact against the 2026-08-30 golden with the two
declared deviations off, `golden_harness` 59/59, and `s20_*` itself 1 of 20
from the shipping pair with that one being the compressor's table. Against
that: the per-sample gate body reads `_gate_gain_<nid>` as its starting
state and the pair driver calls that body for sample 0 of every block, so a
stale word there is not obviously harmless.

**What that means for the window.** The bytes case for `.s21` over `.s20` is
untouched — it is the same audio, verdict for verdict, on a configuration
that already carries `SIMD_DYN`. But `DSP4_SIMD_DYN` is one of the five
switches PW is being asked to sign, S12-5 was cited against it for two
sessions on grounds that turned out to be closed, and this is a different
objection with a measurement behind it. **It is one session's work to
settle** — give the four gate state words the treatment `_comp_gain_`
already gets, then re-run goldnode's GATE arm on the SIMD image and require
64 of 64, which the bar can now score. Recommending adoption before that is
PW's call to make with this on the page, not a call to make by leaving it
off.

### What is left open

* **The FX_ENGINE's parameter set is mostly not wired** (S21-4): eleven
  host-writable cells and three undispatched ones do not reach the audio,
  including the reverb's `Decay` and `PreDelay` and the whole EQ,
  modulation and width sections. Nothing here regressed — they have never
  been wired — but the FX pages in the app will show controls that do
  nothing, and that is PW's call to make before the window rather than
  during it.
* **`Fx<n>On` does not bypass an engine** (S21-4). A user who switches FX 1
  off still hears it and still pays for it. It is a one-branch fix in
  `gen_fx_engine` (test `_fx_on_<nid>` at the top of the body and jump to
  `.fx_passthru_`), and it would also give chip 2 back the FX cost when the
  engines are unused — worth 16 points at D32 with six reverbs idle.
* **`dsp4_c2regime.py --require-driven` counts a FROZEN envelope as a live
  one** (S21-7). "64 of 64 dynamics envelopes live on chip 1" is weaker
  evidence than it reads on a SIMD image; the check should require an
  envelope to MOVE. The capacity figures are unaffected — the paired kernel
  runs both channels whatever it publishes, and `DIAG_BLK_OVERRUN` counted
  the blocks.
* **The worst-block instrumentation over-counts by one diag tick** (S21-6).
  Four instructions in `main.asm`, two call sites, not made this session so
  that every figure above comes from the images S20 staged. It changes no
  audio and no capacity average.
* **Latency is unchanged and not re-measured**: `s21_*` differs from
  `s20_*` in code placement only, and the contract figure stands at 82
  samples / 1.708 ms (measured 80 / 83 on `s20_*` in S20).
* **Nothing rebuilds against any of this**: no contract change, no address
  moves, defs pin `defs-v2026.09.08.4` throughout. Rollback is `blk_*`,
  untouched, and `s20_*` is now a second rollback point with its own
  measured table.
