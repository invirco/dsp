# DLY / TUBE families — hardware vs fixed_ref, 2026-08-23

provenance: AI-drafted 2026-08-23 — prose may carry a statistical watermark; rewrite by hand before publication, then remove this header.

**Both PASS — 0 LSB.** DLY exact at 5 offsets, TUBE exact at 20 points.

## DLY — integer sample tap

`C1_DLY_01`. Impulse injected at `_rx_slot_C1_IN_01`, captured at
`_buf_C1_DLY_01`, with GAIN/FILT/EQ at unity and GATE, COMP and TUBE off.

| offset | impulse lands at | value | expected |
|---|---|---|---|
| 0 | index 0 | 134217728 | 134217728 |
| 1 | index 1 | 134217728 | 134217728 |
| 17 | index 17 | 134217728 | 134217728 |
| 64 | index 64 | 134217728 | 134217728 |
| 200 | index 200 | 134217728 | 134217728 |

Exactly one non-zero sample in each capture, at `index == offset`, carrying
the input word unchanged. The node is a plain integer tap — no
interpolation, no feedback, no wet/dry — so the value is stored and
reloaded with no arithmetic and `fixed_ref` needs no model for it. Offset 0
reads back the word just written, so it is a true passthrough.

Worth recording about the delay pool: `_dly_pool_slot` defaults to **0, not
−1**, so DLY_01 uses shared pool buffer 0 (12000 words, 250 ms) rather than
its local 960-word buffer. Defaults assign DLY_01..08 to slots 0..7 and
DLY_09..32 to local. The pool write pointer is shared with **no ownership
arbitration** — two nodes on one slot would each advance the same pointer
once per sample and scramble both delays. The defaults avoid this, but
nothing enforces it.

## TUBE — saturation curve

`y = x·(1 + sat·(1 − x²))` in Q4.28. Step injected, settled value captured
at `_buf_C1_TUBE_01`.

| sat | in | measured | model | diff |
|---|---|---|---|---|
| 0 | all 5 levels | = input | = input | 0 |
| 0.25 | 33554432 | 41811968 | 41811968 | 0 |
| 0.25 | 134217728 | 159383552 | 159383552 | 0 |
| 0.5 | 33554432 | 50069504 | 50069504 | 0 |
| 0.5 | 134217728 | 184549376 | 184549376 | 0 |
| 1.0 | 33554432 | 66584576 | 66584576 | 0 |
| 1.0 | 134217728 | 234881024 | 234881024 | 0 |
| 1.0 | 268435456 | 268435456 | 268435456 | 0 |

**20 points, worst 0 LSB.** At full scale `1 − x² = 0`, so the curve
correctly returns unity gain regardless of `sat`.

Three details had to be right for bit-exactness, all confirmed against the
source: SHARC `FIX` is **round-to-nearest-even** (not truncation) for the
`sat × 2^28` conversion, which happens in float32; `_mrf_rns28` is
round-half-toward-+∞ then saturate, matching `fixed_ref.rns(v, 28)` +
`sat32`; and the two `1.0 ±` steps are **plain unsaturated integer**
add/sub — only the three MAC results saturate.

## The blocker: ramp_id is the host's job

`_tube_sat` (SPI `0x004D`) read back 0 forever, with `sat`, `target` and
`frames` all zero, and the family looked broken.

The DSP has **no per-address ramp-profile table**. The profile ID travels
in bits 11:8 of the SPI request word — the host must know which parameters
are ramped. A ramped parameter written with `ramp_id = 0` takes the INSTANT
path, which sets only the level word; the node's block-rate code then does
`if frames <= 0: level = target` and clobbers it from a target that was
never set.

`tools/pi/dsp4_config.py` defaults to `ramp_id=0` and `dsp4_diag.py` has no
`ramp_id` parameter at all, so every convenience path silently takes the
wrong one. `dsp4_gain_sweep.py` already carried this warning for
`_auxin_level`; it cost time again here because the knowledge lived in one
script's comment rather than in the tool.

## Defects found by inspection — NOT yet confirmed on hardware

Recorded so they are not lost. Each needs its own measurement before being
treated as fact:

- **Sidechain filter LPF is unaddressable from SPI.** `MW/D32/DSP/gen_dsp.py`
  allocates the COMP sidechain filter 6 dispatch entries for a 10-word
  array (HPF[0..4] + LPF[0]); LPF[1..4] have no SPI address. The generator
  comment says so outright ("only 1 left"). GATE has the same squeeze
  ("only 2 of 5 LPF coefficients fit in 16 words"). The sidechain low-pass
  therefore cannot be configured on either node.
- **`_tube_sat_frames` never returns to 0** — the node does not store the
  decremented count when it reaches zero, so it sticks at 1 after a ramp.
- **Ramp times mean different things on different nodes.**
  `spi_handler.asm` scales every profile's frame count by 32, then TUBE
  decrements once per *sample* while GAIN, FDR and RTG decrement once per
  *block*. GainFast's nominal 3 ms is ~128 samples on TUBE but ~128 blocks
  (~85 ms) on gain. This matters directly for the FDR family's ±2 %
  ramp-time spec, which has not been measured yet.
