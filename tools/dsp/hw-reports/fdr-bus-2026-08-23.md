# FDR / bus summing — hardware vs fixed_ref, 2026-08-23

provenance: AI-drafted 2026-08-23 — prose may carry a statistical watermark; rewrite by hand before publication, then remove this header.

**Gain and pan law: PASS — 0 LSB at 9 points**, after fixing a defect that
made every bus feed wrong at any fader position below unity.

**Ramp time: FAIL — 32× slower than the cell table specifies.** Root cause
identified and measured; the fix is proposed, not applied.

**Bus summing: PARTIAL.** Single-contributor path is exact; multi-term
accumulation is not exercised by this measurement.

## The fader defect — fixed

The fixed-point `FADER_PAN` computed its pan gains as `comp * (1-pan)` and
`comp * pan`, then applied them to the **already-post-fader** mono signal.
The bus feed was therefore `x * level² * (1-pan)`.

| level | L measured (before) | should be | error |
|---|---|---|---|
| 1.0 | 67108864 | 67108864 | 0 dB |
| 0.5 | 16777216 | 33554432 | **−6.02 dB** |
| 0.25 | 4194304 | 16777216 | **−12.04 dB** |

Every channel's contribution to every bus was low by exactly the fader
setting in dB. It is invisible at unity, which is how it shipped.

A **porting regression, not an inherited bug**: the float node it came from
does `f1 = f14 * f7` with `f7 = 1 - pan` and no `comp`
(`dsp_codegen.py:1239`), while the generator comment on the fixed version
still claimed it "matches float node". Fixed in the generator; all 32
channel faders regenerated. Commit `45fdd47`.

After the fix, 9 points across level 1.0/0.5/0.25/0.125 and pan
0/0.25/0.5/0.75/1.0: **0 LSB**, with SHARC `FIX` round-half-even and the
single round at `_acc64_rns28` modelled.

## Ramp time — fails by a factor of 32

`src/ramp_tables.asm` is unambiguous that a frame is a **block**:

    /* GainFast (ID=1) */
    .var = 4;    /* up: 3ms = 4 frames */

4 blocks at 1500 blocks/s is 2.67 ms, which is the 3 ms claimed. But
`spi_handler.asm:255` multiplies the frame count by 32
(`r3 = lshift r3 by 5;  /* × BLOCK_SIZE */`) before storing it.

**Measured** on a GainSafe down-ramp (table: 45 frames = 30 ms), scoping
`_fdr_level_frames_C1_FDR_01` over 1024 samples:

    frames during ramp: first=1371 last=1339  (dropped 32 over 1024 samples)
    samples per decrement: 32

So the count decrements **once per block**, and the stored initial value is
45 × 32 = 1440 blocks = **960 ms against a specified 30 ms**. GainFast's
3 ms up-ramp is likewise 128 blocks = **85.3 ms**.

The ±2 % ramp-time spec fails by 32×, and it fails in the audible
direction: every fader move takes a twelfth of a second.

### Why it is inconsistent rather than uniformly wrong

The ×32 is correct for nodes whose ramp decrements once per **sample**, and
32× too slow for nodes that decrement once per **block**. Both kinds exist:

| decrements per block (32× too slow) | decrements per sample (correct) |
|---|---|
| `gain`, `fdr_level`, `fdr_pan`, `talk_gain`, `comp_makeup` | `fx_mix`, `tube_sat`, `auxin_level`, `mon_level` |

The block-guarded group agrees with the table's own units; the ×32
accidentally compensates for the other group's wrong decrement rate.

### Proposed fix — NOT applied, needs sign-off

1. Remove `r3 = lshift r3 by 5` from `src/chip1/spi_handler.asm:255` and
   `src/chip2/spi_handler.asm:254`, so a frame is a block as the table says.
2. Add a `_sample_idx == 0` guard to the four per-sample ramps so they
   decrement per block too. Their wall-clock duration does not change
   (4 frames × 32 samples ≡ 4 blocks), so this is corrective, not a
   behaviour change for them.

This is deliberately left unapplied. It alters ramp timing for **every**
ramped parameter in the product, and the generator carries six emitter
sites per parameter across the float and fixed paths — that is a reviewed
change of its own, not a tail-end edit. Note the queued KERNEL REWRITE
block states "Control/ramp plane unchanged", so it will not be picked up
there by default.

## Bus summing — what is and is not covered

The single-contributor path is bit-exact: `_buf_C1_BUS_MAIN_L` equals the
fader's L output at every point measured, confirming `_acc64_mac` +
`_acc64_rns28` (one round at readout) and the `_bus_clear_all` ordering —
the readout nodes run after all 32 RTGs, so there is no one-sample lag.

**Not covered:** multi-term accumulation. `DSP4_STRIPS=1` leaves one strip
live, so the accumulator only ever sees one non-zero term, and the "exact
wide accumulate, ONE round at readout" property that `fixed_ref.mix_sum`
exists to guarantee is never exercised — with a single term, per-term
rounding and single-round give the same answer. Testing it properly needs
several strips carrying **distinct** signals, which the current single
injection point cannot produce. Options: a multi-address scope injection,
or the existing `DSP4_PATTERN` firmware to fill the RX region with a
per-lane pattern.
