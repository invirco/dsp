# MTR family — hardware vs fixed_ref, 2026-08-23

provenance: AI-drafted 2026-08-23 — prose may carry a statistical watermark; rewrite by hand before publication, then remove this header.

**The MTR node class FAILS.** Its peak and RMS outputs are numerically
meaningless — off by roughly 33 orders of magnitude — and its RMS never
leaves zero.

**The library meter path PASSES.** `src/lib/meter.asm` +
`_meter_scan_chip1` reads correctly and is the one the host readback
contract actually uses.

There is no reference model for either in `fixed_ref.py`.

## Measured — MTR nodes

Step of 0.5 in Q4.28 (`0x08000000`) injected at `_rx_slot_C1_IN_01`, chain
transparent, settled value at sample 299:

| symbol | raw | as float | should be |
|---|---|---|---|
| `_buf_C1_GAIN_01` (input) | `0x08000000` | — | 0.5 in Q4.28 |
| `_mtr_peak_C1_MTR_01` | `0x07FFDF3B` | **3.85e−34** | ~0.5 |
| `_mtr_rms_C1_MTR_01` | `0x00000000` | **0** | ~0.25 |
| `_mtr_gr_C1_MTR_01` | `0x00000000` | 0 | — |

## Four defects, all confirmed

**1. No fixed→float conversion.** The node does:

    r0 = dm(_buf_C1_GAIN_01);   /* Q4.28 INTEGER */
    f0 = abs f0;                /* same register, read as IEEE-754 */

`r0` and `f0` are the same SHARC register, so the Q4.28 bit pattern is
reinterpreted as a float rather than converted. `0x08000000` (0.5) becomes
3.85e−34. The correct sequence exists elsewhere in the tree —
`src/chip1/block_io.asm:500-503` does `r3 = abs r3; r4 = -28;
f3 = float r3 by r4;` — so the idiom was known and simply not applied here.

The measured peak `0x07FFDF3B` is the input bit pattern after exactly one
0.9995 decay step, so the machinery runs correctly on meaningless input.

**2. RMS is dead.** It read exactly 0 after 300 samples of constant input.
The peak branch does an early `rts` before the RMS update, so RMS only
advances on samples that do *not* set a new peak — and given defect 1 the
squared value underflows to zero anyway.

**3. Decay rate is 32× faster than documented.** The node runs per sample
and applies ×0.9995 per call, while its own comment describes the constant
in terms of a 1500 Hz frame rate. At 48 kHz the peak time constant is
~41 ms, not the ~150 ms intended.

**4. `_mtr_gr` is never written** by any code, though it is declared and
carries a "gain reduction (gate or comp)" comment.

Also worth noting: only two SPI addresses are mapped for these
(`0x1200`/`0x1201`) and their dispatch comments are mislabelled
`post_trim`/`post_fader`. So the broken values *are* host-visible.

## Measured — the library meter, which is correct

`_meter_peaks[]` (`src/lib/meter.asm`), populated by `_meter_scan_chip1` at
block rate:

| input (Q4.28) | `_meter_peaks[0]` | as float | expected |
|---|---|---|---|
| 0.5000 | `0x3EFFDF3B` | 0.49975 | 0.5 × 0.9995 |
| 0.1250 | `0x3DFFDF3B` | 0.124937 | 0.125 × 0.9995 |

Both are exactly one decay step below the input, which is right. This path
does the conversion properly (`float r3 by -28`) and decays once per block,
so its ~1.33 s time constant matches its documentation.

One inconsistency here too, found by inspection and not yet measured:
`_meter_decay_block` is called with 32 entries while `_meter_scan_chip1`
writes 46, so entries 32–45 are scanned but never decayed.

## Recommendation

The MTR node class needs the conversion fix, the RMS ordering fix and a
decay-rate decision before it can be trusted, or it should be removed if
the library meter is the real contract. **That is a design call, not a
transcription fix** — unlike the fader defect there is no correct reference
implementation to port from, and `fixed_ref.py` has no meter model to test
against either way.

Adding a meter model to `fixed_ref.py` is a prerequisite for putting this
family under the harness properly.
