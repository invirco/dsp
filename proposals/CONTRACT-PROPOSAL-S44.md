## What is being proposed

The pair of files per product that `defs/products/<p>/` carries:

| file | purpose |
|---|---|
| `proposals/defs/products/<p>/dsp.csv` | the cell → (chip, page, address) map |
| `proposals/defs/products/<p>/dsp-unmapped.csv` | every defined cell with NO address, and why |

Generated by `MW/D32/DSP/gen_dsp.py --propose` from the DSP4 node graph
(`MW/D32/DSP/SHARC/dsp.csv`) against the pinned definitions. They are not
hand-written and are not to be hand-edited: regenerating reproduces them byte
for byte, which is the check `gen_dsp.py --check-proposal` performs.

The layout deliberately mirrors `defs/products/`, so the hub lands a proposal
by copying the tree across and tagging — no transformation step, nothing to
get wrong in the handoff.

Across both products the one shared address map gains **361** cells, not 356:
the extra 5 are the centre cluster `MainCtr001EqHpf00[1-3]`,

Every new address is in space that was free. The 318 multi-cell addresses are
the pre-existing packed words (EQ freq/gain/Q/shelf in one word, HPF with its
slope, and so on) — the count is **unchanged**, so the proposal introduces no
new packing and unpacks nothing.

**Nothing a host already talks to moves.** A controller built against the
landed map keeps working against the proposed one unmodified; it simply gains
361 addresses it could not reach before.

## What the app side needs (the single-SOT gap, S38-5)

The addresses reach the app through `MW/<P>/MX/_matrix.csv`'s `DspSpi` /
`DspPage` / `DspAdd` / `DspAddHex` columns, which `gen_dsp.py` backfills. Two
things are true there today and both want the hub's attention:

1. **The committed D32 matrix is ALREADY backfilled from this proposal, not
   from the pin.** 5,765 of its 6,999 rows carry a DSP address; the landed
   `defs/products/*/dsp.csv` only covers 5,409 of them. So do
   `ghost_cells.h` (`GHOST_CELLS_COUNT 5810` = the proposed union, not the
   landed 5,449), `dsp_params.asm`, `mx_dsp_map.h` and `dsp_address_map.md`.
   The generated tree has been ahead of the pin since S22–S25. Landing this
   proposal is what makes the pin describe the tree again; it is not a change
   to the tree.
2. **The D24 matrix carries no DSP addresses at all** — 0 of 4,985 rows.
   `gen_dsp.py` backfills D32's matrix and only D32's. A D24 app reading
   `MW/D24/MX/_matrix.csv` has no address column to read, and must go to
   `defs/products/d24/dsp.csv` directly. That is a real gap in the single
   source of truth and it is NOT fixed by landing this proposal; it is a
   generator item, named here so it is not mistaken for one.

## How to land it

1. Copy `proposals/defs/products/{d24,d32}/{dsp.csv,dsp-unmapped.csv}` into
   `invirco/defs` at `products/<p>/`, tag `defs-v2026.09.13.1` (or the hub's
   next number).
2. In this repo: `git -C defs fetch --tags && git -C defs checkout <tag>`,
   then `./regenerate-dsp-contract.sh --update-lock`.
3. `./check-contract-drift.sh --strict` must pass with the ONLY diff being
   `defs` and `defs.lock` — every generated artifact is already at the
   candidate's content, so nothing else should move.
4. Record the contract note per `release-notes-contract-convention.md` and
   update `tasks.md`.
