# Contract proposal S49 — the `Test[1-1]*` self-test family, +13 cells per product

**Status: LANDED** as `defs-v2026.09.16` (`invirco/defs@084dbc1`), consumed
by this repo in session 50 (2026-09-16): pin advanced, `defs.lock` updated,
all four `_matrix.csv` gain the thirteen `Test[1-1]*` cells each
(2,334/3,316/4,998/7,012), D24/D32 matrices backfilled and committed with
their DSP addresses, D32's generated SHARC artefacts gain exactly the
sixteen S49 dispatch words. Zero address moves on any pre-existing cell. See
`findings.md` S50-1..S50-3.

**The unit was booted and measured in the session that produced this, but not
by this proposal: nothing here was derived from the part. Every number below
comes from the generator.**

## 0. What is being asked for, in one paragraph

Two graph nodes were built this session — `TEST_OSC` and `TEST_MEAS`, the
sine oscillator and the RMS / THD+N / noise / crosstalk engine behind the
`Test[1-1]*` cell family — and they want sixteen SPI words on chip 1, thirteen
of which are cells the cell master already names. **The thirteen cells cannot
be addressed until the four product defs declare two keys they do not declare
today.** That def change is the first half of this proposal and only the hub
can land it; the addresses are the second half and this repo derives them.

## 1. A correction to the dispatch, and it is the reason this proposal has two halves

The S49 dispatch states that the thirteen cells are "all in `dsp-unmapped.csv`
as no-graph-node today (defs-v2026.09.14.1)". **They are not — not on any of
the four products, and not in any `_matrix.csv` either.** Checked directly:

```
$ grep -c '^Test001' MW/{D12,D16,D24,D32}/MX/_matrix.csv      ->  0 0 0 0
$ grep  '^Test001' defs/products/*/dsp-unmapped.csv           ->  (nothing)
$ grep -c '^Test\[' defs/gen/matrix/d24-mx-master.csv         ->  0
$ grep -c '^Test\[' defs/common/cells/mx_master.csv           ->  13
```

The thirteen rows exist **only in the cell library**. `defs/tools/def_master.py`
gates every prefix on a product's def keys, and its `PREFIX_RULES` line for
this family is

```python
"Test": ("util", "util.osc"),
```

— scope `util`, function gate `util.osc`. `defs/products/d24/d24.csv` and its
three siblings declare **neither**. (They declare `gen.pink` and `gen.tone`,
which is what gives them the `Noise` family; `util` appears nowhere.) So the
per-product masters carry no `Test` row, the expansion carries no `Test001`
cell, and `gen_dsp.py` — whose proposal is the intersection of the graph's
expansion with the product's **cell set** — drops them before `dsp.csv` or
`dsp-unmapped.csv` is written. A cell no product defines is in neither file;
it is not "unmapped", it is **not present**.

This matters beyond bookkeeping: it is why S49 gate 3 could not be a
`gen_dsp.py --propose` and a `--check-proposal` the way S44's was, and why
there is a script (§5) instead.

directory mirrors `defs/products/`, so the hub lands it by copying the tree
across — the same handoff S44 used.

**The two `Table` strings are the cell master's own** and are not invented
here: `OscFreq` is `0=20/127=20000/[Log]` and `OscLevel` is
`0=-60/127=0/[Lin]` in `defs/common/cells/mx_master.csv`. The wire carries the
ENGINEERING value in both cases, as it does everywhere else in this contract —
Hz for the frequency, LINEAR amplitude for the level, both IEEE single. The
DSP-side sweep table is generated from the `[Log]` law rather than typed, so
the sweep's 128 steps and the host's 128 encoder positions are the same
frequencies by construction.

**Four cells are `ro`.** `RmsResult`, `ThdResult`, `NoiseResult` and
`XtalkResult` are written by the DSP and polled by the host — the same shape
as `Chan*CompMtr`, which S23 published through the meter's own SPI block.
`gen_dsp.py` decided `ro` from the node TYPE until this session (a METER, and
nothing else); the self-test nodes both publish and take words, so the
distinction moved down to the cell and `add_cell()` gained an `access`
argument. Every cell that existed before is unaffected — `access=None` falls
through to the old rule.

**A dispatched word with no cell.** Address 4974 carries `_meas_seq_`, the
window serial the measurement engine bumps when a window closes. It has **no
cell**, because the masters do not name one and this repo proposes addresses
for cells the masters name — it does not invent cell names. The word is
dispatched so a bench tool can read it by address, and it is named here so the
hub can see it when the family next comes up for a contract change. A host
that polls the four results should read the serial either side of them: same
serial twice means the four came from one window.

### The classes that are EMPTY, which is the point

* **cells whose address moved: 0.** Every cell in both the landed file and the
  proposal has an identical row — verified field by field across all 5,766 /
  3,975 / 2,572 / 1,778 shared rows of D32 / D24 / D16 / D12: **zero rows
  differ in any column.**
* **cells removed: 0.**
* **cells that moved between mapped and unmapped: 0.** `dsp-unmapped.csv` is
  unchanged on all four products, to the row.
* **new multi-cell addresses: 0.** The count of addresses carrying more than
  one cell is **318** before and **318** after.
* **chip 2: untouched.** 1,512 words, highest 2,174 (`0x087E`), before and
  after.

The bookkeeping invariant holds on both sides:

| | landed | proposed |
|---|---|---|
| D32 | 5,765 + 1,234 = 6,999 | 5,778 + 1,234 = **7,012** |
| D24 | 3,974 + 1,011 = 4,985 | 3,987 + 1,011 = **4,998** |
| D16 | 2,571 + 732 = 3,303 | 2,584 + 732 = **3,316** |
| D12 | 1,777 + 544 = 2,321 | 1,790 + 544 = **2,334** |

### SPI address consequences

| | landed | proposed |
|---|---:|---:|
| cells with an address (one shared map) | 5,810 | **5,823** |
| chip 1 page 1 — words / highest address | 3,595 / 4,965 (`0x1365`) | 3,608 / 4,980 (`0x1374`) |
| chip 2 page 1 — words / highest address | 1,512 / 2,174 (`0x087E`) | 1,512 / 2,174 (`0x087E`) |

| chip 1 dispatch table entries | 4,968 | **4,984** |

**Every new address is in space that was free**, and it is free BECAUSE of
where the nodes were added: `gen_dsp_csv.py` packs chip 1's addresses
sequentially, so a node inserted anywhere but the end moves every address
above it — the whole map, the MCU ghost table and every stored golden. Both
self-test nodes are the last chip-1 rows in `dsp.csv` and take the next
sixteen words above the LCR block. This is the same rule S22-4 followed for
the matrix sends and it is why the "cells whose address moved" row above is
zero.

**Nothing a host already talks to moves.** A controller built against the
landed map keeps working against the proposed one unmodified; it gains
thirteen addresses it could not reach before.

## 5. How to check it, and why it is a script and not `--check-proposal`

`gen_dsp.py --check-proposal` asks "does the graph reproduce the landed
`dsp.csv`, row for row". It still passes on this tree, and that is not a
mistake — it is the §1 fact showing through: the thirteen cells are in no
product's cell set, so the check cannot see them and reports OK either way.
Relying on it here would be reading a green light aimed at a different
question.

`./proposals/regen-s49-proposal.sh` asks the question that is actually open.
It copies each product def to a scratch directory, appends the two keys,
re-runs **defs' own** `def_master.py` and `expand_matrix.py` against the
pinned cell library, stages the result at the path `sync-defs.sh` already uses
for an unfinished expansion (`MW/<P>/MX/_matrix.expansion.csv`), runs
`gen_dsp.py --propose`, and clears the stage. `--check` does the same and then
diffs the result against what is committed.

**Nothing in `defs/` is written, and no `_matrix.csv` is touched** — the
script refuses to start if a stage file already exists (a half-finished
`sync-defs.sh` run), and it removes its own stages on every exit path. It also
refuses, loudly, if either def key is already present: that means the
prerequisite has landed, this script is obsolete, and the proposal should be
regenerated with a plain `gen_dsp.py --propose` and this script deleted.

## 6. What the app side needs

The same single-SOT path S44 described: the addresses reach the app through
`MW/<P>/MX/_matrix.csv`'s `DspSpi` / `DspPage` / `DspAdd` / `DspAddHex`
columns, which `gen_dsp.py` backfills from the **landed** file. Until the pin
advances past this proposal those four columns stay empty on the thirteen
rows, and a bench tool reaches the words by number — which is what
`tools/pi/dsp4_s49_osc.py` does, with the numbers in one table at the top of
the file and a write/read-back proof of every one of them before a single
result is quoted.

**Four of the thirteen are read-only and the app has no vocabulary for that
yet.** `Access` has carried `ro` since S44 for the meters, and nothing on the
host reads the column. A host that writes to `RmsResult` will find the write
lands in the word and is overwritten by the DSP within 85 ms, which is
harmless and is not a contract the app should be relying on. Flagged here
rather than fixed: it is the hub's to decide whether `Access` grows a reader.

## 7. What this does NOT propose

* **No new cell names.** All thirteen are the cell master's, spelled as it
  spells them.
* **No change to the `Test` prefix rule, the `util` scope or the `util.osc`
  gate.** They exist in `defs/tools/def_master.py` already; this asks four
  products to declare what the library already understands.
* **No `Sys001Test001`.** That cell is a different family (`Sys`, MCU-only by
  `mcu-only-prefixes.txt`) and stays exactly where it is.
* **No shipping-image commitment.** The nodes are behind `DSP4_TEST_NODES`,
  which `shipping.config` sets to 0. Landing the addresses does not turn the
  nodes on; that is a separate ruling with a cycle cost attached to it, and
  the cost is in `MW/D24/DSP/dsp4-s49-20260915.md`.
