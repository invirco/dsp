# Contract proposal S55 — the universal mic-gain law (`common/tables/mic-gain-law.csv`), no address change

**Status: PROPOSED, not landed.** Nothing in `defs/`, a master or a `_matrix.csv` is written by this repo.
Evidence: `findings.md` S55-1..S55-6, data `MW/D24/DSP/s55/` (`law.csv`, `trim-table.md`, `channels.md`).

## Contract note (per `release-notes-contract-convention.md`)

- **Contract version proposed against:** `defs-v2026.09.16.2` (the `defs/` submodule as pinned by `defs.lock`)
- **Products affected:** every product using the D24 analog board's mic preamp (D24 today; any product that reuses the stage)
- **Change class:** one new common table file + a documented consumer rule for an existing cell; no new cell, no address moves
- **Risk:** low — `Chan[1-64]Gain[1-1]` keeps its name, range (0–60 dB) and DSP address; only what the host sends where changes

## 1. What is asked for

A new common declaration, `defs/common/tables/mic-gain-law.csv` (proposed copy:
`proposals/defs/common/tables/mic-gain-law.csv`, generated by `MW/D24/DSP/s55/tools/s55_ingest.py`):

| column | meaning |
|---|---|
| `target_db` | the user's mic gain, 0–60 dB in 1 dB steps (= `Chan[1-64]Gain[1-1]`, master table `0=0/60=60`) |
| `code` | the 6-bit preamp gain code to latch into that channel's 74HC595 register (Q2–Q7) |
| `byte` | the register byte with Q0 (phantom shunt) and Q1 (phantom) at 0 — informative |
| `hw_gain_db` | the measured mean hardware gain of that code re code 0 (15 channels) |
| `trim_db` | the digital make-up, `target_db − hw_gain_db`, **never negative** (PW rule, spec-audio-test-set.md) |

Rule (PW 09-16): for each target the largest mean hardware gain at or below it, so the analog stage never carries more
gain than asked for; the DSP makes up the rest. Targets above the hardware range (54–60 dB; code 63 = +53.11 dB) take
code 63 plus up to +6.89 dB of trim. Targets 1–12 dB ride on code 0 (the first hardware step is 12.84 dB).

## 2. The consumer rule (who reads it) — and why no address is needed

`Chan[1-64]Gain[1-1]` stays the user-facing 0–60 dB cell. The control layer (matrix-app, which already owns the 595
chain) splits it through the table:

1. `code` → the channel's 595 register (the existing hardware-control path; the `mcu`-class GAIN words `Phantom`/`InputSel`
   already show that pattern);
2. `trim_db` → the GAIN node's word 0 — the address `Chan[nnn]Gain001` already has in `products/<p>/dsp.csv`
   (e.g. D24 `C1_GAIN_01` + 0x0000, law `0=0/127=60 Exp`). The law already spans 0–60 dB, so a 0–12 dB trim fits it
   unchanged.

So the GAIN node's DSP address map does not change. The only contract text that changes is the `Notes` column of the
`Chan[1-64]Gain[1-1]` master row, which should name the table: *"Mic preamp gain 0–60 dB; host splits via
common/tables/mic-gain-law.csv into the preamp code and the GAIN node trim"*. The S44-style address check is a no-op:
`gen_dsp.py --check-proposal` is unaffected (no dsp.csv change).

Alternative considered and NOT proposed: a separate `Chan[1-64]GainTrim[1-1]` cell. The GAIN block's four words are
all used (`Gain`, `Pol`, `Phantom`, `InputSel`), so a fifth word would grow the block and move every downstream address
on both chips — exactly what S44 avoided.

## 3. What the table is built from, and its error budget

- 16 powered channels measured (J25–J32, J35–J42; J15–J22 have no rails on this unit); **J29 (MIC 7) excluded**: its
  code-8 stage gives ~9 % less linear gain (−0.85 dB at code 8), a part fault, reported not averaged (S55-2).
- The 15 channels agree within **0.171 dB** at every code (worst at the code-32 stage); at the 25 codes the table
  actually uses, a channel at the spread's edge is off by **≤ 0.078 dB**.
- Frequency: 1 kHz. The low-frequency corner moves with gain (20 Hz −0.41 dB at code 0, −2.06…−2.19 dB at code 63, all
  channels, S55-4); the table is a 1 kHz law and does not correct that.
- One unit, one board. Unit-to-unit spread is the next sample (PW: reported as a finding, not corrected per unit).
